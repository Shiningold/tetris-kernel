## §4 逐条详情

### D1 · 契约基线文件被清空或残缺 → 校验与全套测试照样全绿 · high

**位置**
- `tools/contract_baseline.py:257-263`（`load_baseline`：只验"有没有 entries 这个键"，不验条数、不验 meta）
- `tools/contract_baseline.py:292-307`（`compare`：当前有、基线没有的键一律归入 `added` 并放行）

**证据（实跑）**

把 `tests/baseline/contracts_baseline.json` 的 `entries` 清空成 `{}`：

```
[工具] 契约基线的 entries 被清空（356 条 → 0 条）→ exit=0
       输出：条目 356 条：新增 356 · 变化 0 · 消失 0
       输出尾行：基线校验通过。

[pytest] 全套 → 633 passed, 44 skipped     ← 全绿
```

只删掉其中任意一条（其余 355 条不动）：

```
[工具] 契约基线少了 1 条 → exit=0
       输出：条目 356 条：新增 1 · 变化 0 · 消失 0
       输出尾行：基线校验通过。
[pytest] 全套 → 633 passed, 44 skipped     ← 全绿
```

对照：**同样手法对冻结区基线是红的**——

```
[工具] 冻结区基线的 files 被清空（14 个 → 0 个）→ exit=1
       输出尾行：冻结区基线校验失败：内核 / 规则的内容变了。
```

**为什么是问题**

契约基线的核心口径是"**允许新增键**、禁止已有键变化或消失"。「新增键放行」这条口径是对的（新增事件 / 命令 / 快照字段是正常成长）。但它有一个前提：**基线文件本身是可信的**。一旦基线文件被清空或残缺，"当前有、基线没有"的键就全被当成"新增"放行——**「只增不改」在那一刻静默退化成「只查已有键」**，而且**没有任何一层会亮红灯**：工具绿、pytest 绿、契约基线 356 条的记录还在文档里写着。

这正是这一批花力气要消灭的那个失败模式。项目自己在 `tools/contract_baseline.py:117` 的 docstring 里写着：**"清单读不出来时静默放行，等于把门拆了（守卫要能触发，恒真的守卫等于没守）"**——清单解析有"解析不出 16 项就报错"的下限校验，**基线文件本身却没有**。

`count/ruleSignature` · `count/namedStruct` 这两条计数键钉的是**当前声明**的条数，不是**基线文件**的条数，所以它们挡不住这个洞。

**修法方向（不代项目定）**：在基线文件里钉一条"基线自己有多少条"的计数键（比较时拿**基线里的**计数与**当前的**计数比），或让 `load_baseline` 对条数做下限校验——两条都只要几行。冻结区基线天然免疫（新增文件算差异），**两条基线的口径不一致本身就是线索**。

### D2 · 两道基线门禁自身没有反向用例：把比较逻辑改成恒不报红，CI 仍然全绿 · high

**位置**
- `tests/test_baselines.py:60-69`（契约基线用例：只断言 `returncode == 0`）
- `tests/test_baselines.py:72-83`（冻结区用例：只断言 `returncode == 0`）

**证据（实跑）**

把 `tools/contract_baseline.py` 的判定改成恒不报红：

```python
# 变异：compare() 的最后一行
-    return CheckResult(added=added, changed=changed, removed=removed)
+    return CheckResult(added=[], changed=[], removed=[])
```

```
[pytest] 全套 → 633 passed, 44 skipped     ← 全绿
```

把 `tools/check_frozen_baseline.py` 的差异判定改成恒假：

```python
# 变异
-    if added or changed or removed:
+    if False:
```

```
[pytest] 全套 → 633 passed, 44 skipped     ← 全绿
```

**为什么是问题**

这两条用例断言的是"**跑一遍工具，退出码是 0**"——它证明的是"此刻基线与代码一致"，**没有证明"基线与代码不一致时工具会拒绝"**。于是：

- 有人把 `compare()` 简化成只比对交集（`removed` 那一支掉了）→ **改名 = 删旧键 + 加新键，只看新增会把它当成纯新增**——这正是 `tools/contract_baseline.py:16` 自己写着要防的失效模式，**而现在没人能发现它掉了**；
- 有人把冻结区的差异判定写错一个布尔 → 冻结区形同虚设，而 CI 全绿。

这一条不是"要求测试测试实现"。项目在 `ai_docs/261003.md` 里明确否掉了"把哈希逻辑抄一份进测试"（理由成立：那是影子副本），**但否定的是"抄实现"，不是"验行为"**。正确的形状是：**喂一份故意改坏的临时基线给工具，断言它退出码非 0**——测的是"工具会拒绝"，不需要复制任何哈希实现。

对照批次 C：那一批**每一条新守卫都做了反向验证**（PROGRESS.md 逐条列了"把缺陷放回去，守卫真的红"）。这一批的两道门被称作"接进 pytest 就是牙齿"，**但恰恰缺了批次 C 已经确立的那一步**。

### D3 · 清单有未勾项时，默认校验模式照样 exit 0 并自称「基线校验通过」 · medium

**位置**
- `tools/contract_baseline.py:47`（docstring 的退出码约定）
- `tools/contract_baseline.py:315-324`（`_report_checklist`：只在 `--checklist-only` / `--update-baseline` 两条路上被调用）
- `tools/contract_baseline.py:402-425`（默认校验路径：完全不看清单状态）

**证据（实跑）**

把 `docs/契约v1清单.md` 第 1 项的 `☑` 改成 `☐`（其余不动）：

```
[默认校验模式]  → exit=0
    条目 356 条：新增 0 · 变化 0 · 消失 0
    基线校验通过。                 ← 清单明明有一项没勾

[--checklist-only] → exit=1
    契约 v1 冻结清单未勾完，缺 1 项：
      第 1 项：信封结构：五字段 序号 / 帧号 / 类型 / 负载 / 元数据 及其类型

[--update-baseline] → exit=1
    拒绝生成基线：冻结清单没勾完。
    （基线文件未被改动 ✓）
```

而同一个文件的 docstring 写的是：

> 退出码：0 = 通过；1 = **有红项（清单没勾完** / 已有键变化 / 已有键消失）；2 = 用法或 IO 错误。

**为什么是问题**

**工具自己承诺"清单没勾完"是红项，默认模式却不查。** 而 `docs/契约v1清单.md` 的定位恰恰是"**这份清单管什么**……清单没勾完，基线不许生成"——它是 S17 那道门的钥匙。

更要紧的是它撞上项目自己记过的教训（`PROGRESS.md` 的「S6 审查修订的三条教训」）：

> **「没扫到」不等于「扫了没问题」**——目录不存在时退出码曾是 0 且自称"检查通过"，**是守护脚本最坏的失败模式**（现在退出码 2）。

同一个文件里，"清单文件缺失 / 清单项数不对"已经改成了 exit 2（响亮地红），**但"清单有一项没勾"这条最常见的状态改动，在默认模式下仍然是 exit 0 且自称通过**。它是**校验模式**下的静默放行——用户按文档跑 `python tools/contract_baseline.py`（用法说明里的第一条就是这条），看到的是"基线校验通过"。

### D7 · 「耗时基线」不可复现：P99 实测 3 倍跨度，文档自述的噪声带宽与它自己记的两个数就矛盾 · medium

**位置**
- `docs/plan-M0.md:994`
- `PROGRESS.md:36`

**证据（三次同机实跑 + 文档自述）**

| 来源 | 常态帧 P50 | 常态帧 P99 | 常态帧 max | 超预算帧 |
| --- | --- | --- | --- | --- |
| **文档记的**（`1410da6`） | 391 μs | 490 μs | 2111 μs | 6 帧 |
| **宿主实跑** | 423 μs | **678 μs** | 2585 μs | 9 / 6021 |
| **子 Agent 实跑**（另一份快照，同一台机） | 437 μs | **1459 μs** | 2765 μs | 48 / 6021 |

**为什么是问题**

1. **文档把噪声带宽写小了，而且和自己的数据就矛盾**。`docs/plan-M0.md:994` 写的是"常态帧 P50 在 391–530 μs 之间、**P99 在 490–1176 μs 之间波动（10%–22%）**"——P50 的跨度是 391→530（+12%），可 **P99 的跨度是 490→1176（+140%）**，一句"（10%–22%）"罩不住两个数量不同的东西。两次独立实跑进一步把 P99 拉到 678 μs 与 1459 μs。
2. **"P99 占 31%、都在预算内"这个结论会随噪声摆动**。P99 = 1459 μs 时已经占到预算的 **91%**（子 Agent 那次实跑的工具输出原文："P99 1459（91.2%）"），再高一点就翻预算了。**S16 的完成判据是"开放项 B 有真实值"**，而这个值现在既不是可复现的数，也不是一个稳定落在预算内的结论。
3. **PROGRESS 把不可复现的数当"实测值"落档**（"单帧逻辑开销 **P50 391 μs · P99 490 μs · max 2111 μs**"），而开放项 B 的用途恰恰是"标定降级阈值"（架构 / ADR-031 用 P99 定阈值）。**拿一个跨度 3 倍的 P99 去定 M2 的降级阈值，定出来的阈值没有意义。**

**要区分清楚**：这**不是**说工具测错了——计时区间、口径、分段都是对的（事件数那一列三次实跑完全一致，见 D5）。问题在**落档方式**：把机器噪声当成了"基线值"。

**修法方向**：① 落档时把耗时写成**区间 + 采样次数**（"常态帧 P50 390–440 μs · P99 490–1460 μs，3 次采样"），不写单点；② 事件数（P50 5 · max 15）单独落成**基线文件**并接进 pytest（它是确定性的）；③ 降级阈值另取一个**噪声可控**的量（比如事件数、或者固定 CPU 亲和 + 更长采样后的 P99），别拿墙钟 P99 直接定阈值。

## §6 复核后否掉的疑似问题

审查方不照单全收自己（与子 Agent）的中间结论。以下几条**试过之后站不住**，列出来是为了让下游知道它们**不是**问题：

| 「`normalize_newlines` 可能没生效，跨平台哈希会不一致」 | `read_text` 的通用换行已经把 CRLF 吃掉了，**归一化确实生效**，跨平台可比。成立的只是"死代码 + 归因错"（D10），不是"哈希不可比" |
| 「`--update-baseline` 之后基线文件与入库的不一致」 | 工作区是 CRLF（`core.autocrlf=true`），入库 blob 是 LF，工具写 LF —— **blob 层面逐字节一致**，不是缺陷 |
| 「`CONTRACT_VERSION` 改成 v2 没人管」 | 有守卫：`test_contract_version_declared` 实测变红。成立的只是"基线 `meta` 不校"（D6），不是"版本号无人管" |

| 「`percentile()` 的最近秩实现有 off-by-one」 | 对 `fraction` = 0.99 与 0.50 扫 `n = 1..200000`，与精确有理数上界对比，**0 处不一致**。成立的只是"自检不验它"（D11） |

| 「`run_frame()` 返回值不可信，事件数基线不可信」 | 批次 C 的 C11 修订已给 `run_frame()` 的返回值加了守卫（逐帧断言返回值 == 订阅者收到的条数，`tests/test_host_loop.py:256`）。事件数这一列**三次可复现且与文档相符**，有牙齿 |

## §8 结论与建议

1. **批次 D 的实现质量是好的**：两道基线在**真实漂移**上确实会红——11 组变异全部按预期变红（改类型 / 改名 / 删键 / 冻结面整条新增 / 改注释 / 新增文件 / 坏 JSON / 清单缺项 / 清单异常）；S16 的**事件数**实测值**三次可复现**且与文档逐项相符；`--update-baseline` 的清单拒绝路径**确实拦得住**。
2. **短板是"牙齿的牙齿"**：这两道门禁**自己**没有被反向验证过（D2），而契约基线**自己**一旦残缺就静默失效（D1）。这两条恰好是这一批花力气要消灭的那类问题——**"恒真的守卫等于没守"**。
3. **还有一处"自称检查通过但其实没查"**：清单有未勾项时，默认校验模式照常 exit 0 并自称通过（D3）——与项目自己记过的 S6 教训（"守护脚本最坏的失败模式"）同一类。
4. **开放项 B 的"实测值"目前不能直接用**：耗时在同机三次采样里 P99 跨度 3 倍（D7）。事件数是稳的（D5 的修法方向），耗时应当按区间落档、别拿单点去定 M2 的降级阈值。
5. **落地口径不齐**：同一批里两份基线有文件 + 门禁，第三条"每帧事件数基线"只有文档里的三句话（D5）；「显式刷新」只有纪律没有门禁（D4）。
6. **文档小账**：超预算帧数的分母（D8）、`ruff format` 的文件数与副作用（D9）、清单第 11 项的残留措辞（D12）、PROGRESS 的一处笔误（D13）——都是几分钟能修的。

**建议的处置顺序**：D1 · D2 优先（它们让"接进 pytest 就是牙齿"这句话还差最后一步）；D3 · D4 · D5 · D7 次之（把纪律变成门禁、把基线补齐、把噪声写成区间）；D6 · D8–D13 属清理。

## §9 待项目拍板项

审查方**不代项目定路线**，以下四条需要拍板：

1. **D1 的修法**：① 在基线文件里加一条"基线自己有多少条"的计数键（比较时与当前条目数对账）；② 让 `load_baseline` 对条数做下限校验；③ 或者两条都做（推荐——①防"基线被改小"，②防"基线被清空"）。顺带要定**冻结区基线要不要也补同样的下限校验**（它天然免疫，但口径统一更好读）。
2. **D2 的修法**：① 在 `tests/test_baselines.py` 里加**行为级反向用例**——造一份故意改坏的临时基线，断言工具退出码非 0（不抄哈希实现，与 ai_docs 里否掉的方案不冲突）；② 或者把"守卫自身的反例"单列一个 `tests/test_baseline_guards.py`。另需定：反向用例的临时基线**放哪里**（`tmp_path` fixture 还是仓库内的固定样例）。
3. **D3 的口径**：清单门到底是"**只管生成**"（现状）还是"**校验也管**"。要定这一条，是因为工具自己的 docstring 现在写的是"清单没勾完 = 红项"。若定成"只管生成"，docstring 要改；若定成"校验也管"，`main()` 的默认路径要加一次清单状态检查（`--checklist-only` 的逻辑现成）。
4. **D5 · D7 的落档口径**：事件数落成第三份基线文件（接进 pytest）——是否同意？耗时若不做基线，落档时改成"区间 + 采样次数"（"P50 390–440 μs · P99 490–1460 μs，3 次采样"）是否接受？**开放项 B 的验收物到底是一组数，还是一个可复现的结论**——这一条定了，M2 的降级阈值该怎么取才有意义。
