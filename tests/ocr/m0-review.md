## 4. 发现清单

> 编号沿用本轮 `M0-n`。每条含 path、行号、category、severity、**实跑证据**。
> 变通：所有变异都在只读快照的副本 `.tmp_m0_probe` 上做，**被审代码一行未改**，还原一律用**字节级备份**（`read_bytes()` / `write_bytes()`）。

### 4.1 【高】契约基线的"自证"只防"没同步改计数"——少一条且同步改 `entryCount`，工具照样放行

| 字段 | 值 |
| --- | --- |
| path | `tools/contract_baseline.py` |
| 行号 | 311–346（`baseline_integrity_problems`）· 375（`compare` 的"允许新增键"分支）· 296–309（`load_baseline`） |
| category | test（门禁自证失效） |
| severity | **high** |

**现象**：把基线文件里的某一条**删掉**，同时把自述块里的 `meta.entryCount` **同步改成新的条数**，契约基线校验 **exit 0**，输出"新增键（放行）"——**被删掉的那条被当成"新增键"放过去了**。

**实跑证据**（探针 P1 / P2b，副本内）：

```
P1 少一条且 entryCount 同步改：exit=0
   stdout: 契约 v1 冻结清单：16 项全勾（docs/契约v1清单.md） |
           新增键（放行）：command/hardDrop/lifecycleGated |
           条目 356 条：新增 1 · 变化 0 · 消失 0 | 基线校验通过。

P2b 删 50 条且 entryCount 同步改：exit=0
   stdout: … 新增键（放行）：envelope/seq | 新增键（放行）：envelope/frame | …
```

对照：**不改**计数键时同一个操作是红的（探针 P2）——

```
P2 少一条且 entryCount 不改：exit=1
   stdout: 基线自身不可信（红）：基线自述块记着 356 条，实际只有 355 条：基线被改过
```

**为什么是缺陷**：这正是批次 D 审查 D1 要治的病——"基线被清空或残缺时，「当前有、基线没有」的键会全被当成新增放行，「只增不改」那一刻静默退化成「只查已有键」"。修订加的 `meta.entryCount` **只挡住了"删了条目但没改计数"这一种失手**；而"顺手刷新基线"或"手改基线"的人，**顺手把计数一起改了**——那正是最可能发生的那条路径。

**根因**：**计数键与被计数的条目在同一个文件里**。所谓"自证"是**自己证明自己**，证明力上限就是"有人只改了一处"。

**影响面**：契约面"只增不改"是 M0 最不可返工的那道防线（B-4 / ADR-054）。它现在的真实强度是"**条目少了几条而没人同步改计数**会被抓到"，而不是"条目少了几条会被抓到"。

**修法方向（不代项目拍板）**：
- 把"基线应当有多少条"放到**基线文件之外**（另一份文件 / git 里的历史提交 / CI 常量），自证跨文件才成立；
- 或者改口径：**新增键不再无条件放行**——新增必须显式登记（例如先生成一份"待登记"清单再合并），这样"基线少一条"与"契约新增一条"就不再同形；
- 或者退回"少一条就是红"的强口径（代价：新增键也要走一次显式流程）。

> **对照：冻结区基线没有这个洞**——少一个文件必然报"新增文件（红）"（探针 P3/P3b，exit=1）。**事件数基线也没有**——帧数对不上直接红（探针 P4/P4b，exit=1）。**只有契约基线有**，因为它是三道门里唯一允许"新增键"的。

### 4.2 【中】`--reason` 必填（D4 修订）**没有任何守卫**：去掉它，643 条测试全绿

| 字段 | 值 |
| --- | --- |
| path | `tools/contract_baseline.py` · `tools/check_frozen_baseline.py` · `tools/measure_frame_cost.py` |
| 行号 | 489 / 226 / 575（`if args.update_baseline and not args.reason:`） |
| category | test |
| severity | **medium** |

**实跑证据**（探针 M15）：把 `if args.update_baseline and not args.reason:` 改成 `if False:`（即取消"刷新基线必须写明理由"这条要求）之后——

```
pytest 全套：exit=0 · 643 passed, 44 skipped in 35.86s
不带 --reason 刷新基线：exit=0   （修订后应为 2）
```

**为什么是缺陷**：批次 D 审查 D4 的原话是"显式刷新基线只有纪律没有门禁"，修订把它做成了**工具级硬要求**（不给理由就 exit 2）。但**这条要求自己没有任何反向用例**——它被谁撤销，**全套 pytest 一声不响**。这正是 D2 的原话在 D4 上的重演："只断言跑一遍是绿的"不等于"坏掉时会红"。

**影响面**：三份基线（契约 / 冻结区 / 事件数）的刷新都是"静默覆盖"的高危动作——`--reason` 是唯一的留痕手段。

**修法方向**：加一条反向用例——跑 `--update-baseline` 不带 `--reason`，**断言退出码非 0 且基线文件未被改动**（三份基线各一条）。

### 4.3 【中】采集工具 `--self-test` 的用例**只断言退出码**，而退出码正是被测代码自己算的

| 字段 | 值 |
| --- | --- |
| path | `tests/test_baselines.py` · `tools/measure_frame_cost.py` |
| 行号 | 134–144（`test_the_measurement_tool_passes_its_own_self_test`）· 331（`_self_test`） |
| category | test |
| severity | **medium** |

**实跑证据**（探针 M14）：把 `_self_test()` 改成开头就 `return problems`（即恒返回空 = 恒通过）——

```
pytest test_baselines.py：exit=0 · 12 passed in 16.19s
   → 自检被改成恒通过，pytest 仍绿 = 该门禁没有独立牙齿
```

**为什么是缺陷**：批次 D 审查 D11 要求"`--self-test` 要**验**，不能只是跑一遍"，修订照做了——期望值写死在 `SELF_TEST_EXPECTED` / `SELF_TEST_PERCENTILE_CASES` 里，`percentile()` 被改坏时它会红（这一点实测有效）。**但用例本身只断言"退出码是 0"**——而退出码是 `_self_test()` 自己决定的。**把判定函数改成恒通过，牙就掉了。**

这与批次 D 审查 D2 是**同一个病**（"只断言 `returncode == 0`"），只不过这次出现在**修订新增的用例**上。讽刺的是：**D2 的修订给三道基线门都补了行为级反向用例，唯独 D11 的正向用例仍是"退出码断言"**。

**修法方向**：用例直接调 `percentile()` / `summarize()`，与**测试文件里另写一份**的期望值比对（抄的是**期望值**，不是实现）；或让 `--self-test` 把实际算出的数**打印出来**，用例解析输出与期望值比。

### 4.6 【中】软降加分**写死在 kernel 里**，规则集接口没有对应口径——换规则集改不了软降得分

| 字段 | 值 |
| --- | --- |
| path | `src/tetris_kernel/kernel/core.py` · `src/tetris_kernel/rules/interface.py` |
| 行号 | 930–931（`before = self._state.score` / `self._state.score = before + 1`）· `rules/interface.py` 195–196（`score_clear` 是唯一的计分签名） |
| category | bug（架构红线 N4 / FR-4.9 的具体缺口） |
| severity | **medium** |

**事实**：软降一格得 1 分这件事，是**内核直接改计分状态**做的：

```python
# core.py:930-931（_cmd_soft_drop 内）
before = self._state.score
self._state.score = before + 1
```

而规则集接口的 8 条签名里（架构 §7.3.1 · `contracts/rules.py` 的 `RULE_SIGNATURES`）**只有 `score_clear(groups, ctx, prev)` 一个计分入口**，它只吃"消行组"——**软降加分不在任何规则口径里**。

**为什么是缺陷**：架构 §7.3.1 定的纪律是"**计分模型可整体替换**"，且 §7.3.1 纪律 1 明写"随时间的一切都是关于 `ctx` 的纯函数"；需求 §7.4 FR-4.9 要求"**规则模块可替换**：按消行判定、重力、计分、边界四项分别可插拔"。**软降得分这一项现在不可插拔**——变体想改软降得分（0 分、每格 2 分、或按等级变），只能改 `kernel/core.py` → **直接撞 G4-1**（内核文件差异必须为空）。

**定性（重要）**：**这不是实现写错，是 M0 定稿的签名集少了一个维度**。M0 的规格把"标准踢墙表 / T-Spin / 连击表"整体推到 M1（spec §4.2），软降计分没有一起推，于是"最小标准实现"里它就落在了内核里。**M1 补完整标准玩法时必然撞上这一条**（标准软降 1 分/格是既定玩法，别的玩法未必）。

**修法方向**：按 **major 变更流程**给规则集补一条软降计分口径（或把软降分并入 `score_clear` 的入参形态）——**不能就地改冻结签名**（`rules/` 在冻结区，`contracts/` 的签名进只增不改基线）。

### 4.7 【中】同因拒绝合并的**窗口口径与规格冲突**：在 M0 唯一的宿主形态下，"防刷屏"零收益

| 字段 | 值 |
| --- | --- |
| path | `src/tetris_kernel/kernel/core.py` · `src/tetris_kernel/host/loop.py` · `docs/plan-M0.md` |
| 行号 | `core.py:451–461`（`run_rounds` 每轮 `flush_rejects()`）· `core.py:671–675`（`_reject` 的窗口自述）· `host/loop.py:166–181`（宿主每帧恰好派发一条 tick）· `plan-M0.md:777` · `:779` · `:796–797` |
| category | documentation（口径分歧；实际效果是功能目标落空） |
| severity | **medium** |

**规格怎么说**（三处口径互相打架）：

| 出处 | 原文口径 |
| --- | --- |
| `docs/spec-M0.md` §7.2 | 「同因拒绝合并：键 = `(phase, 命令类型, 拒绝原因)`……**phase 变化或 `resume` 后重置计数**」 |
| `docs/项目架构.md` §6.5 | 「同一 phase 下连续被拒的命令**只发第一条**，后续合并计数；**phase 变化或 `resume` 后重置计数**」 |
| `docs/plan-M0.md` S10 任务栏（`:779`） | 同上（"phase 变化或 resume 后重置计数"） |
| `docs/plan-M0.md` S10 **实现补记**（`:797`） | 「**合并窗口 = 一批命令**：走 `run_rounds` 时是**一轮**」 |

**规格里"重置条件 = phase 变化或 resume"蕴含的是「同 phase 内跨帧合并」；实现补记写的是「一轮」——一轮就是一批命令，批次一结束就冲刷。**

**宿主复核证据（两条，一起看才说得清）**：

```
① 合并机制本身是对的：
   run_rounds 一轮 10 条同因拒绝 → rejected 事件数 = 1
     载荷 = [{'commandType': 'moveLeft', 'reason': 'game_over', 'args': (), 'mergedCount': 10}]

② 但 M0 的宿主每帧只派发一条 tick → 一轮 = 一条命令 → 窗口永远装不下第二条：
   跑完 10000 帧 · phase = game_over
   command:rejected 条数 = 2739
   mergedCount 分布 = {1: 2739}        ← 一条都没合并
   拒绝理由分布 = {'game_over': 2739}
   前 3 条 = [(7262,'tick','game_over',1), (7263,...), (7264,...)]
   后 3 条 = [(9998,'tick','game_over',1), (9999,...), (10000,...)]
```

**为什么是缺陷**：`plan-M0.md:777` 给 S10 定的**目标是"连续同因拒绝不刷屏"**；而在 M0 交付的唯一宿主形态（`host/loop.py` 每帧恰好一条 tick）下，局结束后**每帧刷一条 `command:rejected`**（第 7262 帧到第 10000 帧，共 2739 条）——**正是这个功能要治的那个场景，收益为零**。

**重要澄清（别误判成"实现坏了"）**：合并机制**本身完全正确**（同一轮 10 条 → 1 组、`mergedCount=10`，`received` 与 `rejected` 成对、计数一致）。**坏的只是窗口定义与规格口径不一致**——不是代码写错，是**规格两处自相矛盾、且矛盾的那一侧恰好让功能落空**。

**为什么这条值得单列**：`plan-M0.md:796` 结尾**明写「请外部审查重点核这一条」**（针对"被拒命令的 `received` 延后发"这条实现补记）。本条就是那个请求的答复——**口径要定，且要由项目拍板**：要么把窗口放宽到「同 phase 跨帧」（功能才有收益，但要处理 phase 变化时的冲刷），要么把 spec §7.2 / 架构 §6.5 的"phase 变化或 resume 后重置"改成与实现一致的措辞（承认窗口 = 一批命令）。

**归属**：窗口定义在 `kernel/`（冻结区），宿主层无法单独修——`run_rounds` 内部每轮 flush，宿主只有 `flush_rejects()` 这个公共口。**要改就得刷冻结区基线 + 写明理由**。

### 4.9 【低】`scan_clears` 的 docstring 说"两条路径同一宽度口径"，列路径实际按**棋盘高**取格子清单

| 字段 | 值 |

| category | documentation |
| severity | **low** |

**docstring 原文**（`:208-210`）：

> **一条线 = 棋盘宽度那么长**：行路径的组是「整行」，列路径的组是「整列」，两者的格子清单都按**同一个宽度口径**（`_board_width`）取——对不齐的棋盘按最窄的一行算，不按行自身的长度算。

**定性**：**行为是对的**——一条列线本来就有"高"那么长；**错的是文档**。但 `rules/` 在冻结区、内容进哈希基线，而 `ClearGroup.cells` 是**下游要用的几何**（塌落动画与事件负载都要它）——文档说错口径，下游按文档实现就会算错行数。

### 4.10 【低】零宽棋盘会让 `scan_clears` 报出"满行"，且格子清单是空的

| 字段 | 值 |
| --- | --- |

| 行号 | 111–128（`_full_indices`）· 198–221（`scan_clears`） |
| category | bug |
| severity | **low** |

**宿主复核证据**：

```
scan_clears([[], [], []]) = (ClearGroup(axis='row', index=0, cells=(), ...),
                             ClearGroup(axis='row', index=1, cells=(), ...),
                             ClearGroup(axis='row', index=2, cells=(), ...))

```

**根因**：`_board_width` 取 `min(len(row) for row in board)` = **0**；行判满用的是 `all(cell != 0 for cell in row[:width])`——**`all()` 对空切片恒真**，于是每一行都算"满"，产出一组"满行但没有格子"的组。

**为什么只算低危**：**从内核走不到**——`Kernel.__init__` 要求 `board_width > 0`。但 `scan_clears` 是**规则集的公开接口**，M4 的变体会直接拿它处理自己造的棋盘；而 `rules/` 在**冻结区**，真要修就得刷基线 + 写明理由。**退化输入现在没人守，将来修起来会贵**。
