## 1. M1 目标与完成判定

### 1.1 一句话目标

**标准玩法补齐，结算与手算一致。** M1 结束时，仓库里有一套**完整、无歧义、可逐条验证**的标准玩法规则：标准踢墙表、三档 T-Spin、完整计分表、锁定延迟、暂存、幽灵落点全部到位，**无头就能玩完整局到顶出**，且结算数字与手算逐项相等。

### 1.2 M1 兑现的五件事

| # | 兑现物 | 说明 |
| --- | --- | --- |
| 1 | **标准规则补齐** | 形状表逐条验证（down 轴 7 种 × 4 朝向 = 28 条）· **SRS 踢墙表逐条验证**（JLSTZ / I / O 三组 + 180° 扩展）· **T-Spin 三类 + Mini + 不消行共五档判定** · 完整计分表（基础分 + 连击 + B2B + 软降）· 完整重力曲线口径 |
| 2 | **锁定延迟与手感参数落地** | 锁定延迟 30 帧 · 重置上限 15 次 · 重置触发条件（移动 / 旋转成功且已落地）· 幽灵落点 · 暂存"每块一次" · 硬降 |
| 3 | **软降计分归规则集** | 内核里写死的 `score + 1` 迁走，改由规则集给分（M0-6）——**这是"换规则集能改软降得分"的前提**，撞 G4-1 的隐患在 M1 拔掉 |
| 4 | **取值域统一收口** | 生命周期标识符、重力轴、消行轴、`commandType` 的取值域**写进类型串**（新增字面量枚举形态）——命令与快照共用同一套标识符，基线从此看得见取值域 |
| 5 | **判据可验** | M1 的门判据各有对应测试；契约基线**跨文件自证**修好（M0-1） |

### 1.3 完成判定（DoD 摘要，全表见 §9）

1. M1 门判据（§9.1）全过，每道门有一个可复跑的测试，**每道门都有反向用例**（把实现打坏 → 必须变红）。
2. **完整一局能玩到顶出**（无头），结算与手算**逐项**相等（分数 / 行数 / 方块数 / 连击 / B2B / 等级）。
3. **形状表与踢墙表逐条验证**：转录表与实现表**逐条相等**，不是"抽查若干条"。
4. **T-Spin 五档判定全对**：single / double / triple / mini / 不消行。
5. **M1 的三次 major 变更全部走显式流程**：契约基线刷新 ×2（取值域收口、规则签名新增）· 冻结区基线刷新 ×1（玩法必然改动 `kernel/` + `rules/`）——**每次都带 `--reason`，提交信息写明理由**。
6. 四条静态检查全绿：`ruff check .` · `ruff format --check .` · `pyright` · `lint-imports` · `pytest`。
7. **范围没越界**：M2–M4 的需求没有在 M1 里提前实现——录像 / 回放 / 降级 / 热插拔 / 渲染器 / 输入适配器 / 变体**仍然不做**（§4.2）。

## 3. 输入 / 输出与对外接口

### 3.1 输入（M1 接受的东西）

| 输入 | 来源 | 约束 |
| --- | --- | --- |
| 种子 `seed: int` | 构造参数 | 不变；M1 全部玩法判据都在同种子下可复现 |
| 规则集标识 `rule: str` | 构造参数 | 不变；M1 不新增规则集，只把**标准规则集**补完整 |
| 命令 `Command` | `execute(cmd)` | **M1 不新增命令**（16 条封闭，契约 v1 冻结） |
| 帧推进许可 | `tick` 命令被接受 | 不变；M1 的玩法全部跑在既有帧模型上 |
| **策略输出** | 测试内确定性策略 | **M1 唯一的"外部驱动"是测试内的确定性策略**（§7.8）——不是 AI（属 M3） |

### 3.2 输出（M1 产出的东西）

| 输出 | 形态 | 约束 |
| --- | --- | --- |
| 事件流 | 信封五字段 | **M1 不新增事件类型**（44 条不变）——M1 需要的信号（锁定延迟、重置、等级变化、T-Spin、分类键）**契约里已全部登记** |
| 快照 | 只读 dataclass | **字段集合不变**（22 顶层 + `board` 5 子字段）；**取值域收口改的是类型串与取值，不是字段** |
| 结算数字 | `score` / `lines` / `combo` / `b2b` / `level` | M1 的核心交付：**每一项都能与手算对上** |

### 3.3 对外接口签名（M1 的契约变更）

M1 只改**一处**接口面：**规则接口从 8 条变 9 条**。

```python
# contracts —— 公共叶子，不 import 任何东西
RULE_SIGNATURES: Mapping[str, RuleSignature]   # 8 条 → **9 条**（M1 新增第 9 条）

# 新增：计分能力的一条（**名称随落定确认，本文用 soft_drop_score 占位**；
#       落位 = 紧跟 score_clear 之后，见 §6.4）
soft_drop_score(ctx: RuleContext, distance: int) -> int
```

- **参数与返回**：`ctx` 是运行时上下文；`distance` 是**本次软降实际下移的格数**（被墙挡住则为 0）；返回**本次软降应加的分**。
- **为什么是独立一条签名，而不是给 `score_clear` 加参数**：`score_clear` 只在**锁定结算**时调用一次，而软降发生在**放置途中**，两者时机不同、频率不同。塞进 `score_clear` 会让"消行结算"背上"移动计分"的语义。
- **为什么不是给 `RuleContext` 加字段**：`RuleContext` 描述的是**跨帧的运行时上下文**（帧号 / 等级 / 已放置数 / 轴 / 步长），而软降距离是**单次命令的参数**。塞进去会让上下文多一个"每帧都要重置"的瞬时量。
- **为什么不能继续写死在 kernel**：内核写死 = 换规则集改不了软降得分（撞 G4-1：M4 落地变体时内核文件必须零差异）。这条是 **M0-6** 挂到 M1 的原因。

> **九条签名的清单**（M1 完成后）：`wrap_cell` · `gravity_vector` · `gravity_interval` · `scan_clears` · `classify_placement` · `score_clear` · **`soft_drop_score`（新）** · `shape_cells` · `kick_offsets`。
> **顺序即声明顺序，进基线，不得重排**（`contracts/rules.py` 现状）。新增条目的落位在 §6.4。

### 3.4 M1 的三次 major 变更（**一次都跑不掉**）

| # | 变更 | 撞红的东西 | 处置 |
| --- | --- | --- | --- |
| **M1-C1** | **取值域统一收口**：把内核要解读的枚举字段的类型串从裸 `str` 改成字面量枚举 | 契约基线里**已有键的哈希变化**（快照 `phase`、规则侧 `RuleContext.axis` / `ClearGroup.axis`、事件 `commandType`） | 显式 `--update-baseline --reason "<理由>"`，提交信息写明理由 |
| **M1-C2** | **规则接口新增第 9 条签名** | 契约基线的**结构性计数键** `count/ruleSignature`（M0 加它就是为了让"整条新增"也撞红） | 显式 `--update-baseline --reason "<理由>"` |
| **M1-C3** | **冻结区内容哈希基线刷新**（`kernel/` + `rules/`） | 冻结区基线 14 个文件的哈希 | 显式 `--update-baseline --reason "<理由>"`，**理由必须写明"标准玩法补齐"而不是"改了点东西"** |

> **为什么取值域收口是 major 变更而不是"补文档"**：类型串进基线（架构 §4.4 末条）。类型串从 `str` 变成 `Literal["not_started", "running", "paused", "game_over"]`——**字符串变了，哈希就变**，已有键的哈希变化 = major 变更。这正是"只增不改"基线该有的行为：**取值域收口是一次真正的声明面变更**。
> **为什么不做它更糟**：取值域只活在散文里 = 没有取值域。契约层测试能拦词汇表的变更，但**基线看不见**——换句话说，"基线绿"不能证明取值域没被偷偷改宽。

## 4. 范围边界

### 4.1 M1 范围内

- **标准规则集补齐**（`rules/`）：形状表验证 · SRS 踢墙表（JLSTZ / I / O 三组 + 180° 扩展表）· T-Spin 五档判定 · 完整计分表 · 完整重力曲线口径 · 软降计分接口实现。
- **规则接口第 9 条签名**（`contracts/rules.py` + `rules/interface.py`）。
- **取值域统一收口**（`contracts/types.py` + `contracts/rules.py` + `contracts/snapshot.py` + `contracts/events.py` + `contracts/commands.py` + `tools/contract_grammar.py`）。
- **内核侧配套改动**（`kernel/`）：软降计分改走规则集 · 锁定延迟与重置上限 · 顶出判定的确认。
- **宿主侧配套改动**（`host/`）：`sim` 增"跑到顶出"模式；**不引入渲染器、不引入输入适配器**。
- **测试内确定性参考策略**：让"玩到顶出"这件事可复现（§7.8）。
- **契约基线跨文件自证**（M0-1）：新增一份独立于基线文件的期望清单，交叉比对。
- **文档同步**：`docs/plan-M1.md` · `docs/决策记录.md`（M1 的新 ADR）· `docs/需求与边界.md` §12（门判据与任务编号落定）· `PROGRESS.md`。

### 4.2 M1 范围外（**明确不做**）

| 不做的事 | 归谁 | 为什么现在做会坏事 |
| --- | --- | --- |
| **渲染器（终端 / tkinter）与输入适配器（DAS / ARR）** | M3–M4 | spec-M0 §4.2 已定归属。M1 判据是**玩法正确性**，不是"人能按键盘玩"。**需求 §12 的"手感达标"在 M1 的口径 = 手感参数（锁定延迟 / 重力曲线 / 软降）定死并可验证**，不是"人操作得爽"——后者要有输入链路才谈得上 |
| **AI 系统** | M3 | M1 的"玩到顶出"用**测试内的确定性策略**，不进 `systems/ai/`（那是 M3 的产物，且 ADR-028 的固定预算纪律在那时才需要） |
| **录像、回放、时间旅行、事件历史查询** | M2 | M1 不落盘、不比对回放。M1 的确定性靠**同种子同命令序列逐帧指纹一致**自证 |
| **降级三档** | M2 | NFR-2 的降级是 M2 的事。M1 只**复测**单帧开销仍在预算内 |
| **热插拔与插件生命周期** | M3 | AC-8 是 M3 判据 |
| **运行期换规则集 / 换轴命令** | M3 | ADR-061 已排到 M3。M1 只把 `axis` 的取值域钉进类型串（**声明面**），不新增命令 |
| **变体实现** | M4 | G4-1 判的是 M4 落地变体时内核差异为空 |
| **落盘路径策略** | M2 | ADR-064：经宿主注入 sink。M1 不落盘 |
| **手感数值标定（guideline 完整重力曲线 / DAS / ARR 调参）** | M4 之后 | M1 把**现有曲线写死为口径**（见 §7.6），数值是否"爽"是另一件事——**判据是"确定、可复现、能手算"**，不是"手感最好" |
| **发布 / exe / GitHub 仓库与许可证** | M4 之后 | ADR-008：发布时点整体推后 |

### 4.3 M1 期间最容易犯的五条

| 编号 | 红线 | M1 的具体含义 |
| --- | --- | --- |
| B-2 | **内核文件不得为玩法需求改动**（`kernel/` + `rules/` 冻结） | **M1 是这条红线唯一被"正当违反"的批次**——标准玩法本身就是玩法需求。**例外必须走显式基线刷新 + 写明理由**（M1-C3），**不能顺手刷**。刷完的基线是 M3 / M4 的比对基准——**M4 落地变体时 `kernel/` + `rules/` 相对它必须零差异** |
| N1 | **单一状态所有者** | 内核之外任何模块不得写棋盘 / 分数 / 活动方块。M1 的参考策略**只能派发命令**（§7.8），不得直接改棋盘 |
| B-5 | **`writeCells` 是外部改变棋盘的唯一合法通道** | M1 的策略**不需要**改棋盘（它只用 `moveLeft` / `moveRight` / `rotateCW` / `softDrop` / `hardDrop` / `hold`）——**M1 不实现任何受控写入的玩法用途** |
| B-9 | **帧推进必须完整消费** | M1 改锁定延迟与重置逻辑时**不得破坏步骤序列的完整性**——`advance_frame()` 的五步顺序不变 |
| **M1-D1** | **不在规则集里藏玩法状态** | 规则集**不可变、无状态**（架构 §7.3.1 纪律 1）。M1 新增的一切（踢墙表、T-Spin 判定、计分表）都是**纯函数 + 字面量常量**，不得出现"上次旋转的方向"这类跨调用状态。**上一手的旋转信息走 `PlacementInfo`**（已有的 6 字段），不靠规则集自己记 |

## 6. 契约面规格（M1 必须改的声明与基线）

### 6.1 事件目录（44 条 · **M1 不新增**）

**类型文法扩展（形态 11 · 字面量枚举）**：

- **写法**：`Literal["down", "left", "right", "up"]`——**用 `Literal[...]` 而不是自造语法**，理由：它是 Python 生态里这个概念的既有名字，`typing.get_origin` / `get_args` 认得，读代码的人不用查本项目的私有文法。
- **文法规则**：形态 11 是**封闭文法的新成员**（形态表从 10 变 11），成员是 ≥ 1 个**字符串字面量**；**只能出现在叶子位置**（不参与嵌套、不参与联合的复杂成员——联合成员可以是形态 11 本身，例如 `Literal["a"] | None`）。
- **解析器要同步**：`tools/contract_grammar.py` 的递归下降解析器**必须支持**，否则新增的声明就是"不合规"（文法表是解析器的规格书，**规则与实例必须同时回验**——这是 S5 踩过的坑）。
- **只扩展一次**：PROGRESS 明确要求"**那是一次文法扩展，只在这一处做一次，别分两次改文法**"。M1 之后**不再单独扩文法**——将来要新形态，一次改到位。

**`phase` 的两套写法统一到哪一边**：**统一到英文标识符**。

- 依据：内核**运行时已经是英文**（`kernel/lifecycle.py` 的 `PHASE_NOT_STARTED = "not_started"` 等），命令侧的拒绝原因（`not_started` / `paused` / `game_over`）也是同一套。
- 中文只存在于**契约的散文里**（`"生命周期状态：待开始 / 运行 / 暂停 / 结束"`）——**散文是给人读的，取值是给机器用的**，两者混在一格里才叫"两套写法"。
- M1 的动作：**散文改成英文标识符 + 类型串收口**。**运行时的取值一个都不改**（已经是英文了）——所以这条变更**只动声明面，不动行为**。

### 6.4 规则接口签名（8 → 9 条 · **M1-C2**）

**新增第 9 条**（计分组）：

```
soft_drop_score(ctx: RuleContext, distance: int) -> int
```

- **落位**：放在 `score_clear` 之后、`shape_cells` 之前（计分组连着排，顺序即声明顺序，进基线不得重排）。
- **实现**：标准规则集返回 `distance × 1`（每格 1 分，guideline 口径）。
- **`distance` 的口径**：本次软降**实际下移的格数**——被墙挡住时为 0（没下移就不给分）；一次软降**最多一格**（软降不是连续下落）。
- **内核侧**：`kernel/core.py:931` 写死的 `self._state.score = before + 1` 换成 `score += ruleset.soft_drop_score(ctx, distance)`。**内核不再知道"软降值多少钱"**——它只负责问规则集要分、然后落笔。
- **被墙挡住时不给分**：M0 的现状是「撞墙 → 直接返回，不加分」（`core.py:908`）——`distance` 为 0 时规则集返回 0，**行为不变**，只是分值来源换了。

**为什么这是 major 变更**：基线里 `count/ruleSignature` 钉住了签名条数（M0 加它就是为了让"整条新增"也撞红——**新增一条签名比改一条签名的参数更大**）。所以新增第 9 条**必然撞红**，必须显式刷新 + 写理由。

### 6.5 快照字段（22 顶层 + `board` 5 子字段 · **字段集合不变**）

M1 **不加字段、不删字段**。只有 `phase` 的**类型串**收口（§6.3）。

- **新增字段会是 major 变更**：架构 §4.4 明写"内核每新增一个状态字段，快照同步新增一个字段"——**新增字段 = 新增键 = 基线绿**（允许新增键），但**新增状态字段同时会撞内核状态清单的一致性守卫**。M1 若发现缺字段，先问"这个状态 FR-10.2 的存档恢复需要吗"——**需要才加**。

**M0-1 的处置（跨文件自证）**：

- 问题：契约基线的 `meta.entryCount` 与被它计数的条目**在同一个文件里**——少一条并同步改计数，工具照样放行（**真跑过**：被删的那条被当成"新增键"）。
- 处置：**期望值移出基线文件**，另立 `tests/baseline/contracts_expected.json`，工具**交叉比对**：基线里的条目集与期望清单里的条目集必须**逐条相等**（不只是条数相等）。

- **新加的门自己也要有反向用例**：M0 抓到 `--reason` 必填与 `--self-test` 两道新门**自身没牙**——把要求去掉，643 条测试照样全绿。**"要求改了没人拦"和"没有要求"是同一种失守**。

## 7. 行为面规格（标准玩法到底怎么算）

> **这一节是 M1 的正题**。M0 的规则实现是"接口定稿 + 最小实现"，M1 把它补成**标准玩法的唯一权威口径**。
> **表与数值的原则**：规则表**落成 Python 字面量常量**（ADR-032），**不进外部数据文件**。本节给出**结构、判定规则与验证方法**；**具体数值以权威表逐条转录后落表**（§7.2 说明为什么不把数值写死在规格里）。

### 7.1 形状表（**逐条验证**）

- **范围**：`down` 轴，7 种方块 × 4 朝向 = **28 条**。M0 的 `SHAPE_TABLE` 已是 SRS 基准坐标（I 用 4×4 盒，其余 3×3，O 用 2×2 且四朝向相同）。
- **M1 的动作**：**逐条验证 + 修正**。验证方法：**测试里落一份独立转录表**（28 条），与实现表**逐条相等**（不是"抽查若干条"）。
- **其余三个轴（`left` / `right` / `up`）**：**留空，属 M4-A5**（形状表 / 踢墙表随重力方向变换）。M0 已在表里留了空位——**M1 不填**。填了会抢走 M4-A5 的判据（"形状表随重力方向变换"）。

> **为什么逐条验证而不是"看着对就行"**：踢墙表与形状表是**离散数据**，错一条就是一个静默的玩法错误——游戏还能跑，只是某个角落转不进去。**这类 bug 不会被任何"跑通"类判据抓到**，只有逐条比对能。

### 7.2 踢墙表（SRS · **逐条验证**）

**结构变更**（M0 的表与方块类型无关，恒等偏移）：

```
KICK_TABLE[轴][(fromRotation, toRotation)][踢墙组] -> tuple[tuple[int, int], ...]
                                        ↑ 新增的一层：踢墙组
```

- **踢墙组**：`"I"` · `"O"` · `"JLSTZ"`——SRS 的权威表就是这三套（JLSTZ 共用一套、I 独立一套、O 不踢墙）。**方块类型 → 踢墙组**的映射由规则集提供。
- **O 组**：只有 `(0, 0)`（O 在 SRS 里旋转不位移）。
- **180°**：SRS 原始规范**不含 180° 旋转**，但命令目录里有 `rotate180`、签名里也含 180°（架构 §7.3.1）。M1 采用**现代通行扩展的 180° 偏移候选表**（JLSTZ 与 I 各一套），并**在 ADR 里写明"180° 无单一权威，采 X 口径"**——**不假装它是 SRS 正统**。
- **候选顺序有意义**：偏移按**优先级**排列，**第一个能落下的就用它**；全部落不下 → **旋转被拒（命令仍被接受，另发受阻事件**，ADR-043）。

**逐条验证**：

- 转录表进测试，**覆盖 16 种转向 × 3 个踢墙组**（8 种 90° 转向 + 4 种 180° 转向 + 4 种同向转向），与实现表**逐条相等**。
- **转录表的来源要与实现表独立**——实现表从权威表抄一遍，测试表再独立抄一遍，**两处抄错同一处的概率低**；这正是 M0 用过的"独立转录"手段。

> **为什么规格里不写死数值**：规格写死的数字**没有第二份来源可比对**——实现照抄规格，测试照抄规格，抄错时三处一起错，**逐条验证就变成了同义反复**。数值必须**从权威表转录**，规格只钉**结构、覆盖范围与验证方法**。这是本项目的既有纪律（"独立转录"），不是偷懒。

### 7.3 T-Spin 判定（**五档** · 需求 FR-4.7）

**判定输入**：`PlacementInfo`（已有的 6 字段——`pieceType` / `rotation` / `cells` / `lastMoveWasRotation` / `kickIndex` / `kickOffset`）。**规则集不自己记"上一手干了什么"**（M1-D1）。

**档位（`tSpin` 字段的取值域，M1 从 2 档扩到 5 档）**：

| `tSpin` | 含义 | 消行 |
| --- | --- | --- |
| `none` | 不是 T-Spin | — |
| `tspin` | 是 T-Spin，但**不消行** | 0 行 |
| `mini` | **T-Spin Mini** | 0 行（Mini 的定义就是"没消行的半个 T-Spin"） |
| `single` / `double` / `triple` | T-Spin 单 / 双 / 三消 | 1 / 2 / 3 行 |

**判定步骤**：

1. **必要条件一**：`pieceType == "T"`——不是 T 一律 `none`。
2. **必要条件二**：`lastMoveWasRotation`——最后一手必须是旋转（平移过来的不算）。
3. **占位统计**：T 的 **3×3 外框四角**中，被占用的**至少三个**。**本次放置的格子自己不算墙**（M0 已如此）。
4. **Mini 与完整的分界**：
   - **Mini**：本次旋转**没有发生踢墙**（`kickIndex` 为 0 / 偏移为 `(0, 0)`）**且** **"前两角"被占**（T 的正面那两个角）**且** **"后两角"没有被同时占满**。
   - **完整 T-Spin**：其余全部情形——包括"用了踢墙"的、包括"后两角也占满"的。
5. **消行后的档位**：按**本次消行数**定档（1 / 2 / 3 → `single` / `double` / `triple`）。**Mini 只在消 0 行时存在**。

**"前两角 / 后两角"的口径**：相对于 T 当前朝向——**T 的"正面"是 T 的三个格子成排的那一侧**（T 的"头"指向相反方向）。四个角按 `(前左, 前右, 后左, 后右)` 定位，**正面两角随朝向旋转**。**口径必须写死在 docstring 与测试里**——"哪两个角是前面的"是这类 bug 的经典来源。

**计分类别（`classKey`）与 `tSpin` 的分工**：

| 情形 | `tSpin` | `classKey` |
| --- | --- | --- |
| 普通消行（无 T-Spin） | `none` | `single` / `double` / `triple` / `tetris` |
| T-Spin 消 1 / 2 / 3 行 | `single` / `double` / `triple` | `tspin-single` / `tspin-double` / `tspin-triple` |
| **T-Spin Mini 消 0 行** | `mini` | `tspin-mini` |
| **T-Spin 消 0 行（非 Mini）** | `tspin` | `tspin-none` |
| T-Spin **Mini 消了行** | `mini` | **按行数取** `tspin-single` / `tspin-double` / `tspin-triple`（Mini 消行按完整 T-Spin 计分） |

> **`tSpin` 与 `classKey` 为什么分两个字段**：它们回答两个不同的问题——**"这是不是 T-Spin（哪一种形态）"** vs **"这次消行按哪张表算分"**。Mini 消行时前者是 `mini`、后者是 `tspin-single`：**形态与计分类别不是一回事**，合成一个字段就丢信息。这正是 M0 把两者分开放的用意。

### 7.4 计分（**完整表 · 与手算一致**）

**基础分**（**项目口径** · 与官方 guideline 有**两处偏离**，逐条见 **ADR-069 · ADR-070**）：

| 类别 | 分值 |
| --- | --- |
| 单消 / 双消 / 三消 / 四消 | 100 / 300 / 500 / 800 |
| T-Spin 单 / 双 / 三 | 800 / 1200 / 1600 |
| T-Spin Mini（不消行） | 100 |
| T-Spin 不消行（非 Mini） | 400 |
| 软降 | **每格 1 分**（归规则集，§3.3） |

**这些数值的第二份来源**：Tetris Wiki `T-Spin` 条目 §Scoring 的表（表头
`! Lines !! Mini T-spin !! T-spin`：`0 || 100 || 400` · `1 || 200 || 800` ·
`2 || 400 || 1200` · `3 || [Impossible.] || 1600`）——**规格写死的数必须能对着
权威源核**（§7.2 那条「数值从权威表转录」在计分表上的具体落法；**转录表也必须
照权威源抄**，照 spec 抄 = 同义反复，见 ADR-070）。

**两处偏离逐条点名**（**不冒充 guideline**——与 ADR-068 的「不冒充 SRS 正统」同一把尺子）：

| # | 情形 | guideline | 本项目 |
| --- | --- | --- | --- |
| 1 | **Mini 消了行**（1 / 2 / 3 行） | 200 / 400 / Impossible | **按完整 T-Spin 计**：800 / 1200 / 1600（M1 拍板） |
| 2 | **0 行的 T-Spin 与 B2B 链** | **不断链**（`T-Spin` §Scoring 明写「0 行的 T-Spin 不断链」） | **断链**——0 行的放置走「落空」分支 → `b2b = False` |

**0 行的两档（Mini 100 / T-Spin 400）是 guideline 原值**——原先写成
`Mini 400 / T-Spin 0`，**那是照 spec 抄错的**（guideline 里 Mini 0 行是 100，
400 是 T-Spin 那一列的 0 行值），已按 **ADR-070** 摆正。

**连击（combo）**：连续消行的次数。**本次消行的连击奖励 = 50 × 消行前的连击数**（首消 0 × 50）。**落空清零**——落空由**内核每次锁定后都调 `score_clear`（含空组）**表达（架构口径不变，M1 沿用）。

**背面连击（B2B）**：链的含义不变——"**当前处于背面连击链中**"（M0 的 `b2b` 位语义）。**M1 补上倍率**：

- **条件**：**本次难消 ∧ 上一手也难消**（`prev.b2b` 就是"上一手在链中"的答案）。
- **倍率**：**×1.5，作用于基础分**（不含连击奖励、不含软降分）。
- **整数不破**：基础分全是 **100 的倍数**，×1.5 后仍是整数（800 → 1200 · 1200 → 1800 · 1600 → 2400）——**`ScoreDelta.scoreDelta: int` 不破**。这条要写进测试（断言类型仍是 `int`）。
- **难消的定义**：四消与 T-Spin 消行。**T-Spin 不消行（`tspin-none`）不算难消**——它没消行，进链会让 B2B 变成"转进去也算数"，与 guideline 不符。
- **落空断链**：落空（空组）时 `b2b = False`。**这是与 guideline 的第二处偏离**——guideline 明写「0 行的 T-Spin 不断链」，而本项目的 0 行放置走的就是落空分支（分类挂在消行组上，0 行没有组可挂 → 规则集不知道发生过 T-Spin）。**改它要改冻结签名**，留到后续里程碑（**ADR-070**）。

**等级**：**每消 10 行升 1 级**。升级由**规则集**算（`score_clear` 返回的 `ScoreState.level`）——**内核不自己数行数定等级**（计分口径归规则集，架构 §7.3.1）。内核只负责**比较前后等级并发出 `progress:level-changed`**。

> **为什么升级归规则集**：换了规则集，升级阈值就该能换。放内核 = 又一个"写死在 kernel"的口径（M0-6 同款病）。

**内核只搬运不判断**：内核拿 `ScoreDelta` 落笔（`score` / `lines` / `combo` / `b2b` / `level`），**不复算、不改写**。

### 7.5 锁定延迟（FR-4.3 · **有限次重置**）

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 锁定延迟时长 | **30 逻辑帧**（0.5 秒 @ 60fps） | 方块落地后开始计时，到期锁定 |
| 重置上限 | **15 次** | **超过上限不再重置**——防止无限旋转拖延 |
| 重置触发 | **移动或旋转成功**，且**方块已落地** | 移不动（被墙挡住）**不重置** |

- **上限到了以后**：锁定延迟**照常到期锁定**（不重置 ≠ 不锁定）。这条要有测试（转 20 次之后仍会锁定）。
- **事件**：延迟开始发 `piece:lock-delay-start`（带延迟时长）· 每次重置发 `piece:lock-delay-reset`（带**已重置次数**）——**两条事件契约里已登记，M1 不加**。
- **归属**：这是**玩法规则**，但**不在规则接口的 8+1 条里**——它由内核实现。理由：锁定延迟是**内核的放置状态机**的一部分，而规则接口的定位是"消行判定 / 重力 / 计分 / 边界"四项 + 两张表 + 软降计分（FR-4.9 的口径）。**加第 10 条签名去管锁定延迟，会把"放置状态机"整个搬进规则集**——那不是 FR-4.9 的意思。**这条边界写死在本文，M1 不许临时再扩**。

### 7.6 重力曲线（**口径写死，数值不标定**）

- **M0 的 10 级表保留**：`GRAVITY_INTERVAL_FRAMES = (60, 50, 40, 30, 20, 15, 10, 8, 6, 5)`（逻辑帧 / 格）。**M1 把这张表确立为口径**（它已经进了冻结区，规则表是字面量常量）。
- **表尾之后**：等级 > 10 一律取表尾值 **5 帧**（M0 已是此行为，M1 确认）。
- **下限**：间隔 **≥ 1 帧**（间隔 0 不是重力）。
- **M1 不做**：guideline 的完整 20 级曲线与手感标定。**理由**：M1 的判据是"确定、可复现、能手算"，不是"手感最好"。**手感调参属 M4 之后**（§4.2）。

### 7.7 顶出与结束判定

- **顶出**：新方块的**出生位置与已有方块重叠** → 结束本局（`game_over`）。
- **结束事件**：`game:over`（带分数 / 行数 / 结束原因）——契约已登记。
- **结束后**：帧号照走、**推进许可不再授予**（M0 的既有行为，M1 沿用）；宿主在**跑到顶出时停帧**（§7.8）。
- **出生位置**：7 种方块的水平居中位置按各自盒子算（I 用 4×4 盒居中，其余 3×3，O 用 2×2）——**随 §7.1 的形状表逐条验证**。

### 7.8 「无头可玩到底」（M1 的**验收载体**）

M1 判据的第一条是"**完整玩到顶出且结算与手算一致**"。要判这件事，得**真的玩一局**——但 M1 不做渲染器、不做输入适配器、不做 AI。

**做法**：一个**测试内的确定性参考策略**（`tests/support/`），它**只看快照、只派发命令**：

- **不许直接改棋盘**（N1）——**策略只能派发命令**（`moveLeft` / `moveRight` / `rotateCW` / `softDrop` / `hardDrop`）。
- **必须确定性**：同棋盘 → 同一串命令（不许用随机数、不许用时间）。
- **目标**：把方块放到能消行的位置；**消不掉就硬降**——**最终必然顶出**。所以"顶出"不依赖策略聪明，**依赖策略不作弊**。

**宿主侧**：`sim` 增"跑到顶出"模式——跑到底出后停帧并输出**结算八项**（分数 / 行数 / 方块数 / 连击 / B2B / 等级 / 最终棋盘指纹 / 事件数）。

> **为什么策略放 `tests/support/` 而不是 `systems/ai/`**：`systems/ai/` 是 M3 的产物，且 ADR-028（固定搜索预算）那套纪律要跟 AI 一起落地。M1 要的只是**一个可复现的驱动**，不是**一个会下棋的系统**。放错位置的代价是 M3 要先拆掉它再重做。

### 7.9 内核侧配套改动（**逐条列出，不许顺手改别的**）

| # | 改动 | 位置 | 为什么要动内核 |

### 11.3 `RuleContext.stepMs` 的语义（**仍未决 · 需在 plan-M1.md 落定**）

架构 §7.3.1 只给了字段名与类型（`stepMs: int`），**没说它是谁算、给谁用**——事件侧 `progress:level-changed.gravityInterval` 是**逻辑帧数**，`gravity_interval(ctx)` 也返回逻辑帧数，**毫秒这条线在契约里没有第二个落点**。契约里已如实记为"语义待定"。

**两个选项（都是 major 变更）**：

| 选项 | 动作 | 代价 |
| --- | --- | --- |
| **A（本文推荐）** | **定义它**：语义 =「**宿主逻辑步长（毫秒）**」，由**宿主**从可注入时钟算出、经 `ctx` 递给规则集；规则集**只透传不用**（标准玩法的重力间隔用逻辑帧数，不看毫秒） | 字段留着、语义补上；**`RuleContext` 的成员表与类型串要改** → 契约基线撞红（M1-C1 一起刷） |
| B | **删掉它** | `RuleContext` 从 5 字段变 4 字段 → 同样是 major 变更；**且以后要加回来又是一次 major** |

**M1 的标准玩法两条路都用不到它**——所以这条**不是 M1 的阻塞项**，但**必须显式落定**（PROGRESS 明确要求：**不要在实现期临时发明一个含义**）。**建议随 M1-C1 的那次基线刷新一起落定**（选 A），理由是：**契约里留一个"语义待定"的字段，比留一个语义明确的字段危险**——语义待定的字段会被下一个人按自己的理解用。
