| 项目 | 内容 |
| --- | --- |
| 适用范围 | **M1 可玩**：标准玩法补齐，内核 + 规则完整到能无头玩完整局 |
| 上游 | `docs/spec-M1.md`（规格：目标 / 输入输出 / 边界 / 非功能 / 验收）· `docs/需求与边界.md` §12（门判据与编号）· `docs/项目架构.md` §4.4 / §6 / §7.3 / §7.6 · `docs/plan-M0.md`（批次纪律的来源） |
| 本文件管什么 | **怎么一步步做、每步怎么验、每步怎么提交**。规格说"做成什么样"，本文件说"按什么顺序做" |

| 日期 | 2026-10-24 |

> **三句话读法**：① 阶段按**功能**切，每阶段 = 一个可独立提交、独立验证的逻辑改动；② 每阶段自带**验证方案**（跑什么命令、看什么结果、什么算过）；③ 阶段编号 `S0…S15` 是**本计划内部编号**，不是正式任务编号（正式编号随做随定，落定前不编造）。
>
> **本计划同时落定 M1 的门判据编号**：`G1-1`…`G1-9`（见 §5.2），**随本计划写进 `docs/需求与边界.md` §12 注册表**。落定前不引用，落定后就是正式编号。
>
> **M1 与 M0 最大的不同**：**M1 会改动冻结区**（`kernel/` + `rules/`）。这是标准玩法本身的必然结果（B-2 红线的唯一正当例外），但**每一次改动都要有显式的基线刷新 + 写明理由**（§5.4）。**M1 刷完的基线，就是 M3 / M4 的比对基准**——M4 落地变体时 `kernel/` + `rules/` 相对它必须零差异。

## 1. 总体路线

### 1.1 阶段总览

**先看阶段链（谁在谁前面），再看批次（怎么并行写）。**

```

     ↓

S2  取值域统一收口        ├→ S4 stepMs 语义落定 ┐
S3  规则接口第 9 条签名   ┘                      ├→ S6 契约基线两次显式刷新
```

> **串行链不变**：M1 的阶段顺序是**依赖顺序**，不是排期单位。批次只是把**互不相干**的阶段放到一起并行。
> **M1 与 M0 的结构差异**：M0 的"契约面"在批次 B 之前已全部冻结；**M1 的契约面阶段本身就是三次 major 变更**（§5.4），所以批次 A 不是"只写声明"——它是"**改声明 + 显式刷新基线**"，**改与刷必须在同一个批次里连着做完**，不能拖到收尾。

### 1.2 四段结构

| 段 | 阶段 | 批次 | 性质 | 为什么这样排 |
| --- | --- | --- | --- | --- |
| **A 契约面** | S0–S6 | A | **改声明 + 显式刷新基线** | M1 的三次 major 变更全在这里（取值域收口 · 第 9 条签名 · 冻结区外的一切声明变更）。**声明改完必须当批刷基线**——拖到收尾会攒成"一次性大刷新"，理由写不具体，且中途任何一次跑测试都会红 |

### 1.3 每阶段的硬约束（**贯穿全部阶段**）

| # | 约束 |
| --- | --- |
| 1 | **一次提交 = 一个阶段（或阶段内一个逻辑改动）**；格式化与逻辑改动分开提交 |
| 2 | **不在本阶段做别的阶段的事**——尤其 A 段不写规则实现、C 段不改声明 |
| 3 | 每阶段结束时，**质量门必须全绿**（§5.1），否则不进入下一阶段 |
| 4 | 发现上游设计错误 → **回退到划错边界的那个阶段**修正，不在当前阶段打补丁（需求 §12「门与回退」） |
| 5 | 每个阶段跑完立刻更新本文件 §3 状态表与该阶段的任务框 |
| 6 | **并行写手的文件归属必须互斥**——同一批次内一个文件只能属于一个写手；重叠就把两个阶段拆到不同批次（或交给同一个写手串行做） |
| 7 | **包级导出与状态文档归集成者**——`*/__init__.py` · `PROGRESS.md` · `ai_docs/**` · `docs/**` · `README.md` · `tests/conftest.py` · `tests/baseline/**` 由集成者统一收口，子代理不碰 |
| 8 | **并行写手只交工作区改动，不自己提交**——同一分支上并行提交会撞 git 索引（索引是单一共享资源）；提交由集成者按阶段串行切分 |
| 9 | **基线文件一律由集成者生成 / 刷新**——三份基线 + M1 新增的期望清单**全是脚本生成的**，写手不碰；刷新必须带 `--reason` |
| 10 | **M1 的规则表数值必须"独立转录"**——实现表抄一份，测试表**另抄一份**，两处独立（spec §7.1 / §7.2） |

### 1.4.2 文件归属（并行安全的前提）

1. **一个文件在同一批次内只能属于一个写手**。并行安全性来自"文件归属互斥"，不是来自"小心避开"。
2. **包级 `__init__.py` 不属于任何写手**——多个写手都要往里加导出，混写必冲突。导出面由**集成者**在批次落地时统一收口。
3. **共享设施一律归集成者**：`tests/conftest.py` · `tests/baseline/**` · `PROGRESS.md` · `ai_docs/**` · `docs/**` · `README.md`。**其他批次不碰**；批次 A / B 的测试文件必须自给自足（不依赖 `conftest.py` 的新 fixture）。
4. **提交由谁切，按"有没有并发写手"定**：**并发写手之间**只交工作区改动，由**集成者**按阶段切提交；**同一写手串行做的阶段**（如 A2 的 S2 → S3 → S4）由该写手**自己按阶段提交**（`git add -- <自己的文件>`，**不用 `git add -A`**）。两种情形都是"一次提交 = 一个阶段"。

### 1.4.4 跨阶段接口先验定（并行写手能同时开工的前提）

并行写手不能靠"等对方写完"才能开工。所以凡是**一个写手要用另一个写手产出的东西**，那个东西的**签名必须先在本文件写死**，谁实现都得照它来。

| 约定项 | 签名 / 形态 | 产出方 | 消费方 |
| --- | --- | --- | --- |
| **字面量枚举形态（文法形态 11）** | 类型串写作 `Literal["a", "b"]`——**用 `Literal[...]`，不自造语法**。成员 ≥ 1 个字符串字面量；**只能出现在叶子位置**；联合成员可以是形态 11 本身（如 `Literal["a"] \| None`）。**封闭文法**从 10 个形态变 11 个 | S1（`contracts/types.py` 的文法表 + `tools/contract_grammar.py` 的解析器） | S2（四条字段的类型串）· S6（基线哈希的类型串） |
| **类型串生成器** | `types.literal_enum(values: tuple[str, ...]) -> str`——**由取值域元组派生类型串**，`Literal["down", "left", "right", "up"]` 与 `AXIS_VALUES` **不可能分叉** | S1 | S2 · 全部引用处 |
| **生命周期取值域** | `types.PHASE_VALUES = ("not_started", "running", "paused", "game_over")` · `types.PHASE_LITERAL = types.literal_enum(PHASE_VALUES)` | S1（`contracts/types.py`） | S2（快照 `phase` 类型串）· S4（`kernel/lifecycle.py` 的 `PHASE_*` 改为**从 contracts 取**，消除两处抄写） |
| **重力轴 / 消行轴类型串** | `rules.AXIS_LITERAL = types.literal_enum(AXIS_VALUES)` · `rules.CLEAR_AXIS_LITERAL = types.literal_enum(CLEAR_AXIS_VALUES)`（常量仍住在 `contracts/rules.py`，因为那是它们的域） | S2 | S2 自身 · S6 |
| **命令名类型串** | `commands.COMMAND_TYPE_LITERAL = types.literal_enum(tuple(COMMAND_SPECS))`——**由注册表派生**，不另抄一份名单 | S2 | S2（事件 `commandType` 类型串） |
| **规则接口第 9 条** | `soft_drop_score(ctx: RuleContext, distance: int) -> int`，**落位 = 紧跟 `score_clear` 之后**（声明顺序进基线，不得重排） | S3（`contracts/rules.py` + `rules/interface.py` 的 `RuleSet` 协议） | S9（实现）· S11（内核调用）· S6（基线计数键） |
| **规则表结构** | `KICK_TABLE[轴][(from, to)][踢墙组] -> tuple[tuple[int,int], ...]`；踢墙组 ∈ `{"I", "O", "JLSTZ"}`；方块类型 → 组 的映射由规则集提供；`O` 组只有 `(0,0)` | S7（`rules/tables.py`） | S8 / S9（`rules/standard.py` 的查表）· S10（转录表比对） |
| **T-Spin 词汇** | `tSpin` ∈ `{"none", "tspin", "mini", "single", "double", "triple"}` · `classKey` ∈ `{"none", "single", "double", "triple", "tetris", "tspin-none", "tspin-mini", "tspin-single", "tspin-double", "tspin-triple"}`（**规则集定义的域，契约层不钉**） | S7（`tables.py` 的域常量） | S8 / S9（判定与计分）· S11（内核只透传） |
| **计分表** | 基础分 100/300/500/800 · T-Spin 800/1200/1600 · Mini 100 · 不消行 T-Spin 400（**两档 0 行分值是 guideline 原值**，ADR-070 摆正）· 连击奖励 `50 × 消行前连击数` · B2B **×1.5 作用于基础分**（基础分全为 100 的倍数 → 结果仍是 `int`） | S7（表常量） | S9（`score_clear` 实现）· S13（手算比对） |
| **软降计分** | 标准规则集：`soft_drop_score(ctx, distance) = distance × 1`；`distance` = 本次实际下移格数（被墙挡住 = 0） | S9 | S11（内核 `_cmd_soft_drop` 改为调用它，**删掉写死的 `+1`**） |
| **锁定延迟参数** | 延迟 **30 逻辑帧** · 重置上限 **15 次** · 重置触发 = 移动 / 旋转**成功**且方块**已落地** | S11（`kernel/frame.py` + `kernel/core.py`） | S13（G1-5） |
| **内核对外操作面** | 不变（`execute` / `advance_frame` / `snapshot`）——**M1 不改内核的对外形状** | S11 | S12 · S13 |
| **宿主操作面** | `HeadlessLoop.run_frames(frames, *, until_game_over: bool = False) -> RunReport`（**新增可选参数，不改已有参数的语义**） | S12 | S13（门判据跑完整局） |
| **参考策略接口** | `policy.decide(snapshot: Snapshot) -> tuple[str, ...]`——**只看快照、只返回命令类型名**（命令参数全为无参命令）；**不许直接改棋盘**（N1） | S13 | S13 自用 · 门判据用例 |
| **门判据用例命名** | `pytest -k` 命中名固定见 §5.2（**不许中途改名**——改了复跑命令就失效） | S13 | §5.2 |

> **为什么这些必须先验定**：A2 与 B2 都要用 A1 / B1 的产出物，**并行写手之间没有协商通道**。一方改签名另一方必然踩空——**接口变更先改本文件，由集成者裁决**（§6.5 第 9 条）。

### 1.4.5 「审查—分支—搭车」工作流

沿用 M0 的纪律，**一个字不改**：

1. 批次分支 `feature/batch-<字母>`，**链式分支点**（下一批从上一批的落笔提交起，不回 `master`）。
2. 批次合并用 `--no-ff`，保留批次边界。
3. **写手只交工作区改动，不自己提交**（并发时 git 索引会互相覆盖）。
4. **审查期间写下一批时"只加不改"**——批次 N 的修正落地后 merge 进批次 N+1 的分支再合并 N+1。
5. **审查修正逐条核实**：报告本身不是可靠清单（M0 的教训：报告自陈计数有误、建议要复核）。成立项在原批次分支上修正，**修正提交单独一笔**（`修复：按 batch-X 审查报告修订…`）。
6. **批次内各阶段提交分别保留**；合并批次分支不抹掉"一次提交 = 一个阶段"。

## 2. 阶段通用模板

每个阶段按同一套结构写，字段含义固定：

| 字段 | 含义 |
| --- | --- |
| **目标** | 这一阶段结束时世界是什么样（一句话） |
| **任务** | 可勾选的动作清单，粒度 = 一次提交或一次小改动 |
| **涉及文件** | 本阶段允许触碰的文件（**清单外的文件不许动**） |
| **批次 / 写手 / 文件归属** | 本阶段在哪个批次、由哪个写手做、独占哪些文件（并行安全的前提，见 §1.4.2） |
| **验证方案** | 跑什么命令、看什么结果、什么算过 |
| **完成判据** | 勾完任务的充分条件（与验证方案互相印证） |
| **提交** | 建议的提交标题（`类型：主题`）+ 该提交应包含的文件 |
| **常见坑** | 这一阶段最容易犯的错，来自红线与 ADR |

### 5.4 三次 major 变更的处置流程

M1 的三次 major 变更**一次都跑不掉**（spec §3.4）。流程统一为四步：

1. **改声明 / 改实现**（工作区改动，**不提交基线刷新**）。
2. **显式刷新**：`--update-baseline --reason "<理由>"`——**不带 `--reason` 一律拒绝且不落盘**（M0 修好的门，**M1 沿用且不得放宽**）。
3. **提交信息写明理由**——**基线刷新的提交**正文必须写清改了什么、为什么（AGENTS.md 提交规范）。
4. **反向验证**：喂一份改坏的临时基线给工具，断言退出码非 0。

| # | 变更 | 撞红的东西 | 落笔阶段 | 理由该写什么 |
| --- | --- | --- | --- | --- |
| **M1-C1** | 取值域统一收口 + `stepMs` 语义 | 契约基线**已有键的哈希变化** | S6（与 M1-C2 合成一笔，见 §5.5-3） | "把内核要解读的枚举取值域写进类型串（字面量枚举形态），契约面 major 变更" |
| **M1-C2** | 规则接口新增第 9 条签名 | 契约基线**结构性计数键** `count/ruleSignature` | S6（与 M1-C1 合成一笔，见 §5.5-3） | "规则接口新增第 9 条（软降计分），签名表结构性计数键变化" |
| **M1-C3** | 冻结区内容哈希基线刷新 | 冻结区基线 14 个文件的哈希 | S14-1 | "标准玩法补齐（M1）：规则表与内核玩法逻辑按 spec-M1.md §7 落地" |

> **"顺手刷新"是明令禁止的**：契约 v1 已冻结，此后只增不改——**任何改动要么是"新增键"（绿），要么走 major 变更**。M1 有三次正当的 major 变更，**一次都不许多**。

### 5.5 批次 A 的执行偏差（三处 · 已按工程判断处理并留痕）

计划与实际不符的三处，写在这里**而不是只留在提交信息里**——下一个读计划的人
看到"S6 刷两次""S3 先见红"时，得知道实际发生了什么、为什么。

1. **规范拼写取单引号**（S2）：计划里写的是 `Literal["a", "b"]`。但 PEP 563
   存注解时编译器把内嵌的字符串字面量**统一重加成单引号**，而契约的类型串要与
   注解**逐字相等**（内核导入期的契约对齐自检就是逐字比）——规范拼写只能是
   `Literal['down', ...]`。**双引号解析器照收**（那是排版），基线哈希的是规范化
   串。计划里的双引号示例属**排版**，不影响任何验收口径。
2. **第 9 条签名的实现提前落地**（S3）：计划写的是"先见红，等 S9 兑现"。实测
   **签名自检与 pyright 的协议一致性行都会红到 S9**，与「每阶段质量门全绿」
   直接冲突。改为 S3 把标准实现一并落地（`distance × 1`，即 spec §1.4.4 的
   预验定口径），"先见红"改成**反向验证**（临时从 `StandardRuleSet` 去掉那条 →
   pyright 报 `soft_drop_score is not present` + 签名自检用例变红 → 精确改回）。
   S9 的「软降计分实现」随之**缩小为「完整计分表」**。
3. **契约基线只刷了一次，不是两次**（S6）：计划假设 M1-C1（取值域收口）与 M1-C2
   （第 9 条签名）落在不同阶段、各刷一次。实际执行里 S2 与 S3 **在 S6 之前就都已
   提交**，**一次快照必然同时捕获两处变更**。要凑出两次内容不同的刷新，就得
   **回退一处已实现的契约变更**——那是**计划外的破坏性变更**（M1 只允许三次 major
   变更），比少一次刷新更糟。改为：**一次刷新**，`--reason` 里把 M1-C1 / M1-C2
   两条口径都写进去，提交正文把两块足迹分开列（20 条已有键的哈希变化 = M1-C1 ·
   4 条新增键 + `count/ruleSignature` = M1-C2）。**§5.4 的流程不变**：显式刷新 ·
   带理由 · 提交写明理由。

**逐条独立复跑核实，不照单全收**——**高危项判定为误报，本轮没有按报告改一行表值**。

| 报告项 | 裁定 | 处置 |
| --- | --- | --- |
| H-1 · I 组 180° `L⇒R` 第二候选方向反了 | **误报** | **不改代码**；补来源注释 + 留证（本节） |

#### H-1 为什么是误报（**照报告改会引入真 bug**）

报告的前提是：「`S,Z,I-180° rotation` 一节**没有单独给 I 一段** —— I 与 S / Z
共用同一张表，第二候选就是 `(-1, 0)`」。**前提不成立**：那一节里有**三张独立的
表**（S / Z / I 各一张）——小节标题把三个方块写在一起，**很容易看成一张**。

**机检证据**（脚本抽权威页的 wikitext → 落地换算 → 与实现逐条比对，不靠肉眼）：

- 权威源 `S,Z,I-180° rotation` 一节共 **3 张表**；**S 与 Z 两张逐行相同**，**I 表与
  S / Z 只差 `L⇒R` 这一行**：S / Z 的第二候选是 `(-1, 0)`，**I 是 `(+1, 0)`**。
- 落地换算（y 上正 → y 下正取反）后与本项目**逐条比对 8 行全部一致**：
  `JLSTZ` 四行 + `I` 四行，`L⇒R` 行分别是 `(-1, 0)` 与 `(+1, 0)`——**与实现逐字
  相同**。
- 顺带把 **90° SRS 表也机检了一遍**（不信报告的「复核后确认无误」）：tetris.wiki
  `Super Rotation System` 的 **JLSTZ 8 行 + I 8 行 = 16 行，全部逐条一致**。**第三
  张表在 `Arika SRS` 小节里，是另一套旋转系统**，本项目不采用（机检脚本按小节切
  开了，没吃进来）。
- **反向验证**：按报告的建议把实现的 `_KICK_180_I[(3, 1)]` 第二候选改成
  `(-1, 0)` → **S10 的守卫当场报红并点名那一行**（「踢墙表 3 到 1 的 I 组偏移不
  一致：实现 ((0, 0), (-1, 0)) ≠ 转录 ((0, 0), (1, 0))」）→ 精确改回 → 26 passed
  → `git diff` 空。**守卫有牙齿**，报告说的「转录表复刻了同一个错、比对变同义反复」
  不成立。

**为什么必须留这一节**：**高危项照着改 = 把一张对的表改错 = 引入一个静默的玩法
错误**（I 方块 180° 旋转时第二个候选往右挪一格而不是往左）。而报告的结论写得很有
把握——**下一份审查报告或下一个人，很可能只读到那份报告**。**裁定与证据必须留在
仓里**，否则「误报」会变成「没人记得的争议」。

#### 本轮实际改了什么

- `rules/tables.py` 的 `_KICK_180_I` 来源注释：写清「**那一节里有三张独立的表
  （S / Z / I）**、I 与 S / Z 只差 `L⇒R` 一行」，并把这次误报写进去——**这段注释
  是写给下一个读权威页的人的**。
- `rules/standard.py` 的 `_tspin_line_grade`：`cleared <= 0` → `"none"`（L-1）。
  **当前三个调用点都先挡掉 0 行，所以行为不变**；但表里 `tspin-single` = 800 分，
  **将来谁少写一句守卫就会白送 800 分且不报错**。
- `rules/tables.py` 的 `SCORE_TABLE` 口径标注 + `docs/spec-M1.md` §7.4 同步 +
  **ADR-069**（M-1）：**三处偏离逐条点名**，不冒充 guideline。

## 6. Git 策略

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（S6 的两次刷新、S14 的两次刷新、S4 的两笔），**拆开提**。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。
- **并行批次里的提交由集成者串行切分**：写手只交工作区改动（并行 `git add` 会互相覆盖索引），集成者按"一次提交 = 一个阶段"逐笔 `git add -- <该写手的文件>` 后提交。**批次合并用 `--no-ff`**，保留批次边界。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚 · 合并**。

- **破坏性改动**在类型后加感叹号（`新功能!：…`）——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - **S2 取值域收口** = 破坏性（类型串变了 → 按类型串校验的既有消费方要改）→ `重构!：…`。
  - **S3 第 9 条签名** = 破坏性（既有规则集实现要补这一条才满足协议）→ `新功能!：…`。
  - **S6 / S14 的基线刷新** = 破坏性（基线换了 = 比对基准换了）→ `新功能!：…`。
  - **S1 文法扩展** = **不破坏**（形态是新增，既有声明一字未改）→ 不加感叹号。
  - **S7–S13** = 不破坏既有契约 → 不加感叹号。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。**基线刷新的提交必须把理由写进正文**（与 `--reason` 一致）。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S6 之后慎用 reset**：契约基线一旦刷新，回退就等于放弃那次 major 变更——**要重走显式刷新流程并写明理由**（基线与代码对不上会一路红）。
- **S14 之后更慎**：冻结区基线是 **M3 / M4 的比对基准**，回退要连基线一起回退，且**回退理由同样要写进提交信息**。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 A 段（契约）提交行为代码 | 契约会被实现反向塑形，签名晚于实现 = 必被塑形（ADR-061） |
| 3 | 在 B / C 段（行为）顺手改契约声明 | 撞基线；必须走显式更新流程并写明理由 |
| 4 | 阶段内顺手做"别的阶段的事" | M2–M4 的需求提前实现会把还没定稿的东西锁死 |
| 5 | 用 `git commit -a` 批量提 | 容易把不该提的文件带进去 |
| 6 | 并行写手在同一分支上并行提交 | git 索引是**单一共享资源**，两个写手同时 `git add` 会互相覆盖 |
| 7 | 两个写手改同一个文件 | 文件归属互斥是并行安全的**前提**；重叠就拆到不同批次，或交给同一个写手串行做 |
| 8 | 审查期间写下一批时顺手改被审查批次的文件 | 修正回合与新批次同改一个文件必然互相覆盖；下一批**只加不改** |
| 9 | 子代理单方面改跨写手接口 | 并行写手之间没有协商通道；**接口变更先改本文件 §1.4.4**，由集成者裁决 |
| 10 | **顺手刷新基线** | 基线是 M3 / M4 的比对基准；**刷新必须带 `--reason`**（M0 修好的门） |
| 11 | **把 M0 的判断抄进 M1 的实现** | M0 的"最小实现"是**接口定稿**用的，M1 要补的是**完整玩法**——照抄 M0 的占位实现（M0 的 `IDENTITY_KICK`、单档 T-Spin、空组早返回）就是没做 M1 |
| 12 | **在 M1 里做渲染器 / 输入适配器 / AI / 回放 / 变体** | 那是 M2–M4 的活（spec §4.2），做了就"范围没越界"这条判据当场作废 |
