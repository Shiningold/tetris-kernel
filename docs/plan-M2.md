> **三句话读法**：① 阶段按**功能**切，每阶段 = 一个可独立提交、独立验证的逻辑改动；② 每阶段自带**验证方案**（跑什么命令、看什么结果、什么算过）；③ 阶段编号 `S0…S15` 是**本计划内部编号**，不是正式任务编号（正式编号随做随定，落定前不编造）。
>
> **本计划同时落定 M2 的门判据编号**：`G2-1`…`G2-5`（见 §5.2），**随本计划写进 `docs/需求与边界.md` §12 注册表**。落定前不引用，落定后就是正式编号。
>
> **M2 与 M1 最大的不同**：**M2 不动冻结区**（`kernel/` + `rules/`）。M1 是"**正当违反**"冻结区红线的那一次（标准玩法本身就是玩法需求），**M2 连碰都不碰**——它改的是系统层（`systems/`）、总线（`bus/`）、存储适配器（`adapters/`）与宿主装配（`host/`）。**这是"底座而非游戏"的兑现点**：可观测能力全部长在外围，内核一个字节都不改。
>
> **M2 唯一改契约面的地方是"只增不改"**：新增 `replay:` 命名空间的 5 条事件（**新增键**，不是 major 变更）。**M2 的 major 变更预算只有 1 次（M2-C1），不到不许用**（spec §3.4）。

> **串行链不变**：M2 的阶段顺序是**依赖顺序**，不是排期单位。批次只是把**互不相干**的阶段放到一起并行。
> **M2 与 M1 的结构差异**：M1 的批次 A 是"改声明 + 显式刷新基线"两件事连着做；**M2 的批次 A 是三段**——**声明（S1）· 加守卫（S2）· 刷基线（S3）**。**为什么中间插一个"加守卫"**：ADR-077 的 git 背书守卫要**从第一次刷新起就管着那份文件**，所以它必须排在刷新**之前**（M1 的 S6 刷新时没有这层保护）。

### 1.2 五段结构

| 段 | 阶段 | 批次 | 性质 | 为什么这样排 |
| --- | --- | --- | --- | --- |
| **A 契约面与基线** | S0–S3 | A | **只增不改 + 一次显式刷新 + 守卫加固** | M2 只**新增** `replay:` 的 5 条事件（**新增键，撞不了红**），但**声明先行、刷基线在后**——**中间那段不会红**（新增键按契约 v1 的口径放行；§5.1 第 1 处已于 S1 实测后订正）。**真正的代价是那 23 个新键在刷基线之前没有牙齿**（改了没人拦）——**S3 才是给它们上牙**。**S2 的守卫排在刷新之前**（ADR-077） |
| **B 底座** | S4–S5 | B | **写外围，不碰内核** | 三个系统都要往 sink 落盘（所以存储先做），都要订阅事件（所以总线先做）。**`bus/` 在这里封板并生成独立基线**（ADR-019） |
| **C 可观测三系统** | S6–S9 | C | **三个独立系统** | 日志 / 指标 / 回放**互不依赖**，可并行；**回放系统的录制与重放共用 `systems/replay/`，同一写手串行** |

| **E 收尾** | S15 | E | 同步与冻结 | 状态快照 · 决策留痕 · 收官判定 |

### 1.4 并行写手纪律

沿用 M0 / M1 的纪律（plan-M1 §1.4）：

1. **文件归属互斥是并行安全的前提**——两个写手改同一个文件必然互相覆盖。
2. **并行写手之间没有协商通道**——接口变更**先改本文件 §1.3 的文件归属表**，由集成者裁决。
3. **并行写手只交工作区改动**，**不并行 `git add`**（git 索引是单一共享资源）——由集成者串行切分提交。
4. **写手交付前先跑自己范围内的反向验证**；**集成者在批次集成后统一复跑一遍**受影响的几条——并行写手的"破坏 → 红"可能只在自己的文件上成立，合并后仍要确认整批是绿的。
5. **基线一律由集成者生成**（M1 的批次 D 纪律）——写手刷基线 = 橡皮图章。

## 2. 阶段通用模板

每个阶段按同一套结构写，字段含义固定：

| 字段 | 含义 |
| --- | --- |
| **目标** | 这一阶段结束时世界是什么样（一句话） |
| **任务** | 可勾选的动作清单，粒度 = 一次提交或一次小改动 |
| **涉及文件** | 本阶段允许触碰的文件（**清单外的文件不许动**） |
| **批次 / 写手 / 文件归属** | 本阶段在哪个批次、由哪个写手做、独占哪些文件（并行安全的前提，见 §1.3） |
| **验证方案** | 跑什么命令、看什么结果、什么算过 |
| **完成判据** | 勾完任务的充分条件（与验证方案互相印证） |
| **提交** | 建议的提交标题（`类型：主题`）+ 该提交应包含的文件 |
| **常见坑** | 这一阶段最容易犯的错，来自红线与 ADR |

- **提交**：`新功能：实现事件轨迹导出与事件流查看面板` —— 含 `systems/metrics/**`（导出侧）· `host/cli.py` · `tests/test_event_trace.py`。
  > **加感叹号**：`inspect` 子命令从"占位即报错"变成"真跑" → **既有调用方若依赖占位行为，会失效**。
  > **实测落笔**：`新功能!：实现事件轨迹导出与事件流查看面板`。
- **常见坑**
  - **把面板做成 GUI** → 那是渲染器（M3–M4）。**FR-7.3 自己写的是"（开发态）"**。
  - **导出时"顺手"规范化了负载** → 那就不是原轨迹了。**只读**。
  - **过滤按事件名而不是命名空间** → FR-3.2 明写"事件按命名空间划分"。
  - **反向验证写成"全名前缀匹配"** → **抓不住"按名字模糊匹配"这个真实破坏**（全名与名字是两段）。**验证要照着"实现可能怎么写坏"来写**，不是照着自己想的那个坏法写。

### 5.4 major 变更的处置流程

1. **改声明 / 改实现**（工作区改动，**不提交基线刷新**）。
2. **显式刷新**：`--update-baseline --reason "<理由>"` / `--update-expected --reason "<理由>"`——**不带 `--reason` 一律拒绝且不落盘**（M0 修好的门，M1 沿用，M2 沿用**且不得放宽**）。
3. **提交信息写明理由**——**基线刷新的提交**正文必须写清改了什么、为什么（AGENTS.md 提交规范）。
4. **反向验证**：喂一份改坏的临时基线给工具，断言退出码非 0。

| --- | --- | --- | --- | --- |
| — | **新增 `replay:` 命名空间的 5 条事件**（**不是 major 变更**） | 契约基线的**新增键**（事件不加计数键——架构 §4.4） | S3 | "新增 replay: 命名空间的五条事件声明（只增不改，既有键零变化）" |

## 6. 提交序列

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（S3 的两份基线、S5 的总线与基线、S14 的基准与基线刷新），**拆开提**。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。
- **并行批次里的提交由集成者串行切分**：写手只交工作区改动（并行 `git add` 会互相覆盖索引），集成者按"一次提交 = 一个阶段"逐笔 `git add -- <该写手的文件>` 后提交。**批次合并用 `--no-ff`**，保留批次边界。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚 · 合并**。

- **破坏性改动**在类型后加感叹号（`新功能!：…`）——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - **新增 `replay:` 事件** = **不破坏**（既有事件与命令一字未改；旧消费方按"未注册的事件类型"处理——NFR-9 明写容错）→ 不加感叹号。
  - **契约基线刷新**（S3）= **破坏性**（基线换了 = 比对基准换了）→ `新功能!：`。
  - **`bus/` 独立基线首次生成**（S5）= **破坏性**（多了一份比对基准）→ `新功能!：`。
  - **`replay` / `inspect` 从占位变真跑**（S9 / S11）= **破坏性**（旧调用方若依赖"占位即报错"的行为，会失效）→ `新功能!：`。
  - **S1–S2 · S4 · S6–S8 · S10 · S12** = 不破坏既有契约 → 不加感叹号。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。**基线刷新的提交必须把理由写进正文**（与 `--reason` 一致）。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S3 之后慎用 reset**：契约基线一旦刷新，回退就等于放弃那次刷新——**要重走显式刷新流程并写明理由**（基线与代码对不上会一路红；**且 git 背书守卫会拦**）。
- **S5 之后更慎**：`bus/` 独立基线是 **M3 / M4 的比对基准之一**，回退要连基线一起回退，且**回退理由同样要写进提交信息**。
- **冻结区基线 M2 没刷**——这是 M2 的优点：**回退 M2 的任何阶段都不涉及冻结区基准**。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 A 段（契约）提交行为代码 | 契约会被实现反向塑形（ADR-061） |
| 3 | 在 B / C / D 段（行为）顺手改契约声明 | 撞基线；必须走显式更新流程并写明理由 |
| 4 | 阶段内顺手做"别的阶段的事" | M3–M4 的需求提前实现会把还没定稿的东西锁死 |
| 5 | 用 `git commit -a` 批量提 | 容易把不该提的文件带进去 |
| 6 | 并行写手在同一分支上并行提交 | git 索引是**单一共享资源**，两个写手同时 `git add` 会互相覆盖 |
| 7 | 两个写手改同一个文件 | 文件归属互斥是并行安全的**前提**；重叠就拆到不同批次，或交给同一个写手串行做 |
| 8 | 审查期间写下一批时顺手改被审查批次的文件 | 修正回合与新批次同改一个文件必然互相覆盖；下一批**只加不改** |
| 9 | 子代理单方面改跨写手接口 | 并行写手之间没有协商通道；**接口变更先改本文件 §1.3**，由集成者裁决 |
| 10 | **顺手刷新基线** | 基线是 M3 / M4 的比对基准；**刷新必须带 `--reason`**（M0 修好的门） |
| 11 | **手改基线文件 / 期望清单** | 那是绕过显式刷新流程；**git 背书守卫（S2）会当场拦下** |
| 12 | **在 `systems/` 里 `open()` 或决定路径** | 破 M2-D2 + 破依赖方向；路径是宿主的事（ADR-064 / ADR-074） |
| 13 | **让可观测系统缓存或修改内核状态** | 破 M2-D1；`G2-3` 当场红，而这类污染极难被发现 |
| 14 | **给录制加有界可丢队列** | 丢一条命令 = 录像静默分叉（ADR-030 明确否决） |
| 15 | **刷新冻结区基线** | M2 不碰冻结区，**没有理由可写的刷新就是橡皮图章**（ADR-019） |
