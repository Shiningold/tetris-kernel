## A. 选型：用什么库

### ADR-001　事件总线自研（约 300 行）　`已定`

- **决策**：自己写，不用任何第三方事件总线。
- **否决**：`blinker`（缺优先级、中间件、历史与隔离）· `pubsub`（缺优先级与隔离，维护活跃度低）· `anyio`（本身不是事件总线）· asyncio 方案（直接违背"单逻辑线程串行推进"）。
- **理由**：需求对总线的要求是精确/通配/全局三种订阅、优先级、中间件、环形历史与区间查询、异常隔离、分发期间状态不变、同帧多轮 FIFO——没有成熟库同时满足。而这条总线是全项目地基（M0 的 31 条任务里 13 条直接依赖它），自研反而比拼装半成品更可控，且天然满足"内核零第三方依赖"。

### ADR-002　渲染宿主用 tkinter（标准库）　`已定`

- **决策**：主窗口用 tkinter + Canvas，事件流面板用原生 Text + `tag_config`。
- **否决**：PyGame / Arcade / Pyglet（图形框架把手感、输入、渲染耦合成"框架式"主循环，违背"渲染器只是又一个订阅者"，且引入编译型依赖）· Textual（基于 asyncio，与单逻辑线程串行推进冲突，且比 rich 重）。
- **理由**：标准库零依赖，宿主与内核的分离是需求硬约束；Tk 8.6 已在 py312 实测可用。

### ADR-003　内核 / 总线 / 规则零第三方依赖　`已定`

- **决策**：只用 `dataclasses` / `typing` / `enum` / `json` / `random` / `time`。
- **否决**：任何第三方运行时依赖。
- **理由**：架构约束 N7 与 NFR-4 要求内核不依赖特定运行时、图形接口或文件系统的专有能力。这是"内核可脱离一切独立运行"（AC-5）的前提。

### ADR-004　不用 asyncio / 事件循环驱动逻辑　`已定`

- **决策**：内核状态推进串行化，单逻辑线程。
- **否决**：asyncio 与任何事件循环框架。
- **理由**：N3 要求串行化推进。asyncio 会让"同帧多轮 FIFO"变回嵌套重入，"分发期间状态不变"不再成立。**注意约束的是单个内核实例，不是禁止多实例并行**（千局模拟走多进程，见 ADR-018）。

### ADR-005　类型检查用 pyright，不用 mypy　`已定`

- **决策**：pyright 1.1.414，内核与总线 `strict`，其余 `standard`；建议装 `pyright[nodejs]` extra 自带 Node 二进制。
- **否决**：mypy。
- **理由**：本机已有 Node v24.16.0；pyright 对 `frozen=True` dataclass 与 `tuple` 窄类型的处理更符合本项目"不可变优先"的写法。`nodejs` extra 比默认 nodeenv 路径可靠。

### ADR-006　构建后端只用 uv_build　`已定`

- **决策**：`uv + uv_build`，只留一个构建后端。
- **否决**：hatchling。
- **理由**：uv_build 是 uv 自带的，少一个构建依赖；后端二选一即可，两个并存没有收益。

### ADR-007　架构静态检查用 import-linter，不自研全部　`已定`

- **决策**：方案 A——import-linter 三类契约（`layers` / `forbidden` / `independence`）+ 自研补充脚本（禁平台名、事件登记、禁墙钟、冻结基线）。
- **否决**：方案 C（全部自研 AST 脚本）。
- **理由**：**起决定作用的一条**——G4-1"内核文件差异为空"是唯一不可妥协的核心判据，它成立的前提是分层边界**机器可验证**。import-linter 是当前唯一成熟、且原生支持三类契约的 Python 工具。全自研要重写"带完整导入链的违规报告"，且**把唯一的裁判变成自己的代码**——漏报比误报危险得多。

### ADR-008　发布渠道：只发 GitHub Releases　`已定`（2026-10-23 改）

- **决策**：交付渠道是 GitHub Releases——源码 tag + `uv build` 的 sdist/wheel + PyInstaller 免安装 exe（分窗口版 / 控制台版）。**不发 PyPI**。
- **否决**：PyPI 发布（原方案：PyPI 为主、exe 为补充）。
- **理由**：**包名先被否决**——`tetris` 在 PyPI 上已被他人占用（`dzshn/python-tetris`），本项目不能顶着别人的名字发布；改名之后又没有必须上架的理由。**其次，发布不可撤回**——PyPI 的版本号一旦发布就不能重用，改名、撤包都要另起名字；GitHub 的 tag 可以随时撤，代价小得多。**最后，PyPI 解决的痛点本项目没有**——面向的是"下载就能玩"的用户，他们要的是 exe，不是 `pip install`。
- **原理由留档**：原方案写"PyPI 才是国内最可达的渠道（直连与清华/阿里镜像本机实测均 200），exe 的下载点才是麻烦的那个"。这条实测结论仍然成立，但它只在"发 PyPI"的前提下才构成理由；不发 PyPI 之后，它变成"exe 下载点在国内确实更难"的证据——**GitHub Release 之外的国内可达性要单独解决**，属发布落点，M4 前再定。

### ADR-009　打包前必须先做非 editable 安装　`已定`

- **决策**：`uv pip install .`（不是 `-e .`）后再打包。
- **否决**：直接对 editable 安装打包。
- **理由**：editable 安装留下的 `.pth` 在 `--onefile` 打包时偶发解析失败。

### ADR-010　随机源只用 `random()` 与 `getrandbits()`　`已定`

- **决策**：两个原语；7-bag 洗牌自己实现 Fisher-Yates。
- **否决**：`shuffle` / `sample` / `choice`。
- **理由**：它们的实现细节在 CPython 版本间变过，`shuffle` 与 `sample` 的算法在 3.11 前后有变化——同样种子 + 同样状态取出的序列可能变，**升级 Python 会让全部旧录像集体作废**。只用两个原语，MT 状态就是序列的唯一决定因素。

### ADR-011　随机源用 `random.Random`（MT），状态可导出　`已定`

- **决策**：标准库 MT，状态 625 个整数 ≈ 7.17 KiB；录像头额外记 `rngStateVersion` 与 `pythonVersion`。
- **否决**：不记版本号。
- **理由**：已实测 `getstate()`/`setstate()` 往返可完全复现。但**状态容器格式曾随 Python 版本变过**（3.9 前为列表、之后为元组，版本号也不同），不记这两项，将来升级 Python 会**静默重放出不同结果**。

### ADR-012　终端输出用 rich，但不进 tkinter GUI 路径　`已定`

- **决策**：rich 只服务 CLI 报告与终端渲染器；tkinter 的事件流面板用原生 Text + `tag_config`。
- **否决**：把 rich 的输出塞进 tkinter Text。
- **理由**：tkinter 的 Text 控件不认 ANSI 转义序列，要走 Console 的 Segment API 逐段解析样式再映射成 Text tag（约 50–100 行）——那是一条小型渲染管线，把 rich 从"CLI 报告工具"拖进了 GUI 渲染路径。

### ADR-013　测试用 pytest + hypothesis　`已定`

- **决策**：pytest 9.1.1 + hypothesis 6.170.5（仅 dev 依赖）。
- **否决**：只用手写遍历脚本。
- **理由**：需求要求"构造脚本遍历所有状态变更路径"，属性测试能覆盖手写覆盖不到的空间（含非法命令、生命周期混乱、重复方块）。**两条纪律**：内核随机源固定种子；hypothesis 开 `derandomize=True`（见 ADR-053）。

### ADR-014　日志用标准库 `logging`　`已定`

- **否决**：structlog。
- **理由**：`logging` 的 handler 机制已原生支持多输出目标与分级，够用。

### ADR-015　CLI 用标准库 `argparse`　`已定`

- **否决**：click / typer。
- **理由**：子命令已够用，不为一个 CLI 引第三方运行时依赖。

### ADR-016　事件负载用 `frozen=True` dataclass + tuple　`已定`

- **否决**：pydantic。
- **理由**：事件信封要求高性能与不可变；dataclass + tuple 更轻更快。清单类字段一律 `tuple[tuple[int, int, int], ...]`。

### ADR-017　录像与存档用 JSON　`已定`

- **决策**：录像与存档用标准库 `json` 序列化。
- **否决**：msgpack / orjson · **数据库 / ORM / 后端框架**。
- **理由**：录像体积问题靠"只录命令"（ADR-045）解决；JSON 可读、可 diff、对版本兼容友好。不用数据库的理由是需求已定不做账号、排行榜与云端存储（W-2），存档与录像是自包含文件，标准库 `json` 足够。

## B. 结构与机制：系统长成什么样

### ADR-018　千局模拟用多进程，不做"关闭事件分发"的快速模式　`已定`

- **决策**：`ProcessPoolExecutor`，每局一个任务，进程池大小 = CPU 核数；`chunksize` > 1；汇总前按种子排序。
- **否决**：**"关闭事件分发"的批量快速模式**（明确否决）· 每局 fork 一个进程。
- **理由**：关闭事件分发会直接违反 N5 与 AC-2 事件完备性。按种子排序是因为浮点累加顺序随调度变化，否则统计输出不可复现。

### ADR-019　冻结区只锁 `kernel/` + `rules/`，`bus/` 暂不冻结　`已定`

- **决策**：冻结区严格对齐 G4-1；`bus/` 另列独立基线，等 M2 总线封板后再启用。
- **否决**：一开始就把 `bus/` 一起冻结。
- **理由**：M2 要给总线加中间件、历史查询、计数，批批刷新基线会变成**橡皮图章**——一条每次都被刷新的基线等于没有基线。

### ADR-020　事件类型注册表放 `contracts/`，绝不进冻结区　`已定`

- **决策**：注册表在冻结区外，`contracts/` 另立"只增不改"基线（键 = 事件类型名，值 = 负载字段声明的哈希）。
- **否决**：常量表放 `kernel/` 或 `rules/` · `contracts/` 完全不管。
- **理由**：变体加事件类型时若常量表在冻结区，冻结检查必红——要么加豁免（冻结作废），要么改内核（G4-1 作废）。而"冻结区外"不等于不加检查：既有类型的**负载语义**改了就能改变重放结果（那是 major 变更），冻结检查看不见它。基线哈希**机器可读声明**而非 `.py` 文件内容，否则改个注释就报警。

### ADR-021　只读视图走 `ctx.view()`，不提供 `bus.view()`　`已定`

- **决策**：订阅者签名统一 `handler(event, ctx)`，`ctx.view()` 惰性取视图，按发布点缓存。
- **否决**：总线上的只读访问器 `bus.view()`。
- **理由**：**决定性理由**——访问器可以在任何时候被调用，那时内核处于什么状态没有定义，会把"分发期间内核状态不变"这条结构性事实**退回成约定**。上下文形式天然关掉这个口子。

### ADR-022　帧号推进与推进许可分离　`已定`

- **决策**：帧号 +1、帧内序号归零在 tick **出队时**发生；推进许可在 tick **被接受**时授予。
- **否决**：帧号在"被接受"时才 +1。
- **理由**：`command:received` 在出队执行前发布，被接受只在执行之后才知道。若帧号在被接受时才 +1，tick 的 `received` 带旧帧号、`accepted` 带新帧号——**一条命令两个帧号**，审计链与回放对齐在每帧都有的 tick 上错位一格。

### ADR-023　帧推进五步，并写死加步的充要条件　`已定`

- **决策**：重力 → 锁定 → 消行 → 塌落 → 出生。
- **否决**：加第六步（默认不加）；整批返回不 step 化。
- **理由**：整批会让所有事件共享"执行后的最终态"，`piece:locked` 的订阅者读到的是已消行、已塌落、已出生的棋盘。**加一步的充要条件**：某订阅者需在两既有步骤间观察稳定状态，**且**该状态无法由任一既有事件的负载自足表达。两问都答不上来就不加。

### ADR-024　录像不逐帧记 tick　`已定`

- **决策**：不记。回放宿主自己每帧生成一条 tick，靠 `pause`/`resume` 的帧号 + 内核门禁重建空档；**回放宿主自生成的 tick 同样占帧内序号 0**。
- **否决**：逐帧记 tick。
- **理由**：回放宿主不需要它；记 tick 反而多一处编号对齐负担（回放宿主的编号规则必须与原局逐帧一致）；tick 是录像里最大头的内容而信息量近乎为零。

### ADR-025　命令参数禁浮点　`已定`

- **决策**：`args` 只含 JSON 标量（`int`/`str`/`bool`/`None`）与其元组，反序列化按命令类型还原。
- **否决**：允许浮点。
- **理由**：JSON 里 `1.0` 与 `1` 不可区分，重放时可能拿到不同的参数。**注意 `extensions` 允许浮点，口径不同是对的**——`args` 参与重放（参数不能漂），`extensions` 不参与重放判定，只承载变体状态的可读摘要与渲染用标量。

### ADR-026　指纹用 blake2b + TLV 编码　`已定`

- **决策**：`hashlib.blake2b` 对规范化字节序列求摘要；TLV = 1 字节类型标签 + 4 字节小端长度 + 值；棋盘行优先、`extensions` 按 key 排序、输入前加域分隔前缀；布尔与整数区分编码。
- **否决**：内置 `hash()` · JSON 文本算指纹 · 逐值打补丁式编码表。
- **理由**：`str`/`bytes` 的内置 hash 受 `PYTHONHASHSEED` 随机化影响，跨进程不稳定，指纹比对会毫无规律地失败。JSON 文本的格式化差异（浮点表示、空格、转义）会让同一份数据产生不同文本。早期那张编码表漏了 tuple / None / 元素边界三类歧义（`("ab","c")` 与 `("a","bc")` 会撞），TLV 一次解决三类。

### ADR-027　视图缓存键用"发布点"，不用步骤名　`已定`

- **决策**：缓存粒度是"一次 publish"；`ctx.step` 只是给订阅者看的标签，不参与缓存。
- **否决**：用步骤名当键。
- **理由**：一条命令产生两次发布（`received` 执行前、`accepted` 执行后），AI 一帧多条命令时更多。用步骤名当键，订阅者会读到**过期**状态——不崩、结果偏、极难发现。

### ADR-028　AI 搜索预算固定　`已定`

- **决策**：固定深度/迭代次数，一次算完再派发。
- **否决**：按耗时自适应 · 帧内增量搜索。
- **理由**：约束是"计算量与机器负载无关"，不是"什么时候算"。否则 AI 每帧算多少取决于当时剩多少时间，派发的命令序列不再确定，**回放静默分叉**（比"丢一条命令"更难查）。AI 每帧重算没问题——重算次数由策略决定，不由耗时决定。

### ADR-029　tkinter 帧循环用 `after(5)` + 累加器补帧　`已定`

- **决策**：`after(5)` + `time.monotonic()` 累加器，设最大追帧数（默认 5），时钟源必须可注入。
- **否决**：`after(1)`（实测吃满一个核的 91%）· `after(16)`（实测最大抖到 31.53ms，会整帧错过）· `after(2..15)`（Windows 定时器分辨率约 15.6ms，一律被上舍入）。
- **理由**：实测 `after(5)` ≈ 64 次/秒、0.65% 单核，是唯一兼顾的选项。逻辑步长严格 60Hz 由累加器保证，与 tick 周期无关，**不影响确定性与回放**。

### ADR-030　回放录制走同步订阅者　`已定`

- **决策**：内存 list 累积，局末或周期点一次性落盘。
- **否决**：有界可丢队列（日志/指标那套异步策略）。
- **理由**：丢一条命令 = 录像静默分叉，NFR-1 / AC-1 / G2-1 全废。"不可丢"靠**没有队列**保证，不靠队列策略。
- **落盘怎么落地**：见 ADR-064——回放系统不自己开文件，宿主注入 sink。

### ADR-031　降级三档固定顺序，带滞回　`已定`

- **决策**：① 关闭调试事件 → ② 降低日志级别 → ③ 关闭事件历史缓冲；手动只开放第 ① 档；自动降级 P99 > 1.6ms（600 帧窗口）降档、P99 < 1.0ms 持续 1800 帧升档。
- **否决**：引入"关闭事件分发"的快速模式 · 第 ③ 档暴露给用户手关。
- **理由**：三档都不伤指标系统；关事件分发会破坏事件完备性。第 ③ 档不暴露是因为用户手关会让时间旅行调试"看起来坏了"。判据用 P99 不用均值。

### ADR-032　规则表落成 Python 字面量常量　`已定`

- **决策**：踢墙偏移表、计分表随规则模块一起进冻结基线。
- **否决**：落成外部数据文件。
- **理由**：那会让"内核文件差异为空"变成文字游戏（规则被改到冻结区之外），且引入 IO 依赖撞上"内核不依赖文件系统专有能力"，还给冻结基线开洞。M4-3 的"变体参数可外部配置"指变体自己的调参，不冲突。

### ADR-033　回放暂停用宿主级，不用内核级 `pause`　`已定`

- **决策**：宿主级暂停 = 不跑帧循环、帧号冻结、不产生任何命令。
- **否决**：回放暂停实现成内核级 `pause` 命令。
- **理由**：`pause`/`resume` 是被接受的命令 → 会被录进录像 → **回放自己污染录像**。

### ADR-034　`variants/` 禁止 import `kernel` / `bus` / `adapters` / `host`　`已定`

- **决策**：变体与 `systems` 同级，只能 import `systems` / `rules` / `contracts`。
- **否决**：允许变体直接引用内核。
- **理由**：一旦变体能 import 内核，它就能把内核私有结构当自己的 API——**内核没被改，但 G4-1"内核文件差异为空"就只剩形式**。变体要的一切都必须走 `rules` 替换或 `systems` 插件两个口子。

### ADR-035　插件不需要运行时沙箱　`已定`（需求决策 13）

- **决策**：不需要进程隔离 / 权限沙箱；要的是**失败隔离**（FR-3.4）与**卸载干净**。
- **否决**：任何插件沙箱机制。
- **理由**：个人项目里插件与内核同信任级别。

### ADR-036　`extensions` 的 key 必须唯一　`已定`

- **决策**：重复 key 即结构错误并记错；宿主合并时校验。
- **否决**：去重取末值。
- **理由**：那会把一个 bug 变成一个静默的覆盖。`extensions` 是 tuple 不是 dict，可以写出重复 key → 语义不明且指纹失真。

### ADR-037　拓扑是坐标映射函数，不是参数　`已定`

- **决策**：规则集提供 `wrap_cell(x, y, w, h) -> tuple[int, int]`（标准=恒等、圆柱=x 环绕、莫比乌斯=x 环绕 + y 翻转），**内核在所有坐标访问点都过一遍**，标准玩法走恒等快路径。
- **否决**：把拓扑当成参数传。
- **理由**：莫比乌斯环绕行后上下翻转是**行为**，"多一个参数"表达不出来。不定这条，M4-C 落地时就要在内核里加调用点——破得和"规则接口签名没留维度"一模一样。

### ADR-038　同因拒绝合并防抖　`已定`

- **决策**：同一 phase 下连续被拒的命令只发第一条，后续合并计数；键 = (phase, 命令类型, 拒绝原因)；`mergedCount` 起始值 = 1；`received` 与 `rejected` 成对合并。**合并窗口 = 一批命令**（`run_rounds` 的一轮；单独逐条调 `execute()` 时窗口就是这一条命令）。
- **否决**：逐条发一条 rejected。
- **理由**：那是一条**实现动作**，一帧能刷出几十条事件。**配额超限是本条最典型的应用场景，不是例外**——配额满时队列里剩 50 条命令，走合并分组，不是刷 50 条。同时必须写明"**满足形式是'一条事件承载 N 次拒绝'，不是'没有事件'**"，否则 AC-2 的事件完备性检查会误判成事件缺失。
- **窗口口径（2026-10-24 补 · M0 全量审查 M0-7）**：原先只有"连续"与"重置"，**读不出窗口的边界**——规格与架构各说各话。窗口 = **一批命令**这条要写进所有引用处（spec §7.2 / 架构 §6.5 / plan S10），否则同一件事会在三个文件里各写一遍、各改一遍。**M0 的无头宿主每帧只派发一条 tick** → 窗口里装不下第二条 → `mergedCount` 恒为 1，**防刷屏在 M0 零收益**（机制是对的，真实输入接入之后才有意义）。

### ADR-039　重入语义：命令入队 + 同帧多轮（Round）　`已定`（需求决策 1）

- **决策**：订阅者在分发期间派发的命令一律进队列，当前分发结束后按 FIFO 执行，其产生的事件触发新一轮分发。
- **否决**：递归调用栈展开。
- **理由**：同一事件的所有订阅者因此看到同一份状态，递归被展开为轮次而非调用栈；"分发期间内核状态不变"成为结构性事实。轮次数与单帧命令数双上限，超限丢弃余量并发事件；AI 在帧内派的命令仍于本帧下一轮生效，不损失响应性。配套见 ADR-040。

### ADR-040　轮次与命令数上限按帧累计　`已定`

- **决策**：两个计数器每帧开始清零；`tick` 自身不计入命令数；超限判定发生在"取队执行"之前，不跨帧顺延。
- **否决**：按单轮累计。
- **理由**：按单轮算 8×100 = 800 条/帧，上限形同虚设。

## C. 需求决策的本文映射

### ADR-041　事件粒度三级　`已定`（需求决策 2）

- **决策**：语义事件 / 批量差异事件 / 调试事件，调试事件默认关闭。
- **否决**：统一粒度。
- **理由**：批量差异（如 `board:changed` 的变化格子清单）避免逐格发事件；调试事件默认关闭是为了性能预算（NFR-2）。

### ADR-042　快照是拉取式　`已定`（需求决策 4）

- **决策**：事件只说"发生了什么"，需要状态的一方主动拉快照。
- **否决**：事件自带完整状态。
- **理由**：事件更小、回放更小。配套：帧末宿主拉一次快照并分发给所有渲染器。

### ADR-043　旋转失败：命令被接受，另发受阻事件　`已定`（需求决策 6）

- **决策**：旋转无合法落点时命令仍被**接受**，另发受阻事件。
- **否决**：走拒绝通道。
- **理由**：旋转失败是合法游戏行为，不该进拒绝通道——**拒绝只留给"当前状态根本不该发这个命令"**。这条区分让日志与反作弊清晰得多。

### ADR-044　DAS/ARR 归输入适配器　`已定`（需求决策 8）

- **决策**：手感参数属输入适配器；内核只认"移动一格"这类原子命令。
- **否决**：手感参数进内核。
- **理由**：换设备调参不影响录像复现（FR-8.3 要求调参不触发状态变更）。

### ADR-045　回放录命令序列，不录事件序列　`已定`（需求决策 9）

- **决策**：录被**接受**的命令（含种子与规则集标识），来源随命令记录；回放期间命令源独占。
- **否决**：录事件序列。
- **理由**：事件粒度会随版本调整而失效，不适合长期存档；事件流只作为回归断言基线（FR-6.4）。**回放期间必须卸载 AI / 教学 / 网络系统**，否则"重放时 AI 也在下"会直接摧毁确定性。

### ADR-046　日志级别映射放在日志系统内　`已定`（需求决策 10）

- **决策**：事件不自带级别，级别由日志系统按事件类型映射。
- **否决**：事件自带级别字段。
- **理由**：事件不该知道自己有多重要——同一事件排障时是 trace，演示时可能是 info。

### ADR-047　受控写入不算破坏"唯一写入者"　`已定`（需求决策 14）

- **决策**：外部系统改变棋盘统一收敛为 `writeCells`，由内核校验后落笔并照常发 `board:changed`。
- **否决**：给外部开直接写通道。
- **理由**：它把"外部直接写"变成"外部请求 + 内核裁决"，落笔与发事件仍全部由内核完成，N1 与 N5 都不破。同帧多请求命中同一格默认后者覆盖（可配置为后者被拒），单帧写入量设上限。**必须在 M3 定型**，否则 M4 会很想开后门。

### ADR-048　变体怎么实现：看是否改变"棋盘上发生了什么"　`已定`（需求决策 17）

- **决策**：需要改变棋盘 → 替换规则模块或走受控写入；不需要（如节奏化）→ 纯订阅者，完全不碰内核。
- **否决**：按"实现难易"选路径。
- **理由**：这条判据直接决定 G4-1 能不能兑现。

### ADR-049　变体状态用扩展字段承载，内核不理解内容　`已定`（需求决策 18）

- **决策**：`extensions: tuple[tuple[str, JsonScalar], ...]`，只放标量，禁止容器与嵌套；复杂状态由变体自己持有，帧末宿主合并进 `extensions`。
- **否决**：让内核认识变体状态。
- **理由**：这是"变体加状态但内核不改"的风险缓解——内核只原样携带与序列化。

### ADR-050　先做变体 A（重力可旋转）　`已定`（需求决策 19）

- **决策**：先做 A，变体 B 作为第二个验证点。
- **否决**：先做 B（落地后生长）。
- **理由**：A 只触及规则模块、不涉及受控写入，是"零内核改动"最干净的证明，且上手就有新鲜感。B 路径更长。

## D. 环境与工具链纪律

### ADR-051　禁用 `uv sync` / `uv venv`　`已定`

- **决策**：只用 `uv pip install --python D:\miniconda3\envs\py312\python.exe ...`。
- **否决**：`uv sync` / `uv venv`。
- **理由**：它们会自建项目 `.venv`，把包装到 conda 环境之外，绕过"必须用 py312"这条规矩。已实测 `uv pip list --python <conda 解释器>` 可用。

### ADR-052　ruff 只认环境内那一份　`已定`

- **决策**：py312 环境内的 0.17.1；CI 里钉死版本。
- **否决**：用 PATH 上的 0.15.17。
- **理由**：两个版本格式化结果不同，不钉死会在不同机器上打架。

### ADR-053　hypothesis 必须开 `derandomize=True`　`已定`

- **决策**：属性测试关闭自身生成随机性。
- **否决**：只固定内核种子。
- **理由**：**只固定内核种子不够**——hypothesis 自己的生成随机性也是变量，不关掉它，CI 上的偶发失败无法复现。

### ADR-054　事件目录只允许追加　`已定`（NFR-9 / B-4）

- **决策**：禁止重定义既有类型的负载语义；未知类型按信封解析后静默丢弃或记 trace，不得中断分发或重放。
- **否决**：修改既有事件类型的负载语义。
- **理由**：改负载语义就能改变重放结果，属于 major 变更。机器化实现见 ADR-020 的"只增不改"基线。

### ADR-055　一个录像 = 一局　`已定`

- **决策**：`game:created` 开新录像；`reset` 被接受时结束当前录像并开下一份。
- **否决**：一份录像装多局（若真要，必须按边界切段、每段独立重置帧号、按段回放）。
- **理由**：这样录像里帧号永不重复，回放不需要分段逻辑。

### ADR-056　视图与快照是同一个 dataclass　`已定`

- **决策**：不写两套"几乎相同"的结构。
- **否决**：为视图单独定义一个类。
- **理由**：两套结构长期必然漂移。

### ADR-057　两个订阅入口共享同一个注册表　`已定`

- **决策**：`subscribe(event)` 与 `subscribe_system(event, ctx)` 共享注册表与优先级序列，**排序在合并之后进行**。
- **否决**：按入口分两张表。
- **理由**：否则"业务订阅者先于日志订阅者"（FR-3.3，M 级）在跨入口时不成立。

### ADR-058　内核内部用可变结构，导出时深拷贝　`已定`

- **决策**：内部 `list[list[int]]`，快照导出深拷贝成 `tuple[tuple[int, ...], ...]`。
- **否决**：内部也用 tuple。
- **理由**：内部用 tuple 每次落子都要整体重建嵌套元组；只冻结外层则快照与内核共享内层列表，渲染器一改就破"只有内核能写状态"。

### ADR-059　视图通道对渲染器关闭　`已定`

- **决策**：渲染器走单参数入口，只消费帧末宿主推送的那一份快照。
- **否决**：给渲染器也开 `ctx.view()`。
- **理由**：否则"帧末只拉一次"退化成 N 次。**注意 `bus.publish` 对两个入口都开放**——发布能力与视图能力无关，渲染器要发自产事件 `render:frame`。

### ADR-060　`rng:next` 默认开启，负载瘦身　`已定`

- **决策**：默认开启（不随调试事件一起关）；负载 = 随机值 + 序号 + 状态指纹（短哈希），**不含完整 MT 状态**。
- **否决**：默认关闭 · 负载带完整状态。
- **理由**：FR-5.3 是 M 级要求，随机序列审计依赖它；频率不高（7-bag 每方块约 1 次取值），默认开启代价可忽略。负载不可变 + 625 元素 ≈ 每次取值构造一份，一局几百方块就是几 MB 常驻负载。完整状态只在存档路径导出。

### ADR-061　规则接口签名在 M0 定稿，`M3-18` 降级为复核　`已定`

- **决策**：四项签名 + 形状表 / 踢墙表接口在 M0 建壳时定死，**签名声明进 `contracts/` 基线**（第四部分）；`M3-18` 只做复核，复核不通过只能走 major 变更流程，不允许顺手改。签名表见 `项目架构.md` §7.3.1。
- **否决**：`M3-18` 定稿（原方案）· 形状表 / 踢墙表留到 M3 · 规则集持有可变内部状态 · 运行期切换在 M0 就实现。
- **理由**：`rules/` 自 M0 进冻结区，而标准规则是 M 级需求、M1 就要实现——**签名晚于实现必被实现反向塑形**，补维度即改冻结区；ADR-019 把这件事说得很直白：批批刷新的基线是橡皮图章。规则集不可变、随时间变化表达为关于 `ctx` 的纯函数，是为了让 FR-10.2 存档恢复零负担。签名进基线是"定死"的牙齿——改签名会撞基线，只能走显式 `--update-baseline` 并写明理由。
- **补一条原本没人提的空白**：需求 §10 说变体 A「切换经命令通道」，但命令目录 16 条里没有对应命令，这是需求内部的矛盾。**解法是排到 M3，不是 M0 抢跑**：M0 只把 `axis` 作为 `RuleContext` 的字段预留（签名必须覆盖变体维度），M3 增补"运行期换规则集"的命令与门禁（内核改动随 M3 刷新基线），M4 变体 A 直接用 M3 已有的能力——**G4-1 约束的是 M4 落地变体时内核差异为空，M3 的改动不违反它**。若在 M0 就实现切换，既违反"不实现其他阶段的需求"，也会让 M3–M4 的批次边界失守。
- **冷却 / 防抖动不进内核**：它是输入适配器的节流或插件自己的策略，内核与规则集都不需要知道"多久能再切一次"。这条若搞混，就会有人给内核加 `lastSwitchFrame`、再把规则集签名撑出一个"能否切换"的维度——那正是本 ADR 要避免的"补维度"。

### ADR-062　信封五字段，元数据三键　`已定`

- **决策**：信封去掉"逻辑时间戳"，改五字段（序号 / 帧号 / 类型 / 负载 / 元数据）；元数据 = `source` / `producer` / `cause` 三键。录像透传原始 `source`，live / replay 是宿主上下文，不占该字段。
- **否决**：时间戳保留为可独立写入字段 · 改成帧内发布序号 · 回放时把 `source` 写成 `replay` · `cause` 指向全局事件序号。
- **理由**：冗余字段是分叉源——它一旦可独立写入，回放校验时就能与帧号对不上，而它还会被算进基线哈希，将来想删就是一次 major 变更。逻辑时间 = 帧号 × 步长（步长由 `clock:tick` 的负载给出、录像头记录），派生即可；有效游戏帧数按 `clock:tick` 计数（架构 §6.1），本来就不靠这个字段。录像改写 `source` 会让 FR-6.4 的事件流回归基线永久失配。
- **一条实现上的硬约束**：`cause` **不指向全局事件序号**——序号由总线在入队时分配（架构 §4.2），内核生成事件草稿时还拿不到它。因果标识只能用内核侧已有的 **(帧号, 帧内序号)**（架构 §6.3）。
- **连带**：回放期间命令源独占的兜底改由**宿主层**拦截派发（内核不按运行模式分支，FR-8.5；`source` 在回放时透传原值，也不能当模式判据）。

### ADR-063　插件生命周期事件由 host 发出，类型名不动　`已定`

- **决策**：`kernel:system:installed` / `kernel:system:removed` 由 **host** 发出，`producer` = `host`；事件目录加"产出者"列；`kernel/` 与 `rules/` 源码内不得出现这两个事件名字面量、不得出现任何系统名。
- **否决**：由内核发出（需在内核建系统表，破 N1 / N6 的精神）· 改名迁出 `kernel` 命名空间。
- **理由**：改名的连锁成本高于用 `producer` + 机器检查立纪律——44 个事件是需求资产，改名要连锁改需求表与订阅过滤。而**"产出者"列一次性解决全部 44 个事件的归属不明**：`kernel:ready` / `kernel:error` / `state:changed` / `metric:sampled` / `render:frame` 的产出者此前全靠猜，而 FR-9.2 的依赖图生成与 FR-3.4 的异常隔离都要它。命名空间 ≠ 产出者，`kernel:` 前缀说的是"这件事属于内核实例"，不必然是内核干的。
- **连带三条**：`kernel:system:removed` 的负载带 `clean: bool`，卸载不干净就记错，但**不占用 `kernel:error`**（§6.4 已限定它只留给订阅者异常）；订阅返回句柄，卸载时校验该系统的订阅全部注销、待发布队列里的自产事件全部丢弃；事件负载里的"配置"必须是扁平 JSON 标量映射，不可序列化对象一律不进事件（否则回放与导出会炸）。

### ADR-064　落盘经宿主注入的 sink，路径不写死　`已定`

- **决策**：回放 / 日志 / 指标等需要落盘的部件**不自己开文件**——宿主装配时注入一个 sink（可调用对象），部件只负责"录什么、什么时候交出去"。**路径必须可注入**（测试注入 `tmp_path`），**文件名不带墙钟**。
- **否决**：部件里直接 `Path.home()` / `open()` · 引入 platformdirs 决定目录 · 文件名带时间戳。
- **理由**：`systems/` 不能 import `adapters/`（依赖方向），回放系统在 systems 层、存储在 adapters 层——**它连 import 存储适配器都不行，更别说自己决定路径**。不定这条，M2 实现时几乎必然有人在回放系统里写 `Path.home()`：既破 §4.1（systems 只能订阅 + 派发），也让测试没法隔离。路径可注入是 NFR-3「内核 100% 可无头运行」的前提之一，留到 M2 再想就晚了。文件名不带墙钟，是因为录像头已有种子 + 规则集标识 + 版本——带时间戳会让"同一局录两次"产生两份文件，AC-1 的 200 局比对分不清哪份是哪份。不引 platformdirs 是 ADR-003 的精神：多一个依赖没收益，`os.environ` + `pathlib` 二十行就够。
- **跨平台目录策略**（`%LOCALAPPDATA%` / `~/Documents` / `Path.home()`）留到 M2 定，**但边界现在就钉**。

### ADR-065　活动方块不变量：命令只能用自己声明过的拒绝原因　`已定`

- **决策**：把「running 态没有活动方块」从**契约缺口**改判为**内核不变量破坏**。架构 §6.8 定下不变量：*命令执行时（帧推进已被完整消费后），`phase == running` 必然持有活动方块*。据此定一条统一规则——**命令只能用自己声明过的拒绝原因**：六条移动 / 旋转命令声明了 `no_active_piece`（**防御性保留**：正常执行走不到），`hold` 没声明 → 契约没描述这个状态，就没有可发的拒绝事件 → 内核以 `KernelInvariantError` 终止，**不硬造一条没声明的拒绝原因**。`_reject` 加守卫：实现发出的原因不在该命令的 `reject_reasons` 里，当场抛异常。
- **否决**：给 `hold` 的 `reject_reasons` 加上 `no_active_piece`（走 major 变更流程）· 六条命令也一律抛异常、`no_active_piece` 整条作废 · 让 `hold` 静默拒绝成 `invalid_argument` / `illegal_transition` · 把条款写进 `contracts/commands.py` 当唯一落点。
- **理由**：**改契约的声明元组 = 撞基线 = major 变更流程**（`command/hold/rejectReasons` 是基线里的一条键），而需求 §8.2 给 hold 列的情形里本来就没有「无活动方块」——加上去是需求与契约两头都要动。**不变量条款是对系统行为的陈述，不碰任何命令声明**：落点在架构 §6.8，契约与需求只**引用**它，**冻结面零改动**（基线仍 355 条）。这条同时闭掉 S3 报告的 M3 预警（「要么临时给 hold 加拒绝原因——那时基线可能已冻结，就是一次 major 变更」）。
- **规则是统一的，结果不同只是因为声明不同**：六条命令声明了 `no_active_piece`，所以那条路径照常拒绝（需求 §8.2 明写它们可因「无活动方块」被拒）；`hold` 没声明，所以它**没有"可拒绝"这个选项**——不是两套口径，是同一条规则遇到两张不同的声明表。
- **对宿主的义务**：宿主**必须完整消费**帧推进的步骤序列（架构 §6.2）；提前 `break` 会留下"锁定已完成、消行未做"的半帧，此后内核在需要活动方块时**抛 `KernelInvariantError` 而不是静默拒绝**——这是**故意的**：静默拒绝会把内核的损坏藏起来，抛出来才查得到。宿主要 catch 它，并据此报「装配层提前退出了帧推进」。
- **连带**：`_reject` 的守卫把「实现 ↔ 契约」这一环从测试挪到**运行期**——原先只有「契约 ↔ 转录表」，实现发一个没声明的原因时**没人拦**（12 值枚举本身看不出破绽：值合法，**归属**不合法）。

### ADR-066　重力间隔由内核兑现：快照增补 `gravityTimer`，事件面零改动　`已定`

- **决策**：内核的帧模型**消费规则集已经冻结的 `gravity_interval(ctx)` 签名**——落格间隔查规则集的等级表（标准 1 级 = 60 帧落一格），内核不写死帧数。为此**契约面增补一个快照字段 `gravityTimer`**（**距下一次落格还有几帧，0 = 本帧到期**），**随方块出生重置**（新方块在第 `间隔` 帧落第一格）；间隔变短（等级下降）时把剩余帧数**夹到新间隔**。**触地判定仍每帧做**（幽灵落点走 0 格即触地），所以**间隔不拖慢锁定**——M0 的「落即锁」不变。
- **否决**：① 维持「每帧一格」把这处口径写死（M1 再兑现，要重开契约）· ② 改 `clock:gravity` 的负载或语义（加一个「本帧是否真的落格」的字段）· ③ 把计时放进 `RUNTIME_ONLY_STATE`（不进快照）· ④ 让内核自己维护一张间隔表（绕过规则集）· ⑤ 把间隔留给宿主层（宿主决定何时调 `advance_frame`）。
- **理由**：**节奏是规则集的事，帧模型是内核的事**——`gravity_interval` 已经在 `contracts/rules.py` 冻结（ADR-061）却没人消费，**契约声明了接口却不兑现，等于让实现反向塑形签名**。兑现它绕不开一个跨帧状态，而**内核状态必须全部进快照**（清单第 15 项 / FR-10.2）→ 只能给契约加字段。**这条改动按基线纪律落在「允许新增键」一侧**（架构 §4.4：允许新增字段，禁止已有键的哈希变化）——既有键的哈希一个没动，所以**不撞基线**：快照字段 21 → 22、基线条目 355 → 356。**走的是 major 的纪律不是 major 的破坏**：显式记录、更新需求表与契约清单、留回归守卫。**没有碰 `rules/`**（间隔表是规则集自己的东西，已实现）。
- **事件面零改动**：`clock:gravity` 每帧照发，未到期时 `dx` / `dy` 记 0——这与既有的「重力受阻时位移为 0」**是同一条语义**（订阅者据此知道"这一帧重力没能推动方块"），所以**不改负载、不改语义、不新增事件**。**旧录像仍可回放**（事件流没变）。
- **触地判定为什么留在每帧**：间隔只管「什么时候下移」，不管「有没有到底」。若把触地也等到落格帧才判，方块贴地后要最多等一个间隔才锁定——那是**锁定延迟**，与 M0 的「落即锁」（`lockTimer` 恒 0）冲突。判据改成「幽灵落点走 0 格」（等价于"再往重力方向走一格会撞"），既复用已有的幽灵计算，又让触地与锁定留在同一帧。
- **不兑现的代价**：M0 的每一局都在「每帧一格」的快 60 倍节奏下跑完——无人操作的一局约 250 帧就顶出结束，10000 帧的 G0-1 里**前 ~250 帧在真打、其余全是「tick 被拒」的拒绝路径**；开放项 C（每帧真实事件数）会采到拒绝路径上的数。兑现之后，10000 帧里前 ~8000 帧都在真打，采到的数才是常态帧的数。

### ADR-067　`RuleContext.stepMs` 的语义落定为「宿主逻辑步长（毫秒）」　`已定`

- **决策**：`RuleContext.stepMs` = 「**宿主逻辑步长（毫秒）**」——**宿主**从可注入时钟（真实 / 虚拟，架构 §5.3）取本帧的**固定步长**，经 `ctx` 递给规则集；规则集**只透传不用**（标准玩法的重力间隔用**逻辑帧数**，`gravity_interval(ctx)` 返回帧数，不看毫秒）。字段**保留，不删**。
- **否决**：① **删掉该字段**（原选项 B）· ② 定义成「当前重力间隔（毫秒）」（M0 前的旧写法）· ③ 定义成「距上次落格过了多少毫秒」· ④ 让内核自己算毫秒。
- **理由**：**语义待定的字段会被下一个人按自己的理解用**——把「待定」留在契约里，等于把解释权交给下一个实现者，而它落进的是**冻结签名**（ADR-061），被按自己的理解用过之后再改又是一次 major 变更。**毫秒这条线在契约里只有这一个落点**：事件侧 `progress:level-changed.gravityInterval` 是逻辑帧数，`gravity_interval(ctx)` 也返回逻辑帧数——**节奏是规则集的事，帧模型是内核的事**，而**步长是宿主的事**（架构 §5.3：时钟源落宿主层，内核只认逻辑帧、不读墙钟）；宿主本来就有 `Clock.step_ms()`，把它当固定步长递进来是它现成的职责（逻辑时间 = 帧号 × 步长，与 `clock:tick` 的负载同一口径）。**「只透传不用」是关键**：字段留在契约里是给**变体**留的——将来若有变体要按毫秒调手感，那是变体自己的事，契约层不替它决定；而标准玩法再多一条时间线，就多一处会悄悄分叉的真相。**删字段同样是 major 变更**，将来要加回来又是一次 major——**留着、补上语义，最省**。
- **连带**：
  - `contracts/rules.py` 的 `RuleContext` docstring 从「语义待定」改成确定描述，写明**谁算、给谁用**；**类型串一个字符没动**（docstring 不进基线，只有类型串进）→ 这次改动**不影响契约基线**。
  - **生命周期取值收敛到契约层单一来源**：四个状态名的字面量表只在 `contracts/types.py`（四个 `PHASE_*` 常量 + `PHASE_VALUES` + `Phase` 别名）；`kernel/lifecycle.py` 的 `PHASE_*` 由它派生（S2 已落），`contracts/commands.py` 的**门禁三值**（`REJECT_REASONS` 的前三项 · `REJECT_REASON_CATEGORIES["lifecycle"]` · `LIFECYCLE_REJECT_REASONS`）也改为引用常量——**门禁三值就是三个状态名本身**（架构 §7.3.1「门禁三值从状态派生」），`kernel/core.py` 的 `_guard_reason` 同理。**值一个没变**（`"paused"` 仍是 `"paused"`）→ 契约基线的键与哈希不变。
  - **三条机器守卫**（`tests/test_contracts_declarations.py`）：① `ctx.stepMs` 的值必须等于**宿主给的步长**（宿主给 16 → 规则集看到 16）② `rules/` 里**不得读 `ctx.stepMs`**（透传不用是这条口径的一部分）③ `contracts/` 与 `kernel/` 里**不得再出现这四个取值的字面量**（docstring 与注解除外）——抄第二份字面量表正是这类分叉的温床。

### ADR-068　180° 踢墙表采 TETR.IO / Jstris 口径；SRS 表的 y 分量取反落到本项目坐标　`已定`

- **决策**：标准踢墙表 = **SRS 权威 90° 表**（JLSTZ 一套 · I 一套 · O 不踢墙）+ **180° 扩展表两套**（JLSTZ 一套 · I 一套）。**180° 没有单一权威**：本项目采 **Hard Drop Tetris Wiki 的 `Rotation System in TETR.IO` 条目**——具体取**TETR.IO 与 Jstris 共用的那两级候选**（JLSTZ 组）与**该条目 I 方块那一段的两级候选**（I 组）。**不冒充 SRS 正统**。另外：权威表的坐标是 **y 上正**，本项目是 **y 下正** → **落地时 y 分量一律取反**。
- **否决**：① **把自造的 180° 表说成 SRS 正统**（SRS 原始规范根本不含 180°；冒充 = 把项目的自定口径绑在别人名下，日后对不上要背锅）· ② **采 NullpoMino 的 180° 表**（候选到 11 档，出自日厂街机口径，不是"现代通行"）· ③ **采 TETR.IO 的六级 180° 表**（T / L / J 三者各不相同、各带"不可能"档位，**凑不成"一组一套"**，与 spec §7.2 定的表结构冲突）· ④ **不做 180° 踢墙**（命令目录里有 `rotate180`、签名里也含 180°，一律拒绝等于功能缺失）· ⑤ **权威表的 y 直接照抄**（本项目坐标 y 下正，照抄 = 整个踢墙方向上下颠倒，**而两遍独立转录可能一起错**——都照着权威表抄同一个方向，比对抓不到）。
- **理由**：**表是离散数据，错一条不会让任何"跑通"类判据变红**，只会让某个角落转不进去——所以表必须**从权威源逐条转录**而不是凭印象写，且来源要说得清楚。三条来源事实：① **SRS 原始规范不含 180°**——Tetris Wiki 的 `Super Rotation System` 与 Hard Drop 的 `SRS` 两处都只给 8 种 90° 转向；② **180° 的现代通行口径在 TETR.IO / Jstris 一系**，Hard Drop 的 `Rotation System in TETR.IO` 条目记的就是它，并明说"Jstris 只用六级里的前两级"；③ **前两级对 JLSTZ 全体统一**（T / L / J / S / Z 的第一档都是 `(0,0)`，第二档按转向分别是 `(0,+1)` / `(+1,0)` / `(0,-1)` / `(-1,0)`），正好落进"JLSTZ 与 I 各一套"的表结构。**y 取反这一条是硬约束**：`PlacementInfo.cells` 与 `SHAPE_TABLE` 的坐标都是 y 下正，权威表是 y 上正，**不取反就是把踢墙方向整体上下颠倒**——所以这条换算必须写进注释与 ADR，好让第三遍复核的人知道该查哪一步。
- **连带**：
  - `rules/tables.py` 的四张基准表（`_KICK_90_JLSTZ` / `_KICK_90_I` / `_KICK_180_JLSTZ` / `_KICK_180_I`）**逐行对应权威表的行**，再由 `_build_kick_table()` 摊成 16 种转向 × 3 个踢墙组——**每个权威行只出现一次**；手抄成 48 条时"复制粘贴错一条"的风险被消掉。
  - `rules/tables.py` 与 `tests/test_rules_m1.py` 的注释都写死了 **y 上正 → y 下正取反** 这条换算，并各留一份权威行原值对照（例：JLSTZ 的 0→R 权威行 `(0,0) (-1,0) (-1,+1) (0,-2) (-1,-2)` → 本项目 `(0,0) (-1,0) (-1,-1) (0,+2) (-1,+2)`）。
  - **踢墙组映射由规则集提供**（`tables.KICK_GROUP_BY_PIECE`）：J / L / S / T / Z → `"JLSTZ"`，I → `"I"`，O → `"O"`（O 组只有 `(0,0)`——SRS 里 O 旋转不位移）。

### ADR-069　T-Spin 计分采「项目口径」：与官方 guideline 的三处偏离逐条点名　`已定`

- **决策**：标准规则的**基础分表**（`tables.SCORE_TABLE`）按**项目口径**落地（分值来自 spec §7.4，M1 拍板时已定），**口径标注为「项目口径」而不是「guideline 口径」**——本项目的 T-Spin 计分与官方 guideline 有**三处偏离**，**逐条点名**：

  | 情形 | guideline | 本项目 |
  | --- | --- | --- |
  | T-Spin 消 0 行 | 400 | **0**（`tspin-none`） |
  | Mini 消 0 行 | 100 | **400**（`tspin-mini`） |
  | Mini 消 1 / 2 / 3 行 | 200 / 400 / Impossible | **按完整 T-Spin 计**（800 / 1200 / 1600） |

  **其余分值与 guideline 逐条相同**：完整 T-Spin 消 1 / 2 / 3 行 = 800 / 1200 / 1600 · 普通消行 1 / 2 / 3 / 4 = 100 / 300 / 500 / 800 · **难消的定义也与 guideline 一致**（消了行的 T-Spin 不分 Mini 与否都算难消；**消 0 行的 T-Spin 不算难消，也不断 B2B 链**）。
- **否决**：① **把项目口径说成 guideline 口径**（= 把项目的自定口径绑在别人名下，日后对不上要背锅——与 ADR-068 的「不冒充 SRS 正统」同一把尺子）· ② **只改代码注释、不改规格里的同一句**（`tables.py` 与 `spec §7.4` 两处都写着「guideline 口径」，只改一处 = 换个地方继续骗人）· ③ **把偏离悄悄抹平**（偏离要么改值、要么改标注，**不能两头不落**：把值改成 guideline 原值却不改 spec，就是另一条 major 变更，不在本轮）。
- **理由**：**口径标注错 = 读表的人按错的前提做判断**。`SCORE_TABLE` 上原来那句「guideline 口径」会让人以为 Mini 消行只值 200（实际 800）、T-Spin 消 0 行值 400（实际 0）——**表上写着的那个前提是错的，比表里的数错更隐蔽**（数错会被手算抓到，标签错不会）。**偏离本身不是 bug**（spec §7.4 的分值与 PROGRESS 的 M1 拍板都写死了「Mini 消行按完整 T-Spin 计分」），**要修的是标签与留痕，不是分值**。**三处偏离逐条点名**，下一个看表的人一眼能知道哪儿不一样、为什么不一样。
- **连带**：
  - `rules/tables.py` 的 `SCORE_TABLE` docstring 改成「项目口径 · ADR-069」，并列出三处偏离。
  - `docs/spec-M1.md` §7.4 的「基础分（guideline 口径）」同步改成「项目口径 · 与 guideline 有三处偏离（ADR-069）」——**规格与代码说的是同一件事**。
  - **偏离的两档今天送不到计分**：`tspin-none` 与 `tspin-mini` 挂在**消行组**上，而消 0 行的放置**没有组**（内核调 `score_clear((), …)` 落空）——**这两档的分值目前不影响任何一局游戏**，投递路径要改冻结签名（留到后续里程碑）。

### ADR-070　T-Spin 不消行的两档分值摆正到 guideline 原值，并补记「0 行 T-Spin 断 B2B 链」这条偏离　`已定`

- **决策**：**把 `tspin-none` 与 `tspin-mini` 的基础分摆正成 guideline 原值**（`tspin-none` = **400** / `tspin-mini` = **100**，Tetris Wiki `T-Spin` 条目 §Scoring 的表：`0 || 100 || 400`），并**把「0 行的 T-Spin 会断 B2B 链」逐条记成偏离**。摆正后本项目与 guideline 的偏离**由三处减为两处**：① **Mini 消行按完整 T-Spin 计**（分值）② **0 行 T-Spin 断 B2B 链**（语义）。**同时把计分表转录的「转录源」从 spec 改成权威源**——测试里的独立转录表必须照 guideline 的表抄，**不能照 spec §7.4 抄**。

- **否决**：① **保持现值**（Mini 400 / T-Spin 0）——**把一个没有出处、且与自称口径矛盾的数永久写进计分表**，而它迟早要真发出去（投递路径修好就进账）· ② **全盘对齐 guideline**（Mini 消行也改 200 / 400 / Impossible）——**要新增 classKey 并改判定**，超出本轮范围，且推翻 M1 拍板的一条 · ③ **连 B2B 断链的实现一起改**——**要改冻结签名 = 第四次 major 变更**，不开（缺口记进 `PROGRESS.md` 的待办）· ④ **只改 ADR 的措辞、不动表值**——**那等于把一个错数写死在表里**，「标签对了、数还错着」比两头都错更坏。

- **理由**：
  - **源头查实了**：落地那笔 `2232b28` 的正文自己写着「`tspin-mini`（**guideline 口径 400 分**）」——**当初是照 guideline 抄的，抄错了**：400 是 guideline 表里 **T-Spin 那一列**的 0 行值，Mini 自己那格是 **100**。**仓里找不到任何一条支持现值的理由**（spec §7.4 只给了结果，PROGRESS 只写了「Mini 消行按完整 T-Spin 计分」那一条）。
  - **同一个错抄了三遍**（spec §7.4 → `rules/tables.py` → 测试转录表），所以**「独立转录表比对」抓不住它**——那张表的**转录源是 spec**，不是权威源，**两边一起错 = 比对变同义反复**。**实测过**：两边同时改成一个错值，全套仍然绿。**修法必须落在「转录源」上，不是加更多比对**。
  - **改值不开第四次 major 变更**：`tools/contract_baseline.py` 只扫 `contracts/`（计分值不在声明面）→ **契约基线不碰**；`rules/` 在冻结区，但**冻结区基线本来就是红的**，S14 随 M1-C3 一起刷；事件数基线不碰。
  - **运行时影响为零**：这两档**今天送不到计分**（消 0 行的放置没有消行组可挂分类）——**改的是一张迟早要发出去的表的正确性，不是任何一局游戏的观感**。
  - **摆正后口径能一句话讲清**：「**Mini 只在不消行时打 1/4 折（100 = 400 的一折），一旦消行就跟完整 T-Spin 同分**」——现值（Mini 400 > T-Spin 0）讲不出任何一句话。

- **连带**：
  - `rules/tables.py` 的 `SCORE_TABLE` 两值摆正 + docstring 改成「两处偏离（ADR-069 · ADR-070）」并**逐条点名**（含 B2B 那条）。
  - `tests/test_rules_m1.py` 的独立转录表两值摆正，**转录源改写为 guideline 的表并把表内容抄进注释**（含表头）——**注释就是这次事故留下的那道防线**。
  - `docs/spec-M1.md` §7.4 的表摆正 + 加「**数值的第二份来源**」与「**两处偏离逐条点名**」两张表 + B2B 那条补偏离标注。
  - `docs/plan-M1.md` §1.4 的先验定表与 S7 任务清单里的数同步（M1 未收官 → 仍是活文档）。
  - **ADR-069 加更正标注**（**原文不改**）——决策记录是历史，但**假话不能只留着**：那句「也不断 B2B 链」与实现不符。
  - **实现的缺口仍在**：0 行的 T-Spin 断链（要改冻结签名）+ 0 行两档送不到计分，**同一根因**（分类挂在消行组上，0 行没有组可挂）——记进 `PROGRESS.md` 的待办，留到后续里程碑。

### ADR-071　软降计分归规则集：规则接口新增第 9 条签名　`已定`

### ADR-072　类型文法的字面量枚举形态（形态 11）：取值域写进类型串　`已定`

- **决策**：封闭的类型文法**扩一个形态 11**——**字面量枚举**（`Literal[...]`），并**只扩这一次**。四条内核要解读取值域的字段（快照 `phase` · `RuleContext.axis` · `ClearGroup.axis` · 事件 `commandType`）的**类型串里带上取值域**。类型串**由取值域派生**（`types.literal_enum()` 从取值域元组生成），**不手写**。
- **否决**：① **不扩文法**，取值域只写在散文里（基线看不见取值域变过 → **契约基线只剩"改没改"这一个信号**）· ② **用 `str` + 运行时校验**（校验会跑，但**基线哈希的是类型串**——`str` 不变，基线显示全绿而实际取值域已经变了）· ③ **扩成通用约束类型**（`Annotated` / `NewType` 等——形态要无限多，破坏"封闭文法"这个前提）· ④ **手写类型串 + 另抄一份取值域**（两处静默分叉时基线显示全绿——**这正是派生要解决的问题**）。
- **理由**：**类型串是基线唯一看得见的东西**——契约基线哈希的是声明，不是值；取值域不写进类型串，它变没变基线不知道。**文法是封闭的**：不扩形态 11，就没有办法把取值域写进类型串，基线就永远看不见取值域。**只扩这一次**是因为每多一个形态，解析器与回验表就多一处要维护的地方——**取值域统一收口是 M1 的一次性动作**，不是常态。
- **连带**：
  - `contracts/types.py` 增 `literal_enum()` 与 `escape_literal_member()`；生命周期取值域（四个状态名）**收成单一来源**（`PHASE_*` 常量 + `PHASE_VALUES` + `Phase` 别名），`kernel/lifecycle.py` 与 `contracts/commands.py` 由它派生——**值一个没变**，只是不再各抄一份。
  - `contracts/rules.py` 的 `AXIS_LITERAL` / `CLEAR_AXIS_LITERAL`、事件侧 `commandType` 的类型串全部派生。
  - **规则集自己定义的取值域不收口**（`tSpin` / `classKey` / `hold` / `next` / `rule`）——**钉死会把变体挡在门外**（G4-1 的隐患）；这些字段登记在 `RULE_SET_DEFINED_FIELDS` 里**点名豁免**。
  - **类型串一变，已有条目的哈希跟着变** → 契约基线撞红 → 按 **M1-C1** 显式刷新，理由写明"把内核要解读的枚举取值域写进类型串"。
  - **门 `G1-7`**：类型串含取值域 · 文法解析器支持形态 11 · **域外值构造即被拒**（反向用例）。

### ADR-073　契约基线的跨文件自证：期望值移出基线文件，另立期望清单　`已定`

- **决策**：契约基线的**期望值移出基线文件**，另立 `tests/baseline/contracts_expected.json`，两份清单**逐条**相等才算过。**残余上限写实记录**：两份文件都在仓内，**同时改两份仍能骗过工具**——更硬的后续选项（git 历史 / CI 常量）推到 M2 契约再冻结时再议。
- **否决**：① **继续用基线文件里的自述块**（`meta.entryCount`）——**自述块与被它计数的条目在同一个文件里**，少一条并同步改计数，工具照样放行（被删的那条被当成"新增键"）· ② **把计数键删掉**（那更糟：连"少了一条"都看不出来）· ③ **维护两份完整清单**（M1 选的是**基线文件本身作为实现侧、期望清单作为期望侧**——不是抄两份实现）· ④ **引入 git 历史 / CI 常量做期望源**（更硬，但 M1 阶段引入外部依赖不划算）。
- **理由**：**同一个文件里的"自证"只防"有人只改了一处"**。M0 全量审查实测过：删一条契约 + 同步改 `meta.entryCount` → **643 条测试全绿**。这是 M0 审查挂到 M1 的账（M0-1）——M0 不修是因为契约 v1 已冻结、三种修法都要动架构级口径。**M1 第一次新增事件 / 命令时正好拍板**：把期望值放到**基线文件之外**，两份**逐条**相等——"少一条并同步改计数"骗不过它了。
- **连带**：
  - `tests/baseline/contracts_expected.json` 新增（**脚本生成**，不手写）；`tools/contract_baseline.py` 增跨文件比对这一层。
  - **两份清单逐条相等**才算过 → **门 `G1-6`**（**删一条契约并同步改计数必须被拒绝**，有反向用例）。
  - **残余上限写进规格与决策记录**——不假装防住了。**下一次契约再冻结时（M2）要重新评估**（更硬的期望源：git 历史 / CI 常量）。
  - **两份期望清单同时被改仍能骗过工具**——这条上限留在 `PROGRESS.md` 的卡点里，不藏。


### ADR-074　录像与存档的默认落盘路径：项目优先，回落 home　`已定`

- **决策**：宿主装配 sink 时采用的**默认落盘路径策略**是——**项目目录优先，项目目录不可写时回落用户主目录**：
  - 项目下建 `<项目根>/.tetris-data/`；
  - 不可写（只读介质 · Program Files 之类）时回落 `~/.tetris/`；
  - **写入只有一处**（要么项目、要么 home，**不在两处各写一份**），读也读同一处；
  - **不设环境变量**：不读 `TETRIS_DATA_DIR` 之类，也不要求用户预先配置任何东西。
- **否决**：① **只用 `Path.home()`**（项目外的工具与 CI 跑不出一份可随项目搬运的录像；"项目下"是就近可取的那份）· ② **三平台各配一套规范目录**（`%LOCALAPPDATA%` / `~/Library/Application Support` / `~/.local/share`——语义最"正确"，但要维护三套分支，且**与 ADR-064 否决 platformdirs 的理由同源**：为一个目录引入跨平台分支不划算）· ③ **两处都写**（冗余一份便于携带，但**"读哪一份"立刻成了问题**——同一局录像在两处分叉，回放比对会假红）· ④ **只认环境变量、不给兜底**（"开箱即用"直接炸：装完第一次跑就报错）。
- **理由**：ADR-064 把边界钉死了（**路径必须可注入** · **文件名不带墙钟** · **部件不自己开文件**），但把"**默认路径**"明确留到 M2 定。默认路径要同时满足三件事：① **能跑**（不配置也能用）② **能搬**（项目里带着录像一起走）③ **不会在只读安装目录上炸**。项目优先 + 回落 home 恰好三条都满足。而**"写入唯一"是硬要求**——两处都写会让"同一局录两次"产生两份来源不同的文件，AC-1 的 200 局比对分不清哪份是哪份（ADR-064 否决"文件名带时间戳"时用的正是这个理由）。
- **连带**：
  - 路径策略属于**宿主装配层**（`host/`），**不是** `systems/replay/` 的一部分——`systems/` 连 import `adapters/` 都不行（依赖方向），更不该决定路径。
  - 目录**由程序自己创建**（含父目录），已存在则复用；**不可写时**按同一策略回落，**不静默失败**（回落这件事要能被用户看见）。
  - 落盘目录 `.tetris-data/` **必须进 `.gitignore`**——录像与存档是运行产物，不该入库。
  - 测试**一律注入 `tmp_path`**（ADR-064 的硬要求）；默认路径策略**由一条独立用例覆盖**，不参与批量测试。

### ADR-075　回放系统发事件，并新开 `replay:` 命名空间　`已定`

- **决策**：回放系统（`systems/replay/`）**发出事件**，并**新开一个 `replay:` 命名空间**（M2 新增 5 条）：`replay:recording-started`（种子 · 规则集标识）· `replay:recording-stopped`（命令数 · 帧数）· `replay:playback-started`（种子 · 规则集标识 · 命令数）· `replay:playback-stopped`（四项比对结果）· `replay:frame-stepped`（帧号 · 该帧命令数）。需求 §8.1 的「新增事件必须归入既有命名空间」**保留，但加一条写明的例外**指向本 ADR。
- **否决**：① **不发事件**（回放系统完全静默）——那它就**没法被观测**：FR-7.3 的事件流面板看不到录制与回放的过程，"这一局录到哪了"没有任何信号源，日志与指标也订阅不到· ② **塞进 `game:` / `kernel:` 既有命名空间**（`game:` 讲的是"这一局发生了什么"，`replay:` 讲的是"这条录像处于什么状态"——**两种时间轴混在一个命名空间里，按命名空间过滤时会把两者搅在一起**，而 FR-7.3 的过滤能力正是按命名空间做的）· ③ **塞进 `command:`**（`command:` 的语义是"内核收到了一条命令"，回放是宿主侧行为，产出者对不上）· ④ **新开命名空间但不改 §8.1 的约定**（那会让约定与实现分家——**约定说"归入既有命名空间"，实现却新开了一个**，下一个批次读约定时会以为新开命名空间是违规的）。
- **理由**：**每个事件类型都是一条永久承诺**（契约 v1 冻结，§8.1 的约定就是为此），所以新开命名空间必须**写明理由并改约定**，不能默默做。而"录制 / 回放"确实是一个**独立的能力域**：独立的生命周期（开始录制 → 停止录制 → 开始回放 → 停止回放）、独立的产出者（`systems/replay/`）、独立的订阅者（事件流面板 · 日志 · 指标）。**命名空间是"按关注点分组"的，不是"按数量省着用"的**——17 个命名空间不是问题，把两种时间轴搅在一起才是问题。
- **连带**：
  - `contracts/events.py` 增 `replay:` 命名空间的 5 条声明，**产出者**填 `systems/replay/`。
  - **契约基线新增键**（事件与命令**不加计数键**——架构 §4.4 明确"允许新增事件与命令"）→ 基线与期望清单**同笔显式刷新**（带 `--reason`），**不是 major 变更**（没有既有键的哈希变化）。
  - 需求 §8.1 的事件目录表增 5 行；**那句约定加一条写明的例外**（本 ADR 是那条例外的依据，不是"实现顺手做的"）。
  - 事件数基线（`frame_events.json`）**可能随 M2 的订阅与录制而变**——若变，**显式刷新 + 写理由**，不得顺手刷。

### ADR-076　NFR-1 的回放一致性单独立门 `G2-5`（1000 局）　`已定`

- **决策**：NFR-1 的「连续 **1000 局**回放指纹零差异」**单独立一道门 `G2-5`**，与 `G2-1`（200 局 · 四项全等）**并列**；`G2-1` 的 200 局**不加严**。
- **否决**：① **并进 `G2-1`**，把 200 局改成 1000 局（门数不变，但**一道门扛两件事**——失败时说不清是"四项比对不过"还是"零差异不过"，而门本来就是逐条定位用的）· ② **只把 `G2-1` 改成 1000 局**、不新增门（同上，且**顺手改判据比不改更糟**——改过的门会让历史执行记录对不上）· ③ **明确不设门**，只在 spec 里记为期望（NFR-1 就没有硬门兜着了；**"需求里写着"不等于"有人验"**）。
- **理由**：NFR-1 早就写着「连续 1000 局回放指纹零差异」，但门判据表里只有 `G2-1`（200 局 · 四项全等）与 `G2-4`（千局**模拟**总时长 ≤30 分钟）——**"1000 局回放零差异"这条既不属于前者也不属于后者，一直没有门兜着**（`G2-4` 管的是时长，回放一致性不在它里面）。**一条 NFR 没有门 = 没人验**，M2 正好是兑现它的时候。分成两道门而不是一道：**门是定位工具**——`G2-1` 验"结果对不对"（四项逐条相等），`G2-5` 验"多局之下还稳不稳"（1000 局零差异），两者失败含义不同，**混在一起就定位不了**。
- **连带**：
  - 需求 §12 的门判据表增 `G2-5`；M2 的批次行「开门判据」补"1000 局回放零差异"。
  - `G2-5` 的复跑入口与 `G2-1` **不共用命中名**（`pytest -k` 的命中名是"门还在不在"的唯一入口，共用会让这道门的生死无从分辨）。
  - `G2-5` 的成本要写进性能预算（1000 局回放比 200 局重 5 倍）——它与 `G2-4`（千局 ≤30 分钟）**跑的是同一批局**，**同机同时段一起跑**，**不许互相引用对方的数字当结论**（跨时段的绝对值不可引用，见 plan-M1 §7 R10）。

### ADR-077　契约期望源搬到 git 历史背书：基线与期望清单必须与 `HEAD` 逐字节一致　`已定`

- **决策**：契约基线与期望清单的**权威性由 git 历史背书**——新增两条元守卫用例，断言两份文件与 `git show HEAD:<路径>` 的内容**逐字节相同**。**期望值的权威源仍是活契约**；变的是"**谁动了这两份文件**"由 git 回答，**不再由文件自己的 `meta` 回答**。
- **否决**：① **把期望清单从 git 历史派生**（基线文件里记一个基准 commit，工具检出那个 commit 重新导入契约模块、算出期望条目集）——**更硬，但代价大**：派生要在历史提交上执行仓库自己的 Python（worktree + 子进程导入），多一套隔离机制、多一类失败模式，而且**它把期望清单变成机器产物：人看不了、改不了、审不了**· ② **搬进 CI 常量 / 发布产物**（最硬，但本项目**还没有 CI**，为一个基线先搭一套 CI 是本末倒置）· ③ **只加一条"期望清单 == 活契约"的守卫**（已有，挡不住"同时改两份"）· ④ **什么都不做**（ADR-073 写明"更硬的后续选项推到 M2 再议"——**M2 就是那个时机**）。
- **理由**：ADR-073 写死的残余上限是「两份文件都在仓内 → **同时改两份仍能骗过工具**」。这个洞的根子不是"多了一份文件"，而是：**工具拿基线文件的内容当权威**——**直接编辑基线文件就能让工具变绿**，而没人检查这份编辑是不是走了显式刷新流程。所以要堵的不是"文件数量"，而是**"文件可以被悄悄改"**。git 是这个仓库里唯一**改了就一定留痕**的东西：**改动进了提交就有人看得见；没进提交，守卫当场报红**。于是骗过工具的门槛从「改两个文件」提到「改两个文件 + 提交 + 让这次提交被人看见」——**不是防住了蓄意绕过，是把静默绕过变成了留痕绕过**。
- **连带**：
  - 两条守卫接进 pytest（与既有三份基线的用例同处）：基线文件 == `HEAD` 版本 · 期望清单文件 == `HEAD` 版本。**工作区改了但没提交 → 红**——这**正是"显式刷新 + 同笔提交"流程的强制执行**，与既有流程**不冲突**（M1 的 S6 就是"改声明 + 刷基线 + 同笔提交"，提交后守卫自然绿）。
  - 守卫**不区分"谁写的"，只区分"改了但没提交"与"改了且已提交"**；失败信息要**明确指出该怎么走**（`--update-baseline --reason` / `--update-expected --reason`），**不许静默跳过**；在**非 git 工作区**里也要报红并说清原因，不许假装通过。
  - **残余上限照旧写实**：这条守卫**仍然挡不住蓄意绕过**——能把两个文件改好再提交的人，也能改好 git 历史。**ADR-073 那句"同时改两份仍能骗过工具"要改写成"能骗过，但一定留痕"**，不美化。
  - **不新增独立门**：这两条守卫是**质量门的一部分**（spec §9.2），不是独立判据。

### ADR-078　录像头追加「局末四项」：让四项比对自足　`已定`

- **决策**：录像头在**版本 · 种子 · 规则集标识**之外**追加「局末四项」**（棋盘指纹 · 分数 · 行数 · 方块数）。**四项由宿主在局末注入**（`outcome_provider`），**系统层不碰内核状态**（M2-D1）——四项里的**棋盘指纹只能从内核快照拿**，指纹的算法也只有内核那一份（抄第二份就是第二个真相）。
- **否决**：① **基准存在录像之外**（比对时另取一份"原局"）——那要**同时持有原局与录像**，而 `G2-1` 的 200 局比对与 CLI 的单文件重放都只有录像，**基准必须自足** · ② **只比分数与行数**（不带棋盘指纹）——四项里少一项就少一维，棋盘内容变了分数没变的情况就分不出来（批次 D 审查 D5 同一类洞）· ③ **把四项塞进录像体的每一行**——那不是"头"，而是把基准重复了 N 份 · ④ **由系统层自己去问内核要四项**——破 M2-D1（可观测系统只订阅事件、不写状态）；且指纹算法会多出第二份实现。
- **理由**：**比对要能自足地做**。录像不带基准时，四项比对只能"打印不能比"——`replay` 子命令拿到的只是回放结果，拿不到"对不对"的判据。**基准写进头里，四项比对就变成一个自包含的判定**：读录像 → 重放 → 取四项 → 与头里的四项逐条比。**格式仍是 JSON Lines 的第一行**，不引入第二份文件、不引入配对的约定。
- **连带**：
  - **spec §6.4 的格式表仍写三项**——spec 自 M2 入档后未再改（它是 M2 的**参照**，改它等于改需求），**差异记在 `docs/plan-M2.md` §S8 的订正说明与本条**。
  - 录像格式的**版本号不变**（`v1`）：本条是**头里多一个字段**，不是字段含义变更，老录像**读得动**（缺字段按缺省处理）——**不构成破坏性变更**。
  - `replay:recording-stopped` 与 `replay:playback-stopped` 的负载**不动**（契约面只增不改，M2-D4）。

### ADR-079　装配层一个事件都不发；种子与规则集标识从 `kernel:ready` 取　`已定`

- **决策**：**宿主装配层只造零件，不造事件**——装配过程**一个事件都不发**。因此种子与规则集标识**不进工厂签名**（工厂保持 `(bus, sink)` 两参），录制系统**订阅 `kernel:ready` 事件**自己取那两项，`replay:recording-started` 在**内核就绪**时才发。
- **否决**：① **工厂签名收四个参数**（`bus · sink · seed · rule`）——装配层转发一份拷贝就有**两份真相**：内核那份与装配层那份迟早分叉，而**录像头里的种子错了，回放起的就是另一个局**（四项比对会红，但原因难查）· ② **录制器构造时发 `replay:recording-started`（S8 的原做法）**——那等于让**装配层自己造事件**，宿主的这条不变量被零件破坏；而且订阅者在构造**之前**挂上就收不到、在之后挂上就收得到，**订阅时序成了隐含契约** · ③ **由装配层在造完零件后统一发一条"系统已装配"事件**——多一条事件类型 = 多一条永久承诺（契约面只增不改），而且**装配层造事件这个动作本身就是问题** · ④ **录制系统自己去查内核要种子**——破 M2-D1（系统层不碰内核状态）。
- **理由**：**内核是种子与规则集标识的权威**——它发 `kernel:ready` 时带着那两项，订阅那条事件是**唯一一份真相**的读法。而"装配层一个事件都不发"这条不变量本来就存在（`tests/test_host_loop.py` 里那句"装配层不该自己发事件"守的就是它），**它不能由零件自己破坏**——零件在构造时发事件，等于让装配层承担了"造事件"的职责。两条叠起来，**工厂签名自然退回两参**，`tests/test_storage_adapter.py` 里 S4 留下的两条既有用例**一个字都不用改**。
- **连带**：
  - **录制器的种子与规则集标识改从 `kernel:ready` 取**——`RecordingSystem.__init__` **不再收 `seed` / `rule`**（S8 引入的这两个构造参数在本条下撤掉；该系统**尚未合进 `master`**，不构成破坏性变更）。
  - **三条宿主不变量用例显式关掉可观测系统**（`observability_enabled=False`）：它们验的是"宿主 ↔ 内核"这条路径，而可观测系统自己也会往总线上发事件（`log:entry` · `metric:sampled`），混进来就不是对拍了；**断言一字未改**，另补一条专测"装配层一个事件都不发"的用例。
  - **事件数基线按 spec §6.5 显式刷新**（理由"M2 引入可观测系统"）：固定场景的事件构成变了（常态帧 P50 5 → 12 · P99 5 → 12 · max 15 → 32），**常态帧数 7381 逐字未变**。**不是 major 变更**（契约面一个字节没动，冻结区与 `bus/` 独立基线也都没动）。
  - **基线场景刻意开着可观测系统**：`systems/` 与 `host/` 都不在冻结区，可观测系统多发一条事件，声明面与文件哈希面都看不出来——**这第三份基线正是为堵这个洞而存在的**。

### ADR-080　存档恢复需要内核恢复入口：只解冻 `kernel/core.py` 一个文件　`已定`

- **决策**：给内核加**恢复入口**——`Kernel.export_state()`（导出存档点）与 `Kernel.restore_state()`（从存档点恢复），外加一个 `KernelArchive` 冻结 dataclass。**只解冻 `kernel/core.py` 一个文件**。存档格式（`systems/replay/archive.py` · 纯数据）与内核结构之间的**映射放在宿主层**（`host/archive.py`）。**M2-D5（冻结区一个字节都不动）就此破例一次**，冻结区内容哈希基线**显式刷新**（带 `--reason`），理由写进提交正文。
- **否决**：① **宿主直接写内核的私有状态**（宿主拿存档去改 `kernel._state` 等字段）——破「**只有内核能写状态**」（架构 §7.1 · 需求 N1），而且宿主从此认识内核的内部结构（内核改一次结构就要改宿主）· ② **S10 只做序列化、恢复推到 M3**——丢 S 级需求 FR-10.2（「可从序列化数据恢复」），spec §7.5 明写它是 M2 的交付物，spec §9.3 的兑现表也指着它 · ③ **恢复 = 重放录下来的命令序列**——与「**存档 ≠ 录像**」矛盾（ADR-045：录像记命令 · 存档记状态），而且**存档必须能独立恢复**，重放依赖命令序列 · ④ **改 `kernel/lifecycle.py` 加一个"置相"入口**——为了恢复多解冻一个文件（本来只需要一个），而且状态机存在的意义就是裁决迁移合法性，**直接置相等于绕过它** · ⑤ **改 `kernel/rng.py` 把取值计数也塞进 `rngState`**——`rngState` 的契约类型是 `tuple[int, ...]`（ADR-011 的扁平化状态，626 个 int），加计数会**改既有键的含义**（契约面变更 = major 变更预算）；而且取值计数是**实例内记账**，不是局面状态。
- **理由**：
  - **FR-10.2 是硬判据**：「恢复后继续推进的结果与未中断时一致」——恢复后跑 N 帧，与"不中断直接跑 N 帧"**逐帧指纹全等**。不兑现它，M2 的 `G2-2` 与 spec §9.3 的兑现表都落空，**S 级需求就只是需求文档里的一行字**。
  - **恢复要写内核的私有状态，而只有内核能写状态**。所以恢复入口**只能在内核里**——宿主绕过去写字段就是破 N1，这条没有折中。
  - **只解冻一个文件是能少解冻就少解冻**：`kernel/lifecycle.py` **不用改**——相位恢复**走合法迁移**重建（`not_started` → `start` → `pause` / `end`；回到 `not_started` 用 `reset`），**状态机自己裁决，不绕过它**；`kernel/rng.py` **不用改**——随机源状态用既有的 `export()` / `import_state()` 往返（ADR-011 的口径 1）。
  - **B-2 的字面没破**：`kernel/` + `rules/` **不得为玩法需求改动**——存档恢复**不是玩法需求**（它是持久化 / 可观测能力）。但 M2-D5 的「冻结区 M2 全程只读」**确实破了**，所以**写实记在 `docs/plan-M2.md` §S10 与 `docs/spec-M2.md` §4.3 的订正说明里**——**红线被破必须写在红线的旁边，不能只写在别处**。
  - **冻结区基线的刷新是显式的、带理由的**：理由写进提交正文（"M2 兑现 FR-10.2 存档恢复需要内核的恢复入口"），与 M1「标准玩法补齐」的先例同一条路径。**刷新这份基线不是"换了比对基准"**——它报的就是"冻结区动了"，这次它**应该**报红。
- **连带**：
  - `tests/baseline/kernel_hashes.json` **显式刷新**：14 个文件里**只有 `kernel/core.py` 变化**，**无新增、无消失**。**契约面一个字节没动**（M2-D4 兑现）：383 条契约基线与期望清单零变化 · 事件注册表仍是 49 条 · 命令目录仍是 16 条 · 快照仍是 22 个顶层字段。**M2-C1 的 major 变更预算仍未动用**（冻结区破例**不是**契约变更，不消耗它）。
  - **恢复路径不发新事件类型**：契约面只增不改，M2 只新增 `replay:` 那 5 条（M2-D4 的字面）。"恢复路径逐条有事件"由**恢复之后的帧**兑现——判据是**恢复之后的事件流与未中断的那一段逐条相等**（类型 · 帧号 · 负载 · 元数据）。
  - **存档 ≠ 录像**：两种格式**不共用一套**。存档是**单个 JSON 文档**（头四件套：格式版本 · 种子 · 规则集标识 · 随机源状态；体：局面），录像是 **JSON Lines**（头三件套 + 命令序列 + 局末四项）。
  - **规则集与种子必须对得上**：恢复时内核核对存档头里的 `rule` 与 `seed`，**对不上当场报错**（NFR-9：不猜、不静默降级）；**棋盘尺寸与内容对不上**同样报错（尺寸不符的棋盘碰撞判定全错，而指纹照样算得出来）。
  - **判据必须跨过一次取片袋补货**：随机源**只在补袋时**才被取用（标准玩法第 237 帧补第二袋）。**窗口不够长，"存档里带没带 `rngState`"这条判据就测不出来**——S10 实做时踩到过：短窗口下把 `rngState` 从恢复路径里去掉，用例**照样全绿**。所以那条用例要跑 320 帧。
  - **`rng:next` 的取值序号是实例内记账**：恢复到**同一个内核**时它接着往上走（`KernelRng` 的 docstring 本来就这么写）；恢复到**新内核**时从 0 起——那是新实例自己的账，**与局面无关**，FR-10.2 的判据（逐帧指纹全等）不受影响。

### ADR-081　事件轨迹落成「有序字段对」；面板与导出器是同一个对象　`已定`

- **决策**：事件轨迹（FR-7.4 的离线导出）落成 **JSON Lines**，每行一条事件，**负载与元数据用「有序的字段对」**（`[["字段名", 值], ...]`）而不是字典；**只读事件流面板**（FR-7.3）与**导出器是同一个对象**（`systems/metrics/trace.py` 的 `EventPanel`）——视图里有的就是能导出的。
- **否决**：① **负载落成字典**（`{"seed": 0}`）——JSON 字典**静默吞掉重复键**，而字段对不会；而且内存里负载本来就是 `tuple[tuple[str, 值], ...]`，**用同样的形状落盘，读回来逐字段相等是构造出来的，不是比出来的** · ② **导出器与面板分成两个对象**——两个订阅者意味着**每条事件被投递两次**（两份内存），而且"面板暂停了"与"导出不完整"这两件事会**各说各话** · ③ **导出成一个大 JSON 文档**（整个轨迹一个数组）——一行一条才能逐行 diff（与录像同一条理由 · ADR-045），而且文件一大就没法用文本工具看 · ④ **给轨迹另立一个系统包**（`systems/trace/`）——系统之间互不直调（import-linter 的独立性契约），新开一个包要多一条契约与一份导出清单，**收益不抵成本**（plan-M2 §S11 的任务项写的就是"`systems/metrics/`（或独立模块，按职责归位）"）。
- **理由**：
  - **"逐条相等"这条判据要求无损**：契约的取值域（`int | str | bool | float | None | tuple[...]`）里**容器只可能是元组**——所以"每个 JSON 数组还原成元组"就是**无损**的还原，导出的轨迹能**逐条与源事件流相等**（类型 + 负载 + 序号）。**"顺手规范化一下负载"就毁掉这条判据**——规范化过的东西不是原轨迹。
  - **面板与导出器同体，是因为它们本来就是同一件事**：都是"把事件流**原样**留下来"。**暂停的是视图，不是内核**（订阅者拦不住总线，也拦不住内核）——"完整轨迹" = 不暂停 + 不过滤的那一份。
  - **住在 `systems/metrics/` 里**：与指标系统同族（**只订阅事件流、只产出派生文件**）；指标系统产**采样**，轨迹产**离线文件**——都不是事件，所以**不需要新增事件类型**。
- **连带**：
  - **落盘只走 sink**（M2-D2 · ADR-064）：轨迹模块**不 `open()`、不知道路径**（有一条用 AST 查代码的用例守着）；`tetris inspect --export <文件>` 的路径由**宿主**给（`FileSink`）。
  - **`inspect` 子命令从占位变真跑** → **破坏性**（既有调用方若依赖"占位即报错"的行为，会失效）→ 提交标题带 `!`。
  - **可观测系统在 `inspect` 里一律不装配**（`observability_enabled=False`）：面板要看的是**内核的事件流**——多几个订阅者只会多几条 `log:entry` / `metric:sampled` 混在里面，看的人分不清哪条是内核发的。
  - **CLI 的 `--json` 视图用对象、轨迹文件用字段对**：前者是**视图**（`jq` 好取），后者是**格式**（读回来要逐条还原）。两者是不同消费者，**形状不同是有意的**。
  - **过滤按命名空间**（`contracts.events.namespace_of` 是**单一权威** · 架构 §4.4），**不是按事件名**——需求 §8.1 明写"事件按命名空间划分"，ADR-075 正是为了让 `replay:` 与 `game:` **在过滤时分开**。
  - **契约面一个字节没动**：FR-7.3 / FR-7.4 都不需要新事件——面板与导出器都是**普通订阅者**，它们的产出是**文件**。

### ADR-082　降级控制器住在宿主层；第 ③ 档由总线提供「关历史缓冲」的开关　`已定`

- **决策**：降级控制器落**宿主层** `host/performance.py`（`DegradationController`）——它是**宿主对"这个整机还扛不扛得住"的判断**，内核既不知道日志系统也不知道总线。**第 ③ 档「关闭事件历史缓冲」由总线提供公开开关** `EventBus.set_history_enabled(enabled)`：**关的是环形历史缓冲，不是事件分发**（ADR-031 明写否决"关闭事件分发"）。为此**改 `bus/bus.py` 一个文件**（超出 plan-M2 §S12 的文件清单），**`tests/baseline/bus_hashes.json` 显式刷新**（带 `--reason`，理由写进提交正文）。**手动档位只接受 0 与 1，且是「下限」**。**装配层默认不装降级控制器**（`assemble(degradation_enabled=False)` 是默认值）。
- **否决**：① **宿主私取 `bus._history` 直接清空**——破封装（宿主从此认识总线的私有结构），而且 `bus/` 走 pyright strict，**私有属性在类型上就说不通** · ② **把降级控制器放进 `systems/`**——它要同时指挥**总线**与**日志系统**：系统之间互不直调（import-linter 的独立性契约），降级控制器也**不是普通订阅者**（它改别人的配置，不消费事件）· ③ **给总线加一个「关闭分发」的开关**——ADR-031 明写否决：那会破坏**事件完备性**（状态变更不再伴随事件），也撞 B-1 / B-10 两条红线 · ④ **三档做成三个独立开关让用户自己挑**——ADR-031 定的是**逐级降**（超预算了先退一档，还超再退一档），让用户手挑三档等于把策略交给用户 · ⑤ **手动档位开放到第 ③ 档**——ADR-031 明写"第 ③ 档不暴露给用户手关"（用户手关会让时间旅行调试"看起来坏了"）· ⑥ **把降级接进 `host/cli.py`**——M2 是**无头批次**，没有实时宿主去测每帧耗时，**喂帧开销的接线留给 M3**；plan-M2 §S12 的文件清单里也没有 CLI · ⑦ **关掉缓冲时不清空旧条目**——那一档的收益是省下每条事件的追加开销**与内存占用**，留着旧条目既占内存又不给新证据。
- **理由**：
  - **降级是"整机"的决定，不是某一个系统的决定**：① 动日志系统、② 动日志系统、③ 动总线——三个部件分属两层（`systems/log/` 与 `bus/`），**只有宿主层同时看得见它们**（架构 §4.1：宿主是唯一知道"怎么把部件拼起来"的地方）。
  - **第 ③ 档必须真的关缓冲**：只是"不再往缓冲里塞"的话，缓冲还占着内存——这一档的收益（降帧开销、降内存）就没有了。
  - **关缓冲不等于关分发**：订阅者照常收到每一条事件，**状态变更仍伴随事件**——**事件完备性不受损**（ADR-031 三档的共同底线）。
  - **手动档位是「下限」不是「上限」**：用户说"至少关掉调试事件"，没说"别再降了"——自动降级照样能在它之上继续降。**反过来不成立**：手动**不能**把自动降下来的第 ③ 档按回去（那正是"第 ③ 档不手关"）。
  - **改 `bus/` 要显式刷新基线**：ADR-019 说 `bus/` 另列独立基线，"批批刷新会变橡皮图章"——**这次是一次性的真实功能变更**（不是反复刷新），理由写进提交正文。**冻结区 `kernel/` + `rules/` 一个字节没动**。
- **连带**：
  - **`bus/` 的改动只有三处**：`set_history_enabled()` + `history_enabled` 属性 + `_deliver` 里的一行条件。**分发路径一个字没动**（`publish` 与订阅者投递部分原样）。
  - **默认不装配**：`assemble(degradation_enabled=False)` 是默认值——M2 无头，**没有实时宿主去测每帧耗时**，`observe_frame(cost_ms)` 由调用方喂。
  - **判据用 P99 不用均值，实测发现 P99 也会漏掉单个尖峰**：600 个样本的 P99 取第 **594** 个（最慢的 6 个不算），所以**单个尖峰看不见**——判据的口径是"**窗口里最慢的那 1%**"，不是"任何一个尖峰"。用例里刻意造了 **7 个尖峰**（占窗口 1.17%）才让 P99 看见它，而**均值 0.59ms 在预算内**——**换成均值这条判据就瞎了**。
  - **滞回带的实现细节**：P99 落在 [1.0, 1.6] 之间 → **不升不降**，且**升档计数清零**（"回落就不升"）。
  - **第 ① 档是类型级精确黑名单，不是抬阈值**：默认映射下 debug 级 = `board:changed` / `board:collapsed` / `piece:moved` / `piece:spawned`；**trace 级的 `rng:next` 不跟着关**（ADR-060 明写它不随调试事件一起关）。第 ② 档抬到 `info` 才会把 trace 级一起关掉——**这正是两档的实质差别**。
  - **契约面一个字节没动**：降级控制器**不发事件**，三档都不新增事件类型（M2-D4）。

### ADR-083　错误级联：同一个订阅者在一轮排空里只报一次错　`已定`

- **决策**：总线在**一轮排空**（`_drain_pending`）里，对**同一个订阅者**只产生**一条** `kernel:error`；它再抛错只记 **trace**（不进错误事件）。"已经报过错事件的订阅者"这张表**在一轮排空结束时清零**。
- **否决**：① **只防"错误事件自身"**（原样）——挡不住**间接级联**（见下面的路径）· ② **给事件打"因果标记"，只压制被污染的那几条**——精确，但要多维护一套"哪些待发事件是错误引发的"的账（总线要记住每个待发信封的来源），而**级联的边界本来就模糊**：`log:entry` 的 `cause` 是 `None`（它确实是"某个错误的后果"，却查不出来源）· ③ **让日志系统不产 `log:entry` 事件**——面板就看不见错误条目，**可观测性打折**；而且下一个"会产事件的订阅者"照样触发同样的级联（**修的是这一处，不是这一类**）· ④ **在宿主层限流**——级联发生在总线内部，宿主既看不见也拦不住。
- **理由**：
  - **这是 `G2-2` 门判据逼出来的**：门判据要求"注入一个必然抛错的订阅者 → 内核**继续正常运行**"。在**开着可观测系统**的真实装配下，这一条**当场挂死**——事件数无上界，宿主卡死（实测：总线序号与待发布队列无上界地涨）。
  - **级联的路径**：原事件 → 抛错订阅者 → `kernel:error` → **日志系统把错误写成 `log:entry`** → 那条新事件又落回抛错订阅者 → 又一个 `kernel:error` → ……**闭环**。原来的防线只挡"错误事件自身再产生错误事件"，**挡不住这条间接路径**。
  - **一轮排空 = 级联的边界**：宿主**逐条发布**事件（`host/loop.py` 的 `_publish_batch` 逐条转发），所以**一个原始事件引发的一切后果都落在同一轮排空里**；一轮排空结束，级联就该结束。
  - **不丢信息**：同一个订阅者在**原始事件**上抛错，那条错误事件照常发出（点名是谁炸的）；**级联里**的重复错误进 trace（`bus.traces()` 查得到）。**另一个**订阅者在同一轮里第一次炸，照样拿到自己的错误事件。
  - **边界代价（写实记录）**：同一个订阅者在一轮排空里**对两个不同原始事件**抛错，**第二条**只进 trace。实测中这不会发生——宿主逐条发布，每条各自一轮排空。
- **连带**：
  - **改 `bus/bus.py` 一个文件** → `tests/baseline/bus_hashes.json` **显式刷新**（带 `--reason`）。**这是本批次第二次刷新 bus 基线**：两次都是**真实功能变更**（第 ① 次是 S12 的"关历史缓冲"开关，第 ② 次是这条错误级联防线），**不是反复刷新换基准**（ADR-019 担心的"橡皮图章"指的是后者）。
  - **冻结区 `kernel/` + `rules/` 一个字节没动**；**契约面一个字节没动**（`kernel:error` 的负载四字段照旧）。
  - **门判据 `G2-2` 写在真实装配上**（可观测系统全开）——**不在"关掉可观测"的特殊配置上取巧**（"只会绿、不会红的检查等于没检查"）。

### ADR-084　千局基准用参考策略局；预算与种子表起点一处真相　`已定`

- **决策**：① 千局基准（`G2-4` 的探针工具与门判据）跑**参考策略局**——策略从 `tests/support/policy.py` **动态载入**（`src/` **不 shipping** 参考 AI）；② **千局基准的定义**（预算 `THOUSAND_BUDGET_SECONDS` = 1800 秒 · 种子表起点 `THOUSAND_BASE_SEED` = 20261000）**住在 `host/performance.py`**——与降级阈值 `DEGRADE_P99_MS` 同处**性能预算的唯一真相**，**测量工具与门判据用例都从这里取**；③ **配对 A/B 分三档**（M1 终局默认 · M2 `--no-observability` · M2 默认装配），**同机同时段交替采样**。
- **否决**：① **纯重力局**（宿主只派 `tick`）——每局 **7671 帧** → 1000 局并行约 **31 分钟**，**卡在 30 分钟预算线上过不了** · ② **固定帧数模拟**（每局只跑 N 帧）——量的是"跑 N 帧要多久"，不是"玩完一局要多久"，与"千局模拟"不是同一件事 · ③ **"关闭事件分发"的快速模式**——ADR-018 已明写否决（破坏事件完备性 · B-1 / B-10）· ④ **把参考策略搬进 `src/`**——库里不 shipping 一个"参考 AI"（`systems/ai` 是将来 AI 系统的位置，不是现在塞一个参考策略的地方）· ⑤ **工具与门判据各写一份种子表起点**——两个真相 → "同一批局"落空 → 两个数不可比 · ⑥ **只跑 M1 / M2 两档**——**分不清是内核变了还是可观测系统的分发成本** · ⑦ **把「每局耗时之和」当成串行实测值**——那串数**含并行争用**，是上界。
- **理由**：
  - **局的形态决定基准有没有意义**：预算判的是"1000 局模拟要多久"，**局的形态就是这件事的工作量**。纯重力局过不了预算；参考策略局每局约 2434 帧 → 1000 局 **467.6 秒**，**余量充足**。
  - **参考策略是现成的、确定性的**：`G2-1` / `G2-5` 已经在用它——**基准与门判据跑同一批局**，两个数互相印证（spec §7.3）。
  - **一处真相**：降级阈值与千局预算都是**性能预算**，同一个文件；**种子表起点跟着预算走**——"同一批局"是它俩能互相印证的前提（一局的帧数随种子在 1755–3300 之间波动，种子表不同 → 总工作量不同 → 两个数不可比）。
  - **动态载入 + 载入不到就明确报错**：**不静默退化成纯重力局**——那量的是另一件事，两个数对不上，预算就失去意义。
  - **三档 A/B 各归各的因**：**M1 终局的装配里根本没有三个可观测系统**（M1 的 `Assembly` 只有内核 / 总线 / 时钟）——所以"M1 默认"≡"M2 `--no-observability`"，两者的差值是 **M2 内核与总线自身的增量**（实测 **+10 μs / 帧**），而"M2 默认装配 − M2 裸跑"是**三个可观测系统的分发成本**（实测 **+145 μs / 帧**，对应每帧事件数 **5 → 12**）。**只跑两档就分不清这两件事**。
  - **那 +10 μs 是 M2-D1 的性能侧证据**：「可观测是订阅者、不是内核的一部分」——关掉三个系统，内核的开销几乎不变。
- **连带**：
  - **契约面一个字节没动**（新常量不产生事件）；**冻结区 `kernel/` + `rules/` 一个字节没动**（`host/performance.py` 不在冻结区）。
  - **事件数基线没变**（复检绿）→ **不刷新**。
  - **工具的数与门判据的数的关系**：工具量的是"**玩**"（标准装配 · 跑完整局），门判据量的是"**录 + 放**"（含重放）——**门判据那个数才是判据**；工具那个数是同一批局的**工作量子集**（少做重放那段），**用来探机器余量**。
  - **`G2-4` 的用例已随 `G2-5` 落在 S13**（元守卫不许留"待落地"的例外）。

### ADR-085　三个可观测产物各有各的落盘出口；追加与覆盖是两种语义　`已定`

- **决策**：① **日志 · 指标 · 录像各有各的落盘出口**——装配层用 `ObservableSinks` 把三个出口打包，`assemble(sinks=…)` 注入（**一个产物一个文件**）；② **两种写入语义是两个类，不是一个类的两种模式**：`FileSink`（**覆盖** · 整份交出 · 原子替换）给录像，`AppendSink`（**追加** · 一条一条）给日志与指标；③ **局末四项的 provider 由宿主注入**（`OutcomeProvider`），四项算法**只有 `host/replay.py` 的 `four_items_of()` 一处**——重放驱动器与装配层共用它；④ `assemble(sink=…)` → **`assemble(sinks=…)`**（**破坏性变更**）。
- **否决**：① **三个产物共用一个 sink**（修订前的实现）——**后写的覆盖先写的**：用覆盖语义写日志，文件里只剩最后一条（审查 H1 的实证：30 帧后文件里只剩 131 字节的一条日志）· ② **一个类的两种模式**（`FileSink(path, mode="append")`）——**写错了就是数据丢**，让类型把这件事说清楚比让人记参数强 · ③ **日志与指标也用覆盖语义**——它们是**一条一条往外冒**的流，覆盖后只剩最后一条 · ④ **录像也用追加语义**——文件里会攒着一份份残缺的录像；而且**追加没有原子性**（进程被强杀时文件末尾可能留半行），录像是**整份交出**的产物，不能接受 · ⑤ **让系统层自己去取内核快照**——破 M2-D1（系统层不碰内核状态），且**棋盘指纹的算法只有内核那一份**，抄第二份就是第二个真相 · ⑥ **工厂拿内核而不是拿 provider**——最窄能力原则：系统层只见到一个可调用对象 · ⑦ **在装配层另抄一份四项算法**——两处算出不同的值 → 四项比对**假红** · ⑧ **规则集标识进文件名时做 slug 替换**——文件名要能**反查回规则集**，悄悄把 `a/b` 改成 `a-b`，查录像时才知道自己拿错了：**错了就报错**。
- **理由**：
  - **"写入只有一处"说的是一条落盘路径，不是一个文件**——ADR-074 那句口径被读成了"一个文件"，审查 H1 就是这么来的。**同一局录像在两处分叉**是 ADR-074 真正防的事，而"三个产物挤一个文件"防不住它、只会制造另一种分叉。
  - **数据丢是静默的**：文件还在、录像还在，**只是内容不对**——用覆盖语义写日志，事后没人会想到"日志只剩最后一条"。
  - **两种语义各有各的保证**：覆盖 + 原子替换让录像**不留半截文件**（半截录像比没有录像更坏——它会骗过"录像齐了吗"的检查）；追加让日志**一条不少**，代价是末尾可能留半行——**日志流能接受，录像不能**。保证不同，就不该是同一个类。
  - **四项必须只有一处算法**：重放驱动器算的是"**重放出来的**四项"，装配层给的是"**录下来的**四项"，两处必须算出同一个值，否则 `G2-1` 的四项全等**永远红**。
- **连带**：
  - **`assemble(sink=…)` → `assemble(sinks=…)` 是破坏性变更**（提交标题带 `!`）；`Assembly.sink` → `Assembly.sinks`。
  - **`default_sink()` 保留**（**覆盖语义**）——适合"整份交出"的产物；日志与指标走新的 `default_sinks()`（一次解析目录、造三个出口）。
  - **录像的文件名仍由 `recording_filename()` 给**（文件名是**录像格式的一部分** · spec §7.1）——装配层不另起名字；规则集标识**当场校验**（路径安全），不悄悄改写。
  - **契约面一个字节没动**（383 条零变化）；**冻结区 `kernel/` + `rules/` 一个字节没动**（只动 `host/` 与 `adapters/`）；**事件数基线没变**（复检绿）→ **不刷新**。
  - **门禁**：H1 三条（三个出口各是各的 · 追加与覆盖各归各 · 端到端三文件且日志不止一条）+ H2 三条（内存里的录像带四项 · 落盘的录像带四项 · 不注入 provider 就没有基准）。

### ADR-086　系统自动发现取代手写名单：声明与工厂住在系统自己的包里　`已定`

- **决策**：宿主**扫描系统目录**发现可用系统，**不维护任何手写名单**——每个系统包下有一个 `manifest.py`，里面放着 `SYSTEM_MANIFEST`（声明）与 `create_system`（工厂）两个约定的名字。**新增一个系统 = 新增一个包，既有文件零改动**。声明进契约面（`contracts/systems.py`）并进契约基线；工厂住在系统自己的包里（**工厂要 import 具体实现，不能进契约面**）。
- **否决**：① **宿主维护一张系统名单**——名单一旦存在，每个新系统都要改一个既有文件 → **`G3-1`（新增能力 = 新增文件）永久失去牙齿**（plan-M3 S10 的落地提交判据直接不成立）· ② **声明集中登记在一个既有文件里**——同 ①，只是换个位置 · ③ **声明与工厂分居两处**——两处各写一份订阅集就会分叉，**而分叉了没人查得出来**；同源放最省事 · ④ **用装饰器或 entry_points 自动注册**——**导入即注册 = 导入即有副作用**，破「装上才生效」的语义（`ImportPurityGuard` 守的就是这条）· ⑤ **让宿主 import 具体的系统实现**——宿主不认识具体系统，它只认「声明 + 工厂」这个形状。
- **理由**：
  - **`G3-1` 只有在这一条成立时才可机验**——「落地提交的 `git diff --name-status` 每行都是 `A`」是**差异断言**，它要求新增能力**不改任何既有文件**。名单或集中登记表**必然**是既有文件。
  - **扫描比名单更接近真相**：系统包就在那儿，**它带自己的声明**——**事实源与实现同处一地**。名单是**第二份真相**，而第二份真相迟早与第一份分叉。
  - **发现只读，不改状态**：扫描只登记，不装系统、不订阅、不发事件——**装配是宿主的事**（`host/registry.py`）。
- **连带**：① **重名即报错**（名字是清单的键，两个系统抢一个名字时后扫到的会悄悄顶掉先扫到的）② **声明与工厂可以分开住**（M2 的三个内建可观测系统的工厂住在宿主层——它们的落盘出口由宿主注入），但**声明必须在包里** ③ **契约基线新增一类键** `system/<名字>`（**只增不改**：允许新增系统条目，禁止既有条目的哈希变化）④ **清单与目录不是一回事**：`declared_manifests()` 回答「有哪些系统」，`system_catalog()` 回答「哪些能装」。

### ADR-087　换规则集只在非 running 态被接受；未登记的规则集明确拒绝　`已定`

- **决策**：① `switchRuleSet` 的**门禁不走统一的生命周期门禁**（`lifecycle_gated = False`）——**由内核自己判 phase**：`running` 态一律 `illegal_transition`，**待开始与已结束态被接受**；② **规则集未登记 → `unknown_rule_set`**——**明确拒绝，不拿当前规则集顶替**；③ **换了就是重开一局**（局面重置 · 相位回待开始 · 随机源回初始种子 · **扩展槽清空**），并发 `kernel:rule-set-changed` + `game:reset` 两条事件；④ **帧号不归零**（录像与重放靠帧号对齐）；⑤ **内核不知道有哪些规则集**——规则集由**宿主注入的解析器**给出，**没注入 = 一条都换不了**（NFR-5 的纯净度）。
- **否决**：① **局中也允许切换**——半局换规则集 → 同一局里前后两套规则 → **录像重放静默分叉**（破 AC-1 / NFR-1）；**拒绝比勉强支持便宜** · ② **未登记时拿当前规则集顶替**——"换了个寂寞"，调用方以为换了而实际没换，**静默的假成功比报错坏得多**（与 `replay` 遇到没登记的规则集明确拒绝同款，M3 沿用）· ③ **统一生命周期门禁直接用**——通用门禁是"phase ≠ running 一律拒"（架构 §7.1），而换规则集**恰恰要在非 running 态被接受** → 只能 `lifecycle_gated = False` + 内核自判 · ④ **切换后保留原局面**——新旧规则的形状与踢墙不同 → 旧局面在新规则下可能**非法** · ⑤ **扩展槽带过去**——变体状态与旧规则集绑定，带过去就串味 · ⑥ **帧号归零**（跟 `reset` 一样）——`reset` 的语义就是"从头开始"，**换规则集换的是规则，时间轴照走**。
- **理由**：
  - **局中切换会毁掉录像重放的一致性**：重放靠的是"**同种子 + 同命令序列 → 同结果**"，而命令序列里的那条切换**在不同帧执行会得到不同的规则集**——分叉是**静默的**。
  - **明确拒绝 > 勉强支持**：M3 的两个变体方向（替身规则集与变体规则集）都证明了"换规则集"这条路径**本身是通的**，缺的是**可靠的拒绝语义**。
  - **内核不认识规则集名字是架构要求**：规则层是可替换的（变体落地属 M4），**内核只认"按标识取规则集"的解析器**。
- **连带**：① **M3 唯一一次冻结区破例**：`kernel/core.py`（换规则集入口）+ `kernel/commands.py`（`str` 参数校验——`switchRuleSet` 的 `rule` 是字符串，内核原本只认 `int` / `INT_TUPLE` / `CELLS`）→ **冻结区基线显式刷新带 `--reason`**（S8 · `c81d0cc`）→ **`rules/` 一个字节没动** ② **宿主侧规则集登记表 `RULE_SETS`**（标识 → 规则集 · 变体待 M4）③ **契约面新增 1 条事件 + 1 条命令 + 1 条拒绝原因**（**全是新增键**，不撞红）④ **M3-C1 的用途**（新增命令改写 `COMMAND_TYPE_LITERAL` → 4 个既有键哈希变化）是**新增命令必然要花的那一次**（spec §3.4）。

### ADR-088　跨切的拒绝原因必须有机器守卫：导入期当场炸，不许只写在文档里　`已定`

- **决策**：**配额与参数不合规格是跨切的拒绝原因**（架构 §6.4）——**每一条命令的声明都必须带上 `quota_exceeded` 与 `invalid_argument`**。这条规则由 `contracts/commands.py` 的 `CROSS_CUT_REJECT_REASONS` + `missing_cross_cut_reasons()` 落成**可执行的不变式**，**导入期当场炸**（漏了直接 `ValueError`，报错带出漏了哪几条、缺了哪些原因）。
- **否决**：① **只在 docstring 里写明**（M0 → M3 的实际做法）——**没有任何一处机器守着**，于是 `start` / `pause` / `resume` / `reset` **从 M0 起就漏了** `quota_exceeded`，一路漏到 M3 审查报告才被翻出来（**四年**）· ② **只靠测试钉**——测试是**事后**的，导入期那条能**当场**挡下（漏了 → 任何 import 都炸，比任何一条用例都早）· ③ **把跨切原因逐条写进每条声明**（现状）——**写着写着就漏了**，而"每一处都要记得"正是不可靠的那种设计 · ④ **让内核按实际行为自动改声明**——契约面是**公共叶子**，不该被实现反推。
- **理由**：
  - **声明与内核行为分家时，消费方按 `reject_reasons` 枚举拒绝面就会漏**——契约说"这条命令不会被配额拒"，而内核对它照发 `quota_exceeded`（探针实证）。**声明是给消费方看的，漏了就是骗消费方**。
  - **"写在文档里"不等于"落进每一条声明"**——这是本 ADR 要记住的那句话。**规则要能执行，才守得住**。
  - **导入期当场炸是最快的失败**：它把错误从"消费方踩空"提前到"库根本 import 不进来"。
- **连带**：① **M3-C2 动用**：补齐 5 条命令的声明 → 契约基线 **5 个 `command/<名字>/rejectReasons` 键哈希变化**（major 变更 · 显式刷新带 `--reason` · `0af6c3d`）② **修的是契约不是内核**——内核的行为是对的（配额超限时被丢弃的**任何**命令都以 `quota_exceeded` 被拒，架构 §6.4）③ **机器守卫 + 一条测试双保险**：导入期当场炸（快）+ `tests/test_contracts_declarations.py` 钉一道（看得见）。

### ADR-089　系统声明自证要校验产出者：合法值 = 代号表 ∪ 系统自己的名字　`已定`

- **决策**：`check_manifest_types()` **新增 `known_producers` 参数**，校验声明里的 `producer`：**合法值 = 产出者代号表 ∪ 本系统自己的名字**。本模块**不 import 注册表**（`events.py` / `commands.py` 与它同层，互相 import 会成环）——**口径在契约面，数据由调用方递进来**（与同模块既有的两条校验同一手法）。
- **否决**：① **不校验 producer**（M3 审查前的样子）——**产出者拼错时基线照收、安装照过**，而消费方按 producer 过滤事件时会**静默漏掉整个系统的事件**（**声明与实际发事件的人对不上，没有任何一处会红**）· ② **只允许代号表里的值**——**不发事件的系统**（`rotations`——产出是计数文件而不是事件）**没有事件产出者可填**；需求 §8.2 的 `producer` 本来就允许「系统名」· ③ **本模块直接 import `events.py`**——`contracts/systems.py` 是**公共叶子**，plan 写明它「不 import 任何东西」；同层互相 import 会成环 · ④ **让每个系统自己保证**——**没人保证**。
- **理由**：
  - **拼错了没有任何一处会红**是这一类洞的共同特征：基线只钉**声明**，不钉**声明与实现对不对得上**。
  - **"系统自己的名字"是需求写明的合法值**（§8.2）——**不发事件的系统**产出是文件不是事件，产出者代号就是系统名。
  - **参数传递而不是直接 import**：这与 `known_events` / `known_commands` 两条既有校验**完全同款**——**同模块不另立一套规矩**。
- **连带**：① **调用点全部更新**（`tools/contract_baseline.py` · 三处测试）② **契约基线不变**（`producer` 的值一个都没改——**校验变严不改声明**）③ **新增两条用例**：拼错必报 / 系统自己的名字必放行（**双向有牙**）。

## E. M4：变体 · 实时宿主 · AI · 录像升版

### ADR-090　变体走显式登记表，不进自动发现　`已定`

- **决策**：**变体不自动发现**——变体是"玩法"不是"插件"，**走宿主层独立的登记表**（`host/variants.py` 的 `register_variant()`）：**标识 → 变体**（规则集 + 附带系统 + 版本）。**在册就按标识选，不在册就明确报错**（不拿标准规则集顶替）。**内建变体（变体 A 的三个轴）在命令行进程启动时即登记**（`main()` 里调用 · 幂等）→ **`tetris variants` 的清单 ≡ 登记表**。
- **否决**：① **变体也进自动发现**——M3 的发现扫的是 `systems/` 目录，**变体是玩法不是插件**；混进同一张注册表会让**名字空间打架**（系统名 vs 变体名）② **把登记表放 `contracts/`**——`contracts/` 是**公共叶子**（不 import 任何东西），**变体要 import `rules/` 与 `systems/`** → 声明放进公共叶子 = 让公共叶子依赖实现 ③ **不给变体留"空清单"这个状态**——有内建变体之后"清单为空"是个没有意义的状态 → 换成更强的判据「**清单 ≡ 登记表**」（S3 落定）④ **没登记就顶替标准规则集**——顶替会让"四项不等 / 五项不等"的报错**失去指向性**（M2 的 `replay` 已是这个口径，M4 沿用）⑤ **自动发现变体（靠扫描 `variants/` 目录）**——变体要接线（规则集 + 附带系统 + 装配），**扫描出来的名字接不上线**。
- **理由**：
  - **变体要接线，系统不接线**——系统的工厂是自足的（装上就能跑），变体不是（它要指定用哪套规则集、带哪些系统）。**"扫出来就能装"这条规律在变体这里不成立**，硬套就会造出一个扫得出来却装不上的东西。
  - **"新增能力 = 新增文件"在变体这条路上不成立**——变体必须进既有文件（登记表）才能被选中；**这条判据（G4-1）本来就是给"玩法可换"用的，不是给"变体可加"用的**。
  - **清单 ≡ 登记表**比"清单可能为空"更好用：**恒等关系可机检**，空清单只能靠"碰巧为空"蒙对。
- **连带**：① **变体登记表住在宿主层**（架构 §4.1：唯一知道怎么把部件拼起来的地方是装配层）② **`RULE_SETS` 扩表**登记变体规则集 ③ **变体声明进契约基线**（`system/<名字>` 一条键 · **只增不改**）。

### ADR-091　变体 A 的表用轴变换实现；轴绑在规则集实例上；消行口径仍是"满行消"　`已定`

- **决策**：① **形状表与踢墙表由标准表做刚体变换得到**（绕盒中心 90°），**不做四轴全量真值表**；② **朝向编号不重编号**（刚体旋转与 SRS 旋转可交换）；③ **轴是规则集实例的不可变常量**（内核恒传 `ctx.axis="down"`）→ **"切轴" = 开局前换一份轴不同的规则集**（`switchRuleSet`），**不是局中随时转轴**；④ **横向重力下消行口径仍是"满行消"**（内核的塌落按行），**软降与左右移仍是屏幕方向**；⑤ **踢墙语义是变体自定义的**，不是标准 SRS——**这句话写进变体自己的文档**。
- **否决**：① **抄一套四轴全量真值表**——**机械数据量**省下来了，省不下来的是"这句话必须写清楚"；而且**四轴里有一轴（up）在内核语义下不成立**（`y < 0` 是出生区 → 方块会飞出棋盘）② **让内核按 `ctx.axis` 变重力方向**——`kernel/core.py` 恒传 `down` → **改内核 = M4-D1 破**（冻结区零改动是 M4 的验收基准）③ **局中随时转轴**——给轴开一条内核可变通道 = 内核改动；且**换规则集本就禁止局中切换**（ADR-087）④ **横向重力下改成"消列"**——内核的 `step_clear` / `step_collapse` 按行 → **轴感知的塌落 = 内核改动 = M4-D1 破**⑤ **重编号朝向**——**相对旋转才是手感**；重编号会让玩家按 CW 看到的变成逆时针（手感受不住）⑥ **给变体 A 开 forbidden 契约豁免**（S3 一度拆成"只对 `variants.gravity` 严"）——**那是我自己引入的偏离** → 已恢复架构原样（**全体变体禁内核 / 总线**）。
- **理由**：
  - **"重力方向随 `ctx.axis` 变"是规格自己写出来的、不成立的一句**——**执行期对着内核源码核出来并改口径，比照着规格写出一个假的实现强**。
  - **刚体旋转与 SRS 旋转可交换**（`T(SRS_顺(down[r])) = SRS_顺(T(down[r]))`）→ **形状整体转 90° 之后，玩家按 CW 看到的仍然是屏幕上的顺时针**。
  - **旋转重力没有物理对应的真 SRS**——踢墙偏移按轴映射是**变体自定义语义**，**不写清楚，后来人会拿标准 SRS 的直觉去用它**。
  - **横向重力的一局很短是结构性代价，不是漏做**：重力没有 y 分量 → 方块停在顶行、堆叠沿 -x 展开 → 棋盘横向只有 10 格 → 三四个方块就顶出（实测 `gravity-right` 种子 7：3 个方块 / 451 帧）。**要让方块往屏幕下方堆，得让重力有 y 分量或让出生与堆叠按轴走**——**两件都要改内核**。
- **连带**：① **K2 / K4 / K5 / K6 四条取舍落定**（spec-M4 §3.3）② **登记三份规则集实例**（`gravity-down` / `gravity-right` / `gravity-left`）③ **变体 A 的消行口径与操作口径写进变体自己的文档**（不是只写在计划里）。

### ADR-092　扩展槽协议归声明方；合并在宿主层；帧末合并；变更不另发事件　`已定`

- **决策**：① **协议（`ExtensionProvider`）住在变体层**（`variants/extensions.py`）——实现方**有同名方法就算数**（结构化类型），**变体不必 import 协议模块**；② **合并器在宿主层**（`host/extensions.py`）：**只放标量 · key 唯一 · 命名空间由宿主加**（`growth.crystalCount`）；③ **帧末合并**（帧推进之后、状态事件之前 · 分发之外）；④ **走内核既有的私有入口 `Kernel._set_extensions`**（内核 M0 已定型的入口 → **冻结区零改动**）；⑤ **扩展槽变更不另发事件**——**观测面是快照**（`extensions` / `extensionFingerprint`）。
- **否决**：① **协议放 `contracts/`**——契约面零变更当场破（`G4-7`）② **协议放宿主层**——变体 import 宿主 → **红线破**（架构 §2.3 / §4.1 / §7.7，且 forbidden 契约**是传递性的**）③ **内核加公开的 `set_extensions`**——**新开公开入口就是冻结区破例**（M4-D1）④ **扩展槽变更时发 `state:changed`**——**判据不成立**（`state:changed` 的判据是 `snapshot.version`，而 `_set_extensions` **不 `_touch()`** → 版本号不变）**且负载 13 个字段由契约固定、不含扩展槽** → **发了也看不出变了什么**，还会把"版本号递增即状态变更"的语义破掉 ⑤ **合并失败只记错不抛**——**静默少一个扩展** → 回放第五项对不上**且看不出原因** ⑥ **扩展槽放晶体坐标清单**——违反"只放标量"（架构 §5.4）→ **摘要（晶体数）进槽，完整状态留在变体手里** ⑦ **重复 key 去重取末值**——重复 key 是**结构错误**，当场炸比悄悄挑一个值强。
- **理由**：
  - **"扩展槽变更要有事件"是执行期发现站不住的规格**——**先改规格，再写代码**（不是写完代码回头圆）。
  - **变体层禁 import 宿主，且禁令传递**——**协议不能住宿主层**（否则变体得反过来 import 宿主）；**契约面零变更**也不能进 `contracts/` → **只剩变体层一个落点**。
  - **校验全在宿主做**：内核只原样携带、不理解内容——**校验放进内核就是让内核开始理解内容**。
  - **帧中合并 → 订阅者读到半帧状态** → 事件与状态对不上。
- **连带**：① **扩展槽是回放校验的第五项**（`G4-2`）→ 少一个扩展 = **四项全等而第五项不等**，且**看不出原因** → 重复 key 当场炸 ② **内核 `_set_extensions` 不 `_touch()`**——版本号不动是**有意为之**（§③）。

### ADR-093　AI 不引 numpy：纯 Python 启发式 + 固定预算 + 与人类同通道　`已定`

- **决策**：① **AI 用纯 Python 启发式**（不引 numpy）——**固定 40 个候选**（4 朝向 × 10 列）· **搜索深度 1** · **整数权重**（lines 1000 / holes -800 / agg -30 / bump -20 / landing -5）；② **决策路径里不许出现 `time`**（**不按耗时自适应 · 不做帧内增量搜索**）；③ **AI 订阅 `piece:spawned` + `clock:tick`，经 `bus.subscribe_system`（双参）拿 `ctx.view()`**，经 `CommandChannel` 派 `moveLeft/moveRight/rotateCW/rotate180/rotateCCW/hardDrop`——**与人类走完全相同的通道**，**`source='ai'` 只作元数据**；④ **每块只规划一次**（`piece:spawned` 重开闸门），**规划坐标 = 执行坐标**（用**当下视图**规划，不预测）；⑤ **AI 不进默认装配**；⑥ **AI 的几何只认 `down` 轴**（变体 A 的表在 `variants/`，**系统层不得 import 变体层**）→ **AI × 变体 A 不在 S9 范围**。
- **否决**：① **引 numpy**——**少一个依赖**（numpy 要额外钉版本才敢保证复现）· **纯 Python 天然确定** ② **按耗时自适应预算**（"算到 5ms 就停"）——**同一录像在不同机器上重放出不同结果** → **破 AC-1 / NFR-1**（B-8）③ **帧内增量搜索**（上一帧没算完这帧接着算）——同上，且**分叉是静默的** ④ **AI 直接改棋盘**——**破 N1 / N5**（AI 是订阅者 + 命令源）⑤ **内核里出现 `source == 'ai'` 的分支**——**破 FR-8.5** ⑥ **AI 预测落点后再等若干帧才执行**（规划坐标 ≠ 执行坐标）→ 人类那边是"看一眼再动"，AI 这边变成"隔几帧动" → **不再是同一个语义** ⑦ **AI 进默认装配**——**事件数基线会变**（`G4-9` 零污染）⑧ **让系统层 import 变体层拿变体 A 的表**——**横向依赖**（变体层与系统层同级）。
- **理由**：
  - **"固定预算"是回放可复现的前提**：命令序列随机器负载变化 → 回放静默分叉 → **录像校验全废**。
  - **枚举 + 整数权重 = 天然确定**：没有浮点、没有随机、没有时间 → **同一输入必得同一输出**。
  - **与人类同通道是"底座而非游戏"的兑现点**：AI 不是内核的一部分，**它就是另一个订阅者 + 另一个命令源**——**内核不因它分支**。
  - **踢墙用 `KICK_TABLE["down"]`**、**碰撞口径与内核 `_collides` 一致**——**两处真相会让 AI 规划出内核不认的落点**。
- **连带**：① **AI 的声明进契约基线**（新增 `system/ai` 一条键 · 既有键哈希不变）→ **M4 契约基线刷两次**（S4 变体 B · S9 AI），**与 spec §6.6「只刷一次」有出入，照实记**（M3 也有两次的先例）② **产出者代号表增 `ai`**（**代号表不进基线**，但守卫要求每个代号有人用）③ **`tetris play --ai` 开关**（S8 遗留）**在 S9 之后可用**。
- **后续订正**：**「固定 40 个候选」这句在 M5 被订正**（40 既不是枚举数、也不参与剪枝）→ **ADR-097**。**本 ADR 的其余决策继续有效**。

### ADR-094　录像格式升 v2：头加 `variant`；第五项单列；v1 按"无变体"处理　`已定`

- **决策**：① **录像头加 `variant` 字段**（**变体标识与规则集标识不是一回事**——变体 B 的规则集就是标准的）；② **写出永远是 v2**，**读入兼容 v1 与 v2**，**未知版本明确报错**（不许静默当 v1）；③ **`Recording.outcome` 仍是 `FourItems`**（保住 M2 / M3 的门禁与既有调用方），**第五项单列** `extension_fingerprint: str|None`——**`None` = 该录像没有第五项**；④ **v1 录像按"无变体"处理**（**不是拒绝**）：宿主比较时用**空槽摘要**参与比较，并在输出里标明「**该录像是 v1：无变体第五项**」；⑤ **录像基准与重放基准都在 `game:over` 事件那一刻取**；⑥ **回放按录像头的 `variant` 装配变体**（规则集 + 附带系统），并**帧末合并扩展槽**；⑦ **变体局录像文件名单独带变体名**（`recording-<规则集>[-<变体>].jsonl`）。
- **否决**：① **v1 录像直接拒绝**——NFR-9 明写"旧版本数据可被识别并给出明确处理策略，而非静默损坏"；**拒绝也是策略，但这里的正确策略是"按无变体处理"**（v1 必然是标准玩法）② **把 `FourItems` 改成五字段结构**——**M2 / M3 的门禁与既有调用方全部要改** → **代价远大于收益**；**第五项单列**是同一件事的最小改动 ③ **让 `systems/replay` 自己算空槽摘要**——该包**禁 import `kernel.snapshot`**（既有门禁）→ **由宿主兑现**（`EMPTY_EXTENSION_FINGERPRINT`）④ **静默把未知版本当 v1 读**——**静默损坏** ⑤ **拿结构指纹当扩展指纹**——**两个哈希不是一回事**（架构 §5.4）→ **四项全绿而结果不同** ⑥ **笼统报"四项不等"**——变体局最常见的分叉原因就是扩展状态 → **指认不到就等于让人猜谜** ⑦ **在录像落盘那一刻（局末之后）再取基准**——**扩展槽在帧末合并**，取晚一步会差一帧的变体状态 → **基准与重放基准必须同事件对称**。
- **理由**：
  - **"无第五项"是一种合法状态，不是一种缺失**——v1 录像**真的没有**第五项 → 用 `None` 表达"没有"，而不是用**空槽摘要**冒充"有一个空的第五项"→ **两者在比较时等价，在解释时不等价**。
  - **录像格式升版是破坏性改动**（旧工具读不了新文件）→ 提交标题带 `!`。
  - **扩展槽合并在帧末**（ADR-092）→ **基准取 `game:over` 那一刻**（同一事件）→ 录像与重放**天然对称**。
- **连带**：① **`replay:playback-stopped` 事件仍发四字段**——**契约面不可加第五项**（契约 v1 只增不改，且加字段要改既有键哈希 = major 变更）② **生长变体的晶体计数口径顺带修正**：`crystal_count` 改为**按盘面镜像现算**（值为 8 的格数）——回放时录像里的 `writeCells` 与变体自发的 `writeCells` 会**写同一格两次**，**累加会多算** → 变体局第五项对不上 ③ **CLI 退出码三条口径不变**：五项全等 0 / 不等 1 / 没有基准或规则集（变体）未登记 2。

### ADR-095　M4 性能复测分档记账：四档 + 一档对照腿；三条口径不许混；新工具不碰老工具　`已定`

- **决策**：① **四档之外加一档对照腿 `m4-default`**（M4 树的默认装配）——**不把「M4 这棵树本身的开销」单独量出来，变体那一档的差值就不纯**（差值里混着两样东西）；② **三条口径不许混**：**逻辑帧预算只算"推进那一帧"**（内核推进 + 事件分发 · NFR-2）· **渲染 / 落盘 / 导出 / 网络 IO 不进预算但单独记** · **AI 的决策耗时算逻辑帧的一部分**（NFR-2 只排除渲染那一类）→ **单列一条**；③ **AI 的决策耗时怎么量**：把 `systems/ai/system.py` 的 `plan_placement` 换成计时包装器 → **量到纯决策耗时**（不含事件分发与派命令）；④ **配对 A/B 同机同时段交替采样 3 轮**，**驱动是参考策略**（`tests/support/policy.py`），**从被测的那棵树里取**并把**内容哈希记进输出** → **"两棵树的驱动代码一样"可核**；⑤ **新工具 `tools/measure_m4_cost.py`**（`--src` 换树）——**不动 M2 时代的 `measure_frame_cost.py`**（它的口径已被事件数基线锁住），**统计口径从它借**（最近秩 P99），**不另抄一份**；⑥ **换树后当场验"量的是哪棵树"**（加载路径不在 `--src` 下就报错）；⑦ **帧窗口按档取小**（变体 B 约 600 帧就顶出 → 窗口开太大，后半截帧全落在 `game_over` 的拒绝路径上），**顶出即停**，**实测帧数记进输出**；⑧ **事件数基线未变**（新系统不进默认装配）→ **不刷**。
- **否决**：① **把 AI 决策耗时混进"整帧耗时"** → 说不清是谁慢，超预算时改不动 ② **拿 M3 收官那次的绝对值当对照** → **跨时段的绝对值不可引用**（M1 的 S14 栽过这一回）③ **用固定动作串驱动** → 变体档撑不到采样窗口就顶出，后半截帧量的是拒绝路径 ④ **在工具里重写一遍实时帧序** → **两处真相**（帧协议只有一份）⑤ **顺手把 M2 的 `measure_frame_cost.py` 改成多档** → **老工具的口径已被事件数基线锁住**，改了基线就作废 ⑥ **只跑"基准 vs 全开"两档** → 中间两档的账混在一起，**分不清是谁的**。
- **理由**：
  - **"各归各的因"要求每档只比一个变量**——对照腿就是那个"只差树不变"的变量；**不设它，变体的账就混着 M4 树自己的账**。
  - **NFR-2 只排除了渲染那一类**——AI 决策发生在事件分发里，**它就是逻辑帧的一部分**；把它藏起来等于把预算判据悄悄放松。
  - **口径不能抄两份**——百分位与汇总从老工具借；**抄一份就是第二个真相**，两处算出不同的 P99 就没法比。
  - **量错树而不报错，比量错树还糟**——它会给出**看起来很像真的**数（所以换树后当场验加载路径）。
- **连带**：① **全开档 P99 ≈ 3.34 ms 超 NFR-2 的 1.6 ms 预算**（超的是 AI 决策帧 · AI 决策 ≈ 1.55 ms/次）——**AI 不进默认装配 → 默认路径 P99 ≈ 1.20 ms 仍在预算内**；**全开档超预算作为卡点记录**，属后续优化项（剪枝 / 候选数可调），**不在 M4 范围**（M4-D3 禁按耗时自适应）② **独立交叉核对**：另写探针直接量同一个 `plan_placement` → **不带变体时 P50 只有 251 μs，带变体 B 时 1260 μs** → **变体 B 的晶体把 AI 的落点扫描变贵了约 5 倍**（这条交叉核对是"AI 贵"与"变体让它更贵"两件事的唯一分界）③ **实时档走产品自己的 `assemble_play` + `PlaySession`**（虚拟时钟 · 不真的等）→ **不重写帧序** ④ **测量期间机器上不能有别的负载**——首轮采样与 pytest 并发，数字整体抬高（AI 决策从 1.55 ms 虚高到 3.2 ms），**空机重跑才作数**。

### ADR-096　AI 落点搜索的等价提速：改算法形态，不改决策　`已定`

- **决策**：① **M5 的正题是"等价提速"**——**同一个 AI · 同一个局面 · 同一个决策**，**但决策成本降一个量级**；② **改算法形态，不改搜索语义**：候选集 · 搜索深度 · 枚举顺序 · 权重 · 打分口径**一字未改**，只把"每个候选各算一遍"换成**剖面一次算好 + 解析式下落 + 路径前缀和 + 增量打分 + 按朝向预计算**；③ **提速的实现形态**：`_Profile` 剖面（每行填充数 · 每列有格行 / 顶行 / 洞数 · 基准分项）· 每列二分查「下面第一个有格的行」得落点 · 每列「出生行上放不放得下」的前缀和把路径判定变成 **O(1)** · 打分只算**受影响的列与它相邻的对** · **命令序列与结果对象只在赢家身上造**；④ **安全网先行**：**参照实现冻结在 `tests/support/ai_reference.py`**（M4 那版的逐字副本 · 只用于差分 · **不进 `src/`**）· 差分测试逐条比**落点 · 分数 · 命令序列** · 另配**手抄锚点表**（源码字面量）**挡住"两份一起改坏"**；⑤ **确定性纪律不变**（M4-D3）：决策路径**无 `time`** · 候选数与深度是**固定常量** · **不按耗时自适应** · **不分摊到多帧**；⑥ **等价性证据**：一次性高强度对照 **229,320 次零差异**（7 种局面生成器 × 七种方块 × 六个出生列 × 三个出生行）· 测速 **1136 μs → 203 μs（5.6×）** · `tests/test_m4_ai.py` 的既有期望值**一个没改**。
- **否决**：① **改算法（位棋盘 / 预计算表）**——**会改掉 AI 的选择** → 那不是提速，是**换了一个 AI**（录像分叉 · 期望值重抄）② **改候选集或搜索深度来省时间**——同上，且 M4-D3 把它们定为**固定预算** ③ **把决策分摊到多帧**——M4-D3 明写不做（**分帧 = 同一录像在不同机器上分叉**）④ **按耗时自适应（"算到 5 ms 就停"）**——**破 AC-1 / NFR-1** ⑤ **只写差分测试、不写手抄锚点**——差分防不住"两份一起改坏"（M1 `G1-1` 的老坑）⑥ **参照实现放进 `src/`**——**第二个真相进产品** ⑦ **为了让新实现通过而改既有期望值**——**那不是提速，是换个 AI**。
- **理由**：
  - **"快"不是目的，"快且一样"才是**：提速一旦改了决策，录像就分叉、期望值要重抄——**代价远大于收益**。
  - **剖面一次算好是纯赚**：每局算一次的量（行填充 · 列顶 · 洞数）与候选数无关 → **候选越多越赚**。
  - **增量打分的坑在"相邻对算两遍"与"洞数只算一列"**：所以**四条等价纪律逐条有测试守着**，不是靠人看。
  - **差分 + 锚点两道牙缺一不可**：差分挡"改坏一份"，锚点挡"改坏两份"。
- **连带**：① **`MAX_CANDIDATES` 的声明当场作废**（它写 40，而实际枚举 64）→ **ADR-097 单独订正**（**声明订正不混进功能提交**）② **M4 审查报告 L1**（`tests/ocr/m4-review.md`）独立指出过同一个病 → M5 直接采信、不重复论证 ③ **等价纪律成为 M5 的长期回归网**（`tests/test_m5_ai_equivalence.py`）④ **提速的收益上限已被摸清**（纯 Python 等价提速 ≈ 6×）→ **全开档 P99 仍在 1.6 ms 预算外约 4 %**（见 ADR-098）。

### ADR-097　AI 候选预算的声明订正：枚举数与评估数各自说人话　`已定`

- **决策**：① **`MAX_CANDIDATES` 订正为 64**，口径写死为「**`ROTATION_COUNT` 个朝向 × 每个朝向（棋盘宽度 + 两侧各 `COLUMN_MARGIN` 列）个起手列**」→ **10 宽的标准棋盘上是 4 × 16 = 64**；② **另立两个固定常量** `ROTATION_COUNT = 4` 与 `COLUMN_MARGIN = 3`，并让**实现的枚举真的用它们**（声明与实现**同一处真相**）；③ **"真正会被评估的候选数"不当常量**——它**随局面变化**（平移路径被挡住的候选先被剔除）：实测 **0–36 个**（中位 32 · 均值 27 · 300 个随机局面 × 七种方块）→ **它是上界，不是定值**；④ **代码注释里两个数各说各的话**，不许再混（以前写"4 朝向 × 棋盘宽度 = 40"，**三个数两两对不上**）；⑤ **`G5-5` 改成可机检**：断言**声明 = 实现实际枚举的候选数**（把实现里的路径判定包一层计数器，**数出来**）· 断言**声明 = 枚举规则算出来的数**（用内核默认宽度 `DEFAULT_BOARD_WIDTH`）· 断言**任何局面下被打分的候选数 ≤ 声明**。
- **否决**：① **让 `MAX_CANDIDATES` 等于"会被评估的候选数"**——**那个数不是常量**（随局面变）→ 写死它就是**又一句谎言**（而且比 40 更坏：40 至少是个整齐的假数）② **把 `MAX_CANDIDATES` 删掉**——审查报告建议过，但**预算要有声明**：M4-D3 的"固定预算"纪律需要**看得见的常量** ③ **让 `MAX_CANDIDATES` 变成真的截断器**（枚举到 40 个就停）→ **会改掉 AI 的选择**（枚举范围变了 → 落点可能变）→ **那不是提速，是换 AI** ④ **按局面动态定候选数**——**破 AC-1 / NFR-1** ⑤ **声明写"约 64"**——**"约"就是可以不准**。
- **理由**：
  - **声明的价值在于能被机检**：原来的 40 **既不对应枚举数、也不对应评估数、也不参与任何逻辑** → 读者按它理解必然错。
  - **把"定值"与"上界"分开说**，比给一个假的定值诚实：枚举数是**定值**（64）· 评估数是**上界内的变量**。
  - **门判据要能咬**：原措辞"声明值 = 实际会被评估的候选数"**默认了评估数是定值**——实测证明它不是 → 措辞改成**声明 = 实际枚举数**（可数、可机检），**并保留"评估数 ≤ 声明"的约束**。
- **连带**：① **门判据措辞同步修订**（`docs/需求与边界.md` §12 的 `G5-5` 与 `docs/spec-M5.md` §9.1）——**只改口径表述，不放松门**（反而多了三条机检）② **`tests/test_m5_ai_equivalence.py` 增两条预算用例**（`-k budget` 入口）③ **M4 的 ADR-093 里"固定 40 个候选"那句同时作废**（它记的是当时的实现事实；本 ADR 取代它）。

### ADR-098　M5 的性能账：AI 降一个量级，全开档仍超预算的账不全是 AI 的　`已定`

- **决策**：① **复测口径沿用 M4-S12**（`tools/measure_m4_cost.py` · 五档 · **配对 A/B 同机同时段 · 空机 · 3 轮** · seed 20261120 · 400 帧 · 100 预热）——**不改工具**（它的口径被基线锁住）；② **额外做一轮"合并样本"测量**（**同一个工具 · 同一套口径** · 24 局 · **288 个决策样本**）——**理由**：一次 400 帧的运行**只有 13 个决策样本**，**最近秩 P99 ≈ 最慢那一次** → **统计上不成立**（跨轮次在 252–543 μs 之间跳）；③ **如实记账**：AI 决策 **P50 1607 → 259 μs（6.2×）** · **合并样本 P99 3418 → 1481 μs（2.3×）** · **max 16820 → 2403 μs（7.0×）** · mean 1735 → 290 μs（6.0×）· **全开档逻辑帧 P99 3998 → 2428 μs（1.65×）**；④ **G5-2 判为未达标**（合并样本 P99 = 1481 μs > 门槛 400 μs）——**不为了让它变绿而改门槛**；⑤ **AI 已不再是逻辑帧的越界者**：**不含 AI 的四档**（m3-baseline · m4-default · m4-variant · m4-realtime）**两腿代码完全相同** → 观测到的差异**就是抖动本身**（逻辑帧 P99 抖动 ±2 %–26 %），而**全开档剩下的越界来自变体 B 档与实时宿主档自身**（各 P99 ≈ 1.4–2.0 ms，叠加 ≈ 2.4 ms）；⑥ **M5 不承诺把全开档压进 1.6 ms**（spec §11.2 路线 ③ 要改 NFR-2 口径 · **需用户拍板**）；⑦ **后续三条路**：**尾部优化**（深盘面上被打分的候选更多 → 但剪枝会改 AI 的选择 → **不是提速是换 AI** → 需另立项并重新过等价网）· **改 NFR-2 口径** · **接受现状并把门槛按合并样本口径重订**（**改门需拍板**）。
- **否决**：① **把 G5-2 的门槛改成 1500 μs 让它变绿**——**改门让它绿 = 门没了** ② **只报单局 P99（410 μs）当达标**——那是 13 个样本里**最慢那一次**，跨轮次在 252–543 μs 之间跳，**不成立** ③ **拿 M4 收官那次的绝对值当对照**——**跨时段不可引用**（所以配对 A/B 同机同时段重测）④ **改 `measure_m4_cost.py` 凑口径**——它的口径被基线锁住 ⑤ **用剪枝把尾部砍掉**——**会改掉 AI 的选择**（M5 的正题就是"不改决策"）⑥ **只测全开档一档**——**说不清是谁的账**（四档里只有全开档带 AI，其余四档两腿代码相同 → **它们量的是抖动**）。
- **理由**：
  - **P99 是尾部的度量，尾部要靠样本量**：13 个样本的 P99 就是最大值——**换个种子就变**。**门槛必须配样本量一起定**，否则门是"看运气"。
  - **AI 已经不是越界者**：全开档 P99 从 3998 降到 2428 μs，**降掉的 1570 μs 正好是 AI 的那部分**；剩下的 2428 μs 里，**变体档与实时档各自就占了 1.4–2.0 ms**——**那是另一个议题**（M4 就已经记过：变体 B 把 AI 的落点扫描变贵约 5 倍）。
  - **"没达标"要照实写**：把门改成"刚好能过"的数，等于把门拆了；**如实记账 + 给出后续三条路**，才是这条 ADR 的价值。
- **连带**：① **`G5-2` 的判定说明按真相改写**（`docs/需求与边界.md` §12 与 `docs/spec-M5.md` §9.1）：**门槛不变，但注明"单局 P99 只有 13 个样本、须以合并样本口径判"**——**只补口径，不放松门槛** ② **PROGRESS 卡点段记两笔账**：AI 的账（已清）与全开档的账（**不是 AI 的**）③ **M5 的收官判定里 G5-2 记为未达标**（`docs/plan-M5.md` §3 与 §8 如实标注）④ **测量期间不许有别的负载**——本轮复测全程空机（与 pytest 并发会让数字虚高，M4-S12 踩过）。

### ADR-099　首个公开发布（v0.1.0）：四个附件 + releases 分支；「分窗口版」按现实改口径　`已定`

- **决策**：① **首个公开发布是 `v0.1.0`**（`pyproject.toml` 的版本号**不抬**——它从未对外存在过，没有"旧版本要兼容"的压力；抬号是下一个版本的账）；② **四个附件**：`tetris_kernel-0.1.0.tar.gz`（sdist）· `tetris_kernel-0.1.0-py3-none-any.whl`（wheel）· `tetris-cli.exe`（控制台版 · 全部子命令）· `tetris-play.exe`（双击即玩版）；③ **「分窗口版」按现实改口径**——**`--windowed` 的空窗口版不做**：仓库里**没有 tkinter 代码**（渲染层只有 `adapters/render/terminal.py`），而 `--windowed` 会把 `sys.stdout` / `sys.stderr` 置为 `None`（rich 默认写 stdout）→ 双击后**只有一个闪一下就消失的空窗口**。**双击即玩版 = 开一个控制台窗口跑终端版 `play`**：无参数即进游戏，退出前等一次回车（否则窗口随进程一起关，玩家看不到结算统计）；带参数时与控制台版**完全等价**；④ **渠道仍是 GitHub Releases，不发 PyPI**（ADR-008 不变）；⑤ **打包脚本入库**（`release/`：两个 `.spec` + 两个入口脚本 + `build.ps1` + 发布说明），**产物不入库**（`dist/` 已被 `.gitignore` 忽略）——**重建只需 `pwsh -File release/build.ps1`**；⑥ **releases 分支的用法**：从 `master` 切出 `releases` → 在其上提交打包脚本与发布说明 → 打 tag `v0.1.0` → **合并回 `master`（`--no-ff`）** → 回填哈希；⑦ **国内下载点：只走 GitHub Release 直链，先不做镜像**。
- **否决**：① **做 `--windowed` 的空窗口版**——双击闪一下就没，比没有更糟 ② **这次一并发 PyPI**——ADR-008 的三条理由（包名被占 · 发布不可撤回 · 用户要的是 exe 不是 `pip install`）一条都没消失 ③ **打包脚本不入库**——每次发布靠回忆重建，**不可复现 = 不可追溯**；exe 本来就不该入库（二进制 diff 不可读、仓库膨胀），但**重建它的脚本必须入库** ④ **立刻上国内镜像**——没有量级依据，先记直链数据再决定 ⑤ **把 exe 提交进仓库**——同 ③ ⑥ **抬到 0.2.0**——0.1.0 从未对外发布过，抬号解决不了任何问题。
- **理由**：
  - **"分窗口"这个词是 M1 时代的设想**（架构 §1 写"渲染是 tkinter"），**代码从来没走到那一步**——发布不能按设想发，只能按现状发。**把口径改掉，比发一个空窗口诚实**。
  - **控制台窗口就是"双击即玩"的现状最优解**：终端渲染器 + 键盘适配器 + 真实时钟都已经在（M4-S8），双击 → 开窗口 → 直接玩，**零新增渲染代码**。
  - **可复现性优先于便利**：脚本入库后，任何人 clone 下来跑一条命令就能重建同样的四个附件——**这是"发布"能被审计的前提**。
  - **releases 分支保留批次边界**：发布动作（打包脚本 + 发布说明 + tag）留在独立分支，主线只回填结果——和 M1–M5 的批次分支同一套纪律。
- **连带**：① **`docs/项目架构.md` §9 补「实际发布形态」一条**（附件清单 · 改口径的理由 · 重建命令）② **发布说明 `release/RELEASE_NOTES-v0.1.0.md` 写清"不是图形版"与已知边界**（`G5-2` 未达标 · 仅 Windows x64 · 无镜像）③ **PyInstaller 6.22.3 是构建期依赖，不进 `pyproject.toml` 的运行时依赖**——`pyproject.toml` 的 `dev` 组也**不加**它（它是打包工具，不是开发工具；`release/build.ps1` 头注里写了怎么装）④ **打包后要把 editable 安装装回去**（`uv pip install -e .`）——否则本地 `pytest` 会跑到 site-packages 里的旧副本。

### ADR-100　M6 图形版：tkinter · 快照驱动的渲染器 · 输入整套复用 · `--windowed` 打包　`已定`

- **决策**：① **技术栈 = tkinter**（**标准库**）——**零新依赖**，`pyproject.toml` 的 `dependencies` 一字不改；② **图形渲染器是快照驱动的**（`update_snapshot(snapshot)` → 重画整幅画面），**不复用 `TerminalRenderer` 的事件镜像逻辑，也不动 `TerminalRenderer` 的既有行为**——**理由**：渲染器模块头写明它可以消费"**事件与快照**"，而**快照的 22 个字段已经带齐了画完整画面所需的一切**（`board` · `active` · `ghostDelta` · `hold` · `holdUsed` · `next` · `score` · `lines` · `level` · `combo` · `b2b` · `lockTimer` · `phase`）；图形版要的是**整幅画面**，重画一整块比增量改字符更简单也更可靠；③ **输入逻辑整套复用 `KeyboardInput`**——图形层只做「**tkinter 键名 → 归一键名**」这一层翻译，**DAS / ARR / 命令翻译 / 两条输入事件全部由既有适配器负责**（**不写第二套**）；④ **节拍归宿主**：图形侧只注入一个**会泵 tkinter 事件循环的 `sleeper`**，输入**走队列**（tkinter 回调入队 → `poll_keys` 取队），**不用 `after()` 定时器接管游戏循环**；⑤ **主菜单 = 玩法三选一（标准 / 重力旋转 / 落地生长）+ 难度三档**，**难度口径 = 起始等级**（1 / 5 / 10，用**既有的 `setLevel` 命令**落地，**不新增命令**）；⑥ **打包**：`release/graphics_launcher.py` + `release/tetris-graphics.spec`（**`console=False` · `--windowed`**）→ `tetris-graphics.exe`，**与 v0.1.0 的两个 exe 并存**；⑦ **M6 契约面零变更**（事件 / 命令 / 快照字段 / 契约基线 / 冻结区 / 事件数基线全零变化）。
- **否决**：① **pygame** → **多一个运行时依赖**（本项目的适配层只依赖标准库是既有纪律）· exe 更大 ② **把图形渲染器做成 `TerminalRenderer` 的子类** → **语义别扭**（"图形渲染器是终端渲染器的子类"这句话本身就不通）③ **给图形层复制一份事件镜像逻辑** → **两处真相**，改一处忘一处就是画面与终端版分叉 ④ **图形层自己重写 DAS / ARR / 命令翻译** → **手感必然漂**，同一个种子会走出不同的局 ⑤ **用 tkinter 的 `after()` 定时器接管游戏循环** → **节拍就不只属于宿主了**，宿主那套"掉队少跑几帧 / 积压丢弃 / 降级喂帧"会失效 ⑥ **沿用 v0.1.0 那个 `--windowed` 空窗口版** → **它不是图形版**（双击闪一下就没）。
- **理由**：
  - **"再加一个渲染器"是这套架构最该有的用法**：M4 已经证明过渲染器只是又一个订阅者；M6 只是**换一个渲染器 + 换一个输入来源**，内核连事件都不用多发一条。
  - **快照驱动 vs 事件驱动**：事件驱动的价值在"**只画变化的部分**"；tkinter 画 10×20 + 面板的量级（每帧几百个 item）**根本不需要省**——用"每帧重画"换掉"第二套镜像"，是拿一点算力换掉一整类分叉风险，划算。
  - **手感是复现的前提**：DAS / ARR 一旦分叉，`G6-5` 的"同种子同输入同指纹"立刻不成立——**所以输入必须复用而不是重写**。
  - **节拍只有一个主人**：宿主是"什么时候推进一帧"的唯一决定者（架构 §5.3：**内核不读墙钟**）——图形层若用定时器接管，掉队与降级就没人管了。
- **连带**：① **`G6-1`…`G6-6` 登记**（`docs/需求与边界.md` §12 · 门判据以"**图形层与既有层说的是同一件事**"为主线）② **M6 规格与计划入档**（`docs/spec-M6.md` · `docs/plan-M6.md`）③ **`host/play.py` 与 `host/assembly.py` 要改**（图形渲染器与事件泵的接线 · 图形装配）——**宿主层可改，冻结区不可改** ④ **CLI 增 `graphics` 子命令**，**`play` 与 `tetris-cli.exe` 的行为一个字都不许变** ⑤ **`G6-6` 必须是桌面级真机冒烟**——`--windowed` 打包 tkinter 有已知坑（与 ADR-009 的 editable 坑同类），**不靠推断，靠真跑**。
