## A. 选型：用什么库

### ADR-001　事件总线自研（约 300 行）　`已定`

- **决策**：自己写，不用任何第三方事件总线。
- **否决**：`blinker`（缺优先级、中间件、历史与隔离）· `pubsub`（缺优先级与隔离，维护活跃度低）· `anyio`（本身不是事件总线）· asyncio 方案（直接违背"单逻辑线程串行推进"）。
- **理由**：需求对总线的要求是精确/通配/全局三种订阅、优先级、中间件、环形历史与区间查询、异常隔离、分发期间状态不变、同帧多轮 FIFO——没有成熟库同时满足。而这条总线是全项目地基（M0 的 31 条任务里 13 条直接依赖它），自研反而比拼装半成品更可控，且天然满足"内核零第三方依赖"。

### ADR-002　渲染宿主用 tkinter（标准库）　`已定`

- **决策**：主窗口用 tkinter + Canvas，事件流面板用原生 Text + `tag_config`。
- **否决**：PyGame / Arcade / Pyglet（图形框架把手感、输入、渲染耦合成"框架式"主循环，违背"渲染器只是又一个订阅者"，且引入编译型依赖）· Textual（基于 asyncio，与单逻辑线程串行推进冲突，且比 rich 重）。
- **理由**：标准库零依赖，宿主与内核的分离是需求硬约束；Tk 8.6 已在 py312 实测可用。

### ADR-003　内核 / 总线 / 规则零第三方依赖　`已定`

- **决策**：只用 `dataclasses` / `typing` / `enum` / `json` / `random` / `time`。
- **否决**：任何第三方运行时依赖。
- **理由**：架构约束 N7 与 NFR-4 要求内核不依赖特定运行时、图形接口或文件系统的专有能力。这是"内核可脱离一切独立运行"（AC-5）的前提。

### ADR-004　不用 asyncio / 事件循环驱动逻辑　`已定`

- **决策**：内核状态推进串行化，单逻辑线程。
- **否决**：asyncio 与任何事件循环框架。
- **理由**：N3 要求串行化推进。asyncio 会让"同帧多轮 FIFO"变回嵌套重入，"分发期间状态不变"不再成立。**注意约束的是单个内核实例，不是禁止多实例并行**（千局模拟走多进程，见 ADR-018）。

### ADR-005　类型检查用 pyright，不用 mypy　`已定`

- **决策**：pyright 1.1.414，内核与总线 `strict`，其余 `standard`；建议装 `pyright[nodejs]` extra 自带 Node 二进制。
- **否决**：mypy。
- **理由**：本机已有 Node v24.16.0；pyright 对 `frozen=True` dataclass 与 `tuple` 窄类型的处理更符合本项目"不可变优先"的写法。`nodejs` extra 比默认 nodeenv 路径可靠。

### ADR-006　构建后端只用 uv_build　`已定`

- **决策**：`uv + uv_build`，只留一个构建后端。
- **否决**：hatchling。
- **理由**：uv_build 是 uv 自带的，少一个构建依赖；后端二选一即可，两个并存没有收益。

### ADR-007　架构静态检查用 import-linter，不自研全部　`已定`

- **决策**：方案 A——import-linter 三类契约（`layers` / `forbidden` / `independence`）+ 自研补充脚本（禁平台名、事件登记、禁墙钟、冻结基线）。
- **否决**：方案 C（全部自研 AST 脚本）。
- **理由**：**起决定作用的一条**——G4-1"内核文件差异为空"是唯一不可妥协的核心判据，它成立的前提是分层边界**机器可验证**。import-linter 是当前唯一成熟、且原生支持三类契约的 Python 工具。全自研要重写"带完整导入链的违规报告"，且**把唯一的裁判变成自己的代码**——漏报比误报危险得多。

### ADR-008　发布双轨：PyPI 为主，exe 为补充　`已定`

- **决策**：方案 A——PyPI（wheel + `python -m tetris_kernel`）+ PyInstaller 免安装 exe 两个产物。
- **否决**：方案 B（只发 PyPI，不做 exe）。
- **理由**：交付范围已定为"公开下载给别人玩"，只发 PyPI 等于明知要发却先发。**反直觉的事实**：PyPI 直连与清华/阿里镜像本机实测均 200，**PyPI 才是国内最可达的渠道**，exe 的下载点才是麻烦的那个。所以 exe 降级为补充、发布落点 M4 前再定。

### ADR-009　打包前必须先做非 editable 安装　`已定`

- **决策**：`uv pip install .`（不是 `-e .`）后再打包。
- **否决**：直接对 editable 安装打包。
- **理由**：editable 安装留下的 `.pth` 在 `--onefile` 打包时偶发解析失败。

### ADR-010　随机源只用 `random()` 与 `getrandbits()`　`已定`

- **决策**：两个原语；7-bag 洗牌自己实现 Fisher-Yates。
- **否决**：`shuffle` / `sample` / `choice`。
- **理由**：它们的实现细节在 CPython 版本间变过，`shuffle` 与 `sample` 的算法在 3.11 前后有变化——同样种子 + 同样状态取出的序列可能变，**升级 Python 会让全部旧录像集体作废**。只用两个原语，MT 状态就是序列的唯一决定因素。

### ADR-011　随机源用 `random.Random`（MT），状态可导出　`已定`

- **决策**：标准库 MT，状态 625 个整数 ≈ 7.17 KiB；录像头额外记 `rngStateVersion` 与 `pythonVersion`。
- **否决**：不记版本号。
- **理由**：已实测 `getstate()`/`setstate()` 往返可完全复现。但**状态容器格式曾随 Python 版本变过**（3.9 前为列表、之后为元组，版本号也不同），不记这两项，将来升级 Python 会**静默重放出不同结果**。

### ADR-012　终端输出用 rich，但不进 tkinter GUI 路径　`已定`

- **决策**：rich 只服务 CLI 报告与终端渲染器；tkinter 的事件流面板用原生 Text + `tag_config`。
- **否决**：把 rich 的输出塞进 tkinter Text。
- **理由**：tkinter 的 Text 控件不认 ANSI 转义序列，要走 Console 的 Segment API 逐段解析样式再映射成 Text tag（约 50–100 行）——那是一条小型渲染管线，把 rich 从"CLI 报告工具"拖进了 GUI 渲染路径。

### ADR-013　测试用 pytest + hypothesis　`已定`

- **决策**：pytest 9.1.1 + hypothesis 6.170.5（仅 dev 依赖）。
- **否决**：只用手写遍历脚本。
- **理由**：需求要求"构造脚本遍历所有状态变更路径"，属性测试能覆盖手写覆盖不到的空间（含非法命令、生命周期混乱、重复方块）。**两条纪律**：内核随机源固定种子；hypothesis 开 `derandomize=True`（见 ADR-053）。

### ADR-014　日志用标准库 `logging`　`已定`

- **否决**：structlog。
- **理由**：`logging` 的 handler 机制已原生支持多输出目标与分级，够用。

### ADR-015　CLI 用标准库 `argparse`　`已定`

- **否决**：click / typer。
- **理由**：子命令已够用，不为一个 CLI 引第三方运行时依赖。

### ADR-016　事件负载用 `frozen=True` dataclass + tuple　`已定`

- **否决**：pydantic。
- **理由**：事件信封要求高性能与不可变；dataclass + tuple 更轻更快。清单类字段一律 `tuple[tuple[int, int, int], ...]`。

### ADR-017　录像与存档用 JSON　`已定`

- **决策**：录像与存档用标准库 `json` 序列化。
- **否决**：msgpack / orjson · **数据库 / ORM / 后端框架**。
- **理由**：录像体积问题靠"只录命令"（ADR-045）解决；JSON 可读、可 diff、对版本兼容友好。不用数据库的理由是需求已定不做账号、排行榜与云端存储（W-2），存档与录像是自包含文件，标准库 `json` 足够。

## B. 结构与机制：系统长成什么样

### ADR-018　千局模拟用多进程，不做"关闭事件分发"的快速模式　`已定`

- **决策**：`ProcessPoolExecutor`，每局一个任务，进程池大小 = CPU 核数；`chunksize` > 1；汇总前按种子排序。
- **否决**：**"关闭事件分发"的批量快速模式**（明确否决）· 每局 fork 一个进程。
- **理由**：关闭事件分发会直接违反 N5 与 AC-2 事件完备性。按种子排序是因为浮点累加顺序随调度变化，否则统计输出不可复现。

### ADR-019　冻结区只锁 `kernel/` + `rules/`，`bus/` 暂不冻结　`已定`

- **决策**：冻结区严格对齐 G4-1；`bus/` 另列独立基线，等 M2 总线封板后再启用。
- **否决**：一开始就把 `bus/` 一起冻结。
- **理由**：M2 要给总线加中间件、历史查询、计数，批批刷新基线会变成**橡皮图章**——一条每次都被刷新的基线等于没有基线。

### ADR-020　事件类型注册表放 `contracts/`，绝不进冻结区　`已定`

- **决策**：注册表在冻结区外，`contracts/` 另立"只增不改"基线（键 = 事件类型名，值 = 负载字段声明的哈希）。
- **否决**：常量表放 `kernel/` 或 `rules/` · `contracts/` 完全不管。
- **理由**：变体加事件类型时若常量表在冻结区，冻结检查必红——要么加豁免（冻结作废），要么改内核（G4-1 作废）。而"冻结区外"不等于不加检查：既有类型的**负载语义**改了就能改变重放结果（那是 major 变更），冻结检查看不见它。基线哈希**机器可读声明**而非 `.py` 文件内容，否则改个注释就报警。

### ADR-021　只读视图走 `ctx.view()`，不提供 `bus.view()`　`已定`

- **决策**：订阅者签名统一 `handler(event, ctx)`，`ctx.view()` 惰性取视图，按发布点缓存。
- **否决**：总线上的只读访问器 `bus.view()`。
- **理由**：**决定性理由**——访问器可以在任何时候被调用，那时内核处于什么状态没有定义，会把"分发期间内核状态不变"这条结构性事实**退回成约定**。上下文形式天然关掉这个口子。

### ADR-022　帧号推进与推进许可分离　`已定`

- **决策**：帧号 +1、帧内序号归零在 tick **出队时**发生；推进许可在 tick **被接受**时授予。
- **否决**：帧号在"被接受"时才 +1。
- **理由**：`command:received` 在出队执行前发布，被接受只在执行之后才知道。若帧号在被接受时才 +1，tick 的 `received` 带旧帧号、`accepted` 带新帧号——**一条命令两个帧号**，审计链与回放对齐在每帧都有的 tick 上错位一格。

### ADR-023　帧推进五步，并写死加步的充要条件　`已定`

- **决策**：重力 → 锁定 → 消行 → 塌落 → 出生。
- **否决**：加第六步（默认不加）；整批返回不 step 化。
- **理由**：整批会让所有事件共享"执行后的最终态"，`piece:locked` 的订阅者读到的是已消行、已塌落、已出生的棋盘。**加一步的充要条件**：某订阅者需在两既有步骤间观察稳定状态，**且**该状态无法由任一既有事件的负载自足表达。两问都答不上来就不加。

### ADR-024　录像不逐帧记 tick　`已定`

- **决策**：不记。回放宿主自己每帧生成一条 tick，靠 `pause`/`resume` 的帧号 + 内核门禁重建空档；**回放宿主自生成的 tick 同样占帧内序号 0**。
- **否决**：逐帧记 tick。
- **理由**：回放宿主不需要它；记 tick 反而多一处编号对齐负担（回放宿主的编号规则必须与原局逐帧一致）；tick 是录像里最大头的内容而信息量近乎为零。

### ADR-025　命令参数禁浮点　`已定`

- **决策**：`args` 只含 JSON 标量（`int`/`str`/`bool`/`None`）与其元组，反序列化按命令类型还原。
- **否决**：允许浮点。
- **理由**：JSON 里 `1.0` 与 `1` 不可区分，重放时可能拿到不同的参数。**注意 `extensions` 允许浮点，口径不同是对的**——`args` 参与重放（参数不能漂），`extensions` 不参与重放判定，只承载变体状态的可读摘要与渲染用标量。

### ADR-026　指纹用 blake2b + TLV 编码　`已定`

- **决策**：`hashlib.blake2b` 对规范化字节序列求摘要；TLV = 1 字节类型标签 + 4 字节小端长度 + 值；棋盘行优先、`extensions` 按 key 排序、输入前加域分隔前缀；布尔与整数区分编码。
- **否决**：内置 `hash()` · JSON 文本算指纹 · 逐值打补丁式编码表。
- **理由**：`str`/`bytes` 的内置 hash 受 `PYTHONHASHSEED` 随机化影响，跨进程不稳定，指纹比对会毫无规律地失败。JSON 文本的格式化差异（浮点表示、空格、转义）会让同一份数据产生不同文本。早期那张编码表漏了 tuple / None / 元素边界三类歧义（`("ab","c")` 与 `("a","bc")` 会撞），TLV 一次解决三类。

### ADR-027　视图缓存键用"发布点"，不用步骤名　`已定`

- **决策**：缓存粒度是"一次 publish"；`ctx.step` 只是给订阅者看的标签，不参与缓存。
- **否决**：用步骤名当键。
- **理由**：一条命令产生两次发布（`received` 执行前、`accepted` 执行后），AI 一帧多条命令时更多。用步骤名当键，订阅者会读到**过期**状态——不崩、结果偏、极难发现。

### ADR-028　AI 搜索预算固定　`已定`

- **决策**：固定深度/迭代次数，一次算完再派发。
- **否决**：按耗时自适应 · 帧内增量搜索。
- **理由**：约束是"计算量与机器负载无关"，不是"什么时候算"。否则 AI 每帧算多少取决于当时剩多少时间，派发的命令序列不再确定，**回放静默分叉**（比"丢一条命令"更难查）。AI 每帧重算没问题——重算次数由策略决定，不由耗时决定。

### ADR-029　tkinter 帧循环用 `after(5)` + 累加器补帧　`已定`

- **决策**：`after(5)` + `time.monotonic()` 累加器，设最大追帧数（默认 5），时钟源必须可注入。
- **否决**：`after(1)`（实测吃满一个核的 91%）· `after(16)`（实测最大抖到 31.53ms，会整帧错过）· `after(2..15)`（Windows 定时器分辨率约 15.6ms，一律被上舍入）。
- **理由**：实测 `after(5)` ≈ 64 次/秒、0.65% 单核，是唯一兼顾的选项。逻辑步长严格 60Hz 由累加器保证，与 tick 周期无关，**不影响确定性与回放**。

### ADR-030　回放录制走同步订阅者　`已定`

- **决策**：内存 list 累积，局末或周期点一次性落盘。
- **否决**：有界可丢队列（日志/指标那套异步策略）。
- **理由**：丢一条命令 = 录像静默分叉，NFR-1 / AC-1 / G2-1 全废。"不可丢"靠**没有队列**保证，不靠队列策略。

### ADR-031　降级三档固定顺序，带滞回　`已定`

- **决策**：① 关闭调试事件 → ② 降低日志级别 → ③ 关闭事件历史缓冲；手动只开放第 ① 档；自动降级 P99 > 1.6ms（600 帧窗口）降档、P99 < 1.0ms 持续 1800 帧升档。
- **否决**：引入"关闭事件分发"的快速模式 · 第 ③ 档暴露给用户手关。
- **理由**：三档都不伤指标系统；关事件分发会破坏事件完备性。第 ③ 档不暴露是因为用户手关会让时间旅行调试"看起来坏了"。判据用 P99 不用均值。

### ADR-032　规则表落成 Python 字面量常量　`已定`

- **决策**：踢墙偏移表、计分表随规则模块一起进冻结基线。
- **否决**：落成外部数据文件。
- **理由**：那会让"内核文件差异为空"变成文字游戏（规则被改到冻结区之外），且引入 IO 依赖撞上"内核不依赖文件系统专有能力"，还给冻结基线开洞。M4-3 的"变体参数可外部配置"指变体自己的调参，不冲突。

### ADR-033　回放暂停用宿主级，不用内核级 `pause`　`已定`

- **决策**：宿主级暂停 = 不跑帧循环、帧号冻结、不产生任何命令。
- **否决**：回放暂停实现成内核级 `pause` 命令。
- **理由**：`pause`/`resume` 是被接受的命令 → 会被录进录像 → **回放自己污染录像**。

### ADR-034　`variants/` 禁止 import `kernel` / `bus` / `adapters` / `host`　`已定`

- **决策**：变体与 `systems` 同级，只能 import `systems` / `rules` / `contracts`。
- **否决**：允许变体直接引用内核。
- **理由**：一旦变体能 import 内核，它就能把内核私有结构当自己的 API——**内核没被改，但 G4-1"内核文件差异为空"就只剩形式**。变体要的一切都必须走 `rules` 替换或 `systems` 插件两个口子。

### ADR-035　插件不需要运行时沙箱　`已定`（需求决策 13）

- **决策**：不需要进程隔离 / 权限沙箱；要的是**失败隔离**（FR-3.4）与**卸载干净**。
- **否决**：任何插件沙箱机制。
- **理由**：个人项目里插件与内核同信任级别。

### ADR-036　`extensions` 的 key 必须唯一　`已定`

- **决策**：重复 key 即结构错误并记错；宿主合并时校验。
- **否决**：去重取末值。
- **理由**：那会把一个 bug 变成一个静默的覆盖。`extensions` 是 tuple 不是 dict，可以写出重复 key → 语义不明且指纹失真。

### ADR-037　拓扑是坐标映射函数，不是参数　`已定`

- **决策**：规则集提供 `wrap_cell(x, y, w, h) -> tuple[int, int]`（标准=恒等、圆柱=x 环绕、莫比乌斯=x 环绕 + y 翻转），**内核在所有坐标访问点都过一遍**，标准玩法走恒等快路径。
- **否决**：把拓扑当成参数传。
- **理由**：莫比乌斯环绕行后上下翻转是**行为**，"多一个参数"表达不出来。不定这条，M4-C 落地时就要在内核里加调用点——破得和"规则接口签名没留维度"一模一样。

### ADR-038　同因拒绝合并防抖　`已定`

- **决策**：同一 phase 下连续被拒的命令只发第一条，后续合并计数；键 = (phase, 命令类型, 拒绝原因)；`mergedCount` 起始值 = 1；`received` 与 `rejected` 成对合并。
- **否决**：逐条发一条 rejected。
- **理由**：那是一条**实现动作**，一帧能刷出几十条事件。**配额超限是本条最典型的应用场景，不是例外**——配额满时队列里剩 50 条命令，走合并分组，不是刷 50 条。同时必须写明"**满足形式是'一条事件承载 N 次拒绝'，不是'没有事件'**"，否则 AC-2 的事件完备性检查会误判成事件缺失。

### ADR-039　重入语义：命令入队 + 同帧多轮（Round）　`已定`（需求决策 1）

- **决策**：订阅者在分发期间派发的命令一律进队列，当前分发结束后按 FIFO 执行，其产生的事件触发新一轮分发。
- **否决**：递归调用栈展开。
- **理由**：同一事件的所有订阅者因此看到同一份状态，递归被展开为轮次而非调用栈；"分发期间内核状态不变"成为结构性事实。轮次数与单帧命令数双上限，超限丢弃余量并发事件；AI 在帧内派的命令仍于本帧下一轮生效，不损失响应性。配套见 ADR-040。

### ADR-040　轮次与命令数上限按帧累计　`已定`

- **决策**：两个计数器每帧开始清零；`tick` 自身不计入命令数；超限判定发生在"取队执行"之前，不跨帧顺延。
- **否决**：按单轮累计。
- **理由**：按单轮算 8×100 = 800 条/帧，上限形同虚设。

## C. 需求决策的本文映射

### ADR-041　事件粒度三级　`已定`（需求决策 2）

- **决策**：语义事件 / 批量差异事件 / 调试事件，调试事件默认关闭。
- **否决**：统一粒度。
- **理由**：批量差异（如 `board:changed` 的变化格子清单）避免逐格发事件；调试事件默认关闭是为了性能预算（NFR-2）。

### ADR-042　快照是拉取式　`已定`（需求决策 4）

- **决策**：事件只说"发生了什么"，需要状态的一方主动拉快照。
- **否决**：事件自带完整状态。
- **理由**：事件更小、回放更小。配套：帧末宿主拉一次快照并分发给所有渲染器。

### ADR-043　旋转失败：命令被接受，另发受阻事件　`已定`（需求决策 6）

- **决策**：旋转无合法落点时命令仍被**接受**，另发受阻事件。
- **否决**：走拒绝通道。
- **理由**：旋转失败是合法游戏行为，不该进拒绝通道——**拒绝只留给"当前状态根本不该发这个命令"**。这条区分让日志与反作弊清晰得多。

### ADR-044　DAS/ARR 归输入适配器　`已定`（需求决策 8）

- **决策**：手感参数属输入适配器；内核只认"移动一格"这类原子命令。
- **否决**：手感参数进内核。
- **理由**：换设备调参不影响录像复现（FR-8.3 要求调参不触发状态变更）。

### ADR-045　回放录命令序列，不录事件序列　`已定`（需求决策 9）

- **决策**：录被**接受**的命令（含种子与规则集标识），来源随命令记录；回放期间命令源独占。
- **否决**：录事件序列。
- **理由**：事件粒度会随版本调整而失效，不适合长期存档；事件流只作为回归断言基线（FR-6.4）。**回放期间必须卸载 AI / 教学 / 网络系统**，否则"重放时 AI 也在下"会直接摧毁确定性。

### ADR-046　日志级别映射放在日志系统内　`已定`（需求决策 10）

- **决策**：事件不自带级别，级别由日志系统按事件类型映射。
- **否决**：事件自带级别字段。
- **理由**：事件不该知道自己有多重要——同一事件排障时是 trace，演示时可能是 info。

### ADR-047　受控写入不算破坏"唯一写入者"　`已定`（需求决策 14）

- **决策**：外部系统改变棋盘统一收敛为 `writeCells`，由内核校验后落笔并照常发 `board:changed`。
- **否决**：给外部开直接写通道。
- **理由**：它把"外部直接写"变成"外部请求 + 内核裁决"，落笔与发事件仍全部由内核完成，N1 与 N5 都不破。同帧多请求命中同一格默认后者覆盖（可配置为后者被拒），单帧写入量设上限。**必须在 M3 定型**，否则 M4 会很想开后门。

### ADR-048　变体怎么实现：看是否改变"棋盘上发生了什么"　`已定`（需求决策 17）

- **决策**：需要改变棋盘 → 替换规则模块或走受控写入；不需要（如节奏化）→ 纯订阅者，完全不碰内核。
- **否决**：按"实现难易"选路径。
- **理由**：这条判据直接决定 G4-1 能不能兑现。

### ADR-049　变体状态用扩展字段承载，内核不理解内容　`已定`（需求决策 18）

- **决策**：`extensions: tuple[tuple[str, JsonScalar], ...]`，只放标量，禁止容器与嵌套；复杂状态由变体自己持有，帧末宿主合并进 `extensions`。
- **否决**：让内核认识变体状态。
- **理由**：这是"变体加状态但内核不改"的风险缓解——内核只原样携带与序列化。

### ADR-050　先做变体 A（重力可旋转）　`已定`（需求决策 19）

- **决策**：先做 A，变体 B 作为第二个验证点。
- **否决**：先做 B（落地后生长）。
- **理由**：A 只触及规则模块、不涉及受控写入，是"零内核改动"最干净的证明，且上手就有新鲜感。B 路径更长。

## D. 环境与工具链纪律

### ADR-051　禁用 `uv sync` / `uv venv`　`已定`

- **决策**：只用 `uv pip install --python D:\miniconda3\envs\py312\python.exe ...`。
- **否决**：`uv sync` / `uv venv`。
- **理由**：它们会自建项目 `.venv`，把包装到 conda 环境之外，绕过"必须用 py312"这条规矩。已实测 `uv pip list --python <conda 解释器>` 可用。

### ADR-052　ruff 只认环境内那一份　`已定`

- **决策**：py312 环境内的 0.17.1；CI 里钉死版本。
- **否决**：用 PATH 上的 0.15.17。
- **理由**：两个版本格式化结果不同，不钉死会在不同机器上打架。

### ADR-053　hypothesis 必须开 `derandomize=True`　`已定`

- **决策**：属性测试关闭自身生成随机性。
- **否决**：只固定内核种子。
- **理由**：**只固定内核种子不够**——hypothesis 自己的生成随机性也是变量，不关掉它，CI 上的偶发失败无法复现。

### ADR-054　事件目录只允许追加　`已定`（X-1 / NFR-9）

- **决策**：禁止重定义既有类型的负载语义；未知类型按信封解析后静默丢弃或记 trace，不得中断分发或重放。
- **否决**：修改既有事件类型的负载语义。
- **理由**：改负载语义就能改变重放结果，属于 major 变更。机器化实现见 ADR-020 的"只增不改"基线。

### ADR-055　一个录像 = 一局　`已定`

- **决策**：`game:created` 开新录像；`reset` 被接受时结束当前录像并开下一份。
- **否决**：一份录像装多局（若真要，必须按边界切段、每段独立重置帧号、按段回放）。
- **理由**：这样录像里帧号永不重复，回放不需要分段逻辑。

### ADR-056　视图与快照是同一个 dataclass　`已定`

- **决策**：不写两套"几乎相同"的结构。
- **否决**：为视图单独定义一个类。
- **理由**：两套结构长期必然漂移。

### ADR-057　两个订阅入口共享同一个注册表　`已定`

- **决策**：`subscribe(event)` 与 `subscribe_system(event, ctx)` 共享注册表与优先级序列，**排序在合并之后进行**。
- **否决**：按入口分两张表。
- **理由**：否则"业务订阅者先于日志订阅者"（FR-3.3，M 级）在跨入口时不成立。

### ADR-058　内核内部用可变结构，导出时深拷贝　`已定`

- **决策**：内部 `list[list[int]]`，快照导出深拷贝成 `tuple[tuple[int, ...], ...]`。
- **否决**：内部也用 tuple。
- **理由**：内部用 tuple 每次落子都要整体重建嵌套元组；只冻结外层则快照与内核共享内层列表，渲染器一改就破"只有内核能写状态"。

### ADR-059　视图通道对渲染器关闭　`已定`

- **决策**：渲染器走单参数入口，只消费帧末宿主推送的那一份快照。
- **否决**：给渲染器也开 `ctx.view()`。
- **理由**：否则"帧末只拉一次"退化成 N 次。**注意 `bus.publish` 对两个入口都开放**——发布能力与视图能力无关，渲染器要发自产事件 `render:frame`。

### ADR-060　`rng:next` 默认开启，负载瘦身　`已定`

- **决策**：默认开启（不随调试事件一起关）；负载 = 随机值 + 序号 + 状态指纹（短哈希），**不含完整 MT 状态**。
- **否决**：默认关闭 · 负载带完整状态。
- **理由**：FR-5.3 是 M 级要求，随机序列审计依赖它；频率不高（7-bag 每方块约 1 次取值），默认开启代价可忽略。负载不可变 + 625 元素 ≈ 每次取值构造一份，一局几百方块就是几 MB 常驻负载。完整状态只在存档路径导出。
