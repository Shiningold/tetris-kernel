### 1.2 四段结构

| 段 | 阶段 | 性质 | 为什么这样排 |
| --- | --- | --- | --- |
| **A 基础设施** | S0–S1 | 只出壳，不出行为 | 没有壳就装不了依赖；`lint-imports` 的四条契约**第一次真跑起来**就在这里 |
| **B 契约面** | S2–S6 | 只写声明，不写行为 | 契约 v1 一旦冻结就是 major 变更。**声明必须在实现之前定死**，否则被实现反向塑形（ADR-061） |
| **C 行为面** | S7–S14 | 写实现，不改声明 | 行为阶段发现声明缺字段 = 撞基线，必须走显式更新流程，不能顺手改 |
| **D 验证与冻结** | S15–S18 | 验、采数、冻结、收尾 | 冻结基线**收尾才生成**——太早生成会反复失效，成橡皮图章（ADR-019） |

### 1.3 每阶段的硬约束（**贯穿全部阶段**）

| # | 约束 |
| --- | --- |
| 1 | **一次提交 = 一个阶段（或阶段内一个逻辑改动）**；格式化与逻辑改动分开提交 |
| 2 | **不在本阶段做别的阶段的事**——尤其 B 段不写行为、C 段不改声明 |
| 3 | 每阶段结束时，**质量门必须全绿**（见 §5.1），否则不进入下一阶段 |
| 4 | 发现上游设计错误 → **回退到划错边界的那个阶段**修正，不在当前阶段打补丁（需求 §12「门与回退」） |
| 5 | 每个阶段跑完立刻更新本文件 §3 状态表与该阶段的任务框 |

  - **把注册表放进 `kernel/`** → 冻结区，变体加事件类型必撞 G4-1（ADR-020）。
  - **命名空间当产出者** → `kernel:system:installed` 由 host 发，`kernel:error` 由总线发（ADR-063）。命名空间说的是"这件事属于内核实例"，不必然是内核干的。
  - 把"关键负载"当成"完整负载"照抄 §8.1 的举例 → §8.1 是"关键负载"，声明必须**自足**：回放校验要靠它，不能只写"够用就行"的半截字段。
  - **类型声明用 `typing` 对象而不是规范字符串** → `hash(int)` 按对象地址算，跨进程必变；`typing` 对象的 `repr` 随 Python 版本漂移。基线要的是**跨进程稳定**的哈希，所以类型写成规范类型表达式字符串（`"int"` / `"tuple[int, int]"`）。
  - **类型文法的表认不出自己用的类型串** → 文法表是 S6 正则解析器的**规格书**，表里没有的形态会被"看着在基线里、实际没被哈希"，等于没进基线。定文法时必须拿实际用到的类型串逐条回验。
  - **同名字段跨事件不同型** → 通用提取代码（回放校验、完备性检查）会踩空。**同层**的必须改名（`board:changed.cells` → `cellChanges`、`board:lines-cleared.rows` → `rowIndexes`）；**跨域**的（游戏 `level` vs 日志 `level`）改名反而会让字段偏离本域惯例，用 doc 消歧。
  - **同名字段跨域可以，跨层不行** → 负载的 `cause`（成因字符串）与元数据的 `cause`（命令追溯标识）同名是**跨层**，且两个键都在同一个事件对象上，**必须改名**。
  - **给可空字段漏掉 `| None`** → 首次暂存时暂存槽是空的，`taken` 没有值可写。类型只写 `str` 就得靠"空串"这类**没写进契约的约定**兜底，而基线哈希的是声明——约定不写下来等于没有。
  - **共用取值域常量寄居在事件模块里** → 命令参数规格（S3）、快照字段（S4）都要用同一批类型域，寄居在 `events.py` 会让"事件声明"与"通用类型域"两件事纠缠不清。挪到 `contracts/types.py`。

### S9 · 命令通道（phase 门禁 + 三段生命周期）

- **目标**：命令进得来、判得准、被拒也有事件。

  - [ ] 三段生命周期：`command:received`（**出队执行前**发）→ `command:accepted` / `command:rejected`

- **验证方案**

  3. 测试：拒绝事件的 `args` 与原命令**完全一致**（架构 §7.2：缺参数 → 变体"能重放但结果不对"）。

- **提交**：`新功能：新增内核命令通道与生命周期状态机`
- **常见坑**

  - **被拒的命令也占帧内序号** → 序号只对被接受的命令编号，被拒的不占号。

### S10 · 合并防抖与配额

- **目标**：连续同因拒绝不刷屏；配额超限有事件、有限额、不顺延。
- **任务**
  - [ ] 同因拒绝合并：键 = `(phase, 命令类型, 拒绝原因)`；`received` 与 `rejected` **成对合并、计数一致**；`mergedCount` 起始值 = 1；phase 变化或 `resume` 后重置计数
  - [ ] 配额做成**内核构造参数**：轮次上限 **8** / 命令数上限 **100**（实时局默认）；回放宿主注入大得多的上限
  - [ ] 两个计数器**按帧累计**（每帧开始清零，**不是按单轮**）；`tick` 自身不计入命令数
  - [ ] 超限判定发生在"取队执行"**之前**；丢弃剩余命令并补发 `command:rejected`（`quota_exceeded`），**逐条计入合并计数**，**不跨帧顺延**
  - [ ] 两类配额超限统一用 `kernel:quota-exceeded`（靠负载里的配额名区分）；`kernel:error` **只留给订阅者异常**
- **涉及文件**：`src/tetris_kernel/kernel/quota.py` · `src/tetris_kernel/kernel/core.py`
- **验证方案**
  1. 测试：同一 phase 下连续 10 条同因拒绝 → **只发 1 组** `received`/`rejected`，`mergedCount` = 10。
  2. 测试：phase 变化后再次同因拒绝 → **重新发首条**（计数重置）。
  3. 测试：`received` 与 `rejected` 的 `mergedCount` **相等**。
  4. 测试：命令数超限 → 剩余命令被拒（`quota_exceeded`）+ 发出 `kernel:quota-exceeded`；**下一帧计数清零**（不顺延）。
  5. 测试：轮次超限 → 同样走 `kernel:quota-exceeded`，配额名区分开。
  6. 测试：`kernel:error` 在本阶段**不被使用**（只有订阅者抛错才发）。
- **完成判据**：六条验证全过。
- **提交**：`新功能：新增同因拒绝合并与命令配额限制`
- **常见坑**
  - **"没有事件"当作合并结果** → 形式必须是"一条事件承载 N 次拒绝"，否则事件完备性检查会误判成事件缺失（ADR-038）。
  - **配额按单轮累计** → 8 × 100 = 800 条/帧，上限形同虚设（ADR-040）。
  - **配额上限写死成常量** → 回放宿主会被限流丢命令，违反 B-6（录像不允许丢命令）。**必须是构造参数。**

### S11 · 总线（信封 / 序号 / 订阅 / 优先级 / 隔离）

- **目标**：事件有唯一时间轴；订阅者抛错不影响别人。
- **任务**

  - [ ] 待发布队列：分发期间产生的自产事件（`log:entry` / `metric:sampled` / `achievement:unlocked`）延后到分发结束后 FIFO 发出
  - [ ] 环形历史缓冲最小版（最近 N 条）；区间查询与时间旅行留 M2
  - [ ] **不提供 `bus.view()`**（ADR-021）

  3. 测试：通配订阅收到 `piece:*` 全部事件、全局订阅收到全部事件、精确订阅只收一种。

  5. 测试：注入必然抛错的订阅者 → 产生 `kernel:error`，**其余订阅者事件一条不少**，总线继续分发。
  6. 测试：`ctx.view()` 在分发期间返回**同一份**状态（所有订阅者看到一致快照）。
  7. 测试：未知事件类型 → 静默丢弃或记 trace，**不中断分发**。
- **完成判据**：七条验证全过。
- **提交**：`新功能：新增事件总线的信封、订阅与异常隔离`

### S12 · 帧模型（五步 / 帧号语义 / 轮次）

## 6. Git 策略

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（如 S17 的两次提交），拆开提。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚**。

- **破坏性改动**在类型后加感叹号（`新功能!：…`）——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - S17 冻结基线 = 破坏性（此后改契约就是 major）→ `新功能!：…`。
  - 其余阶段不破坏既有契约 → 不加感叹号。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S17 之后慎用 reset**：`contracts/` 基线一旦冻结，回退就等于放弃 v1，必须重走清单流程并写明理由。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 B 段（契约）提交行为代码 | 契约会被实现反向塑形，签名晚于实现 = 必被塑形（ADR-061） |
