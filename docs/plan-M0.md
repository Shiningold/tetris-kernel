### 1.2 四段结构

| 段 | 阶段 | 批次 | 性质 | 为什么这样排 |
| --- | --- | --- | --- | --- |
| **A 基础设施** | S0–S1 | —（已归档） | 只出壳，不出行为 | 没有壳就装不了依赖；`lint-imports` 的四条契约**第一次真跑起来**就在这里 |
| **B 契约面** | S2–S6 | —（已归档） | 只写声明，不写行为 | 契约 v1 一旦冻结就是 major 变更。**声明必须在实现之前定死**，否则被实现反向塑形（ADR-061） |
| **C 行为面** | S7–S14 | A · B · C | 写实现，不改声明 | 行为阶段发现声明缺字段 = 撞基线，必须走显式更新流程，不能顺手改 |
| **D 验证与冻结** | S15–S18 | C · D · E | 验、采数、冻结、收尾 | 冻结基线**收尾才生成**——太早生成会反复失效，成橡皮图章（ADR-019） |

> **C 段跨 A/B/C 三个批次**不是打乱四段结构：C 段只是"不写实现"的那一段，**排期上**它被切成三批，因为 S13 只依赖已冻结的 `contracts/`（可以提前开工），而 S9–S12 共用 `kernel/core.py`（必须串行）。**四段结构管"做什么"，批次管"什么时候一起做"。**

### 1.3 每阶段的硬约束（**贯穿全部阶段**）

| # | 约束 |
| --- | --- |
| 1 | **一次提交 = 一个阶段（或阶段内一个逻辑改动）**；格式化与逻辑改动分开提交 |
| 2 | **不在本阶段做别的阶段的事**——尤其 B 段不写行为、C 段不改声明 |
| 3 | 每阶段结束时，**质量门必须全绿**（见 §5.1），否则不进入下一阶段 |
| 4 | 发现上游设计错误 → **回退到划错边界的那个阶段**修正，不在当前阶段打补丁（需求 §12「门与回退」） |
| 5 | 每个阶段跑完立刻更新本文件 §3 状态表与该阶段的任务框 |
| 6 | **并行写手的文件归属必须互斥**——同一批次内一个文件只能属于一个写手；重叠就把两个阶段拆到不同批次（或交给同一个写手串行做） |
| 7 | **包级导出与状态文档归集成者**——`*/__init__.py` · `PROGRESS.md` · `ai_docs/**` · `docs/**` · `README.md` 由集成者统一收口，子代理不碰 |
| 8 | **并行写手只交工作区改动，不自己提交**——同一分支上并行提交会撞 git 索引（索引是单一共享资源）；提交由集成者按阶段串行切分 |

### 1.4 批次编排（并行写手 + 审查搭车）

> **位置说明**：本节是 §1 的子节（排在 §1.3 之后），因为它讲的是**总体路线的排期方式**，不是某个阶段的细则。

**为什么改**：S7–S18 一共 12 个阶段，其中大半**互不相干**——S13 只依赖已冻结的 `contracts/`，S11 只依赖 `contracts/`，S16 只依赖"内核能跑起来"。串行做等于把"等文件写完"的时间白白花掉。本节把 12 个阶段重排成 **5 个批次**，规定三件事：**谁和谁能同时写**（文件归属）、**跨写手的东西怎么对齐**（接口先验定）、**被审查的批次和下一批怎么并存**（审查搭车）。

### 1.4.2 文件归属（并行安全的前提）

三条规则：

1. **一个文件在同一批次内只能属于一个写手**。并行安全性来自"文件归属互斥"，不是来自"小心避开"。
2. **包级 `__init__.py` 不属于任何写手**——多个写手都要往里加导出，混写必冲突。导出面由**集成者**在批次落地时统一收口（参照 `contracts/__init__.py` 的 `__all__` 一致性测试）。
3. **共享设施按批次归属**：`tests/conftest.py` 归 C2（S15 那一批），`tests/baseline/**` 归 D2（S17 那一批）；**其他批次不碰**。批次 A / B 的测试文件必须自给自足（不依赖 `conftest.py` 的 fixture）。

### 1.4.3 集成者 vs 子代理的职责边界

| 事项 | 集成者 | 子代理（写手） |
| --- | --- | --- |
| 阶段内的模块实现 | — | ✅ 只写自己那一格文件 |
| 阶段内的测试文件 | — | ✅ 只写自己那一格测试文件 |
| 包级 `*/__init__.py` 的导出面 | ✅ 批次集成时统一收口 | ❌ 不碰 |
| `tests/conftest.py` · `tests/baseline/**` | ✅ 按批次归属（C2 / D2） | 按批次归属，其他批次不碰 |
| `PROGRESS.md` · `ai_docs/**` · `docs/**` · `README.md` | ✅ 每批次落地时追加 | ❌ 不碰 |
| 阶段提交 | ✅ 按"一次提交 = 一个阶段"串行切分并落笔 | 只交工作区改动 |
| 五道门 | ✅ 批次集成后统一跑一遍 | 交付前跑自己范围内的 |
| 审查修正回合 | ✅ 逐条核实后修正 | ❌ 审查报告不是可靠清单 |

**为什么这些文件归集成者**：要么被多个写手需要（`__init__.py` 的导出面），要么是"状态快照"类文档（多方并行写必然互相覆盖）。把这两类挪出写手的地盘，是并行不打架的**前提条件**，不是分工偏好。

### 1.4.4 跨阶段接口先验定（并行写手能同时开工的前提）

并行写手不能靠"等对方写完"才能开工。所以凡是**一个写手要用另一个写手产出的东西**，那个东西的**签名必须先在本文件写死**，谁实现都得照它来。

| 约定项 | 签名 / 形态 | 产出方 | 消费方 |
| --- | --- | --- | --- |
| 指纹函数 | `blake2b_hex(payload: bytes) -> str`（blake2b / 16 字节 / 小写 hex）· `tlv_digest(items: tuple[tuple[str, bytes], ...]) -> str` | S7（`kernel/fingerprint.py`） | S8（结构指纹 / 扩展指纹）· S17（工具层另有一份，算法一致） |
| 随机源状态 | 扁平化 `(version, *state)`（626 个 int）；导出时 `gauss_next` 非 `None` 即报错 | S7 | S8（`rngState` 填充）· S15（存档往返） |
| 内核对外操作面 | `execute(command) -> tuple[draft, ...]` · `advance_frame() -> tuple[draft, ...]`（草稿**不含**全局序号） | S9 / S12（`kernel/core.py`） | S14（宿主装配）· S11（总线只吃草稿，不反向调内核） |
| 总线对外操作面 | `publish(draft) -> None`（分配全局序号）· `subscribe(pattern, callback, priority)` | S11 | S14（宿主订阅）· S15（G0-5） |
| 规则集对外操作面 | 8 条签名（`contracts/rules.py` 已冻结） | S13 | S12（帧模型调用）· S14（装配注入） |

**偏离怎么办**：若 A1 实现了与上表不一致的签名，A2 的测试会**红**（这正是要的红）——修正由集成者裁决，**不许子代理单方面改接口**。接口要改，先改本文件。

### 1.4.5 「审查—分支—搭车」工作流

**目标流程**：写完一批 → 交另一个对话审查；审查期间另开分支写关联不大的下一批；审查结束交回 → 本会话逐条核实后修正。

```
feature/batch-a ── A1' A2' A3'          批次 A 的三笔阶段提交（各阶段一次提交）
      │
      ├─ 审查报告：tests/ocr/batch-a-review.md
      │  修正回合：修复提交**追加在 feature/batch-a 上**
      │
      └── feature/batch-b ── B1' B2'    审查 A 期间在新分支上写批次 B
             │                        ← 分支点 = A 的落笔提交（不是 master）
             └─ 审查报告：tests/ocr/batch-b-review.md
      │
      └── feature/batch-c ── C1' C2'    （分支点 = B 的落笔提交）
      │
      └── feature/batch-d ── D1' D2'
      │
      └── feature/batch-e ── E1'
```

> **图上是链，git 上也是链**：每个批次分支都从前一个批次的落笔提交起，**不回到 master**。这样"审查 A 期间在 B 分支上写 B"成立——B 能直接用上 A 的产物；A 的修正落地后要 merge 进 B 分支（规则 3）。

| # | 规则 | 理由 |
| --- | --- | --- |
| 1 | **分支命名** `feature/batch-<字母>`（A–E）；审查修正在**同一分支**上追加提交，不另开分支 | 报告要能对应到被审的那几笔提交 |
| 2 | **分支点**：批次 N+1 从**批次 N 的落笔提交**起（不是从 master 起） | 下一批能直接用上上一批的产物 |
| 3 | 批次 N 的修正提交落地后，必须 **merge 进批次 N+1 的分支**，再合并 N+1 | 否则下一批缺修正，基线与冻结面会错位 |
| 4 | **搭车边界**：下一批**只加不改**——不得修改正在被审查的批次已提交的任何文件；发现该改的，记进 `ai_docs`，等审查回合处理 | 修正回合与新批次同改一个文件必然互相覆盖 |
| 5 | 下一批**不得改** §1.4.4 的接口约定 | 那会同时打断被审查批次和下一批两边 |
| 6 | 审查产物落 `tests/ocr/batch-<字母>-review.md`（与既有 `tests/ocr/S*-review.md` 同目录同格式），**随修复提交入库留证** | 报告留在聊天里就等于没审 |
| 7 | 修正回合**逐条核实**：报告本身不是可靠清单（S2–S6 汇总复核的教训——报告自陈计数有误、建议要复核）。成立项在原批次分支上修正，**修正提交单独一笔**（`修复：按 batch-a 审查报告修订…`），不与新功能混提 | 照单全收会把报告的错误也改进去 |
| 8 | 批次内各阶段提交**分别保留**；合并批次分支用 `--no-ff` 保留批次边界 | 一次提交 = 一个阶段这条不能被批次合并抹掉 |
| 9 | **集成者收口时机**：每批次落地时统一补包级导出、更新 `PROGRESS.md` 与当日 `ai_docs`、更新本文件 §3 状态表——**在合并之前**做 | 散到各写手提交里会互相覆盖，且提交类型会混 |

## 2. 阶段通用模板

每个阶段按同一套结构写，字段含义固定：

| 字段 | 含义 |
| --- | --- |
| **目标** | 这一阶段结束时世界是什么样（一句话） |
| **任务** | 可勾选的动作清单，粒度 = 一次提交或一次小改动 |
| **涉及文件** | 本阶段允许触碰的文件（**清单外的文件不许动**） |
| **批次 / 写手 / 文件归属** | 本阶段在哪个批次、由哪个写手做、独占哪些文件（并行安全的前提，见 §1.4.2） |
| **验证方案** | 跑什么命令、看什么结果、什么算过 |
| **完成判据** | 勾完任务的充分条件（与验证方案互相印证） |
| **提交** | 建议的提交标题（`类型：主题`）+ 该提交应包含的文件 |
| **常见坑** | 这一阶段最容易犯的错，来自红线与 ADR |

  - **`args` 允许浮点** → JSON 里 `1.0` 与 `1` 不可区分，重放拿到不同参数（B-7 / ADR-025）。注意 **`extensions` 允许浮点，口径不同是对的**：`args` 参与重放，`extensions` 不参与。
  - 把"旋转无合法落点"写进拒绝原因 → 它**不在列**：命令仍被接受，另发受阻事件（ADR-043）。
  - **只照抄需求 §8.2 的「可被拒绝的情形」列** → 那一列是按命令列的散文，**漏了三条跨切规则**（门禁 / 配额 / 参数）。只抄列的话，`moveLeft` 的声明里不会有 `paused`，实现期就会出现"暂停期间命令照样执行"。
  - **参数类型复制字面量** → `tuple[int, ...]` 这个形状原先在 `types.py` 的 `ARGS_VALUE` 联合与 `events.py` 的字段声明里各写了一遍，两处会静默分叉。已补 `types.INT_TUPLE` 并全部改为引用（架构 §4.4 末条）。
  - **参数类型不在 `ARGS_VALUE` 取值域内** → 两处各写一份，改动时基线显示全绿而实际已分叉。已写成断言（`test_command_arg_types_within_args_value_domain`）。
  - **文法规则与自家类型串打架** → 规则写着"`None` 只能末位"，而三个取值域都不满足；**S6 照规则写解析器会把合规声明判成"不合规"**。文法表是解析器的规格书，**规则与实例必须同时回验**（S2 的 M1 只修了一半）。
  - **门禁归属靠"从拒绝原因反推"** → 反推的输入还是人手写的字面量，漏写时安静地失效。**必填字段 + 派生**才是构造期就能拦住的形态。
  - **取值域当成"当前用到的集合"去收窄** → 取值域是**通道的契约**；`ARGS_VALUE` 里的 `str` / `bool` 在 v1 没被用到是**有意的余量**，收窄等于给未来的变体命令埋一次 major 变更。

- **落定的判断**
  - **类型文法补形态 10（只读序列 `Sequence[T]`）**：架构 §7.3.1 的签名表原文写的就是 `Sequence[Sequence[int]]`，而内核内部棋盘是可变 `list[list[int]]`（架构 §7.1）——写成 `tuple[tuple[int, ...], ...]` 会逼内核在**逐方块调用的热路径上**每次深拷贝一份棋盘。形态 10 表达"只读视图"，取值域只有 `types.BOARD_VIEW` 与 `Sequence[ClearGroup]` 两条串。
  - **命名结构注册表从 `snapshot.py` 挪到新模块 `structures.py`**：注册表是**类型文法层面**的东西（形态 9 的名单），快照 / 放置 / 规则三处共用，寄居在快照模块是历史巧合。成员表**一律从声明推导**（`FieldSpec` 表或 dataclass 注解），**不另抄一份**。
  - **T-Spin 分类挂在 `ClearGroup.classification` 上，而不是给 `score_clear` 加参数**：冻结的签名表没有给分类留位置，而计分模块看不见分类就没法算 T-Spin 的分值（FR-4.6）。加参数就是改冻结签名（要走 major 变更），挂组上则一行签名不动。内核只做**搬运**，不重新判定。
  - **`PlacementClass` 装两样**：`tSpin`（T-Spin 标记）+ `classKey`（计分类别键，与事件 `board:lines-cleared.classKey` 同名同义）。事件那两个字段同源，计分模块也按 `classKey` 查表。**两者的取值域由规则集定义，契约只声明类型**——换规则集就换词汇，钉死会把变体挡在门外。
  - **`ScoreState` 用快照那套计分字段名**（`score` / `lines` / `combo` / `b2b` / `level`）：同一套命名体系，跨面改一个名字会立刻露馅（架构 §4.4 末条）。
  - **两处 `axis` 是两套词汇**：`RuleContext.axis` 是重力方向（变体维度，契约层钉死），`ClearGroup.axis` 是"这组被消的是行还是列"（`row` / `column`）。同名不同义要在 docstring 里写死，别让实现期混用。
- **常见坑**
  - **签名晚于实现** → `rules/` 自 M0 进冻结区，标准规则 M1 就要实现，签名晚于实现必被实现反向塑形，补维度即改冻结区。
  - **形状表 / 踢墙表不带轴维度** → M4-A5 要求表随重力方向变换，而表又不能由内核变换（内核不做变换）——接口不带轴就选不出表。
  - **顺手加"冷却 / 防抖动"维度** → 那是输入适配器的节流或插件自己的策略，**内核与规则集都不需要知道**。加了就是"补维度"，正是本阶段要避免的。
  - **把"分类无处安放"当成改签名的理由** → `score_clear` 的参数表是冻结签名；解法是让分类搭消行组的便车（`ClearGroup.classification`），不是动签名。
  - **命名结构注册表寄居在某个业务模块** → 它是文法层面的清单，规则侧结构一多就得从快照模块里往外搬；S5 直接新建 `structures.py`。
  - **只声明规则签名、不把新类型串接进文法回验** → 新形态（形态 10）与新类型串不进回验，就是"看着在基线里、实际没被哈希"的失效模式（S3 的教训）。

### S7 · 随机源与时间源

- **目标**：内核随机源可播种、可复现、可审计；内核不读墙钟。
- **任务**
  - [ ] `kernel/rng.py`：可播种随机源，**只用 `random()` 与 `getrandbits()` 两个原语**（ADR-010）
  - [ ] 7-bag 洗牌自己实现 Fisher-Yates（不用 `shuffle` / `sample` / `choice` / `randrange`）
  - [ ] `getstate()` / `setstate()` 往返可复现（ADR-011）
  - [ ] 每次取值产出 `rng:next` 草稿（随机值 + 序号 + **状态指纹短哈希**，**不含完整 MT 状态**，ADR-060）

  - [ ] 时间源可注入（真实 / 虚拟），内核侧只认逻辑帧
- **涉及文件**：`src/tetris_kernel/kernel/rng.py` · `src/tetris_kernel/kernel/fingerprint.py` · `src/tetris_kernel/host/clock.py` · `tests/test_rng.py`
- **批次 / 写手 / 文件归属**：**批次 A** · 写手 **A1** · 独占文件 `kernel/rng.py` · `kernel/fingerprint.py` · `host/clock.py` · 测试 `tests/test_rng.py`。包级 `kernel/__init__.py` 的导出由**集成者**收口。批次内**先交 `kernel/fingerprint.py`**（A2 等它才能自测）。
- **开工前定下的三处口径**（2026-10-24 核实；S7 按此实现）
  1. **`rngState` 用扁平化编码**：`getstate()` 实际返回三元组 `(version:int, state:tuple[int, ...]（625 个）, gauss_next:None | float)`，**塞不进**快照契约声明的 `tuple[int, ...]`。但**只用 `random()` 与 `getrandbits()` 两个原语时 `gauss_next` 恒为 `None`**（已实测），所以状态进出用**扁平化的 `(version, *state)`**（626 个 int），与契约天然吻合——**契约一个字不用改，不撞基线**。导出时若 `gauss_next` 不是 `None` 就**报错**（不报错就等于静默丢状态），导入时复原成 `(version, tuple(state[1:]), None)`。
  2. **时间源落 `host/clock.py`，不进 `kernel/`**：架构 §5.3 明说"内核侧只认逻辑帧"、**宿主的帧循环时钟必须可注入**，而纯净度脚本**禁止 `kernel/` 与 `rules/` 出现 `time.monotonic()`**——真实时钟放不进内核。**真实 / 虚拟是同一接口的两种实现，拆到两层就是两处维护同一对签名**，所以两者一起放 `host/`。`kernel/` 里**不放时钟接口**（内核不用它，放进去是没人用的抽象）。
  3. **指纹工具落 `kernel/fingerprint.py`**：`tools/_toolkit.py` 的 `blake2b_hex` 引不到（`tools/` 不随包发布，`src/` 也不该引脚本层），TLV + blake2b 的实现在内核侧另起一份，**算法与摘要长度与工具层保持一致**（blake2b / 16 字节 / hex）。S7 的状态指纹与 S8 的 `structureFingerprint` / `extensionFingerprint` 共用它。
  - 另定两条：7-bag 的 Fisher-Yates 用 `getrandbits()` + **拒绝采样**取下标（`randrange` 是第三种取法，同样不用）；**状态指纹取"该次取值之后"的状态**（草稿与状态同一时刻，`seq` 与指纹一一对应）。
  - **载荷 dataclass 留在 kernel 内部**——`EventDraft` 的正式形态归 S9 / S11，S7 不提前实现。
- **验证方案**
  1. 测试：同种子两次取 1000 个值，序列**完全相同**；不同种子序列不同。
  2. 测试：`getstate()` → `setstate()` 后序列接得上（存档恢复路径的前置）。
  3. 测试：状态指纹**跨进程稳定**（起一个子进程算同一状态的指纹，比对相等）——这一条专门防 `hash()` 随机化。
  4. 机检：`tools/check_kernel_purity.py` 绿——`kernel/` 内无模块级 `random.*`、无未注入的 `random.Random()`。
  5. 机检：`rng:next` 负载**不含** 625 元素的状态数组（断言负载长度是常数级）。
  6. 测试：**扁平化状态能无损还原**——`export()` → `import()` 往返后序列接得上，且 `gauss_next` 非 `None` 时导出**报错**（这条是开工前新加的：守卫要能触发）。
- **完成判据**：六条验证全过。
- **提交**：`新功能：新增可播种随机源与 rng 事件产出`
- **常见坑**
  - **用 `random.shuffle`** → 它在 CPython 版本间变过，升级 Python 会让全部旧录像集体作废（ADR-010）。
  - **内核随机源被外部取用** → FR-5.3：内核随机源**只服务内核**，AI 等外部系统必须自建实例并显式播种。
  - **`rng:next` 负载带完整 MT 状态** → 一局几百方块就是几 MB 常驻负载（ADR-060）。
  - **把 `getstate()` 的三元组直接塞进 `rngState`** → 类型对不上（契约是 `tuple[int, ...]`），要么撞基线要么静默丢状态——**扁平化**（口径 1）。
  - **把真实时钟写进 `kernel/`** → 纯净度脚本直接报红（架构 §5.3 禁读墙钟）；时钟落 `host/clock.py`（口径 2）。

### S12 · 帧模型（五步 / 帧号语义 / 轮次）

- **目标**：一帧内的执行顺序确定；命令入队不在本轮生效；帧推进不被提前掐断。
- **任务**
  - [ ] `kernel/frame.py`：帧号推进与推进许可**分离**——帧号 +1、帧内序号归零在 tick **出队时**；推进许可在 tick **被接受**时授予

  - [ ] 装配层**完整消费**步骤序列，**不得提前 break**（用 `try/finally` 保证耗尽）
  - [ ] `reset` 归零帧号、帧内序号与版本号
- **涉及文件**：`src/tetris_kernel/kernel/frame.py` · `src/tetris_kernel/kernel/core.py` · `tests/test_frame_model.py`

## 6. Git 策略

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（如 S17 的两次提交），拆开提。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。
- **并行批次里的提交由集成者串行切分**：写手只交工作区改动（并行 `git add` 会互相覆盖索引），集成者按"一次提交 = 一个阶段"逐笔 `git add -- <该写手的文件>` 后提交。**批次合并用 `--no-ff`**，保留批次边界。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚**。

- **破坏性改动**在类型后加感叹号（`新功能!：…`）——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - S17 冻结基线 = 破坏性（此后改契约就是 major）→ `新功能!：…`。
  - 其余阶段不破坏既有契约 → 不加感叹号。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S17 之后慎用 reset**：`contracts/` 基线一旦冻结，回退就等于放弃 v1，必须重走清单流程并写明理由。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 B 段（契约）提交行为代码 | 契约会被实现反向塑形，签名晚于实现 = 必被塑形（ADR-061） |
| 3 | 在 C 段（行为）顺手改契约声明 | 撞基线；必须走显式更新流程并写明理由 |
| 4 | 阶段内顺手做"别的阶段的事" | M1–M4 的需求提前实现会把还没定稿的东西锁死 |
| 5 | 用 `git commit -a` 批量提 | 容易把不该提的文件带进去 |
| 6 | 并行写手在同一分支上并行提交 | git 索引是**单一共享资源**，两个写手同时 `git add` 会互相覆盖；写手只交工作区改动，提交由集成者串行切分 |
| 7 | 两个写手改同一个文件 | 文件归属互斥是并行安全的**前提**；重叠就把两个阶段拆到不同批次，或交给同一个写手串行做，不靠"小心避开" |
| 8 | 审查期间写下一批时顺手改被审查批次的文件 | 修正回合与新批次同改一个文件必然互相覆盖；下一批**只加不改**，接口要改先改本文件 §1.4.4 |
| 9 | 子代理单方面改跨写手接口 | 并行写手之间没有协商通道，一方改签名另一方必然踩空；接口变更先改本文件，由集成者裁决 |
