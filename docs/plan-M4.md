> **M4 的一句话**：**换掉整套玩法，内核一个字节都没动；而且人真的能玩、AI 真的能替人玩。**
> **M4 与 M0–M3 最大的不同**：**M4 是第一个"冻结区零改动"的里程碑**——M1 动过 `rules/` · M2 解冻过 `kernel/core.py` · M3 解冻过 `kernel/core.py` + `kernel/commands.py`，**M4 一个都不许动**。**这一条既是纪律，也是本计划所有阶段的验收基准。**
> **M4 的门形态**：M0–M2 的门是"功能对不对" · M3 的门是"接进来有没有改别人的东西" · **M4 的门是"换掉玩法还能玩、内核没动"**——所以**一半是差异断言**（冻结区哈希 · git 变更清单）**一半是"玩得起来"**。

> **串行链不变**：M4 的阶段顺序是**依赖顺序**，不是排期单位。批次只是把**互不相干**的阶段放到一起并行。
> **M4 的批次 C 有一处"导出面"冲突**：S6 与 S7 都要往 `adapters/__init__.py` 加导出 → **两个适配器写手都不许改 `adapters/__init__.py`**，**导出面由集成者在 S8 统一加**（与 M3 批次 B 的"发现侧拆到独立文件"是同款思路：**让文件归属彻底互斥**）。
> **M4 的批次 B 是 M3 之后第一次真正并行**：两个变体分属两条扩展路径，**文件归属零重叠**，**互不依赖**。

### 1.2 五段结构

| 段 | 阶段 | 批次 | 性质 | 为什么这样排 |
| --- | --- | --- | --- | --- |
| **A 接线面与基线** | S0–S2 | A | **只增不改 + 一次显式刷新** | M4 的契约面改动**只有一处**（变体附带系统的登记 = 新增条目）——**声明先行、刷基线在后**（M2 / M3 的同款教训：新增键在刷基线之前**没有牙齿**）。**接线面先行**，因为两个变体都要经它登记 |
| **B 两个变体** | S3–S4 | B | **两条不同的扩展路径** | **变体 A 换规则集 · 变体 B 挂系统**——**做两条是为了证明"路径成立"，不是为了凑数量**。**两者都受 M4-D1 约束**（只许新增文件）→ **接线面必须先落地**（S1），否则新变体要改既有文件登记 |
| **C 实时宿主与渲染输入** | S5–S8 | C | **两个适配器并行 + 宿主串行** | 变体先落地，**渲染器才能带着变体 A 的规则集画方块**（渲染器按规则集算活动方块格子）→ **B 在 C 之前**。**降级控制器的喂帧接线**（ADR-082 遗留）在实时宿主里才有地方接 |
| **D AI 与录像升版** | S9–S10 | D | **一个系统 + 一次格式升版** | **录像升版要等"变体局真的能被录能回放"**（D 在 C 与 B 之后）。**AI 独立于实时宿主**（AI 可以无头跑）→ **可与 S10 并行**，但**同批次串行更省心** |
| **E 验证与收尾** | S11–S13 | E | **门 + 性能 + 同步** | **门判据写在实现稳定之后**（先写门再写实现 = 门会被实现反向塑形 · ADR-061 的原话）；**性能复测要在全部新东西落地之后**（**AI 的决策耗时与渲染 / 输入的记账口径要在这一阶段定下来**） |

> **批次 A 的 `host/assembly.py` 与 `host/cli.py` 与批次 C 的同名字段重叠** → **C 必须在 A 合并进分支链之后开始**（链式分支点：下一批从上一批的落笔提交起，不回 `master`）。
> **批次 C 的 `adapters/__init__.py` 归集成者**（S8）——**两个适配器写手都不许动它**（§1.1 的说明）。
> **批次 D 的 `host/cli.py` 与批次 C 重叠** → 同理，**D 在 C 之后**。
> **批次 B 的两个变体互不依赖**（一个换规则集、一个挂系统）→ **可以真并行**（M3 批次 C 的同款前提：文件归属零重叠 + 无隐藏依赖）。

### 1.4 并行写手纪律

沿用 M0 / M1 / M2 / M3 的纪律（plan-M3 §1.4）：

1. **文件归属互斥是并行安全的前提**——两个写手改同一个文件必然互相覆盖。
2. **并行写手之间没有协商通道**——接口变更**先改本文件 §1.3 的文件归属表**，由集成者裁决。
3. **并行写手只交工作区改动**，**不并行 `git add`**（git 索引是单一共享资源）——由集成者串行切分提交。
4. **写手交付前先跑自己范围内的反向验证**；**集成者在批次集成后统一复跑一遍**受影响的几条。
5. **基线一律由集成者生成**（M1 的批次 D 纪律）——写手刷基线 = 橡皮图章。

> **M4 追加第六条**：**写手不许顺手"帮别人改一行"**——尤其是**不许动 `kernel/` 与 `rules/`**（M4-D1）。**"帮"的那一行会让 `G4-1` 的 git 变更清单当场判红**，而且**基线刷不回来**（冻结区基线 M4 是"不刷"的）。

### 5.4 major 变更的处置流程

M4 的 major 变更**预算是 1 次**（spec §3.4 的 **M4-C1**）——**计划内一条都不花**（M4 的契约面只新增条目）。流程统一为四步：

1. **改声明 / 改实现**（工作区改动，**不提交基线刷新**）。
2. **显式刷新**：`--update-baseline --reason "<理由>"` / `--update-expected --reason "<理由>"`——**不带 `--reason` 一律拒绝且不落盘**（M0 修好的门，M1 / M2 / M3 沿用，M4 沿用**且不得放宽**）。
3. **提交信息写明理由**——**基线刷新的提交**正文必须写清改了什么、为什么。
4. **反向验证**：喂一份改坏的临时基线给工具，断言退出码非 0。

| # | 变更 | 撞红的东西 | 落笔阶段 | 理由该写什么 |
| --- | --- | --- | --- | --- |
| — | **登记变体附带系统**（**不是 major 变更**） | 契约基线的**新增条目** | S2 | "M4 新增变体附带系统的声明（只增不改，既有键零变化）" |
| — | **录像格式 `v1 → v2`**（**不在契约基线里**） | 录像文件格式 | S10 | "M4 给变体局加第五项比对（扩展指纹），录像格式升 v2；旧 v1 按无变体处理" |
| **M4-C1** | **预留**（若执行期发现不改既有键就做不到） | 契约基线**已有键的哈希变化** | 待定 | **动用前必须先回 spec §3.4 落定用途与理由** |
| — | **冻结区基线**（**M4 全程不刷**） | 冻结区内容哈希 | **无** | **M4-D1：不刷就是成绩** |
| — | **事件数基线**（**M4 不进默认装配 → 不变**） | 事件数基线 | **无** | **M4 的新系统不进默认装配** |

> **"顺手刷新"是明令禁止的**：契约 v1 已冻结，此后只增不改——**任何改动要么是"新增键"（绿），要么走 major 变更**。
> **M4-C1 动用前要先回 spec 落定**（plan-M3 的 R5 纪律）：**不许"顺手改回去"**，**不许"预算还在就随便花"**。
> **冻结区那一栏 M4 是空的**——**两个预算是分开的**（契约面 vs 冻结区）。

### 5.5 审查修订（M4 的代码审查）

> **占位**：M4 的代码审查在 M4 收尾后进行，**报告落 `tests/ocr/m4-review.md`**（M2 / M3 的先例：**报告随修订提交入库留证**）。**审查期间写下一批时"只加不改"**（批次 N 的修正落地后 merge 进批次 N+1 的分支再合并 N+1）。
>
> **M4 的审查要重点盯的三处**（M3 踩过的坑）：
> 1. **变体有没有偷偷改内核**（M4-D1）——**`git diff --name-status` 是判据**。
> 2. **期望值是不是手抄的**（自证被打破的老坑）。
> 3. **门自己有没有牙**（每道门都要先确认它咬得住）。

## 6. 提交序列

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（S2 的两份基线 · S8 的宿主与导出面），**拆开提**。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。
- **并行批次里的提交由集成者串行切分**：写手只交工作区改动（并行 `git add` 会互相覆盖索引），集成者按"一次提交 = 一个阶段"逐笔 `git add -- <该写手的文件>` 后提交。**批次合并用 `--no-ff`**，保留批次边界。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚 · 合并**。

- **破坏性改动**在类型后加感叹号——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - **变体接线面**（S1）= **破坏性**（宿主装配的既有调用方签名可能变）→ `新功能!：`。
  - **契约基线刷新**（S2）= **破坏性**（基线换了 = 比对基准换了）→ `新功能!：`。
  - **两个变体落地**（S3 / S4）= **不破坏既有调用方**（内核与规则集零改动）→ 不加感叹号。
  - **扩展槽回写**（S5）= **新增能力**，既有调用方不变 → 不加感叹号。
  - **渲染器 / 输入适配器**（S6 / S7）= **新增能力** → 不加感叹号。
  - **实时宿主与 `play` 真跑**（S8）= **破坏性**（`play` 的行为从"占位"变成"真跑"· 既有调用方会看到不同输出）→ `新功能!：`。
  - **AI 系统**（S9）= **新增能力** → 不加感叹号。
  - **录像格式 `v1 → v2`**（S10）= **破坏性**（旧消费方读不了新录像）→ `新功能!：`。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。**基线刷新的提交必须把理由写进正文**（与 `--reason` 一致）。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S2 之后慎用 reset**：契约基线一旦刷新，回退就等于放弃那次刷新——**要重走显式刷新流程并写明理由**（基线与代码对不上会一路红；**且 git 背书守卫会拦**）。
- **S8 之后慎用 reset**：实时宿主一旦上线，**`play` 的行为从占位变成真跑**——**回退要连调用方一起回退**。
- **S10 之后慎用 reset**：录像格式升版后，**旧录像仍能读**这条是**兼容承诺**——回退要连兼容处理一起回退。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 A 段（契约）提交行为代码 | 契约会被实现反向塑形（ADR-061） |
| 3 | 在 B / C / D 段（行为）顺手改契约声明 | 撞基线；必须走显式更新流程并写明理由 |
| 4 | 阶段内顺手做"别的阶段的事" | M4 之后的加成名单提前实现就把还没定稿的东西锁死 |
| 5 | 用 `git commit -a` 批量提 | 容易把不该提的文件带进去 |
| 6 | 并行写手在同一分支上并行提交 | git 索引是**单一共享资源**，两个写手同时 `git add` 会互相覆盖 |
| 7 | 两个写手改同一个文件 | 文件归属互斥是并行安全的**前提**；重叠就拆到不同批次，或交给同一个写手串行做 |
| 8 | 子代理单方面改跨写手接口 | 并行写手之间没有协商通道；**接口变更先改本文件 §1.3**，由集成者裁决 |
| 9 | **顺手刷新基线** | 基线是判据本身；**刷新必须带 `--reason`**（M0 修好的门） |
| 10 | **手改基线文件 / 期望清单** | 那是绕过显式刷新流程；**git 背书守卫会当场拦下** |
| 11 | **改 `kernel/` 或 `rules/` 的任何文件** | **M4-D1 的红线**——`G4-1` / `G4-6` 会当场判红。**M4 是第一个零破例的里程碑** |
| 12 | **"内核差一个能力"就加内核** | **M4 的立身之本**——回退到规则集或插件两个口子找解法 |
| 13 | **给 `writeCells` 加参数** | 改既有键 = major 变更；**变体自己算格子**（M4 的取舍 K1） |
| 14 | **渲染器去问内核要棋盘** | **FR-8.2 当场破**——"渲染可整体替换"这条承诺随之失效 |
| 15 | **把 DAS / ARR 的状态放进内核** | **手感参数归输入适配器**（ADR-044） |
| 16 | **让 AI 按耗时自适应搜索** | **同一录像在不同机器上重放出不同结果** → 破 AC-1 / NFR-1 |
| 17 | **在内核里按 `source` 分支** | **破 FR-8.5**（来源只作元数据透传） |
| 18 | **AI 直接改棋盘** | 破 N1 / N5（AI 是订阅者 + 命令源） |
| 19 | **录像格式升版时拒绝旧 v1** | **NFR-9：旧版本数据要被识别并给出明确处理策略**——v1 按"无变体"处理 |
| 20 | **维护一张手写的变体名单** | 名单一出现，变体接线就退化成"改一行代码"——**与 M3-D2 同源的病**（M4 走的是**显式登记表**，但**登记表也必须是唯一真相**，不许在别处再抄一份） |

## 7. 风险与应急

| # | 风险 | 触发信号 | 应急 |
| --- | --- | --- | --- |
| R1 | **"差一点点就能做"→ 改内核** | `G4-1` 红在"冻结区有改动"上 | **回到规则集或插件两个口子找解法**（§6.5 第 12 条）。**这不是"改断言放宽"，是"实现补齐"**——而 M4 的解法**从来不在内核里** |
| R2 | **渲染器偷偷问内核要棋盘** | `G4-3` / `G4-9` 红 | 查**是不是用了 `ctx.view()`**（架构 §4.1：渲染器不得用只读视图通道）· **画面必须能由事件重建** |
| R3 | **变体局"四项全等但结果不同"** | `G4-2` 红，且四项全绿 | 查**是不是拿结构指纹当扩展指纹**（两个哈希不是一回事）· 查**是不是回放时没装变体**（扩展槽空了 → 第五项必然不等） |
| R4 | **性能劣化** | 复测 P99 明显高于**同机同时段**的 M3 对照值 | 记为卡点写进 `PROGRESS.md`；**先分清是哪一项的成本**（变体 / 宿主 / AI）——**判定必须用同机同时段的配对 A/B** |
| R5 | **AI 的决策把帧预算吃穿** | P99 超预算，且分档显示 AI 档明显更高 | **不许按耗时自适应**（M4-D3）→ 只能**改固定预算**（更浅的搜索 / 更少的候选）——**这是策略变更，不是"让它跑快点"** |
| R6 | **录像升版让旧录像读不了** | 兼容用例红 | **v1 按"无变体"处理**（§6.5）——**不是拒绝** |
| R7 | **两个变体并行时互相踩文件** | 合并冲突 / 变更清单里有对方的文件 | 查**文件归属表**（§1.3）——**变体 A 与变体 B 的目录零重叠**，真有重叠就是写手越界 |
| R8 | **M4 撞出既有键的哈希变化** | 契约基线报"已有键的哈希变化" | **停下来**：先回 spec §3.4 落定 `M4-C1` 的用途与理由，再走显式刷新。**不许"顺手改回去"** |

> **风险处置的通用纪律**：**M4 遇到边界问题，回到划错边界的那个阶段修正，而不是在当前阶段打补丁**（需求 §12 的"门与回退"）。**回退不丢用例；允许重写批次。**

## 8. 完成定义（M4 收官判定）

1. **九道门 `G4-1`…`G4-9` 全过**，每道门有可复跑的测试**与反向用例**。
2. **至少两个变体可完整游玩，且内核文件差异为空**（`G4-1`）：冻结区逐文件哈希全等 **且** 变体的落地提交**只有新增文件**（`git diff --name-status` 每行都是 `A`）。
3. **变体局的回放校验多比一项**（`G4-2`）：扩展指纹 · **不等时能单独指认** · **旧 v1 录像仍能读** · **标准局四项语义不变**。
4. **实时宿主可玩**（`G4-3`）：终端渲染 + 键盘输入 + 多渲染器同挂 · **渲染器不碰内核**。
5. **DAS / ARR 可调且不改状态**（`G4-4`）。
6. **AI 与人类走同一命令通道**（`G4-5` · AC-6）· **内核不按 `source` 分支**。
7. **变体落在 `variants/` 独立目录**（`G4-6`）· **扩展槽与扩展指纹随变体状态变化**（`G4-8`）· **变体零污染**（`G4-9`）。
8. **契约面零变更**（`G4-7`）：事件 50 · 命令 17 · 拒绝原因 13 · 快照 22 · 规则签名 9 · **既有键的哈希一个都没变**。
9. **冻结区零改动**：`kernel/` + `rules/` **14 个文件逐字未变**——**M4 全程不刷冻结区基线**。
10. **基线到位**：契约基线 + 期望清单（**只新增条目**）· 冻结区（**14** 个文件 · **不刷**）· 事件数（**不刷**）· **`bus/` 独立基线零变化**；**两条 git 背书守卫生效**（ADR-077）。
11. **质量门全绿**，且 **M4 未新增 skip**。
12. **文档一致**：`docs/plan-M4.md` §3 状态表与提交历史对得上 · `docs/决策记录.md`（ADR-090 起）· `docs/需求与边界.md` §8.1 / §8.2 / §10 / §12 · `PROGRESS.md` 三段改写 · `ai_docs/` 当日条目（五件事齐）。
13. **范围没越界**：需求 §13 的八条**一件都没提前实现**——**无 tkinter 渲染器 · 无音频 · 无条件式写入 · 无更多变体 · 无联网对战**。
14. **批次全部收口**：五个批次**全部 `--no-ff` 合并进 `master`**、批次内各阶段提交**分别保留**。
