### 1.2 M6 的批次与分支

- **一条链**：`feature/m6-batch-a` → `b` → `c` → `d` → `e` → `f`。
- **每批一提交（或几笔）**，**阶段提交逐笔留在历史里**——要回滚就按阶段哈希回滚。
- **收官**：一批 `--no-ff` 合并进 `master` → **再回填哈希**（先合并、再回填）。

### 1.3 M6 为什么这么排（**三句**）

1. **先画出来，再接输入**——渲染器是纯函数式的（快照进、画面出），**最容易单测**；输入与事件循环最麻烦，放后面。
2. **先能看见，再能玩，最后能发**——每一步都有可验证的产出，**不攒到最后一起爆**。
3. **打包放最后**——`--windowed` 的坑要在**前面都稳了**之后才值得踩。

## 2. 阶段通用模板

每个阶段：**先写清判据 → 实现 → 机检 → 质量门 → 提交**。

- **判据先写**：门判据的机检用例**要在实现之前**把断言写出来（哪怕先红）。
- **不改的东西不许动**：内核 / 规则 / 契约 / 事件基线 / `TerminalRenderer` 的既有行为。
- **反向验证**：每阶段的机检都要**改坏一次看它红**，再**精确还原**。
- **提交**：一次一个逻辑改动；**格式化单独一笔**。

- 不许改内核 / 规则 / 契约 / 事件基线。

## 7. 风险与应急

- **事件循环与节拍打架** → `sleeper` 注入 + 输入队列（NFR-6-2 判）。
- **手感漂** → 输入逻辑整套复用 `KeyboardInput`。
- **`--windowed` 打包坑** → S5 真机冒烟，不靠推断。
- **范围蔓延**（想加音效 / 皮肤 / 设置）→ 记进「未决」，**不在 M6 做**。
