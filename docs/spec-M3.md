## 1. M3 目标与完成判定

### 1.1 一句话目标

**新增一个能力 = 新增一个文件；运行中装上一个系统、摘下一个系统，其余系统照常跑。** M3 结束时，仓库里有**一套可验证的扩展机制**：**统一的系统契约与机器可读声明** · **宿主层的系统注册表与运行时热插拔**（装 / 卸 / 重装）· **自动发现**（新系统只靠新增文件即被接上，**既有文件零改动**）· **两个零内核改动的示范系统**（成就 · 统计旋转次数）· **运行期换规则集的机制**（ADR-061）· **CLI 的落盘接线**（M2 遗留）——而且**除 `kernel/core.py` 的一个入口外，冻结区一个字节都没动**。

### 1.2 M3 兑现的六件事

| # | 兑现物 | 说明 |
| --- | --- | --- |
| 1 | **系统统一契约与声明面**（FR-9.1 / FR-9.2） | 每个系统有**同一套契约**：名称 · 版本 · 声明订阅的事件 · 声明发出的命令 · 安装 / 卸载生命周期。声明落在**公共叶子** `contracts/`（不进冻结区）· 声明进契约基线（**新增一个键类**，只增不改） |
| 2 | **系统注册表与运行时热插拔**（FR-9.1 · **AC-8**） | 宿主层持有系统表：**装上**（订阅接入 · 命令通道接通 · 发 `kernel:system:installed`）· **摘下**（退订 · **撤回命令通道** · 停止派发 · 发 `kernel:system:removed`）· **重装后事件流恢复**。**"摘下"必须连命令通道一起撤**——订阅退了但命令还能派出去，等于没摘 |
| 3 | **自动发现 = "新增能力 = 新增文件"的机器可验形式**（AC-3 · NFR-6） | 系统由**自带的声明 + 工厂**被宿主**扫描发现**，**不需要在既有文件里登记一行**。因此"新增一个统计旋转次数的系统"这件事**在 git 上表现为：若干个新增文件，既有文件零改动** |
| 4 | **两个零内核改动示范系统**（FR-9.3 · AC-3） | **成就系统**（`systems/achievements/`）——达成条件时发 `achievement:unlocked`（**契约里已登记**，不新增事件）· **统计旋转次数系统**（`systems/rotations/`）——订阅 `piece:rotated` 计数，产出经 sink 落盘。**两个都不碰内核** |
| 5 | **运行期换规则集**（ADR-061） | 新增命令 `switchRuleSet`（参数 `rule: str`）· 内核提供换规则集入口（**`kernel/core.py` · M3 唯一破例**）· **未知规则集被拒** · **局中切换被拒** · 切换后开局按新规则集跑 · 换规则集是**命令** → 进录像 → 重放时照样切 → 逐帧一致 |
| 6 | **CLI 落盘接线**（M2 遗留） | 三个可观测产物的落盘出口**接线点已就位但命令行没接**（PROGRESS 待办第一条）——M3 在这里定：`tetris sim` 增开关，**三个产物各有各的出口**（日志与指标追加 · 录像覆盖 · ADR-085） |

### 1.3 完成判定（DoD 摘要，全表见 §9）

1. M3 门判据（§9.1）`G3-1`…`G3-6` 全过，每道门有一个可复跑的测试，**每道门都有反向用例**（把实现打坏 → 必须变红）。
2. **新增能力 = 新增文件**：新增「统计旋转次数」系统后，**冻结区逐文件哈希全等** 且 **该系统的实现代码全部落在新增文件里**（`G3-1`）——**由 git 变更清单断言，不是靠人看一眼**。
3. **运行中卸载日志系统，其余系统不受影响；重新装载后事件流恢复**（`G3-2` · AC-8）。
4. **系统清单与依赖图**可机读、可生成文档（`G3-3` · FR-9.2）。
5. **成就系统**是零内核改动的示范（`G3-4` · FR-9.3）。
6. **运行期换规则集的机制**兑现：已登记规则集可切 · 未知规则集被拒 · 局中切换被拒（`G3-5`）。
7. **扩展零污染**：关掉 M3 新增的全部系统后，**内核逐帧指纹与全开时全等**（`G3-6`）——延续 M2 的 `G2-3` 精神。
8. **契约面只增不改**：事件 49 → **50**（新增 `kernel:rule-set-changed`）· 命令 16 → **17**（新增 `switchRuleSet`）· 拒绝原因 12 → **13**（新增 `unknown_rule_set`）· 快照仍 22 顶层字段；**既有键的哈希一个都没变**。
9. **冻结区只破例一次**：`kernel/core.py` 增换规则集入口（显式刷新 · 带理由）· **其余 13 个文件逐字未变** · **`rules/` 零变化**。
10. 五条静态检查全绿：`ruff check .` · `ruff format --check .` · `pyright` · `lint-imports` · `pytest`。
11. **范围没越界**：M4 的需求没有在 M3 里提前实现——**渲染器 · 输入适配器 · 实时宿主 · 变体实现**仍然不做（§4.2）。

## 2. 术语速查

沿用 `docs/需求与边界.md` §4，本文不重新定义。M3 额外需要记住的五个：

| 术语 | 在 M3 的含义 |
| --- | --- |
| **系统（system）** | 可插拔的功能模块（FR-9.1）——**M3 把它落成一份契约**：统一的名字、版本、订阅声明、命令声明、安装 / 卸载生命周期 |
| **系统声明（manifest）** | 一个系统的**机器可读自我介绍**：名字 · 版本 · 订阅哪些事件 · 发出哪些命令。**落在 `contracts/`（公共叶子）**，供 FR-9.2 的依赖图与文档生成使用 |
| **注册表（registry）** | 宿主层持有的**系统表**：谁装上了、谁没装、装卸的入口。**内核不知道它的存在**（N6） |
| **命令通道（command channel）** | 系统往内核派命令的通路。**卸载系统必须连它一起撤**——否则系统"人不在了，话还在说" |
| **自动发现** | 宿主**扫描系统目录**找出可用的系统（凭它们自带的声明），而不是在既有文件里维护一张手写名单。**这是"新增能力 = 新增文件"的机器可验形式** |

## 3. 输入 / 输出与对外接口

### 3.1 输入（M3 接受的东西）

| 输入 | 来源 | 约束 |
| --- | --- | --- |
| 种子 `seed: int` | 构造参数 | 不变 |
| 规则集标识 `rule: str` | 构造参数 / **新命令 `switchRuleSet`** | M3 的命令**按规则集标识切换**；标识必须**已在宿主侧登记** |
| 命令 `Command` | `execute(cmd)` | **M3 新增 1 条**（`switchRuleSet`）——其余 16 条不变 |
| **系统安装 / 卸载请求** | 宿主 API | **M3 新增**：按系统名装 / 摘；**运行中可调用**（AC-8） |
| **要装哪些系统** | 宿主装配参数 | M3 新增：一份**系统名列表**（名单来自**自动发现的清单**） |
| **sink** | 宿主装配注入 | 沿用 M2：三个产物**各有各的出口**（ADR-085） |
| 事件流 | 总线分发 | 不变；M3 的系统**都是普通订阅者**（M3-D3） |

### 3.2 输出（M3 产出的东西）

| 输出 | 形态 | 约束 |
| --- | --- | --- |
| **装卸事件** | `kernel:system:installed` / `kernel:system:removed` | **契约里已登记**（M0 就在册）→ **M3 不新增事件类型** |
| **换规则集事件** | `kernel:rule-set-changed` | **M3 新增 1 条**（新增键）· 负载：规则集标识 · 旧标识 |
| **成就事件** | `achievement:unlocked` | **契约里已登记** → 不新增 |
| **系统清单 / 依赖图** | 命令行输出 + 可机读结构 | 每个系统：名字 · 版本 · 订阅事件 · 发出命令（FR-9.2） |
| **落盘产物** | 三个文件（日志 · 指标 · 录像） | **各走各的 sink**（ADR-085）· 路径由宿主定 |

### 3.3 对外接口签名（M3 的契约变更）

M3 **新增四条声明，不改任何既有签名**：

```python
# contracts —— 公共叶子，不 import 任何东西
EVENT_TYPES: Mapping[str, EventSpec]   # 49 条 → **50 条**（新增 `kernel:rule-set-changed`）
COMMAND_TYPES: Mapping[str, CommandSpec]  # 16 条 → **17 条**（新增 `switchRuleSet`）
REJECT_REASONS: tuple[str, ...]        # 12 条 → **13 条**（新增 `unknown_rule_set`）
SYSTEM_MANIFESTS: Mapping[str, SystemManifest]  # **新增一类键**（每个已登记系统一条）
```

- **系统声明为什么进契约面**：FR-9.2 说"插件可声明其订阅的事件与发出的命令，**用于自动生成依赖图与文档**"——**这份声明是跨方的东西**（系统写、宿主读、工具消费、文档引用），**必须有一个所有方都认的地方**。放 `contracts/`（公共叶子）→ **不进冻结区**、**不 import 任何东西**、**受只增不改基线保护**。
- **为什么声明进基线**：它和事件声明、命令参数规格、快照字段、规则签名是同一类东西——**"插件对外承诺了什么"的机器可读面**。声明改了（换了订阅集 / 换了命令集）**是承诺变了**，应该有牙。**基线新增一个键类**（**只增不改**：允许新增系统条目，禁止既有条目的哈希变化）。
- **系统声明里为什么不放工厂**：工厂要 import 具体实现（`systems/achievements/` 之类）→ **不能进 `contracts/`**（公共叶子不 import 任何东西）。**声明与工厂分两层**：声明在 `contracts/`，工厂在系统自己的包里。
- **`switchRuleSet` 为什么进契约面**：命令是内核与外部之间的封闭契约（FR-2.1"命令集封闭且可枚举"），**新增命令必须登记**。

### 3.4 M3 的 major 变更预算（**1 次 · 不到不许用**）

| # | 变更 | 撞红的东西 | 处置 | 状态 |
| --- | --- | --- | --- | --- |
| **M3-C1** | **新增命令 `switchRuleSet` 改写 `COMMAND_TYPE_LITERAL`**（命令名的取值域类型串） | 契约基线里**已有键的哈希变化**：4 个键（`event/command:accepted/commandType` · `event/command:received/commandType` · `event/command:rejected/commandType` · `event/input:intent/commandType`）——**它们的类型串是命令名的字面量枚举，加一个命令就变** | 显式 `--update-baseline --reason "<理由>"`，提交信息写明理由（S2 · `c0dec84`） | **已动用**（批次 A · S2） |

> **M3 计划内的契约变更不是 major 变更**：新增 1 条事件 + 1 条命令 + 1 条拒绝原因 + **两类新键**（系统声明 · 拒绝原因逐值）= **全是新增键**——架构 §4.4 明确"允许新增键"，**不撞红**。S2 要做的是一次**显式刷新**（带 `--reason`），理由写"M3 新增系统契约面与换规则集命令"，**但它不是 major 变更**。
> **M3-C1 的用途落定了**：它不是「预留以防万一」，而是**新增命令这件事本身必然要花的那一次**——`COMMAND_TYPE_LITERAL` 由 `COMMAND_TYPES` 派生，**新增一条命令就改写它**，于是 4 个既有键的哈希变化。**这不是可以绕开的**：把命令名从类型串里摘出去，基线就看不见命令集变没变（M1 取值域收口的成果会白费）。**代价写明在此处**：这 4 个键的**负载字段名与类型语义一个字没改**（仍是「命令类型」这个字段），变的只是**取值域多了一个成员**。
>
> **S2 实际刷新的两类新键**：系统声明 `system/<名字>`（spec §6.4）· 拒绝原因逐值 `reject/<原因>`——后者是**这一轮补上的洞**：拒绝原因枚举此前只被逐命令的聚合键间接覆盖，**往枚举里加一个值不产生任何新键**，「v1 定死 · 只增不改」在基线上**没有牙齿**。
> **冻结区基线刷新也不是契约面，不占这个预算**——但**破例本身必须写明**（M3 的唯一一次 · §4.3 的订正说明）。

## 4. 范围边界

### 4.1 M3 范围内

- **系统契约面**（`contracts/`）：**系统声明的数据结构** · **已登记系统清单** · `switchRuleSet` 命令声明 · `kernel:rule-set-changed` 事件声明 · `unknown_rule_set` 拒绝原因 · **契约基线新增「系统声明」键类**。
- **宿主层系统注册表**（`host/registry.py` 新增）：安装 · 卸载 · 重装 · **命令通道的接通与撤回** · **装卸事件** · **自动发现**（扫描系统目录）。
- **依赖图与系统清单**（FR-9.2）：每个系统的订阅 / 命令声明汇总成可机读结构 + 命令行输出（`tetris systems`）。
- **成就系统**（`systems/achievements/`）：达成条件判定 · 发 `achievement:unlocked` · 成就定义（系统自己的数据）。
- **统计旋转次数系统**（`systems/rotations/`）：订阅 `piece:rotated` 计数 · 产出经 sink 落盘 · **零内核改动**。
- **运行期换规则集**（ADR-061）：内核入口（**`kernel/core.py` · 唯一破例**）· 宿主侧规则集登记扩展 · 门禁 · 事件 · **录像 / 重放路径的兼容**。
- **CLI 落盘接线**（M2 遗留）：`tetris sim` 增落盘开关 · **三个产物各走各的 sink**。
- **文档同步**：`docs/plan-M3.md` · `docs/决策记录.md`（M3 的新 ADR）· `docs/需求与边界.md`（§8.1 / §8.2 / §12）· `PROGRESS.md`。

### 4.2 M3 范围外（**明确不做**）

| 不做的事 | 归谁 | 为什么现在做会坏事 |
| --- | --- | --- |
| **渲染器（终端 / tkinter）与输入适配器（DAS / ARR）** | **M4** | M3 的判据是"**机制可验**"，不是"人能看着玩"。**M3 不做实时宿主**（PROGRESS 里"M3 要做实时宿主"那条按本次决策改为 M4）——**实时宿主一旦进来，M3 会被撑成 M4 的预演** |
| **变体实现**（重力可旋转 · 生长 · 塌方 · 圆柱 …） | **M4** | G4-1 判的是 M4 落地变体时内核差异为空。**M3 只交付"换规则集的机制"**，不交付第二个真规则集 |
| **第二个真规则集** | **M4** | M3 的换规则集用**测试注入的替身规则集**验证机制（行为与标准规则集相同）——**替身不进仓、不改 `rules/`**；真变体属 M4 |
| **AI 系统 · 教学系统 · 反作弊系统 · 音效系统** | **M4** | 需求 §10 把这四条标成 M3，**M3 只交付它们依赖的机制**（系统契约 · 注册表 · 自动发现）——**具体系统实现属 M4**（需求 §10 的"落地批次"列同步改写） |
| **成就玩法的深度内容**（成就条目本身的丰富度） | M3 之内 | M3 只需要**成就系统这个零改动的样例**（FR-9.3）——成就条目给足能触发、能验证的那些即可 |
| **时间旅行（按全局事件序号随机跳转）** | 后续 | M2 已划出（环形缓冲的随机访问要一套索引）——**M3 不顺手做** |
| **M1 遗留的三条真偏离**（0 行 T-Spin 断 B2B 链 · `tspin-mini` 送不到计分 · 事件数基线够不着 `piece:lock-delay-reset`） | 后续里程碑 | 要改冻结签名 / 基线场景口径——**与 M3 正题无关**，M3 不碰 |
| **发布 / exe / GitHub 仓库与许可证** | M4 之后 | ADR-008 |

### 4.3 M3 期间最容易犯的五条

| 编号 | 红线 | M3 的具体含义 |
| --- | --- | --- |
| **M3-D1** | **卸载必须连命令通道一起撤** | 退订只是"不再听"；**还在派命令 = 没摘干净**。卸载的完整语义 = **退订 + 撤通道 + 停止派发 + 发 `kernel:system:removed`**。**只退订不撤通道的系统，在卸载后还能改变内核状态**——这是 M3 最容易漏的一半 |
| **M3-D2** | **新增能力只许落在新增文件** | 新系统的实现与声明**全部是新增文件**；**既有文件零改动**（靠自动发现，不靠改名单登记）。**这一条是 `G3-1` 的判据来源**——它必须能被 git 的变更清单断言 |
| **M3-D3** | **系统只订阅事件 + 派发命令** | 沿用 M2-D1：M3 的四个系统（成就 · 旋转统计 · 日志 · 指标）**都是订阅者**，**不写棋盘、不写分数、不改活动方块**。`G3-6` 是这条红线的门 |
| **M3-D4** | **冻结区只破例一次** | `kernel/core.py` 增**换规则集入口**（ADR-061）→ **冻结区基线显式刷新一次**（带 `--reason`）。**`rules/` 一个字节都不动**；**除 `kernel/core.py` 外其余 13 个文件逐字未变** |
| **M3-D5** | **落盘仍只走 sink** | 沿用 M2-D2：M3 新增的系统**不许自己 `open()`**、不许决定路径；**路径是宿主的事**（ADR-074 / ADR-085） |

> **M3-D5 的新面孔**：成就系统与旋转统计系统**都要落盘**（成就是事件不是文件；旋转统计是计数文件）——**它们新学的第一条纪律就是"不许自己开文件"**。
> **M3-D2 的边界**：**`host/registry.py` 本身是新增文件**（M3 新建）——但它**一旦落地，后续新增系统就不许再改它**。**"自动发现"的价值正是在这里**：**新系统不许去改注册表**。

## 6. 契约面规格（M3 必须改的声明与基线）

### 6.1 事件目录（49 → **50** 条 · **只增不改**）

M3 需要的信号里，**绝大部分契约里已经登记**：

| 用途 | 事件 | 状态 |
| --- | --- | --- |
| 装上一个系统 | `kernel:system:installed`（负载：插件名 · 配置） | **已登记**（M0 就在册） |
| 摘下一个系统 | `kernel:system:removed`（负载：插件名 · 是否干净） | **已登记** |
| 成就解锁 | `achievement:unlocked`（负载：编号 · 标题 · 触发事件类型 · 触发序号） | **已登记** |
| 换规则集 | **`kernel:rule-set-changed`** | **M3 新增**（新增键） |

**唯一的开口是换规则集**——它是一条**新的事实**，需要一个信号：

| 命名空间 | 事件 | 产出者 | 触发时机 | 关键负载 |
| --- | --- | --- | --- | --- |
| kernel | `kernel:rule-set-changed` | 内核 | 规则集切换被接受 | 新规则集标识、旧规则集标识 |

- **为什么不复用 `game:reset`**：换规则集**必然伴随局面重置**（不同规则的形状 / 踢墙不同 → 旧局面在新规则下可能非法），但**"重置"与"换了规则"是两件事**——**订阅者要能只对后者起反应**（比如把录像头切到新规则集标识、让 UI 换提示文案）。**两个事件都发**：`kernel:rule-set-changed`（换规则集）+ `game:reset`（局面重置）。
- **产出者填"内核"**：换规则的**决定**由内核裁决（命令校验 + 门禁）→ **内核发**。**装卸事件的产出者是 host**（装配是 host 的事 · 需求 §8.1 的"产出者"列）——**同是 `kernel:` 命名空间，产出者不同**（需求 §8.1 已写明这条口径："产出者 ≠ 命名空间"）。
- **既有事件一个都不改**：**不改任何既有事件的负载字段**（改字段 = 已有键哈希变 = major 变更）。**M3-D 全部遵守 `M3-C1` 不到不许用**。

### 6.2 命令目录（16 → **17** 条 · **新增 1 条**）

M3 新增的命令只有一条：

| 命令 | 参数（`args`） | 语义 | 可被拒绝的情形 |
| --- | --- | --- | --- |
| `switchRuleSet` | `rule: str` | 切换到指定的已登记规则集 | 局中切换（`illegal_transition`）· 规则集未登记（`unknown_rule_set`）· 参数不合法（`invalid_argument`） |

- **`switchRuleSet` 的门禁不是通用的生命周期门禁**：通用门禁是"phase ≠ running 一律拒"（架构 §7.1），而换规则集**恰恰要在非 running 态被接受**（待开始 / 已结束）→ 所以它 **`lifecycle_gated = False`**，**由内核自己判 phase**（**局中 = running 态 = 拒绝**）。**门禁归属由契约的 `lifecycle_gated` 字段决定**（架构 §7.1）——**不手写名单**。
- **为什么局中切换被拒**：局中切换意味着**当前活动方块在新规则下可能非法**（形状表 / 踢墙表不同 → 同一个朝向在新规则下落在别的格），**要么把局面整体重置（那不是"切换"了）**，要么引入"半局规则不一致"的局面——**后者会毁掉录像重放的一致性**。**拒绝比勉强支持便宜得多**。
- **`args` 禁浮点**沿用（架构 §7.2）：`rule` 是 `str`。
- **拒绝原因 `unknown_rule_set` 是新增条目**（12 → 13）——**拒绝原因枚举 v1 定死"只增不改"，追加是允许的**（需求 §8.2）。
- **`switchRuleSet` 是命令 → 会进录像**（M2-D3 录被接受的命令）→ **重放时照样切** → 逐帧一致。**回放宿主按录像头的起始规则集标识起内核**，之后的切换由命令序列驱动。**M2 的"回放遇到没登记的规则集明确拒绝"保持不变**——那说的是**录像头**的标识。

### 6.3 快照字段（22 顶层 + `board` 5 子字段 · **字段集合不变**）

M3 **不加字段、不删字段**。

- 换规则集后，快照的 `rule` 字段**值会变**（**规则集标识**）——**值变不影响契约面**（基线哈希的是**声明**，不是值）。
- **扩展槽 `extensions` 沿用既有语义**：换规则集时**清空**（变体自己的状态与旧规则集绑定）——**这是语义决定，不是契约变更**。
- **`G3-5` 不需要新字段**：换规则集后的行为一致性用**逐帧指纹**判定。

### 6.4 系统声明面（**新增一类键** · FR-9.1 / FR-9.2）

| 项 | 内容 | 约束 |
| --- | --- | --- |
| **身份** | `name: str` · `version: str` | **名字全局唯一**（注册表的键） |
| **订阅声明** | `subscribes: tuple[str, ...]` | 每一条**必须是已登记的事件类型**（否则登记守卫红） |
| **命令声明** | `commands: tuple[str, ...]` | 每一条**必须是已登记的命令类型** |
| **产出者** | `producer: str` | 与需求 §8.1 的"产出者"列同义（**不是命名空间**） |
| **落盘需求** | `needsSink: bool` | 该系统是否需要宿主注入 sink（M3 的旋转统计系统要 · 成就系统不要） |

- **声明面进基线**（**新增一个键类** · `system/<name>`）：**允许新增条目**（新增系统是正常成长）· **禁止既有条目的哈希变化**（改了订阅集 / 命令集 = **承诺变了**，要有牙）。
- **订阅声明必须指向已登记的事件**：**这是声明面的自证**——系统声明的事件类型**必须存在于 `contracts/events.py` 的注册表里**（跨文件自证 · 与 M2 的契约基线两文件互校同一路数）。
- **系统声明不描述"怎么装"**：工厂与安装顺序是宿主的事；**声明只说"我是什么"**。

### 6.5 基线规则（M3 期间五份基线）

| 基线 | 文件 | M3 的变化 | 处置 |
| --- | --- | --- | --- |
| 契约基线 | `tests/baseline/contracts_baseline.json` | **新增键**（1 事件 + 1 命令 + 1 拒绝原因 + 系统声明若干）——**不是 major 变更** | 显式 `--update-baseline --reason` + 提交写明理由 |
| 期望清单 | `tests/baseline/contracts_expected.json` | 同上 | 显式 `--update-expected --reason`（**两份要一起刷**） |
| **系统声明** | 同上（**新键类**） | 新增条目 | 与上面两份**同笔刷** |
| 冻结区哈希 | `tests/baseline/kernel_hashes.json` | **变一次**（`kernel/core.py` · **M3 唯一破例**） | 显式刷新 + `--reason`（理由写明"ADR-061 的换规则集入口"） |

> **"刷新基线不带 `--reason` 一律拒绝"这条门不放宽**（M0 修好的门，M1 沿用，M2 沿用，M3 沿用）。

## 7. 行为面规格（扩展机制到底怎么算）

> **这一节是 M3 的正题**。M0 的总线是"发布 / 订阅 / 环形历史"，M1 的玩法是"算得对"，M2 是"看得见"，**M3 要回答的是"接进来有没有改别人的东西"**。

### 7.1 系统契约（FR-9.1 · FR-9.3）

- **统一契约的四件事**：**名字** · **版本** · **声明（订阅 / 命令）** · **安装 / 卸载生命周期**。
- **生命周期只有两个动作**：**装上** 与 **摘下**。**没有"暂停"**——要暂停就别装（这是 M3 的判据 AC-8 的形态：**要么在，要么不在**）。
- **系统不 import 内核**：沿用 M2 的依赖方向——**系统层只能订阅事件 + 派发命令**（M3-D3）。**系统不持有内核对象**，只看事件与只读视图。

### 7.2 注册表与热插拔（FR-9.1 · **AC-8**）

**装上（install）**：

1. 按名字找到系统的**声明与工厂**（自动发现的清单里）→ **名字不在册 → 明确报错**（不静默跳过）。
2. **创建实例** → 接上**命令通道**（系统派命令的通路）。
3. **订阅**它声明的事件（按声明的顺序与优先级接入总线）。
4. 发 **`kernel:system:installed`**（负载：插件名 · 配置）。
5. **装上之后系统立刻开始收事件**——**装卸动作本身不产生内核状态变更**（M3-D3）。

**摘下（uninstall）**：

1. **先撤命令通道**（**M3-D1 的核心**：系统不再能派命令）。
2. **退订**（总线层 `unsubscribe` 原语 · ADR-057 ——**但那只是订阅者级的原语，M3 要的是系统级的完整语义**）。
3. **停止派发**（已经在队列里的命令怎么办？**口径：队列里已入队的命令照常执行**——**丢弃命令会让内核行为依赖卸载时机**，破坏确定性；**命令是"已发生的事实"**）。
4. 发 **`kernel:system:removed`**（负载：插件名 · 是否干净）。
5. **不干净（卸载时有资源没释放）→ 记错**，但**不占用 `kernel:error`**（`kernel:error` 只留给订阅者异常这一种语义 · 架构 §6.4）。

**重装（reinstall）**：

- **卸载后重新装上** → 系统重新订阅 → **事件流恢复**。
- **恢复的判据不是"又开始收事件了"，而是"接缝处的事件序列连续"**（`G3-2`）：**卸载期间的事件没有丢，重新装载后的事件接着来**——**总线的分发不因某个订阅者的进出而改变**。

**为什么"摘下"要连命令通道一起撤**：**订阅退了但命令还能派出去，等于没摘**——系统会继续改变内核状态，而它"已经不在了"（事件流里看不见它）→ **状态变更没有事件伴随**（破 N5）→ **"运行中卸载日志系统"这类判据立刻失效**。**M3-D1 就是这条。**

### 7.3 自动发现（AC-3 · NFR-6 · M3-D2）

- **发现规则**：系统目录下每个子包**自带声明与工厂**（如 `SYSTEM_MANIFEST` + `create_system`）→ 宿主**扫描目录**找出可用的系统。**宿主不维护手写名单**。
- **为什么要扫描而不是手写名单**：手写名单意味着**新增一个系统要改一个既有文件**——**那就不是"新增能力 = 新增文件"了**（M3-D2）。**扫描把这个判据变成可机检的**。
- **扫描的纪律**：被扫描的包**不许有导入副作用**（导入即订阅 / 即开文件 / 即读环境变量）——**导入期只允许定义**。**违反的后果**：宿主一装配就把事件订阅上、或者一 import 就落盘，**"装上才生效"的语义就破了**。**这条要有守卫**（扫到即断言"导入前后总线订阅数不变"）。
- **发现结果的呈现**：**系统清单**（名字 · 版本 · 订阅 · 命令）→ FR-9.2 的**依赖图**由这份清单生成。**依赖图 = 谁订阅了什么 + 谁发出什么命令**，用于回答"这个事件谁在消费""这条命令谁在发"。
- **清单与依赖图必须可机读**（命令行输出 + 可被测试直接断言的结构）——**"给人看的图"不算**。

### 7.4 两个零内核改动的示范系统

**成就系统**（FR-9.3）：

- **订阅**：全局（`*`）或具体事件（由成就定义决定）。
- **产出**：达成条件时发 **`achievement:unlocked`**（**契约里已登记** · 负载：编号 · 标题 · 触发事件类型 · 触发序号）。
- **成就定义**：系统自己的数据（新增文件）——**定义不进契约基线**（**契约面描述"对外承诺"，成就条目是内容不是承诺**）。
- **零内核改动的判据**：`G3-4` ——达成条件时事件照常发出，且**冻结区逐文件哈希全等**。

**统计旋转次数系统**（AC-3 的题面）：

- **订阅**：`piece:rotated`。
- **产出**：旋转次数计数 → **经 sink 落盘**（M3-D5：路径是宿主的事）。
- **它同时是 `G3-1` 的实现体**：**这个系统的全部代码落在新增文件里**，**既有文件零改动**——**由 git 的变更清单断言**（§7.6）。

### 7.5 运行期换规则集（ADR-061）

- **命令**：`switchRuleSet(rule: str)`。
- **门禁**：
  1. **局中（running）→ 拒绝**（`illegal_transition`）——理由见 §6.2。
  2. **规则集未登记 → 拒绝**（`unknown_rule_set`）——**明确拒绝，不拿标准规则集顶替**（M2 的 `replay` 已是这个口径，M3 沿用）。
  3. **参数不合法 → 拒绝**（`invalid_argument`）。
- **接受后**：换规则集 → **重置局面**（新规则集的初始态）→ 发 **`kernel:rule-set-changed`** + **`game:reset`**。
- **"已登记"是谁说了算**：**宿主侧的规则集登记表**（既有 `RULE_SETS`）——**内核不认识具体规则集，只认"当前这一套"**（N6）。
- **录像 / 重放的兼容**：切换是命令 → 进录像 → 重放时照样切 → 逐帧一致。**录像头的规则集标识 = 起始标识**；M2 的"回放遇到没登记的规则集明确拒绝"**保持不变**。
- **M3 怎么验这条机制**：**测试注入一个替身规则集**（行为与标准规则集相同、标识不同）→ 切换后逐帧行为一致；**替身不进仓、不改 `rules/`**。**真变体属 M4**（§4.2）。

### 7.6 "新增能力 = 新增文件"的机器可验（AC-3 · NFR-6 · `G3-1`）

**这条判据必须是机器可验的，不能靠人看一眼。** 判定方式（`G3-1`）：

1. **冻结区逐文件哈希全等**（既有工具：`tools/check_frozen_baseline.py`）。
2. **该系统落地的那次提交，其 git 变更清单里只有新增文件**（`git diff --name-status <提交前> <提交>` → 每一行都是 `A`，**没有 `M`、没有 `D`**）。
3. **既有文件零改动**——**这条是靠第 2 条保证的**：自动发现让新系统不需要登记，因此连"改一行名单"都不该有。

> **为什么必须是差异断言而不是行为断言**：行为断言（"新系统能数出旋转次数"）**证明不了"没有改别人的东西"**——改了 `kernel/core.py` 也能数出旋转次数。**M3 的门要证明的是后者。**
> **这条断言对写手有约束力**：新增系统的阶段**不许顺手改既有文件**（连改注释都不行）——**因为 `G3-1` 会红**。

### 7.7 CLI 落盘接线（M2 遗留）

- **接线点已就位，命令行没接**（PROGRESS 待办第一条）：`assemble()` 不传 `sinks` 时三个出口都是 `None`，**`tetris sim` 不落盘**。
- **M3 的口径**：`tetris sim` 增落盘开关 → **三个产物各有各的出口**（ADR-085）：**日志与指标追加 · 录像覆盖**。**共用一个出口 = 用错语义 = 数据丢**。
- **这不是 M2 的门判据**（`G2-1`…`G2-5` 验的是系统层能力），**M3 也不给它单独立门**——**它是接线，不是能力**。

## 9. 验收标准

### 9.1 M3 门判据（**硬门 · 随 plan-M3.md 落定**）

| 编号 | 判据 | 判定方式 |
| --- | --- | --- |
| `G3-1` | **新增能力 = 新增文件（机器可验）** | 新增「统计旋转次数」系统 → **冻结区（`kernel/` + `rules/`）逐文件哈希全等** 且 **该系统的落地提交在 git 上的变更清单里只有新增文件**（每行都是 `A`，无 `M` / `D`）（AC-3 · NFR-6） |

| `G3-3` | **系统清单与依赖图** | `tetris systems` 列出每个已发现系统的名字 · 版本 · 订阅事件 · 发出命令，**与各自声明逐条相等**；**新增系统仅凭新增文件即出现在清单里**（FR-9.2） |

| `G3-5` | **运行期换规则集的机制** | 已登记规则集可切（切换后开局按新规则集跑、逐帧行为符合该规则集）· **未知规则集被拒**（`unknown_rule_set`）· **局中切换被拒**（`illegal_transition`）· **换完的录像可重放且逐帧一致**（ADR-061） |
| `G3-6` | **扩展零污染** | 同一局跑两遍：一遍开着全部 M3 新增系统，一遍全关 → **逐帧棋盘指纹序列全等**（M2 的 `G2-3` 在 M3 上的延续） |

> **`G3-5` 的"未知规则集被拒"不许拿标准规则集顶替**——M2 的 `replay` 已是这个口径，M3 沿用。

### 9.4 major 变更流程（M3 的至多一次）

1. **改声明 / 改实现**（工作区改动，**不提交基线刷新**）。
2. **显式刷新**：`--update-baseline --reason "<理由>"` / `--update-expected --reason "<理由>"`——**不带 `--reason` 一律拒绝且不落盘**（M0 修好的门，M1 / M2 沿用，M3 沿用**且不得放宽**）。
3. **提交信息写明理由**——**基线刷新的提交**正文必须写清改了什么、为什么。
4. **反向验证**：喂一份改坏的临时基线给工具，断言退出码非 0。
5. **同笔提交**（ADR-077）：刷了基线**必须与这次改动同笔提交**。

> **"顺手刷新"是明令禁止的**。M3 计划内只有一次**新增键**的显式刷新（S2）与一次**冻结区**的显式刷新（S8）——**都不是契约面的 major 变更**。**M3-C1 预留一次，不到不许用**。

## 10. 任务分解与执行顺序

> **详细计划在 `docs/plan-M3.md`**（格式照 `docs/plan-M2.md`：阶段 · 任务清单 · 验证方案 · 审查修订 · 提交序列）。本文只给**阶段骨架与依赖顺序**。

### 阶段 A：契约面与基线（M3 不可返工的部分）

- **A1** 系统声明面（`contracts/systems.py`）+ `switchRuleSet` 命令 + `kernel:rule-set-changed` 事件 + `unknown_rule_set` 拒绝原因 + 需求 §8.1 / §8.2 登记。
- **A2** 契约基线与期望清单的**显式刷新**（新增键 + 新增一类系统声明键）。

> **A 阶段是 M3 唯一"不可返工"的部分**——契约面一改，基线就红，所有下游都要跟着动。**A1 与 A2 之间那段基线必红**（S2 才刷）；**这与 M1 / M2 的第一处预期红同源**。

### 阶段 B：底座（注册表与发现）

- **B1** 系统注册表与运行时热插拔（`host/registry.py`）：装 · 卸 · 重装 · **命令通道接通与撤回**（M3-D1）· 装卸事件。
- **B2** 自动发现 + **系统清单与依赖图**（`tetris systems`）+ **导入无副作用守卫**。

### 阶段 C：示范系统

- **C1** 成就系统（`systems/achievements/`）。
- **C2** 统计旋转次数系统（`systems/rotations/`）——**`G3-1` 的实现体**。

> **两个系统彼此独立**（都只订阅事件），**可并行**；但**两个阶段都受 M3-D2 约束**（只许新增文件）→ **自动发现必须先落地（B2）**，否则新系统就得改既有文件登记。

### 阶段 D：换规则集与落盘接线

- **D1** 运行期换规则集端到端：宿主规则集登记扩展 · **内核入口（`kernel/core.py` · 唯一破例）** · 门禁 · 事件。
- **D2** **冻结区基线的显式刷新**（M3 唯一一次 · 带 `--reason`）。
- **D3** CLI 落盘接线（`tetris sim` 增开关 · 三个产物各走各的 sink）。

### 阶段 E：验证与收尾

- **E1** 六道门判据 + **每道门的反向用例** + **元守卫**（门入口不许中途改名）。
- **E2** 性能复测（P50 / P99 · 同机同时段配对 A/B · 新系统的分发成本记账）。
- **E3** 文档同步（决策记录 · 需求与边界 · PROGRESS · ai_docs）。

> **阶段顺序不可乱**：A → B → C → D → E。**A 先行**是因为契约面一改就撞红；**B 先行**是因为 C 的"只许新增文件"靠自动发现兑现；**D 在 C 之后**是因为换规则集要动内核，而**内核一动，冻结区基线就刷**——**在示范系统落地之后再刷，差异清单才干净**（否则一次刷新里混着两件事）；**E 最后**是因为**门判据要写在实现稳定之后**（先写门再写实现 = 门会被实现反向塑形 · ADR-061 的原话）。
