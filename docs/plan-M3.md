# M3 分阶段执行与验证计划 · Tetris Kernel

| 项目 | 内容 |
| --- | --- |
| 适用范围 | **M3 可扩展**：新增能力 = 新增一个文件（机器可验）· 运行中装卸系统不影响其余系统 |
| 上游 | `docs/spec-M3.md`（规格：目标 / 输入输出 / 边界 / 非功能 / 验收）· `docs/需求与边界.md` §7.9 / §10 / §11 / §12（扩展机制 / 扩展点映射 / 验收 / 门判据与编号）· `docs/项目架构.md` §4.1 / §4.3 / §4.4 / §6 / §7 · `docs/plan-M2.md`（批次纪律与门判据入口的来源）· `docs/决策记录.md`（ADR-019 / ADR-020 / ADR-030 / ADR-054 / ADR-057 / **ADR-061** / ADR-064 / ADR-074 / ADR-079 / ADR-085） |
| 本文件管什么 | **怎么一步步做、每步怎么验、每步怎么提交**。规格说"做成什么样"，本文件说"按什么顺序做" |
| 状态 | **可更新的执行清单**：每阶段完成后勾任务框、把 §3 状态表改成已完成并填入提交哈希 |
| 日期 | 2026-10-27 |

> **三句话读法**：① 阶段按**功能**切，每阶段 = 一个可独立提交、独立验证的逻辑改动；② 每阶段自带**验证方案**（跑什么命令、看什么结果、什么算过）；③ 阶段编号 `S0…S12` 是**本计划内部编号**，不是正式任务编号（正式编号随做随定，落定前不编造）。
>
> **本计划同时落定 M3 的门判据编号**：`G3-1`…`G3-6`（见 §5.2），**随本计划写进 `docs/需求与边界.md` §12 注册表**。落定前不引用，落定后就是正式编号。
>
> **M3 与 M0–M2 最大的不同**：**M0–M2 的门是"功能对不对"，M3 的门是"接进来有没有改别人的东西"**——所以 M3 的门大部分写成**差异断言**（冻结区逐文件哈希全等 · 既有文件零改动 · git 变更清单只有新增文件），而不是"跑一遍看结果对不对"。
>
> **M3 唯一一次冻结区破例**：`kernel/core.py` 增换规则集入口（ADR-061）**+ `kernel/commands.py` 增 `str` 参数校验**（`switchRuleSet` 的 `rule` 是字符串，内核原本只认 `int` / `INT_TUPLE` / `CELLS`）→ **S8 显式刷新冻结区基线**（带 `--reason`）。**`rules/` 一个字节都不动**（M3-D4）。
>
> **M3 的契约面只增不改**：新增 1 事件 + 1 命令 + 1 拒绝原因 + 一类系统声明键 = **全是新增键**，**不撞红**；**M3 的 major 变更预算 1 次（M3-C1），不到不许用**（spec §3.4）。

> **串行链不变**：M3 的阶段顺序是**依赖顺序**，不是排期单位。批次只是把**互不相干**的阶段放到一起并行。
> **M3 的结构差异（对 M2）**：M2 的批次 A 是"**声明（S1）· 加守卫（S2）· 刷基线（S3）**"三段；**M3 的批次 A 只有两段**（声明 + 刷新）——**因为 M2 的 git 背书守卫（M2 的 S2）在 M3 开工前就已生效**，M3 直接沿用，**不需要再加一层**。
> **M3 的批次 D 只有 1 个写手 + 集成者**：换规则集会动 `kernel/core.py`，落盘接线会动 `host/assembly.py` 与 `host/cli.py`——**这几处与批次 B / C 的文件归属不重叠，但 D 内部的 `host/assembly.py` 与 `host/cli.py` 与 B2 有交叉**，**故 D 串行**。

### 1.2 五段结构

| 段 | 阶段 | 批次 | 性质 | 为什么这样排 |
| --- | --- | --- | --- | --- |
| **A 契约面与基线** | S0–S2 | A | **只增不改 + 一次显式刷新 + 新增一类键** | M3 只**新增**（1 事件 + 1 命令 + 1 拒绝原因 + 系统声明）——**新增键撞不了红**，但**声明先行、刷基线在后**。**S2 才是给新键上牙的那一步**（M2 同款教训：新增键在刷基线之前**没有牙齿**） |
| **B 底座** | S3–S4 | B | **注册表 + 发现** | 装卸要能热插拔 → 注册表先行（S3）；**自动发现必须在示范系统之前**（S4）——否则新系统要改既有文件登记，**`G3-1` 当场红** |
| **C 示范系统** | S5–S6 | C | **两个独立系统 · 只许新增文件** | 两个系统互不依赖，可并行；**两者都受 M3-D2 约束**（实现全在新增文件里），**且 B2 的自动发现是它们成立的前提** |
| **D 换规则集与落盘接线** | S7–S9 | D | **唯一一次破例 + 一次接线** | 换规则集要动内核 → **冻结区基线要刷**；**S8 排在 S7 之后、S9 之前**：**刷基线那一笔的差异清单里只有 `kernel/core.py` 与 `kernel/commands.py`**，不与别的改动混在一笔里。**落盘接线是 M2 遗留**（PROGRESS 待办第一条） |
| **E 验证与收尾** | S10–S12 | E | **门 + 性能 + 同步** | **门判据写在实现稳定之后**（先写门再写实现 = 门会被实现反向塑形 · ADR-061 的原话）；**性能复测要在新系统落地之后**（新增两个订阅者的分发成本要显式记账） |

> **批次 B 有一处同文件不同侧的重叠**：`host/registry.py` 的**注册表侧**（装卸语义）与**发现侧**（扫描目录）——**两处写入区域必须分到不同函数块且由集成者串行合并**，或者**把发现侧拆到独立文件** `host/discovery.py`（**推荐**：让文件归属彻底互斥）。**实际按推荐做法落笔**：发现侧拆到了 `host/discovery.py`，文件归属彻底互斥。
> **批次 B 的分支订正（2026-10-27 · 落笔时）**：本表原写 `feature/m3-batch-b`，**实际落笔在 `feature/m3-batch-a` 上**——**批次 B 由一个写手串行完成**（S3 与 S4 顺序依赖：发现要接进注册表），**没有并行写手，因此没有另开分支**。**批次纪律（一次提交一个逻辑改动 · 纯文档不与代码混提）照样成立**——三笔提交各自独立。**批次 C 起恢复"每批一个分支"的写法**（C 的两个系统互不依赖，可并行）。
> **批次 D 的 `contracts/**` 与批次 A 重叠**：S7 若要改 `contracts/`，**必须先在 §1.3 表里登记归属**（并行写手之间没有协商通道）——**S7 按设计不需要改契约面**（声明在 S1 已定）。
> **批次 C 的两个阶段与批次 B 有隐性依赖**：C 依赖 B2 的自动发现——**B 必须先合并进分支链**（链式分支点：下一批从上一批的落笔提交起，不回 `master`）。

### 1.4 并行写手纪律

沿用 M0 / M1 / M2 的纪律（plan-M2 §1.4）：

1. **文件归属互斥是并行安全的前提**——两个写手改同一个文件必然互相覆盖。
2. **并行写手之间没有协商通道**——接口变更**先改本文件 §1.3 的文件归属表**，由集成者裁决。
3. **并行写手只交工作区改动**，**不并行 `git add`**（git 索引是单一共享资源）——由集成者串行切分提交。
4. **写手交付前先跑自己范围内的反向验证**；**集成者在批次集成后统一复跑一遍**受影响的几条。
5. **基线一律由集成者生成**（M1 的批次 D 纪律）——写手刷基线 = 橡皮图章。

## 2. 阶段通用模板

每个阶段按同一套结构写，字段含义固定：

| 字段 | 含义 |
| --- | --- |
| **目标** | 这一阶段结束时世界是什么样（一句话） |
| **任务** | 可勾选的动作清单，粒度 = 一次提交或一次小改动 |
| **涉及文件** | 本阶段允许触碰的文件（**清单外的文件不许动**） |
| **批次 / 写手 / 文件归属** | 本阶段在哪个批次、由哪个写手做、独占哪些文件（并行安全的前提，见 §1.3） |
| **验证方案** | 跑什么命令、看什么结果、什么算过 |
| **完成判据** | 勾完任务的充分条件（与验证方案互相印证） |
| **提交** | 建议的提交标题（`类型：主题`）+ 该提交应包含的文件 |
| **常见坑** | 这一阶段最容易犯的错，来自红线与 ADR |

> **`G3-2` 的第四面是反向验证逼出来的**：前三条用例在「摘下顺序倒过来」时**全绿**——**它们只比事件流，不比顺序**。**门自己有牙，得先确认它咬得住**（同 §5.3 那条"自证被打破"的纪律）。

> **批次里的跑法**：写手交付前先跑**自己范围内**的反向验证；**集成者在批次集成后统一复跑一遍**受影响的几条——并行写手的"破坏 → 红"可能只在自己的文件上成立，合并后仍要确认整批是绿的。

### 5.4 major 变更的处置流程

M3 的 major 变更**预算是 1 次**（spec §3.4 的 **M3-C1**，**已在批次 A 的 S2 动用**）——**审查修订又动用一次（`M3-C2`）**，见下表。流程统一为四步：

1. **改声明 / 改实现**（工作区改动，**不提交基线刷新**）。
2. **显式刷新**：`--update-baseline --reason "<理由>"` / `--update-expected --reason "<理由>"`——**不带 `--reason` 一律拒绝且不落盘**（M0 修好的门，M1 / M2 沿用，M3 沿用**且不得放宽**）。
3. **提交信息写明理由**——**基线刷新的提交**正文必须写清改了什么、为什么（AGENTS.md 提交规范）。
4. **反向验证**：喂一份改坏的临时基线给工具，断言退出码非 0。

| # | 变更 | 撞红的东西 | 落笔阶段 | 理由该写什么 |

## 6. 提交序列

### 6.1 提交粒度

- **一次提交 = 一个逻辑改动**。本计划里 **一个阶段 ≈ 一次提交**；阶段内若有多个独立改动（S2 的两份基线、S7 与 S9 都碰 `host/assembly.py`），**拆开提**。
- **格式化与逻辑改动分开提交**（`ruff format` 单独一笔 `格式：…`）。
- 纯文档提交（`文档：…`）与代码提交（`新功能：…`）不混提。
- **并行批次里的提交由集成者串行切分**：写手只交工作区改动（并行 `git add` 会互相覆盖索引），集成者按"一次提交 = 一个阶段"逐笔 `git add -- <该写手的文件>` 后提交。**批次合并用 `--no-ff`**，保留批次边界。

### 6.2 标题格式（`AGENTS.md`）

`类型：主题`，类型取固定表：**新功能 · 修复 · 文档 · 测试 · 重构 · 性能 · 格式 · 构建 · 持续集成 · 杂务 · 回滚 · 合并**。

- **破坏性改动**在类型后加感叹号——判据：**会不会让旧录像、旧存档或既有调用方失效**。
  - **新增 `switchRuleSet` 命令 + 新增事件** = **不破坏**（既有事件与命令一字未改；旧消费方按"未注册的事件类型"处理——NFR-9 明写容错）→ 不加感叹号。
  - **契约基线刷新**（S2）= **破坏性**（基线换了 = 比对基准换了）→ `新功能!：`。
  - **注册表与自动发现上线**（S3 / S4）= **破坏性**（宿主装配的既有调用方签名可能变）→ `新功能!：`。
  - **换规则集机制**（S7）= **破坏性**（新增命令 + 内核行为扩展）→ `新功能!：`。
  - **冻结区基线刷新**（S8）= **破坏性**（M4 的比对基准换了）→ `新功能!：`。
  - **两个新系统落地**（S5 / S6）= 不破坏既有调用方 → 不加感叹号。
  - **CLI 落盘接线**（S9）= **默认行为不变** → 不加感叹号。
- 标题与正文之间**空一行**，正文写"改了什么、为什么"，用中文。**基线刷新的提交必须把理由写进正文**（与 `--reason` 一致）。

### 6.4 回滚点

- 每个阶段一次提交 = 一个回滚点。某阶段验证不过 → `git revert` 该提交（或 `git reset --hard` 到上一个阶段的提交哈希，**前提是该阶段的改动没有下游依赖**）。
- **S2 之后慎用 reset**：契约基线一旦刷新，回退就等于放弃那次刷新——**要重走显式刷新流程并写明理由**（基线与代码对不上会一路红；**且 git 背书守卫会拦**）。
- **S8 之后更慎**：冻结区基线是 **M4 的比对基准**（G4-1 判的是"M4 落地变体时内核文件差异为空"），回退要连基线一起回退，且**回退理由同样要写进提交信息**。
- **S3 之后慎用 reset**：注册表一旦上线，`host/assembly.py` 的既有调用方签名可能变——**回退要连调用方一起回退**。

### 6.5 不许做的事

| # | 禁止 | 理由 |
| --- | --- | --- |
| 1 | 一个提交里塞多个阶段 | 回滚粒度丢失，git 历史读不出"哪一步做了什么" |
| 2 | 在 A 段（契约）提交行为代码 | 契约会被实现反向塑形（ADR-061） |
| 3 | 在 B / C / D 段（行为）顺手改契约声明 | 撞基线；必须走显式更新流程并写明理由 |
| 4 | 阶段内顺手做"别的阶段的事" | M4 的需求提前实现会把还没定稿的东西锁死 |
| 5 | 用 `git commit -a` 批量提 | 容易把不该提的文件带进去 |
| 6 | 并行写手在同一分支上并行提交 | git 索引是**单一共享资源**，两个写手同时 `git add` 会互相覆盖 |
| 7 | 两个写手改同一个文件 | 文件归属互斥是并行安全的**前提**；重叠就拆到不同批次，或交给同一个写手串行做 |
| 8 | 审查期间写下一批时顺手改被审查批次的文件 | 修正回合与新批次同改一个文件必然互相覆盖；下一批**只加不改** |
| 9 | 子代理单方面改跨写手接口 | 并行写手之间没有协商通道；**接口变更先改本文件 §1.3**，由集成者裁决 |
| 10 | **顺手刷新基线** | 基线是 M4 的比对基准；**刷新必须带 `--reason`**（M0 修好的门） |
| 11 | **手改基线文件 / 期望清单** | 那是绕过显式刷新流程；**git 背书守卫会当场拦下** |
| 12 | **为新增系统改既有文件登记** | **M3-D2 的红线**——`G3-1` 会当场判红（自动发现就是为了免掉这一行） |
| 13 | **卸载系统时只退订、不撤命令通道** | **M3-D1 的红线**——系统"人不在了，话还在说" → 破 N5 |
| 14 | **维护一张手写的系统名单** | 名单一出现，"新增能力 = 新增文件"永久失去牙齿 |
| 15 | **改 `rules/` 或刷新 `rules/` 的基线** | **G4-1 就废了**——M4 落地变体时内核文件差异必须为空 |
| 16 | **局中切换规则集** | 半局规则不一致 → 录像静默分叉 → 破 AC-1 / NFR-1 |

1. **六道门 `G3-1`…`G3-6` 全过**，每道门有可复跑的测试**与反向用例**。
2. **新增能力 = 新增文件**（`G3-1`）：冻结区逐文件哈希全等 **且** 示范系统的落地提交**只有新增文件**（`git diff --name-status` 每行都是 `A`）。
3. **运行中卸载日志系统，其余系统不受影响；重新装载后事件流恢复**（`G3-2` · AC-8）。
4. **系统清单与依赖图**可机读且与声明逐条相等（`G3-3`）· **成就系统**是零改动示范（`G3-4`）。
5. **运行期换规则集的机制**兑现：可切 · 未知被拒 · 局中被拒 · 换完的录像可重放且逐帧一致（`G3-5`）。
6. **扩展零污染**：关掉 M3 全部新系统后内核逐帧指纹与全开时全等（`G3-6`）。
7. **契约面只增不改**：事件 49 → 50 · 命令 16 → 17 · 拒绝原因 12 → 13 · **新增一类系统声明键** · **既有键的哈希一个都没变**。
8. **冻结区只破例一次**：`kernel/core.py` 增换规则集入口 **+ `kernel/commands.py` 增 `str` 参数校验**（显式刷新 · 带 `--reason` · ADR-061）——**其余 12 个文件逐字未变** · **`rules/` 零变化**。
9. **基线到位**：契约基线 + 期望清单（**新增「系统声明」键类**）· 冻结区（**14** 个文件 · 刷过一次）· 事件数（**若变则带理由刷**）· **`bus/` 独立基线零变化**；**两条 git 背书守卫生效**（ADR-077）。
10. **质量门全绿**，且 **M3 未新增 skip**。
11. **文档一致**：`docs/plan-M3.md` §3 状态表与提交历史对得上 · `docs/决策记录.md`（ADR-086 起）· `docs/需求与边界.md` §8.1 / §8.2 / §10 / §12 · `PROGRESS.md` 三段改写 · `ai_docs/` 当日条目（五件事齐）。
12. **范围没越界**：M4 的需求**一件都没提前实现**——**无渲染器 · 无输入适配器 · 无实时宿主** · `systems/ai/` 仍空 · `variants/` 仍空 · **`play` 仍是占位**。
13. **批次全部收口**：五个批次分支全部 `--no-ff` 合并进 `master`、批次内各阶段提交**分别保留**。
