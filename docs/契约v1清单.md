# 契约 v1 冻结清单

> **这个文件管什么**：`contracts/` 的"只增不改"基线**在契约 v1 落定的那一刻首次生成**（`项目架构.md` §4.4 / §7.6）。本清单是那道门的钥匙——**清单没勾完，基线不许生成**。
> **怎么用**：每项后面标了「机检」还是「人检」。**机检项**由 `contracts/` 里的机器可读声明担保：声明不存在或与文档不符，脚本直接判未勾。**人检项**是文档层面的承诺，脚本查不了，靠人读。
> **基线生成脚本必须先跑本清单**：有未勾项就**拒绝生成基线**，并打印缺哪几项——否则"勾完才允许生成"只是一句道德劝告。
> **本清单自身不进基线**：它是一份过程文档，进基线会自锁（清单自己一变，基线就红）。但**生成基线的那次提交，message 里必须写明"契约 v1 冻结"**，日后靠 `git log` 就能定位 v1 的时点。

## 这份清单什么时候勾完

**不是"写代码之前全部完成"——分三段。** 容易混的是："契约 v1 落定"指的是**契约本身**的声明被冻结，不是全部代码写完。

| 时点 | 做什么 | 清单进度 |
| --- | --- | --- |
| **现在**（M0 开工前） | 文档侧定稿：信封 · 元数据 · 快照字段 · 坐标 · 命令参数 · 拒绝原因 · 事件负载 + 产出者 · 规则签名 · `PlacementInfo` 字段 | 5 条**人检**项可勾；11 条**机检**项的文档依据已就位 |
| **M0 骨架** | 写 `contracts/` 的机器可读声明（事件类型注册表 + 字段声明 + 签名声明） | 机检项随声明落地逐条勾上 |
| **M0 收尾** | 清单全勾 → 跑校验脚本 → 生成 `contracts/` 基线，提交写明「契约 v1 冻结」 | 16 条全勾 |

**两份基线管两件事，别混**：

- **`contracts/` 基线**（只增不改）管**接口面**——事件负载、命令参数、快照字段、规则签名的声明。**必须在 M1 写 `rules/` 实现之前冻结**，否则签名在实现期又被反向塑形（ADR-061 要避免的正是这个）。
- **`kernel/` + `rules/` 内容哈希基线**管**实现面**——M0 收尾生成，是 G4-1「内核文件差异为空」的裁判。实现改了它会红，声明改了它不管。

## 生成基线前的最后三步

1. **逐项勾完**——机检项由 `contracts/` 的声明担保，脚本判；人检项靠人读。
2. **跑一次"清单校验"**：`tools/` 下的检查脚本比对文档与声明，**有未勾项就拒绝生成基线**并打印缺项。
3. **生成基线并提交**，message 写明「契约 v1 冻结」——此后任何改动撞基线，都是一次显式的 major 变更提醒。

> **"已声明" ≠ "已过机检"**：状态栏写「已声明」只说明 `contracts/` 里有对应的机器可读声明（本阶段由 `tests/test_contracts_declarations.py` 断言），**机检脚本本身在 S6 落地**——它要比对文档与声明、并作为基线生成的前置门。第 1 / 2 / 5 / 6 / 7 / 8 项的最终判定要等 S6 的脚本跑过一次才算数。

## 勾完之后仍然要做的

- **冻结区基线**（`tests/baseline/kernel_hashes.json`）**在 M0 收尾生成**（内核闭环跑通那天），不是 M0 一开始——太早生成会让基线在开发期反复失效，橡皮图章就白刷了。
- **M0 内部状态清单**与 `PlacementInfo` 的字段随 M0 空壳一起定；快照字段随内核状态同步增补（第 15 项）。
