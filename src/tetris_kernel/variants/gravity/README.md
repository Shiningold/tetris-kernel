# 变体 A · 重力可旋转

> **这是变体自己的文档**——**玩法语义与取舍写在这里**，不靠读代码猜。
> 规格口径在 `docs/spec-M4.md` §7.2 · 计划在 `docs/plan-M4.md` §4 的 S3。

## 玩法

重力方向不再是"下"，而是**右**或**左**：方块从顶部中央出生，沿横向落下，贴着
侧墙堆起来。**形状表与踢墙表随轴变**——方块的"基准贴地面"对齐新的重力方向。

## 三个必须知道的限制

### 1. 轴是**规则集实例的常量**，不是 `ctx` 的字段

内核构造 `RuleContext` 时 `axis` 恒为 `GRAVITY_AXIS`（`kernel/core.py:114` 定义
`"down"` · `:2095` 写进 `ctx`），**内核自己不读 `ctx.axis`**。

**所以"重力方向随 `ctx.axis` 变"在不改内核的前提下做不到**——本变体的轴写在
**规则集实例**上（`GravityRuleSet(axis="right")`），`gravity_vector` **忽略
`ctx.axis`**。

**"切轴" = 换规则集**：登记三份轴不同的规则集（`gravity-down` / `gravity-right` /
`gravity-left`），**开局前选一个**。**局中随时转轴做不到**——内核没有"改轴"这条
通道，而 `switchRuleSet` **局中禁止且会重置局面**。

### 2. 消行仍是"**满行消**"

**内核的塌落是按行的**——`step_clear` 取 `group.index` 当**行号**，`step_collapse`
把被消的行删掉、上面补空行。

**横向重力若要"消列"**，内核的塌落就得改成**轴感知**——**那是内核改动 =
冻结区破例 = M4-D1 破**。**所以变体 A 的口径是：重力方向变，消行仍是"填满一行
消一行"。** 方块往右堆，满行照消——**玩法照样成立**。

### 3. 玩家的操作是**屏幕方向**的

内核的**软降硬编码向下**（`y + 1`）· **左右移动硬编码 `x ± 1`**——这两处要随轴
变就得改内核 → **不做**。

**所以横向重力下**：左右移仍是左右移、软降仍是往屏幕下方挪一格。**只有重力与形状
表随轴变。**

### 附：`up` 轴不做

`up` 轴的重力是 `(0, -1)`，而内核的碰撞判定把 **`y < 0` 当作"棋盘之上的出生
区"**（不算冲突 · `kernel/core.py:2011`）→ 向上重力的方块会**飞出棋盘**。
**四个轴做三个，是有理由的。**

## 表怎么来的（**这条是变体自定义语义，不是标准 SRS**）

- **形状表**：标准 `down` 轴的表**绕盒子中心做刚体旋转**——`right` 轴用视觉
  逆时针 90°（把"下"转到"右"），`left` 轴用视觉顺时针 90°。**绕中心转**保证
  **盒子尺寸不变**，旋转时方块不跳位。
- **踢墙表**：标准偏移**按轴做线性映射**（偏移是相对位移，映射是线性的）。

> **变体 A 的踢墙表是标准偏移的轴映射，不是旋转重力下的真 SRS。**
> 标准 SRS 的踢墙在横向重力下**没有物理对应物**——**别把它当成"横向重力下的
> 标准俄罗斯方块"**。

## 旋转手感：**屏幕旋转**，不是绕重力轴

"横向重力下的旋转应该是绕重力轴"——**那是三维的旋转，二维棋盘表达不了**
（投影到屏幕等于方块的厚度方向变了）。

**变体 A 的旋转是屏幕旋转**（方块在屏幕上转），**这带来一个好处**：形状整体
转了 90°，**但旋转手感不会反过来**——**刚体旋转与 SRS 的旋转可交换**
（`T(SRS_顺(down[r])) = SRS_顺(T(down[r]))`），所以**朝向编号不做重编号**，
玩家按 CW 看到的**仍然是屏幕上的顺时针**。

## 横向重力的一局为什么这么短（**这是结构性的，不是 bug**）

横向重力下方块**沿 x 走、y 不变**——它**永远不会自己往下掉**（重力没有 y 分量）。
于是：

1. 方块从顶行出生 → 沿 x 滚到侧墙 → **停在顶行**；
2. 下一个方块停在它的**左边**（堆叠方向是 -x）→ **顶行被一格一格占掉**；
3. 棋盘横向只有 **10 格**，而一个方块占 3–4 格 → **三四个方块就占满顶行** →
   出生点被占 → 顶出。

**所以横向重力的一局只有几个方块**（实测 `gravity-right` 种子 7：**3 个方块 / 451
帧**）。**这不是实现缺陷，是"内核零改动"的代价**：要让方块往屏幕下方堆，**得让
重力有一个 y 分量，或者让出生与堆叠按轴走**——**两件都要改内核**。

**玩家侧的补偿**：**软降仍然是往屏幕下方挪一格**（内核硬编码 `y + 1`）→ **手动按
软降能把方块往下压**，横向重力下那局是可以"玩"的——**但它不是自动的**。

**这条要写清楚**，免得后来人以为横向重力"没做完"。
