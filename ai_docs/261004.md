### 11:30 · `master` · `feature/m7-batch-a` · `PROGRESS.md` · `ai_docs/261004.md`（分支推送口径改：现在都推 · 主线推成 `master:main`）

**发生了什么**：用户指出——**此前「历史分支不推」是旧规矩，现在改成"都推"**。于是：**M7 立项那一笔**先 `--no-ff` 合并进本地 `master`（`93e54ae`）→ `git push origin master:main`（`e65d687..93e54ae`）→ **远端 34 条 `feature/*` 批次分支一次性全部推上去**（含 M0 的 `feature/batch-a`…`batch-e` 与 M1–M7 的各批次分支）。**顺手查清了一件以前一直没说的事**：**远端默认分支叫 `main`，本地主线叫 `master`**（两边内容始终一致）——所以推主线必须写 `master:main`。

**为什么这么写**（每条一句）：

- **远端有 `main` 也有 `releases`，没有 `master`** → **本地 `master` 没有上游跟踪**（`git branch -vv` 里它是裸的）→ **直接 `git push origin master` 会另建一条远端 `master`**，变成两条内容重复的主线 → **所以推主线写 `master:main`，且不推 `master` 本身**。
- **`git push --all` 在这里是个坑**：它会把本地 `master` 也推成远端 `master`（与 `main` 重复）→ **改用显式列出 `feature/*` 的方式推**（34 条 · 一次到位）。
- **`releases` 分支两边同 commit**（`d2835e1`）→ 推之前先查了祖先关系，**没有非快进风险**。
- **规矩变更要落到 PROGRESS**（不然下一个人还会按旧规矩"不推"）· **PROGRESS 里记下 `master:main` 这个写法**（这是**仓库的既有事实**，不是临时约定）。

**被否掉的方案**：① **`git push --all`** → 远端多出一条与 `main` 重复的 `master` ② **只推当前分支、不推历史分支** → 与用户"现在都推"的口径不符 ③ **把本地 `master` 改名成 `main`** → **改名会让本地历史与远端默认分支对不齐**（且仓库的 `releases` 线与全部历史提交都建立在 `master` 上）· **不值得为一条命名去动历史**。

**踩过的坑**：**`Remove-Item` 被本地安全策略拦**（整条命令被拒，**连 git commit 都没执行**）→ 改用 `rm -- "<绝对路径>"` 走 mavis-trash 的可恢复删除；**带 `cd` 的相对路径删除同样被拦**（"工作目录切换后无法安全校验目标"）→ **删除一律用绝对路径**。

### 11:20 · `master` · `docs/spec-M7.md` · `docs/plan-M7.md` · `docs/需求与边界.md` · `docs/决策记录.md` · `PROGRESS.md` · `ai_docs/261004.md`（M7 立项：现代外壳 · Qt 外置包 + 公开门面 · 双模式 · `config.toml`）

**发生了什么**：**M7 立项**——用户提出「前端渲染窗口很不现代，要改；并把所有内核该有的功能都展现出来；做游玩模式与开发者模式两个模式（像预览图那样）；要有 config 文件、能跳转游戏设置」。**先探现状**（M6 的 tkinter 面板 = 一块 Canvas + 200 个矩形 + 7 条文本；`docs/html源文件/产品预览_源文件.html` 是仓库里已有的"现代"基准），**再由用户拍板四项选型**（2026-10-29）：**PySide6/Qt**（**不作为内核的一部分，做成 GUI 外置插件**）· **可选 extra** · **仓库内独立包 + 只依赖公开门面** · **替换 tkinter 版**（`tetris graphics` 删掉 → `tetris qt`）· **`config.toml` 在项目根** · **同窗切换游玩/开发者双模式**。**最后一轮拍板**：**开发者模式不做装卸系统**（改为**只读展示系统清单**）。**规格与计划入档**：`docs/spec-M7.md` · `docs/plan-M7.md` · `G7-1`…`G7-6` 登记进 `docs/需求与边界.md` §12 · **ADR-101** · PROGRESS 三段改写。

**为什么这么写**（每条一句）：

- **"外置"必须有机器可验的边界**：仓库里 `tetris_kernel/__init__.py` 是空的——**外部前端想接内核只能 import 内部模块**（`host.assembly` · `kernel.snapshot`）→ **那不是外置，是扒着内部实现**。所以 M7 要**新增公开门面 `api.py`**，而 **Qt 包只 import 门面**这条纪律**必须是一条 AST 机检**（`G7-5`）——**靠自觉的纪律会松**。
- **先门面、后外壳**：外壳若先写，它会顺手 import 内部模块（近路最省事）→ 事后收紧纪律就得重写。**先把门面立住**，外壳只能从门面拿东西。
- **画面与手感不重写**：**`GraphicsRenderer`（快照 → `FrameModel`）与 `KeyboardInput`（DAS / ARR）是 M6 的两件宝贝**——**重写一遍就是两处真相**，而且手感一漂，**同一个种子会走出不同的局**（`G7-3` 就地红）。
- **开发者模式是"显形"不是"造功能"**：面板里的每一样东西（事件流 · 指标 · 日志 · 系统清单 · 指纹）**都已经是现成的订阅者**——M7 只是让它们看得见，**内核一行都不用改**。
- **"只读"比"能装卸"更诚实**：**这一局正在玩**的时候给装卸开关，玩家的局面会被 `ai` 接管或被 `growth` 的晶体改写，卸掉 `log` / `metrics` 还会让降级控制器失去输入——**观测面板不该有能力改正在观测的东西**（用户 2026-10-29 拍板改为只读）。**热插拔能力仍在注册表里**（M3 的 `G3-2` 守着），M7 不给它做交互入口。
- **节拍仍归宿主**：Qt 侧只注入"泵事件的 `sleeper`"，**不用 `QTimer` 接管游戏循环**（延续 ADR-100 ④）；**面板刷新按时间节流**（≥ 100 ms · **用时间戳比，不用定时器**）——**每帧十几条事件 × 每帧重排 = 主线程卡死**。
- **可选依赖是"两种用户都要能用"的唯一解**：**装 core 的人不该被迫装 GUI 栈**，**想要图形前端的人也不该为此放弃内核的零依赖**（`dependencies` 一字不改）。
- **配置放项目根**：用户明确选了 `config.toml`（`tomllib` 是标准库 → **零新依赖**）；**用户目录 `~/.tetris/` 新用户找不到** → 另留示例反而更绕。

**被否掉的方案**：① **继续 tkinter 只做美化** → **视觉天花板明显**（原生控件外观 · 无信息密集面板的排版能力）② **本地 Web UI**（标准库 `http.server` + SSE）→ **双击 exe 会拉起浏览器**，"双击即玩"这个交付形态被打破 ③ **FastAPI / Starlette + Vue / React** → **要引入 Node 构建链与多个依赖**，仓库从"纯 Python"变成混合仓，与"底座式 · 零依赖"的定位冲突 ④ **Arcade** → **它是 pyglet + OpenGL 之上的 2D 游戏库**（**4.0 仍在开发中** · 迁 pyglet 3.0）→ **强在画游戏场景，弱在信息密集面板**（`arcade.gui` 与 Qt Widgets 不是一个量级），**且它要接管自己的帧循环** → 与"节拍只有一个主人"正面冲突 ⑤ **PySide6 进主依赖** → 核心用户被迫拉一个 GUI 栈 ⑥ **让 Qt 层直接 import 内部模块** → 那不是外置 ⑦ **开发者模式里放装卸按钮** → 见上（改为只读）⑧ **`QTimer` 接管游戏循环** → 节拍就不只属于宿主了 ⑨ **让面板每帧重排** → 主线程卡死 ⑩ **配置放用户目录** → 用户找不到 ⑪ **用 JSON 当配置** → 不支持注释（tomllib 是标准库，JSON 换不来什么）。

**踩过的坑**：**读 `docs/决策记录.md` 尾部时按行号读到的内容与 `Edit` 的精确匹配对不上**（文件是 CRLF · 末尾无换行）→ **改成不含尾部换行的 `old_string`** 才落笔成功。

### 决定要点

**M5「性能回合」**（等价提速 · S0–S5 · ADR-096…098）

- **M5 的正题是"提速"，但提速最危险的失败模式不是变慢，是「快了但决策变了」**——那不是提速，是**换了一个 AI**（录像分叉 · 期望值重抄）→ **门两头都要有牙**：`G5-1`（结果逐条不变）· `G5-2`（代价降下来）。
- **安全网先行**（S1）：**参照实现冻结在 `tests/support/ai_reference.py`**（不进 `src/`）· **差分测试**（随机局面 + 悬空格子）· **手抄锚点表**（源码字面量 · 防"两份一起改坏" · M1 `G1-1` 的老坑）· **元守卫**（锚点不许有调用 · 参照不许 import 产品 · 参照源码钉 SHA-256）。
- **提速五招**（S2 · 剖面式实现）：剖面一次算好 · 解析式下落（每列二分）· 路径前缀和 · 增量打分 · 按朝向预计算。**候选集 · 深度 · 枚举顺序 · 权重 · 打分口径一字未改**。
- **实测**：决策 **P50 1607 → 259 μs（6.2×）** · **合并样本 P99 3418 → 1481 μs** · 全开档逻辑帧 **P99 3998 → 2428 μs**。**`G5-2` 判为未达标**（门槛 400 μs）——**门槛没改，也没为了让它变绿而改门槛**（**用户拍板「如实收官」** · ADR-098）。
- **P99 要配样本量**：一次 400 帧只有 **13 个决策样本** → 那个 P99 ≈ 最慢那一次 → **判 P99 须以多局合并样本判**（跨时段绝对值不可引用）。
- **预算固定**：AI 决策路径**无 `time`** · **不按耗时自适应** · **不分摊到多帧** · 候选预算**声明 = 实际枚举数**（`MAX_CANDIDATES` 40 → **64** 订正 · ADR-096/097）。
- **后续三条路留给用户拍板**：尾部优化（剪枝会改 AI 的选择 = 换 AI）· 改 NFR-2 口径（改需求）· 按合并样本口径重订门槛（改门）。

**M6「图形版」**（S0–S6 · ADR-100）

- **技术栈 = tkinter**（标准库 · 零新依赖）；**渲染器快照驱动**（`update_snapshot` → 重画整幅画面）——**不复用 `TerminalRenderer` 的事件镜像，也不改它的既有行为**（**复制事件镜像 = 两处真相**）。
- **输入整套复用 `KeyboardInput`**：图形层只做「tkinter 键名 → 归一键名」这一层翻译，**DAS / ARR / 命令翻译 / 两条输入事件全部由既有适配器负责**。
- **节拍仍归宿主**：图形侧只注入"泵 tkinter 事件循环的 `sleeper`"，输入走队列——**不用 `after()` 定时器接管游戏循环**（那样掉队与降级没人管）。
- **难度 = 起始等级**（1 / 5 / 10）· 用**既有的 `setLevel` 命令**落地（**不新增命令 = 契约面零变化**）；**主菜单 = 三玩法 + 三档**。
- **契约面零变更**（`G6-1`…`G6-6` 六门全绿）· **自检口 `--selftest`**（开真窗口跑 30 帧 · **退出码 0 = 通过** · windowed 模式下 stdout 是 `None`，打印不可靠）。

**v0.1.0 首个公开发布**（ADR-099）

- **GitHub Releases 直链** · **四个附件**（sdist · wheel · `tetris-cli.exe` · `tetris-play.exe` + `SHA256SUMS.txt`）· **tag `v0.1.0`** · 发布线走 `releases` 分支 → `--no-ff` 合并回 `master`。
- **打包脚本入库、产物不入库**：exe 是二进制（diff 不可读、仓库膨胀），但**重建脚本必须入库**——**不可复现 = 不可审计**；一条命令 `pwsh -File release/build.ps1` 重建全部产物。
- **PyInstaller 是构建期工具**，**不进 `pyproject.toml`**（既不是运行时依赖也不是开发工具）。

**M4 收官**（S0–S13 · 合并 `323a5ba`）

- **两个变体落地，内核文件差异为空**（`G4-1`）· **变体局回放多比一项扩展指纹**（`G4-2`）· **扩展槽帧末合并**（帧中合并 → 订阅者读到半帧状态）· **契约面零变更**（`G4-7`）。

- **M3 遗留三条进待办**（0 行 T-Spin 断 B2B 链 · `tspin-mini` 100 分送不到计分 · 事件数基线够不着 `piece:lock-delay-reset`）——**前两条修它要动冻结签名 → 要 major 变更预算**。

### 踩过的坑

- **终端渲染器把行尾空格去掉了** → 解析它的画面必须补齐到棋盘宽度，否则整盘错位。

## 2026-10-27

> 本节已按「往日压缩」规则压成要点：留决定与理由，过程叙述、当时的犹豫与已作废的中间状态已删。原始条目在 git 历史里。

### 决定要点

**M3「可扩展」**（S0–S12）

- **新增能力 = 新增文件**（`G3-1` · M3-D2）：**声明与工厂住在系统自己的包里**（`systems/<名字>/manifest.py`），宿主**不维护手写名单**——**集中登记在既有文件里，每个新系统都要改一个既有文件，那条判据当场失去牙齿**。
- **注册表的两个动作两态**：**装上 / 摘下**，**没有"暂停"**（要暂停就别装）；**"标记为不活跃"不是卸载**（还在订阅还在派发，那就是暂停）。
- **摘下顺序不可乱**：**① 先撤命令通道**（M3-D1 的头号坑：只退订不撤通道 = "人不在了，话还在说"）→ **② 退订** → **③ 停止派发**（**已入队的命令照常执行**：命令是已发生的事实，丢弃会让内核行为依赖卸载时机）→ **④ 发 `kernel:system:removed`**（**排在撤通道与退订之后**：订阅者在这个事件里看到的世界已经是"我不在了"）。
- **门的形态与 M0–M2 不同**：M0–M2 的门是"功能对不对"，**M3 的门是"接进来有没有改别人的东西"** → **一半是差异断言**（冻结区逐文件哈希全等 · 落地提交的变更清单只有新增文件），**行为断言证明不了这一点**。
- **每道门都有两面**：**行为面**（新系统确实干活）+ **零污染面**（它没改内核 / 规则 / 契约的既有部分）——**只测行为面，门就只剩一半**。
- **换规则集由内核裁决，宿主只注入解析器**（`RuleSetResolver`）：内核是唯一的状态所有者（N6）→ 换规则集是**状态变更** → 必须走命令通道 → **内核不认识具体规则集的名字**（NFR-5 的纯净度）→ **未登记 → `unknown_rule_set`，绝不拿当前规则集顶替**（顶替会让"四项不等"这个报错失去指向性）。
- **切换 = 重开一局，但帧号不归零**（帧号是宿主时间轴；`reset` 归零是因为它语义就是"从头开始"）。
- **成就按「事件类型 + 计数阈值」定义，不写死玩法名**（定义里出现"标准玩法"三个字，变体那边就不成立）· **实例不自己订阅**（订阅集只有一个真相 = 声明）· **旋转只算成功的**（受阻不计分，但**照样记着"发生过"**）。
- **系统层不许碰内核状态**（M2-D1）· **落盘只走 sink**（系统**知道有 sink，不知道路径** · AST 守卫守着"不 `open()`"）。
- **M2-C2 动用**：**跨切拒绝原因**（`start` / `pause` / `resume` / `reset` / `switchRuleSet` 从 M0 起就漏了 `quota_exceeded`）→ **修的是契约不是内核**（内核行为是对的 · 架构 §6.4）→ 并给跨切规则装上牙齿（**导入期当场炸**）。
- **性能账**（配对 A/B · 同机同时段 · 空机）：**M2 三系统的分发成本 = +151.0 μs/帧** · **M3 的内核与总线自身 = +2.0 μs/帧**（噪声量级 · 换规则集的入口只在局外被调）· **M3 两个新系统的增量 = +9.3 μs/帧**。**P99 仍在 1600 μs 预算内**。

**M2 收官**（S14 性能复测与千局基准 · S15 收尾与状态同步）

- **千局用多进程**（`ProcessPoolExecutor` · 一个局一个任务 · **汇总前按种子排序**，否则浮点累加顺序随调度变化 · 统计输出不可复现）。

### 决定要点

**M2 开工（S0）与批次 A（契约面与基线）**

- **开工前四条待决当场拍板**（ADR-074…077）：**落盘路径**（项目优先 → 不可写时回落 home，写入只有一处、不设环境变量）· **`replay:` 命名空间**（回放系统发事件，新开命名空间 = 扩大承诺面，要写明理由）· **`G2-5` 单独立门**（一条 NFR 没有门 = 没人验）· **期望源搬进 git 背书**。
- **批次 A 的顺序不可乱**：**S1 声明 → S2 守卫 → S3 刷基线**——**守卫要管住第一次刷新之后的那份文件**，所以它不能排在刷新之后。
- **契约面只增不改**：既有 360 条键的哈希**逐条不变**，新增 **23** 条（5 条事件的 13 个负载字段 + 每条 2 个结构性键），事件 44 → **49**，命令仍 16、快照仍 22 顶层；契约基线 360 → **383** 条。
- **"新增键在进基线之前没有牙齿"**：契约 v1 的口径是「允许新增键」→ 新键不在基线里 → 落在"新增键"那一支 → **改了它的类型、删掉它的声明，都没有任何一层会拦**。**S3 不是 bookkeeping，它是那 23 个新键唯一的保护**（实测：刷完后把 `event/replay:frame-stepped/commandCount` 从 `int` 改成 `str` → 报「已有键哈希变化（红）」）。
- **git 背书守卫的三个计划外必做项**：比对前**归一化换行符**（`core.autocrlf=true` 且无 `.gitattributes` → 逐字节比必然永远红）· git 仓库根从"文件所在处"问起（不是从工具自身问起）· 红项带 ASCII 标记（Windows 的 GBK 管道会把中文打散）。
- **残余上限照旧写实**：从"静默绕过"变成"**留痕绕过**"，**挡不住蓄意绕过**——能把两个文件改好再提交的人，也能改好 git 历史。

**批次 B（底座）**

- **落盘路径**：项目优先 → 不可写时回落 home（`<项目根>/.tetris-data/` → `~/.tetris/`），**写入只有一处、不设环境变量**；**回落要能被看见**（返回值给程序读 + stderr 一行给人看——**静默换地方 = 用户找不到录像**）；**原子替换**（先写 `.part` 再 `os.replace`）。
- **总开关的牙齿在"装配"不在"订阅"**：`OBSERVABLE_SYSTEM_FACTORIES` 在开关关掉时**一个都不被调用**——只关订阅而系统还在跑，`G2-3` 会**假绿**。（批次 B 时那张表是空的，批次 C 填入即长牙。）
- **总线增强三件套**：中间件（`EventBus.use`，分发链上横切处理）· 历史查询（`query_history`，**复用订阅模式的那套写法**，**不做按序号的随机跳转**）· 计数（`counts`，**累计**，不靠环形历史算——历史一满计数就跟着丢）。
- **`bus/` 独立基线与代码同笔落笔**：**只有基线没有门禁，它只是躺在仓库里的一份 JSON**。

**批次 C（可观测三系统）**

- **三个系统只订阅事件**（M2-D1）· **落盘只走 sink**（`systems/log` 连 `pathlib` 都不 import）· **录像只录被接受的命令且不可丢**（M2-D3：**靠没有队列保证，不靠队列策略**——队列本身就是丢的来源）。
- **级别由系统内映射得出**（ADR-046）：精确事件类型 → 命名空间 → 兜底；**事件不自带级别**（同一事件排障时是 trace、演示时是 info）。
- **指标口径写死在系统内**：每个 `clock:tick` 一条 `metric:sampled`；**跳过自产**（不自激）；分母为 0 记 0.0。
- **回放 = 原样派发录下的命令**（来源透传原值 · ADR-062）· **帧边界由录下的 `tick` 决定** · **中途开始选①**（从头重放到第 N 帧，状态自然正确）。
- **暂停落为宿主级**（ADR-033）——**S9 唯一一处偏离计划字面的地方**：内核级 pause 是**被接受的命令**，会被录进录像（**回放自己污染录像**），且会让内核进入 `paused`，之后录下的命令全被门禁拒掉，**重放当场分叉**。
- **录像头追加「局末四项」**（ADR-078）——**录像不带基准，比对就没法做**。
- **装配层一个事件都不发**（ADR-079）——种子与规则集标识从 `kernel:ready` 事件里取。
- **事件数基线按 spec §6.5 显式刷新**（理由"M2 引入可观测系统"）：常态帧 P50 5 → 12 · P99 5 → 12 · max 15 → 32（多出来的是 `log:entry` 与 `metric:sampled`），**常态帧数 7381 逐字未变**——变的只是构成不是局数。

**批次 D 前四笔（S10–S13）**

- **S10 存档恢复需要内核恢复入口**（ADR-080）：**只解冻 `kernel/core.py` 一个文件**——**M2 唯一一次动冻结区**，冻结区基线显式刷新带理由，`rules/` 一个字节没动。
- **存档 ≠ 录像**：存档**自包含**（版本 · 种子 · 规则集标识 · **随机源状态** · 棋盘 · 计分 · 计时器 · 活动方块），录像只记被接受的命令。**随机源状态不在存档里 → 恢复后随机序列从头开始 → 后续每帧都可能不同**。**格式 = 单个 JSON 文档**（版本 `v1`）；缺字段 / 类型错 / 未知版本 → `ValueError`（**不静默兜底**）。**恢复不发新事件类型**——判据只能是"**恢复后事件流逐条相等**"。
- **S11 事件轨迹落成「有序字段对」；面板与导出器是同一个对象**（ADR-081）：`EventPanel` 是**普通订阅者**（`pause` / `resume` / `pause_at` / `by_namespaces` / `export_text` / `export_bytes` / `write_to`）；导出用 JSON Lines；过滤按 `namespace_of`。
- **S12 降级控制器住在宿主层**（ADR-082）：① 关 debug 事件 · ② 抬日志阈值 · ③ **关历史缓冲不是关分发**（总线提供 `set_history_enabled()`）；**手动档位只接受 0 / 1 且是"下限"**；**默认不装配**（喂帧开销的接线留给 M3 的实时宿主）。**第 ① 档是类型级精确黑名单**，不是抬 `min_level`（trace 级的 `rng:next` 不跟着关）。
- **S13 五道门判据 + 元守卫**：§5.2 那张表是**单一权威**，元守卫**读表**逐条比对，**选不到就红并点名那个入口**。
- **`G2-4` 的用例提前到 S13 落地**——元守卫**不许留"待落地"的例外**（M1 的 `G1-2` / `G1-3` 就是那么消失的）。
- **错误级联防线**（ADR-083）：**同一个订阅者在一轮排空里只报一次错**，再炸只记 trace（**一轮排空 = 级联的边界**）。

### 踩过的坑

- **门判据写在真实装配上，才会逼出真缺陷**——`G2-2` 写在"三个可观测系统全开"的真实装配上，**当场挂死**：抛错订阅者 → `kernel:error` → **日志系统把错误写成 `log:entry`** → 那条新事件又落回抛错订阅者 → 又一个 `kernel:error` → ……**闭环**（事件数无上界 · 宿主卡死）。原来的防线只挡"错误事件自身再产生错误事件"，**挡不住这条间接路径**。**写在"关掉可观测"的特殊配置上 → 门是绿的，但真实装配里的缺陷没人看见**。
- **"自证被打破"红不了——只能靠源码字面量守卫抓**：把"手抄的期望值"改成"实现算出来的值"之后，**它与实现永远相等**，门判据从此什么都不验（**M1 `G1-1` 的老坑在 M2 的翻版**）。抓住它只能查**它是不是还在源码里以字面量写着**。
- **降级判据用 P99 也可能漏掉单个尖峰**：600 个样本的 P99 取第 **594** 个，**最慢的那 6 个不算**——判据的口径是"**窗口里最慢的那 1%**"，不是"任何一个尖峰"。用例要造 **7 个尖峰**（占窗口 1.17%）才让 P99 看见它，而**均值 0.59ms 在预算内**——**换成均值这条判据就瞎了**。
- **反向验证第一次没红，先怀疑注入**：批次 B 的 S4 第一次注入"两处都写"时把"坏"写成了同处写两遍，测试没红——**是注入错，不是测试没牙**。
- **"永远红"比"没有守卫"更坏**：守卫逐字节比换行符 → 必然永远红 → **让人以为背书在管着**，实际形同虚设。**跨平台比文件内容必须先归一化换行符**。
- **登记守卫抓不到"少了一条声明"**：它抓的是"**用了没登记**"，声明被删时那个字面量一起没了。
- **"新增键"在进基线之前是没有牙齿的**——**计划书自己也会写错**（plan 说基线必红，实测是绿的）。**留着错的计划，下一个人会去改工具**，把正确的"新增键放行"改成"新增键报红"，那才是真的把契约面改坏。
- **半截文件比没有文件更坏**（会让 `G2-1` 拿截断内容当基准比出**假红**）→ 落盘走**原子替换**。
- **内核级 pause 不能录进录像**：它是**被接受的命令** → **回放自己污染录像**，且会让内核停在 `paused` 让之后的命令全被拒 → **重放当场分叉**。
- **一局写两遍 ≠ 备份**——冗余一份便于携带，但"读哪一份"立刻成了问题，同一局录像在两处分叉，**`G2-1` 会假红**。
