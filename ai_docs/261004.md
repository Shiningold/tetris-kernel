**为什么这么写**（每条一句）：

- **H1 · 三个产物各有各的落盘出口**（ADR-085）：**「写入只有一处」说的是一条落盘路径，不是一个文件**——ADR-074 那句口径被读成了「一个文件」。三个产物共用一个出口 → **后写的覆盖先写的**（用覆盖语义写日志，文件里只剩最后一条）。**追加与覆盖是两种语义、两个类**，不是一个类的两种模式（**写错了就是数据丢**）。
- **H2 · 局末四项的 provider 只能由宿主注入**：棋盘指纹的算法**只有内核那一份**（抄第二份就是第二个真相），而系统层**不碰内核状态**（M2-D1）——工厂**拿得到 provider、拿不到 kernel**（最窄能力原则）。**四项的算法只写一处**（`host/replay.py` 的 `four_items_of()`，重放驱动器与装配层共用）。
- **H3 · 「没比」不是「过了」**：`replay` 在录像没有局末四项时退出码原本是 **0**（`equal is not False`）——脚本把「没比」当成「过了」。**退出码 2**（不是 1）——2 在这个 CLI 里的既有含义是「工具没干成活」，**与「四项不等」（1）区分开**。
- **M1 · 没登记的规则集显式拒绝**：`rule_set` 永远是标准规则集、只换 `rule_id` → 变体录像**必然「四项不等」**，而报错只说「四项不等」，**排查方向会被带偏**。接线表 `RULE_SETS` 住在**宿主层**（`rules/` 是冻结区）。
- **M2 · 参数不合契约当场报错**：静默丢参**最坏**——录出来的命令少了一半，重放时状态对不上，**却查不出原因**。同一个概念（录像里的参数必须符合契约）本来有三种处理（两处报错、一处静默丢参），**现在只有一种**。
- **M3 · 措辞与行为对齐**：ADR-081 定了「面板与导出器是同一个对象」——**面板停在哪，导出就到哪**。`--pause-at` 与 `--export` 同时给时**stderr 上有一行响亮提示**（**不响亮就等于骗人**）。
- **M4 · 面板留存有界**：`--limit` 只裁显示不管留存 → 面板驻留**百万级信封**。与 `MetricsSystem` 的采样环形缓冲**同款口径**（默认有界；要全量就**显式**说）。
- **L1 · 级联防线按身份去重**：**同名不等于同一个订阅者**——两个同名订阅者会互相抑制报错，**第二套的异常被吞掉**。中间件的身份是**登记序号**（同一个函数登记两次就是两个中间件）。
- **L2 · 镜像里的布尔不算整数**：`isinstance(True, int)` 为真——**坐标也一样**（`True == 1`，布尔坐标会**悄悄别名**到整数那一格）。同项目其它取整处都排了布尔，**只有这里漏了**。
- **L3 · 可写性真写一次**：`os.access` 在 Windows 的 ACL 场景下**不可靠**——ADR-074「不可写时回落 home」这条承诺**兑现不了**。**判不准就当不可写**（回落路径是安全的那一侧）。

**被否掉的方案**：① **一个类的两种模式**（`FileSink(path, mode="append")`）——用错了就是数据丢，**让类型说清楚**比让人记参数强 · ② **让系统层自己去取内核快照**——破 M2-D1 · ③ **工厂拿内核而不是拿 provider**——最窄能力原则 · ④ **在装配层另抄一份四项算法**——两处算出不同的值 → 四项比对假红 · ⑤ **`or STANDARD_RULESET` 兜底**——兜底就是**静默分叉**，报错信息还会指向错误的方向 · ⑥ **另存一份全量轨迹来兑现「完整轨迹」**——与 ADR-081 的「同一个对象」冲突（**两个订阅者意味着每条事件被投递两次**）· ⑦ **用可调用对象本身当中间件的身份**——同一个函数登记两次就成一个中间件 · ⑧ **拿 `os.access` 当判据**（或只在 docstring 里写它的不可靠）——**承诺要么兑现，要么明说兑现不了**；选兑现。

**连带**：**唯一的破坏性变更**是 `assemble(sink=…)` → **`assemble(sinks=…)`**（`Assembly.sink` → `Assembly.sinks`，提交标题带 `!`）。**新落一条 ADR-085**；**契约基线 383 条零变化**（`M2-C1` 仍未动用）· **冻结区 `kernel/` + `rules/` 一个字节没动** · **事件数基线没变**（复检绿 → 不刷新）· **`bus/` 独立基线显式刷新一次**（L1 改了 `bus/bus.py` · 带 `--reason` · 理由写进提交正文）。

**为什么这么写**：

- **「局」的形态决定基准有没有意义**：预算判的是"1000 局模拟要多久"，**局的形态就是这件事的工作量**。**纯重力局**（宿主只派 `tick`）每局 **7671 帧** → 1000 局并行约 **31 分钟**，**卡在 30 分钟预算线上过不了**；**参考策略局**每局约 **2434 帧** → 1000 局 **467.6 秒**，**余量充足**（ADR-084）。
- **参考策略是测试件，`src/` 不 shipping 参考 AI**：从 `tests/support/policy.py` **动态载入**（`tools/` 不静态 import `tests/`，那会让类型检查去管一棵测试树），**载入不到就明确报错**——**不静默退化成纯重力局**（那量的是另一件事，两个数对不上，预算就失去意义）。
- **预算与种子表起点只有一处真相**：与降级阈值 `DEGRADE_P99_MS` 同住 `host/performance.py`。**工具与门判据必须跑同一批局**——一局的帧数随种子在 1755–3300 之间波动，**种子表不同 → 总工作量不同 → 两个数不可比**。
- **配对 A/B 分三档**：**M1 终局的装配里根本没有三个可观测系统**（M1 的 `Assembly` 只有内核 / 总线 / 时钟）→ 所以「M1 默认」≡「M2 `--no-observability`」；两者的差值归 **M2 内核与总线自身**，「M2 默认装配 − M2 裸跑」归**三个可观测系统的分发成本**。**只跑两档就分不清这两件事**。
- **判据是墙钟总时长**；「每局耗时之和」**含并行争用**，是串行时间的**上界**，不作判据。

**被否掉的方案**：① **纯重力局**——卡在预算线上过不了 · ② **固定帧数模拟**——量的是"跑 N 帧要多久"，不是"玩完一局要多久" · ③ **「关闭事件分发」的快速模式**——ADR-018 已明写否决（破坏事件完备性 · B-1 / B-10）· ④ **把参考策略搬进 `src/`**——库里不 shipping 一个"参考 AI" · ⑤ **工具与门判据各写一份种子表起点**——两个真相 → "同一批局"落空 · ⑥ **只跑 M1 / M2 两档**——分不清是内核变了还是分发成本 · ⑦ **把「每局耗时之和」当串行实测值**——那串数含并行争用。

**实测（2026-10-27 · 同机同时段 · 配对 A/B 交替采样 3 轮 · `--frames 10000 --warmup 1000 --seed 1` · 每轮 6381 个常态帧样本）**：

| 档 | P50 中位 | P99 中位 | max 最大 | 超预算帧 | 每帧事件数 P50 / max |
| --- | --- | --- | --- | --- | --- |
| M1 默认（**无三个可观测系统**） | 411 μs | 681 μs | 3722 μs | 49 / 6381 | 5 / 15 |
| M2 `--no-observability` | 421 μs | 594 μs | 4168 μs | 50 / 6381 | 5 / 15 |
| M2 默认装配（三系统全开） | 566 μs | 796 μs | 5418 μs | 87 / 6381 | 12 / 32 |

- **两个差值各归各的因**：**M2 裸跑 vs M1 默认 = +10 μs/帧（+2.4%）**——**M2 的内核与总线自身几乎没有增量**（这是 **M2-D1「可观测是订阅者、不是内核的一部分」的性能侧证据**）；**M2 默认装配 vs M2 裸跑 = +145 μs/帧（+34%）**——**三个可观测系统的分发成本**，对应每帧事件数 **5 → 12**。
- **P99 仍在 NFR-2 预算内**：M2 默认装配 P99 **796 μs = 1600 μs 的 49.8%**（P50 35.4%）。**跨时段的绝对值不可引用**——只引用配对差值。
- **千局基准**（`--thousand-games 1000` · 种子 `20261000` 起 · 16 进程 · 参考策略局）：**墙钟 467.6 秒**（预算 1800 秒的 **26%**），合计 **2,434,308 帧**（平均 2434 帧/局）。**门判据那一批（录 + 放，同一批局、同一时段）：507.0 秒**（预算的 **28%**）——**这才是 `G2-4` 的判据数**；工具那个数是**工作量子集**，用来看机器余量。
- **事件数基线复检绿**：7381 常态帧 · P50 12 · P99 12 · max 32（**逐帧未变，不用刷新**）。

**反向验证真跑过并精确复原**：`THOUSAND_BUDGET_SECONDS` 改成 `0.001`（**秒**）→ `G2-4` **报红**（`1000 局跑了 507.0s，超预算 0.001s`）→ 精确改回 `30 * 60`。

### 决定要点

**M2 开工（S0）与批次 A（契约面与基线）**

- **开工前四条待决当场拍板**（ADR-074…077）：**落盘路径**（项目优先 → 不可写时回落 home，写入只有一处、不设环境变量）· **`replay:` 命名空间**（回放系统发事件，新开命名空间 = 扩大承诺面，要写明理由）· **`G2-5` 单独立门**（一条 NFR 没有门 = 没人验）· **期望源搬进 git 背书**。
- **批次 A 的顺序不可乱**：**S1 声明 → S2 守卫 → S3 刷基线**——**守卫要管住第一次刷新之后的那份文件**，所以它不能排在刷新之后。
- **契约面只增不改**：既有 360 条键的哈希**逐条不变**，新增 **23** 条（5 条事件的 13 个负载字段 + 每条 2 个结构性键），事件 44 → **49**，命令仍 16、快照仍 22 顶层；契约基线 360 → **383** 条。
- **"新增键在进基线之前没有牙齿"**：契约 v1 的口径是「允许新增键」→ 新键不在基线里 → 落在"新增键"那一支 → **改了它的类型、删掉它的声明，都没有任何一层会拦**。**S3 不是 bookkeeping，它是那 23 个新键唯一的保护**（实测：刷完后把 `event/replay:frame-stepped/commandCount` 从 `int` 改成 `str` → 报「已有键哈希变化（红）」）。
- **git 背书守卫的三个计划外必做项**：比对前**归一化换行符**（`core.autocrlf=true` 且无 `.gitattributes` → 逐字节比必然永远红）· git 仓库根从"文件所在处"问起（不是从工具自身问起）· 红项带 ASCII 标记（Windows 的 GBK 管道会把中文打散）。
- **残余上限照旧写实**：从"静默绕过"变成"**留痕绕过**"，**挡不住蓄意绕过**——能把两个文件改好再提交的人，也能改好 git 历史。

**批次 B（底座）**

- **落盘路径**：项目优先 → 不可写时回落 home（`<项目根>/.tetris-data/` → `~/.tetris/`），**写入只有一处、不设环境变量**；**回落要能被看见**（返回值给程序读 + stderr 一行给人看——**静默换地方 = 用户找不到录像**）；**原子替换**（先写 `.part` 再 `os.replace`）。
- **总开关的牙齿在"装配"不在"订阅"**：`OBSERVABLE_SYSTEM_FACTORIES` 在开关关掉时**一个都不被调用**——只关订阅而系统还在跑，`G2-3` 会**假绿**。（批次 B 时那张表是空的，批次 C 填入即长牙。）
- **总线增强三件套**：中间件（`EventBus.use`，分发链上横切处理）· 历史查询（`query_history`，**复用订阅模式的那套写法**，**不做按序号的随机跳转**）· 计数（`counts`，**累计**，不靠环形历史算——历史一满计数就跟着丢）。
- **`bus/` 独立基线与代码同笔落笔**：**只有基线没有门禁，它只是躺在仓库里的一份 JSON**。

**批次 C（可观测三系统）**

- **三个系统只订阅事件**（M2-D1）· **落盘只走 sink**（`systems/log` 连 `pathlib` 都不 import）· **录像只录被接受的命令且不可丢**（M2-D3：**靠没有队列保证，不靠队列策略**——队列本身就是丢的来源）。
- **级别由系统内映射得出**（ADR-046）：精确事件类型 → 命名空间 → 兜底；**事件不自带级别**（同一事件排障时是 trace、演示时是 info）。
- **指标口径写死在系统内**：每个 `clock:tick` 一条 `metric:sampled`；**跳过自产**（不自激）；分母为 0 记 0.0。
- **回放 = 原样派发录下的命令**（来源透传原值 · ADR-062）· **帧边界由录下的 `tick` 决定** · **中途开始选①**（从头重放到第 N 帧，状态自然正确）。
- **暂停落为宿主级**（ADR-033）——**S9 唯一一处偏离计划字面的地方**：内核级 pause 是**被接受的命令**，会被录进录像（**回放自己污染录像**），且会让内核进入 `paused`，之后录下的命令全被门禁拒掉，**重放当场分叉**。
- **录像头追加「局末四项」**（ADR-078）——**录像不带基准，比对就没法做**。
- **装配层一个事件都不发**（ADR-079）——种子与规则集标识从 `kernel:ready` 事件里取。
- **事件数基线按 spec §6.5 显式刷新**（理由"M2 引入可观测系统"）：常态帧 P50 5 → 12 · P99 5 → 12 · max 15 → 32（多出来的是 `log:entry` 与 `metric:sampled`），**常态帧数 7381 逐字未变**——变的只是构成不是局数。

**批次 D 前四笔（S10–S13）**

- **S10 存档恢复需要内核恢复入口**（ADR-080）：**只解冻 `kernel/core.py` 一个文件**——**M2 唯一一次动冻结区**，冻结区基线显式刷新带理由，`rules/` 一个字节没动。
- **存档 ≠ 录像**：存档**自包含**（版本 · 种子 · 规则集标识 · **随机源状态** · 棋盘 · 计分 · 计时器 · 活动方块），录像只记被接受的命令。**随机源状态不在存档里 → 恢复后随机序列从头开始 → 后续每帧都可能不同**。**格式 = 单个 JSON 文档**（版本 `v1`）；缺字段 / 类型错 / 未知版本 → `ValueError`（**不静默兜底**）。**恢复不发新事件类型**——判据只能是"**恢复后事件流逐条相等**"。
- **S11 事件轨迹落成「有序字段对」；面板与导出器是同一个对象**（ADR-081）：`EventPanel` 是**普通订阅者**（`pause` / `resume` / `pause_at` / `by_namespaces` / `export_text` / `export_bytes` / `write_to`）；导出用 JSON Lines；过滤按 `namespace_of`。
- **S12 降级控制器住在宿主层**（ADR-082）：① 关 debug 事件 · ② 抬日志阈值 · ③ **关历史缓冲不是关分发**（总线提供 `set_history_enabled()`）；**手动档位只接受 0 / 1 且是"下限"**；**默认不装配**（喂帧开销的接线留给 M3 的实时宿主）。**第 ① 档是类型级精确黑名单**，不是抬 `min_level`（trace 级的 `rng:next` 不跟着关）。
- **S13 五道门判据 + 元守卫**：§5.2 那张表是**单一权威**，元守卫**读表**逐条比对，**选不到就红并点名那个入口**。
- **`G2-4` 的用例提前到 S13 落地**——元守卫**不许留"待落地"的例外**（M1 的 `G1-2` / `G1-3` 就是那么消失的）。
- **错误级联防线**（ADR-083）：**同一个订阅者在一轮排空里只报一次错**，再炸只记 trace（**一轮排空 = 级联的边界**）。

### 踩过的坑

- **门判据写在真实装配上，才会逼出真缺陷**——`G2-2` 写在"三个可观测系统全开"的真实装配上，**当场挂死**：抛错订阅者 → `kernel:error` → **日志系统把错误写成 `log:entry`** → 那条新事件又落回抛错订阅者 → 又一个 `kernel:error` → ……**闭环**（事件数无上界 · 宿主卡死）。原来的防线只挡"错误事件自身再产生错误事件"，**挡不住这条间接路径**。**写在"关掉可观测"的特殊配置上 → 门是绿的，但真实装配里的缺陷没人看见**。
- **"自证被打破"红不了——只能靠源码字面量守卫抓**：把"手抄的期望值"改成"实现算出来的值"之后，**它与实现永远相等**，门判据从此什么都不验（**M1 `G1-1` 的老坑在 M2 的翻版**）。抓住它只能查**它是不是还在源码里以字面量写着**。
- **降级判据用 P99 也可能漏掉单个尖峰**：600 个样本的 P99 取第 **594** 个，**最慢的那 6 个不算**——判据的口径是"**窗口里最慢的那 1%**"，不是"任何一个尖峰"。用例要造 **7 个尖峰**（占窗口 1.17%）才让 P99 看见它，而**均值 0.59ms 在预算内**——**换成均值这条判据就瞎了**。
- **反向验证第一次没红，先怀疑注入**：批次 B 的 S4 第一次注入"两处都写"时把"坏"写成了同处写两遍，测试没红——**是注入错，不是测试没牙**。
- **"永远红"比"没有守卫"更坏**：守卫逐字节比换行符 → 必然永远红 → **让人以为背书在管着**，实际形同虚设。**跨平台比文件内容必须先归一化换行符**。
- **登记守卫抓不到"少了一条声明"**：它抓的是"**用了没登记**"，声明被删时那个字面量一起没了。
- **"新增键"在进基线之前是没有牙齿的**——**计划书自己也会写错**（plan 说基线必红，实测是绿的）。**留着错的计划，下一个人会去改工具**，把正确的"新增键放行"改成"新增键报红"，那才是真的把契约面改坏。
- **半截文件比没有文件更坏**（会让 `G2-1` 拿截断内容当基准比出**假红**）→ 落盘走**原子替换**。
- **内核级 pause 不能录进录像**：它是**被接受的命令** → **回放自己污染录像**，且会让内核停在 `paused` 让之后的命令全被拒 → **重放当场分叉**。
- **一局写两遍 ≠ 备份**——冗余一份便于携带，但"读哪一份"立刻成了问题，同一局录像在两处分叉，**`G2-1` 会假红**。
