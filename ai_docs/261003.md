### 15:10 · `feature/batch-c` · `src/tetris_kernel/contracts/snapshot.py` · `src/tetris_kernel/kernel/` · `tests/test_frame_model.py` · `docs/`（契约 v1 增补：兑现重力间隔）

**发生了什么**：批次 C 收口时挂账的卡点「重力间隔要不要兑现」**按裁定兑现**——在 S17 冻结基线之前走一次正式的契约增补流程（提交 `ab6211d`）：快照顶层字段 **21 → 22**（新增 `gravityTimer`），内核的帧模型开始**消费规则集已经冻结的 `gravity_interval(ctx)` 签名**，方块按等级表的间隔落格（标准 1 级 = 60 帧落一格），不再每帧落一格。**事件面零改动**——`clock:gravity` 的负载与语义一个字节没动，既有键的基线哈希一个没动（基线条目 355 → 356，只是新增键）。

**为什么这么写**：

- **「契约声明了接口却不兑现」本身就是问题**：`gravity_interval` 在 S5 就进了 `contracts/rules.py`（ADR-061 冻结签名），S13 也把标准实现写好了，却**没有任何调用者**——内核的 `step_gravity` 只取 `gravity_vector` 的方向向量。**签名晚于实现必被实现反向塑形**，反过来也一样：**签名定了不兑现，等于留了一个空的承诺**。兑现它绕不开一个跨帧状态（"还有几帧才落格"），而**内核状态必须全部进快照**（契约清单第 15 项 / FR-10.2 的存档恢复）→ 只能给契约加字段。
- **走的是 major 的纪律，不是 major 的破坏**：按架构 §4.4 的基线纪律（允许新增键、禁止已有键的哈希变化），这个改动**落在允许的一侧**——既有键的哈希一个没动，所以**不撞基线**。但仍然显式走流程：写 ADR-066 · 改需求 §8.3 的字段表 · 改契约清单第 3 项 · 补六条回归守卫。**「不撞基线」不等于「可以随手改」**——冻结面的一次改动就该留痕。
- **计时语义定成「还有几帧才落格，0 = 本帧到期」**，而不是「已经过了几帧」：倒计时能直接回答"下一帧会不会落"，也让「随方块出生重置」这件事有明确落点（出生时记 `间隔 − 1`，第 `间隔` 帧落第一格）。**中间踩过一次坑**：第一版写成「`timer == 0` 时**下一帧**才落」，于是到期帧整整差一帧——用例直接把这个差值抓了出来（`assert 0 == (0 + 1)`），改判断顺序才对。**差一帧的 bug 用例抓得住，是因为断言钉的是"恰好落一格"而不是"动了"**。
- **触地判定特意留在每帧做**，与落格脱钩：间隔只管「什么时候下移」，不管「有没有到底」。若把触地也等到落格帧才判，方块贴地后要最多等一个间隔才锁定——那是**锁定延迟**，与 M0 的「落即锁」（`lockTimer` 恒 0）冲突。判据用「幽灵落点走 0 格」（等价于"再往重力方向走一格会撞"），既复用已有的幽灵计算（不额外加一遍碰撞扫描），又让触地与锁定留在同一帧。**这条有专门的一条用例守着**（`test_a_grounded_piece_locks_immediately_despite_the_interval`）——间隔一旦拖慢锁定，用例会当场红。
- **间隔变短时把剩余帧数夹到新间隔**：等级下降会让间隔变小（60 → 5），若不夹，节奏会停在旧间隔上。夹的语义是「等级一改，立刻按新节奏走」。
- **实测口径变了**：`sim --frames 100` → 已放置 **0** 块（1.67 秒放不下一块，这是真实节奏该有的样子）；`sim --frames 10000` → 已放置 **12** 块、phase `game_over`（无人操作时方块都落在同一列堆叠，终局与兑现前相同，但事件数从 20449 涨到 41479——因为现在前 ~8000 帧都在真打，每帧都有 `clock:gravity` 与帧末的 `state:changed`，而兑现前那 9750 帧全是「tick 被拒」的拒绝路径）。**这直接改善了开放项 C 的采集口径**：常态帧的数不再被拒绝路径污染。

**被否掉的方案**：

- **维持「每帧一格」把口径写死**（M1 再兑现）——那就要在 M1 重开契约，而 M1 正是要大量加规则的时候，契约在那时更难动；且 M0 阶段就要交出两个**采不准**的开放项。
- **改 `clock:gravity` 的负载或语义**（比如加一个「本帧是否真的落格」的字段）——**没必要**：未到期时 `dx` / `dy` 记 0，与既有的「重力受阻时位移为 0」是**同一条语义**（订阅者据此知道"这一帧重力没能推动方块"）。改负载会撞基线、会让旧录像失效，收益却只有"更精确"——不值。
- **把计时放进 `RUNTIME_ONLY_STATE`（不进快照）**——省掉契约改动，但存档恢复后节奏会重置（FR-10.2：恢复后的局面必须与未中断时一致）。**跨帧的节奏状态必须进快照**，这条没得商量。
- **让内核自己维护一张间隔表**（绕过规则集）——那是把规则抄进内核，变体会立刻分叉（ADR-061 立这条线就是为了让变体只改规则集）。
- **把间隔留给宿主层**（宿主决定何时调 `advance_frame`）——宿主不知道等级，也拿不到规则集；且帧推进的语义是内核的事（架构 §6.2）。

### 踩过的坑

- **审查报告不是完全可靠的清单**——S2 报告自陈 11 项实为 12 · S3-M1 的"11 处"实为 9 处 · S2–S6 汇总报告 §1 的交叉引用指错节（§4 → §3.2）· 同一报告 §4 脚注的 46 文件拆分算成 47。**结论对不代表过程省**，行号 / 计数 / 哈希都要自己复跑。

- **门会静默失效**——pyright 的 `overrides` 键在 1.1.414 已不存在，只警告不报错，strict 一直失效而退出码是 0；`tools/` 里 4 处类型不精确 IDE 看得见、项目的门看不见（`include` 只有 `src`）。**会静默失效的质量门比没有质量门更坏。**
- **守卫恒真**——`RUNTIME_ONLY_STATE` 原本写中文散文，快照字段是英文标识符，**两边不是一个命名空间，交集恒空**，断言永远绿。守卫要能触发，前提是**它守的两边在同一套命名体系里**。
- **键与声明能分家**——字段表的键改了而 `FieldSpec.name` 没改，没有任何断言要求两者相等（反向验证抓到的真实缺口）。已补断言。
- **文法规则字面排除自家示例**——形态 10 的 T 范围写"形态 1–9"，而同行的示例 `Sequence[Sequence[int]]` 里 T 就是形态 10。
- **"AST 静态检查的固有边界"这个定级经不起推敲**——报告把 from-import 与别名归为固有边界，实际两者都可静态判定（`ast.ImportFrom.names` / `ast.alias.asname`）；真正的边界只有"局部变量遮蔽导入名"。**报告的定级是判断，判断可以被推翻，但要拿证据推翻。**
- **验证脚本自己也会骗人**——同秒内改回且长度不变时 `.pyc` 缓存命中陈旧字节码，"明明已还原却仍报红"；所有探针一律带 `PYTHONDONTWRITEBYTECODE=1` 跑。
- **Windows 工具链的几处**——PowerShell 无 heredoc；控制台 GBK（打印中文断言信息抛 `UnicodeEncodeError`，用 `PYTHONIOENCODING=utf-8`）；中文串里混 ASCII 双引号会截断字符串（统一用「」）；`python -m importlinter.cli lint-imports` 静默无输出，**必须用 `Scripts\lint-imports.exe`**；删除带 `cd` 的命令被安全策略拦（单条顶层 `rm --`）；同一条命令里 `cd` 后再写 / 删也被拦（写用 write 工具、只读检查用 bash）；`> $null` 重定向触发拦截；含反斜杠正则的 `-match` 被误判为网络共享访问。
- **"改了 A，没回头看还有谁引用 A"**——S2–S6 汇总复核的 N1 / N2 / N3 三处文档残留，以及 `PROGRESS.md` 漏改的 S2 项数（"14 项"实为 12），全是同一族。**修订完要回头搜一遍引用。**
- **"少守一处"比"多守一处"更难发现**——删掉 `EXPECTED_PAYLOAD` 里一个事件，该事件的字段级用例**静默不再生成**（事件本身仍被另一张表守住，所以不是红灯，只是少了一层守护）。→ **转录表之间也要有集合断言。**
- **删掉包级导出不是纯局部改动**——改了 `contracts/commands.py` 忘了同步 `__init__.py`，import 直接炸。**包级 `__all__` 是一张要一起改的表。**
