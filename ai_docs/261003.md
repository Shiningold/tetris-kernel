**为什么这么写**：

- **负载字段的类型声明用规范字符串，不用 `typing` 对象**。契约基线按字段级哈希类型声明（架构 §4.4），而 `hash(int)` 是按对象地址算的——**跨进程必变**，`typing` 对象的 `repr` 也会随 Python 版本漂移。基线要的是跨进程稳定的哈希，所以类型写成规范类型表达式字符串（`"int"` / `"tuple[int, int]"`）。这个选择在 S6 写基线脚本时会直接省事：字符串可直接正则解析、可直接写进 JSON。
- **负载字段不只照抄 §8.1 的"关键负载"，但也不越界补维度**。§8.1 给的是举例，声明必须**自足**（回放校验要靠它），所以像 `piece:moved` 补了 `blocked`、`piece:locked` 补了 `cells` 与 `tSpin`；但规则相关的枚举取值域（`tSpin` 取哪些值、`classKey` 取哪些键）**留空给 M1 的规则集定义**——M0 只定"字段名 + 类型"，不定值域。
- **事件负载允许浮点，命令 `args` 禁浮点**，两条规则的适用范围写进了模块 docstring。`render:frame` 的耗时、`metric:sampled` 的聚合值本来就带小数；`args` 参与重放、参数不能漂（B-7），所以 `ARGS_VALUE` 的取值域里没有 `float`。
- **测试里独立转录一份需求表**，而不是直接读文档文件。前者是"抄一遍"，抄错就一起错；后者要把 Markdown 表格解析成结构，解析器本身成了新的出错点，而且 S2 阶段文档还在动。独立转录 + 逐条相等，至少保证"注册表"和"人对需求的理解"两处一致。

**被否掉的方案**：

- **类型声明用 `typing` 对象（`int` / `tuple[int, ...]`）**——看着更"类型安全"，但基线哈希跨进程不稳定，且 `repr` 随 Python 版本漂移。改用规范字符串后，类型表达式同时充当**契约的一部分**（读代码就知道字段是什么型），还省掉一层转换。
- **测试直接解析 `docs/需求与边界.md` 的表格**——"文档与声明一致性"看起来更硬，但引入 Markdown 表格解析器这个新出错点，且文档在本阶段仍在改。改成独立转录，代价是转录本身要人工核（已逐条核过）。
- **把负载字段的取值域也定死（如 `tSpin` 的四个取值）**——那是 M1 规则集的事。M0 定了就等于在规则实现前先锁死规则语义（ADR-061 要避免的正是这个）。
- **信封与元数据声明放到 `contracts/envelope.py` 单独一个模块**——S11 的 `bus/envelope.py` 是实现，这个是声明，两者不是一回事；S2 的涉及文件清单里没有新模块，少开文件更省事。

**踩过的坑**：`ruff check` 报了 11 个错——10 个是 E501（`PayloadField(...)` 单行太长），1 个是 UP035（`Mapping` 应从 `collections.abc` 导入）。行长的部分交给 `ruff format` 自动改，UP035 手动改（`from collections.abc import Mapping`）。**格式化与逻辑改动分开提交**的规矩在这里正好省事：格式化的部分没混进逻辑改动里。

**中途走过弯路**：第一版用 `from typing import Mapping` 且类型声明用了 `typing` 对象，写完才意识到基线哈希的跨进程稳定性问题——**这是从 S6 的需求（字段级哈希）倒推出来的约束，不是从 S2 的需求看出来的**。如果不提前想，S6 写基线脚本时会发现哈希每次跑都不一样，然后回头改 44 条声明。**声明层的类型选型，要按"将来基线脚本怎么用"来定，不是按"现在写着顺不顺"来定。**

- **`cause` 不指向全局事件序号**，指向 **(帧号, 帧内序号)**。序号由总线入队时分配（架构 §4.2），**内核生成事件草稿时还拿不到它**——内核侧现成的因果标识只有 (帧号, 帧内序号)（架构 §6.3）。指向全局序号在实现上根本做不到。
- **形状表 / 踢墙表接口必须带轴维度**。M4-A5（形状表 / 踢墙表随重力方向变换）与「内核不做变换、表由规则集整体提供」两条合起来，接口不带轴就选不出表，而表又不能由内核变换。**这是签名必须现在定死的核心理由**，不是"有备无患"。
- **运行期切换排到 M3，不在 M0 实现**。需求 §10 说变体 A「切换经命令通道」，但命令目录 16 条里没有对应命令——这是需求内部的空白。M0 只把 `axis` 作为 `RuleContext` 字段预留（签名必须覆盖变体维度），M3 增补"运行期换规则集"命令与门禁（内核改动随 M3 刷新基线），M4 变体 A 直接用 M3 已有的能力 → **G4-1 约束的是 M4 落地变体时内核差异为空，M3 的改动不违反它**。在 M0 就实现切换是抢跑，会让 M3–M4 的批次边界失守。

**被否掉的方案**：

- **保留「逻辑时间戳」并定义为"有效游戏时间"**——一度认为它与帧号不是同一个量（内核级暂停期间帧号照走、tick 不发），但 §6.1 已经写明"有效游戏帧数 = `clock:tick` 计数"，这个量本来就能从事件流数出来，不必占一个信封字段。而它一旦独立成字段就是分叉源，还会进基线哈希。
- **元数据做成"白名单 + 未知 key 静默保留"**——两头占。既声明"白名单"又允许未知键留存的，实际是"已知键表"；真要严格白名单，未知键就该报错。取后者：已知三键，**未知键静默保留但不解释**（NFR-9 要求的是容错，不是严格）。
- **重命名 `kernel:system:installed` 迁出 kernel 命名空间**——44 个事件是需求资产，改名要连锁改需求表与订阅过滤，代价高于用 `producer` + 机器检查立纪律。**命名空间 ≠ 产出者**：`kernel:` 前缀说的是"这件事属于内核实例"，不必然是内核干的。
- **把 `M3-18` 整个作废**——保留编号但降级为"复核"，这样任务编号表不断链，ADR-061 说清两者的关系。

**还欠着的**：契约 v1 的**冻结清单**（信封字段集 / 元数据键 / 快照字段名 / 16 个命令参数规格 / 拒绝原因枚举 / 44 个事件负载声明 + 产出者 / 规则接口签名）要逐项勾完，才允许生成 `contracts/` 基线；清单本身还没落文件。冻结基线也定在 **M0 收尾**生成，不是 M0 一开始——太早生成会让基线在开发期反复失效，橡皮图章就白刷了（ADR-019 的原话）。

### 09:28 · `ai_docs/`（日志瘦身：往日压缩 + 当日完整）

**发生了什么**：用户指出日志太臃肿——一周一份、条条完整，一天下来 15 条、5000 多字，读的时候得从头扫。定的做法是：**最新的在最上层，前一天总结精简，当天的保留完整**。落成规则：

- 每天一个 `## YYYY-MM-DD` 小节，**节内倒序**（新的在最上）。
- **当天条目只追加不改写**；同一天里被推翻的条目合并成最终结论 + 一句"中途走过弯路"，不留两版并存。
- **往日压缩**：写当天条目前，先把非今天的小节压成「决定要点 / 踩过的坑 / 未决 / 相关文件」四段。留**决定 + 理由 + 会被重新考虑的那条否决理由**；删过程叙述、当时的犹豫、已作废的中间状态。
- 同步改了 `AGENTS.md` 的「AI 决策日志」一节（原来只写"只追加不改写"，与压缩直接冲突）和 `ai_docs/README.md`（原来写"日志只追加，不改写已有条目"，同一处冲突）。

**为什么这么写**：原来的"只追加不改写"是**对当天条目**说的——当天的决定还在发酵，回头改写会掩盖"中途改过"这件事。但它一旦被当成对整个文件的约束，日志就只能单调膨胀，越写越没人读。跨日压缩不丢东西：被删的是**过程叙述**（"当时以为…""写了又删…"），留下的是**决定和理由**，而 git 里本来就存着每一次提交的完整结果。

压缩的判据不是"变短"，是"**变可查**"。四种查法对应四段：那天定了什么 / 为什么不能那样做、我错过什么 / 还有什么悬着 / 东西在哪。留下的"被否掉的方案"只挑**会被重新考虑的那一条**——比如"不建 `docs/路线图.md`"，因为需求 §12 与 `PROGRESS.md` 覆盖不到的那部分（任务编号体系）将来还得有人惦记；而"Conventional Commits 英文前缀"被否掉就不会再被提，不占位置。

**被否掉的方案**：

- **只倒序、不压缩**——文件还是同样长，只是读起来从新到旧，找旧结论仍要翻到底。
- **压到只剩一句话的目录式摘要**——"10-22 整理了文档"这种句子等于没记，读者还得回头翻 git，那日志就白写了。
- **把压缩交给下一个会话做**——压缩的判据是"哪些决定还会被重新考虑"，这需要知道当时的犹豫；隔一个上下文就只剩结论，理由也压没了。**压缩紧跟在记录之后做，才知道该留哪条。**

### 踩过的坑

- **"已迁出"的指针必须顺着读回迁入方。** 拆分原件 §10 的标题是「迭代规划与风险（**已迁出**）」，正文写"已迁至 `docs\路线图.md`"并附了一张迁移对照表——而该文件**根本不存在**。那 33 条门判据、145 条迭代任务、FR→任务号对照表、风险与待定项是**凭空消失**，不是"在别处"。我第一轮建了 `路线图.md` 又删掉，理由是"需求 §12 只有批次级判据，任务清单大半是待补，是空壳"——**这个判断是错的**：错在我只看了拆分后的文件（内容已经迁走），看到"需求侧没有需求"就以为不需要建。回收站扫过，找不回来。
- **反复修改留下的沉积靠通读发现不了**，只有三种形态：**坏的引用**（指向不存在的章节，如 `§7.9`）、**空洞的编号**（看着有、其实没内容，如决策记录里 7 行主题为"—"的映射）、**重复的元叙述**（同一件事说两遍，读者以为是两件事）。这三种正是让后续对话的 LLM 产生同样误解的机制。
- **逐表对照才敢说"没丢东西"**。拿原件当基准、脚本解析表格逐行比对：事件 43→44、命令 16→16、快照 10→12、FR 50→50、NFR 9→9、AC 8→8、S 4→4、N 7→7、W 4→4、术语 16→16、选型表 18→18，"明确不选" 40 条落进 39 条。查出的问题：**1 条真丢**——"数据库 / ORM / 后端框架"，补进 ADR-017；**NFR-6 类别被改成"可维护性"与 NFR-5 重名**，改回"可扩展性"；`extensions` / `extensionFingerprint` 是把原件的脚注升级成契约字段（改进，不是丢失）。
- **`check` 子命令是原件里就有的孤例**——原文只在选型表出现过一次、无任何定义，删掉是对的；但同批还查出原件 §6.1 事件表抬头写 41、表里实际 43——**"41"这个数字在原件里就是错的**，拆分又加了一个事件变成 44，谁都没回头改计数。
- **拆分确实改对了一处**：原件 §6.2 的写入裁决规则写"超限整批拒绝并发出 `kernel:error`"，拆分后改成**配额超限事件**。`kernel:error` 的语义是订阅者异常，拿它表达配额超限会让 M2-23 的错误面板混淆。
- **原件还有一批东西只能确认丢失、找不回来**：7 条历史待定的闭合结论索引（落点写的是《架构设计》§2.5 / §2.8 / §2.12 / §2.18 / §4，拆分后全是坏引用）、tkinter 定时器的原始实测表（`after(1)` 975.2 次/秒、91.15% 单核等，结论保住了，原始数据没了）、6 条开放项的完整表述。结论部分保住了（架构 §1.4 + ADR-029），数字没了。
