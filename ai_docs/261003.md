**为什么这么写**：

- **表是离散数据，错一条不会让任何「跑通」类判据变红**——只会让某个角落转不进去。只能靠**逐条比对**抓，所以两张表都配了**独立转录表**。
- **转录必须是独立的第二遍**：实现表从权威表抄一遍，测试表再独立抄一遍，两处抄错同一处的概率低；**转录表从实现表复制生成 = 同义反复**，比对的价值归零。**当场见效**：形状表的 ASCII 画第一次把 Z 的朝向 3 画错（画成 J/L 家族的形状），比对当场报红——**转录自己也会错**，这正是独立转录的价值。
- **权威表 y 上正、本项目 y 下正 → y 分量取反**。**换算在抄的时候做**（转录表直接抄成 y 下正），不是抄 y 上正再在测试里取反——两边都取反的话，「整个踢墙方向上下颠倒」这种**系统性**错误比对抓不到。
- **180° 没有单一权威**：SRS 原始规范根本不含 180°。采 **TETR.IO / Jstris 口径**（Hard Drop 的 `Rotation System in TETR.IO` 条目），**不冒充 SRS 正统**，写进 **ADR-068**。**只取 TETR.IO 与 Jstris 共用的那两级**：TETR.IO 的六级表在 T / L / J 之间各不相同，**凑不成「一组一套」**，而前两级对 JLSTZ 全体统一，正好落进「JLSTZ 与 I 各一套」的结构。

**批次化与并行写手**

- **M0 剩余阶段（S7–S18）重排成 5 个批次**，切批依据是**文件归属互斥**，不是"看起来像一组"——S9 / S10 / S12 **共用 `kernel/core.py`** → 同一批、由同一写手串行；同批的 S11 才享受并行。**同批 ≠ 并行，同批只是"一起排期"。**
- **并行安全三条**：① **文件归属互斥**（包级 `__init__.py` 不属于任何写手，导出面由集成者统一收口）② **跨写手的东西先验定签名**（并行写手之间**没有协商通道**）③ **写手只交工作区改动，不自己提交**（git 索引是**单一共享资源**，并行 `git add` 会互相覆盖）。
- **分支用链式分支点**（下一批从上一批的落笔提交起，不回 master）→ "审查 A 期间写 B"成立；审查搭车边界是**只加不改**；批次合并用 `--no-ff` 保留批次边界。
- **"接口先验定"救过一次真**——批次 B2 的 `Draft` Protocol 最初按可写属性写，实测**冻结 dataclass 不满足可写属性型 Protocol**（pyright `reportArgumentType`）→ 改成只读 `@property`，冻结与非冻结两种 dataclass 都能满足，而属性名与类型与先验定的完全一致。
- **"接口先验定"只覆盖签名，覆盖不了实现细节**——批次 A 集成时抓到 `import_state` 用**当前实例**的 version 复原状态，等于把 ADR-011 的版本检测绕过去 → 当场修（**会导致静默错误结果**的一类缺陷，不是风格问题）。

**口径缺口先定口径、再改实现**

- **连击与 `b2b` 在 M0 内没有任何地方定义过**——批次 A 审查查出的 A1 / A2 根因是**口径缺口**不是实现错。口径定成：**连击** = 连续消行次数，**落空清零**（落空由**内核每次锁定后都调 `score_clear`（含空组）**表达，内核不自己改 `combo`）；**`b2b` 这一位** = 「**当前处于难消链中**」（本次难消即入链，普通消行或落空断链）。
- **`b2b` 只有一个比特，标准定义递推不出来**——`prev.b2b=False` 分不清"上一手是普通消行"和"上一手是难消但链还没起"。所以换的是**含义**而不是字段（给 `ScoreState` 加第 6 个字段 = 改契约 = major 变更）。
- **B2B 倍率（M1）的条件 =「本次难消 ∧ `prev.b2b`」**——`prev.b2b` 正是"上一手在链中"的答案，规则集在计分时当场算得出。
- **语义归规则集，不归契约层**——`b2b` / `combo` / `tSpin` / `classKey` 同理（`RULE_SET_DEFINED_FIELDS` 的理由：内核只透传、取值域归规则集），写进 `rules/standard.py` 的 docstring 与 plan 的 S13 段即可。
- **行为面阶段不碰契约**——A6 / A7 的"正解"都要动契约（加单事件常量 / 加标量联合常量）→ 改用**导入期自检**（事件名与注册表对齐）与**导入期断言**（别名 ↔ 契约常量）：风险一样被挡住，冻结面零改动，基线仍是 355 条。

**契约 v1 增补与重力间隔**

- **"契约声明了接口却不兑现"本身就是问题**——`gravity_interval` 在 S5 就进了 `contracts/rules.py`（ADR-061 冻结签名）、S13 也把实现写好了，却**没有任何调用者**。兑现它绕不开跨帧状态，而**内核状态必须全部进快照** → 只能给契约加字段：快照顶层 **21 → 22**（新增 `gravityTimer`），事件面**零改动**（基线条目 355 → 356 只是新增键）。
- **计时语义定成「还有几帧才落格，0 = 本帧到期」**（不是"已经过了几帧"）——倒计时能直接回答"下一帧会不会落"，也让"随方块出生重置"有明确落点（出生时记 `间隔 − 1`，第 `间隔` 帧落第一格）。
- **触地判定特意留在每帧做**，与落格脱钩——间隔只管"什么时候下移"，不管"有没有到底"；判据用「幽灵落点走 0 格」，既复用已有计算，又让触地与锁定留在同一帧（否则方块贴地后要最多等一个间隔才锁定，与 M0 的"落即锁"冲突）。

**基线与门禁**

- **基线的增删口径**：允许新增键 · 禁止已有键哈希变化 · **已有键消失同样报红**（改名 = 删旧键 + 加新键）；**签名与命名结构是冻结面**（`count/ruleSignature` · `count/namedStruct` 钉住条数），**快照是"至少包含"**，**事件与命令允许新增**。
- **"允许新增键"的前提是基线文件本身可信**——基线被清空或残缺时，"当前有、基线没有"的键全被当成新增放行，**「只增不改」在那一刻静默退化成「只查已有键」**。→ 两份基线的自述块各加一个「自己有多少条」（`meta.entryCount` / `meta.fileCount`），校验时对账；**契约版本号是双向对账的**（源码侧升了、基线侧被改了，两边都红）。
- **基线刷新必须显式、必须写明理由**——批次 D 收口时两份基线各红一条，红的位置正好是那两笔**已显式批准**的改动。先跑校验确认"只有这两处、其余 0 变化 0 消失"，刷新后再跑一次确认全绿，理由写进提交信息。**不顺着改**——顺手刷新就是橡皮图章。
- **两份基线接进 pytest**——生成基线却没人跑它，等于没有牙齿。**跑的是工具本身**（子进程调脚本），不把哈希逻辑抄一份到测试里（抄一份就是影子副本）；**先断言基线文件存在**（工具在基线缺失时打印「基线尚未生成」然后放行，不先钉住这一点，用例会空跑变绿）。
- **行为落在声明面与文件哈希面的缝里**——`bus/` 与 `host/` 不在冻结区，宿主层多发一条事件，声明面与文件哈希面都看不出来 → 新增**第三份基线**：每帧事件数（固定场景 **种子 1 · 预热 0 · 6100 帧**，**逐帧**记录）。**逐帧比而不是只看 P50 / max**——多出来的几条事件挪到别的帧上也是行为变了。
- **耗时不进基线**——同机三次采样 P99 实测 490 → 678 → 1459 μs（跨度 3 倍），拿噪声当标准就是拿噪声当基准。**开放项 B 的验收物是一个可复现的结论 + 一个区间**，**M2 的降级阈值不能拿墙钟 P99 直接定**。
- **基线 meta 里不留"第几次刷新、因为什么"的字段**——会破坏"逐字节可复现 / 幂等"；改用 `--reason` 必填 + 打印「旧 → 新」差异摘要，理由落在提交信息里。

**审查与批次落笔**

- **审查方不改被审代码、不切主工作区分支**——一律 `git archive` 导出只读快照，所有变异在副本上做，**字节级备份还原**（用空串 `replace` 还原会插坏文件）。**每个结论都要有实跑输出**，不写"推演"。
- **审查方不代项目拍板**——契约版本号的修法、反向用例放哪、清单门的口径、开放项的落档形态四条都列进报告待拍板；**C1（`state:changed` 产出者声明与实际不符，且已进基线）由项目拍板**：改 `host` 是 major 变更，不改就把这条例外写进 ADR。
- **审查报告不是可靠清单**——批次 A 的 15 项全部复现，但**其中一项的机制判断是错的**（报告说加标量联合常量会新增一条基线条目，实测**类型串常量是定义、不进基线**）。
- **两处口径与 plan 的字面写法有出入，按实际落地的写**——① 被拒命令的 `command:received` 是**延后发的**（合并窗口关闭时才发这一对，`received` 与 `rejected` 成对合并、计数一致）；② 快照的 `next` 放**当前一袋剩下的全部方块（≤7）**，渲染取前 5 个（少放两个的话"这袋还剩哪几个"只活在内核私有字段里，**存档恢复后取片序列会分叉**）。
- **44 个 skip 是设计如此**——它们是"该命令被接受"的用例，拒绝路径的断言对它们不成立；真正要全覆盖的验证 ①（16 命令 × 4 phase）**一个都没跳**。
- **批次 E 收口**：PROGRESS 三段整体重写（**删历史留口径**，同一形状只允许一处权威定义）· README 状态行与使用段订正（**文档说出来的必须是现在能做的**：`play` / `replay` / `inspect` 是占位，`tetris` 不带子命令会直接报错退出）· **AGENTS.md 的提交类型表补「合并」**（仓库里已有两笔 `合并：` 前缀提交，规则文件与实际做法分家要先改表）· 五个批次 `--no-ff` 合并进 `master` · 门禁 **643 passed · 44 skipped**。

### 踩过的坑

- **"审完一个批次"不等于"审完 M0"**——批次审查天然只看自己那批的 diff，**跨批次的口径冲突看不见**；本轮最重的一条（合并窗口）就是批次 D 的修订与 S10 的规格在**两次不同的批次**里各说各话，合并后才暴露。
- **报告的定性也要复跑，"探针可复现"≠"结论成立"**——M0-4 的探针（把自述块判定改成恒返回空）确实让全套仍绿，那说明**那段没被任何用例覆盖**，不等于**那段没作用**。**"没被覆盖"≠"没作用"**——补一条反向用例比删一层真牙便宜。
- **"退出码断言"不算守卫**——退出码是**被测代码自己算的**。最锋利的一次反向验证：把 `percentile()` 改成返回最小值，**并把工具自己的期望值一起改成坏实现的输出**——工具的 `--self-test` 仍然 exit 0 自称通过，**测试层的独立转录照样抓住**。
- **新加的门自己也要有反向用例**——把 `--reason` 的要求去掉、把 `compare()` 改成恒不报红、把冻结区差异判定改成恒假，**全套 pytest 仍然全绿**。**"要求改了没人拦"和"没有要求"是同一种失守。**
- **口径分歧 ≠ 实现坏了**——合并窗口那条是**措辞打架**，改文档三处统一即可，**不动实现**。
- **门会静默失效**——pyright 的 `overrides` 键在 1.1.414 已不存在，只警告不报错，strict 一直失效而退出码是 0。**会静默失效的质量门比没有质量门更坏。**
- **探针会污染自己的结论**——第一轮探针新增了 `kernel/_probe.py` 却没清理，把后续三个探针的结果污染成"冻结区门禁变红"；清掉残留重跑后以重跑为准。**写在这里是为了让下游别误引第一轮数据。**
- **并行 `git add` 会撞 git 索引**（单一共享资源），后一个写手把前一个的暂存内容顶掉——并发写手只交工作区改动，提交由集成者按阶段串行切。
- **`.git` 写坏的典型表现是"指针坏、对象好"**——`HEAD` / `refs` / `index` 都是可再生的指针，**`objects` 与 `logs` 才是历史本体**。恢复顺序：分清哪层坏 → 写回 `HEAD` → 从 reflog 与对象库取回分支 ref（合并提交的两个父提交都在 → 那次合并没丢）→ **把坏 index 挪开**（不删，留着能查）→ `reset --mixed` 重建 → 零字节文件从对象库 `restore` → 删临时产物。**提交过的东西不会因为崩溃丢**——前提是**提交过**。
- **零字节文件 = 内容已提交的信号**——长度还在但内容全零，多半是掉电时数据块没落盘。
- **差一帧的 bug 用例抓得住，是因为断言钉的是"恰好落一格"而不是"动了"**——重力计时第一版写成"到期帧下一帧才落"，用例直接把这个差值抓了出来（`assert 0 == (0 + 1)`）。
- **计数漂移是复发的病**——"41 vs 43 vs 44"（文档抬头与实际行数对不上）· "25 passed 实为 27" · "73 files 实为 84"（子集口径 vs 规范命令口径）· "开放项只剩 2 条"后面列了 4 条。**每次改完要回头搜一遍引用。**
- **快照 `next` 砍回 5 个**会让"袋里还剩哪几个"只活在内核私有字段里，**存档恢复后取片序列会分叉**（FR-10.2）——行为面阶段改契约 = 撞基线 = major 变更流程，所以在**类型不变**的前提下把袋内剩余一并放进去。
- **别把 44 个 skip 硬改成断言**——拒绝路径的断言对它们不成立，跳过是设计如此。

### 决定要点

- **契约类型声明用规范类型表达式字符串，不用 `typing` 对象**——基线按字段级哈希类型声明，要的是**跨进程稳定**：`hash(int)` 按对象地址算，`typing` 对象的 `repr` 随 Python 版本漂移。字符串还能直接解析、直接写进 JSON。**声明层的类型选型按"将来基线脚本怎么用"定，不按"现在写着顺不顺"定。**（**被否**：`typing` 对象——看着更"类型安全"，实际把基线变成每次跑都不一样的东西。）
- **测试里独立转录需求表做交叉核对，不直接解析 Markdown 表格**——解析文档的测试会把这层交叉核对变成**自证**（声明与它自己解析出来的表相等，等于没比）。代价是转录本身要人工核；已逐条核过。
- **同名字段跨事件必须同类型，例外显式写进测试的例外表**——通用提取代码（回放校验 / 事件完备性检查 / 指标通用提取）按字段名处理负载，同层同名不同型必然踩空。`level`（游戏等级 `int` vs 日志级别 `str`）是跨域同名，**不是缺陷**，写 doc + 例外表即可。
- **负载的 `cause` 与元数据的 `cause` 不改名，用 doc 消歧**——两者**跨层**（负载 vs 元数据）而非同层；元数据的 `cause` 是 ADR-062 定死的三键不能改，为消歧而改名代价大于收益（要动 4 条事件的字段名）。
- **门禁归属做成必填字段 `CommandSpec.lifecycle_gated`**（无默认值，漏表态直接 `TypeError`），三个生命周期原因**由它派生**——推导只挪走"名单会分叉"的风险，挪不走"漏写会静默"的风险（代价是"暂停期间命令照样执行"）。
- **参数类型引用常量不复制字面量**（`types.INT_TUPLE` / `CELLS` / `SCALAR_MAP` / `NEXT_QUEUE` / `BOARD_CELLS` / `VECTOR2`）——复制字面量的后果是"常量改了、声明没跟着改，两处静默分叉，基线却显示全绿"。**禁浮点只约束 `args`**（参与重放、参数不能漂，B-7）；事件负载与 `extensions` 允许浮点，口径不同是对的。
- **快照 = 内核状态全集（"至少包含"）**——内核每加一个状态字段，快照必须同步加一个，否则存档恢复缺一块。内核侧字段清单**一行一字段 + 两侧点分路径**（`board.width` / `active.pieceType`），`derived` 标出算出来的三条。
- **命名结构注册表放 `contracts/structures.py`，成员表从声明推导**——注册表是**类型文法层面**的清单（形态 9 的名单与成员表），快照 / 放置 / 规则三处共用，寄居在 `snapshot.py` 是权宜；**不另抄一份名单**。
- **形态 9 的引用按成员表展开后再哈希**（文法附加规则第 4 条）——把引用当别名哈希，改了成员表基线全绿，冻结形同虚设。
- **类型文法表是 S6 解析器的规格书，规则与实例必须同时回验**——S3 改规则 1（`None` 可作普通成员）、S5 改形态 10 的 T 范围，都是因为规则字面排除了自家示例；**规格书自相矛盾时，机检会忠实地把合规声明判成不合规**。
- **取值归属判据：内核要解读的字段 → 契约层钉死且构造即校验；内核只透传的字段 → 规则集定义，点名豁免**（`RULE_SET_DEFINED_FIELDS`）。判据不是"要不要加校验"，而是**内核读不读这个字段**。
- **T-Spin 分类搭消行组的便车**（挂 `ClearGroup.classification`），**不给冻结签名加参数**——`score_clear(groups, ctx, prev)` 里没有分类的位置，而计分模块看不见分类就算不了 T-Spin 的分值；**维度不缺，通道缺**。
- **基线的键口径**：键 = 字段名 / 事件类型名 / 命令类型名 / 签名参数名，值 = 规范化后类型串哈希。**允许新增键 · 禁止已有键哈希变化 · 已有键消失同样报红**（改名 = 删旧键 + 加新键）。**签名与命名结构是冻结面**（两条计数键 `count/ruleSignature` · `count/namedStruct` 钉住条数），**快照是"至少包含"**（顶层加字段必须绿），**事件与命令允许新增**（架构 §4.4 明说，不加计数键）——三者的增删口径不同是有意的。

- **文档拆成三份**——`docs/需求与边界.md`（做什么）/ `docs/项目架构.md`（怎么做）/ `docs/决策记录.md`（为什么），`AGENTS.md` 只当入口指路。**被否**：把三份内容回抄进 `AGENTS.md`——抄一遍就会漂移，两处维护同一件事是长期漂移的起点。
- **提交标题用封闭的中文类型表** `【类型：主题】`（新功能 / 修复 / 文档 / 测试 / 重构 / 性能 / 格式 / 构建 / 持续集成 / 杂务 / 回滚），破坏性判据取"会不会让旧录像、旧存档或既有调用方失效"——与项目里"会不会改变重放结果"是同一条口径。**被否**：Conventional Commits 的英文前缀 · 自造"改进/优化"这类分不清归属的类型。
- **建 `ai_docs/`**，一周一文件 `YYMMWW.md`，周按周一所在月归属、月内从 1 数周次。**被否**：ISO 周数——跨年跳号，也不体现"月内第几周"。
- **不建 `docs/路线图.md`**（当天建了又删）。它能抄的都已经在需求 §12 里，不能抄的（任务编号）本来就没有——**一个内容全是"待补"的文件比没有文件更糟**，它让人以为编号的事有地方管着。**被否**：留个占位等编号齐了再填 · 把 M0–M4 任务清单全写进去（那些编号不存在，写出来就是编造）。**处置**：任务清单归 `PROGRESS.md`「待办」栏，门判据编号归需求 §12 新增的小表。
- **门判据编号归 `docs/需求与边界.md` §12**，把原先散在 `AGENTS.md`（G2-1 / G2-4 / G4-1 / G4-2 / G4-6）与 `项目架构.md`（G4-1 / G4-2 / G4-6 / M0-28 / M3-18）正文里的编号登记到一处，M0 / M1 / M3 标待补。**被否**：建 `docs/路线图.md` 专门收编号——新开文件就得多维护一份目录结构和一处引用。
- **一致性问题靠机械校验**：脚本数表格行数 / 查被引用的 `§N.M` 存不存在 / 拿 60 条 ADR 的定义表对每个引用点查表。**被否**：只改手上正在改的那一份、剩下的"回头再说"——这正是沉积能攒到"41 vs 44"的原因。
- **`AGENTS.md` 压到 500 字**（3 万多字节 → 502 汉字）：删「实现红线」整节（约 50 条，指 `项目架构.md` §7）与「开工前」整节，再删与架构 §3 重复的目录树。**被否**：把红线压缩成几行摘要留着——摘要太粗等于没说，太细就等于把 §7 又抄了一遍。**指路比复述可靠。**
- **删掉拆分前的两份合并稿**（`俄罗斯方块内核_需求文档.md` / `技术栈选型决策.md`），并清掉它们留下的噪声。**被否**：删 `ai_docs/` 里的历史条目来"消噪声"——日志的价值恰恰是"为什么这么写"，删条目等于把决策过程抹掉（改成在日志顶部加状态说明：历史照留，但标明那些文件已不在，别去找）· 把"33 条门判据"这个数字补回文档（**没有备份**，编出来的编号会变成下一个坏引用，写"待补"至少不骗人）。
- **`PROGRESS.md` 定位为快照**，只剩「当前在攻 / 待办 / 卡点」三段，历史表与 M1–M4 逐条清单整块删掉（9 KB → 3 KB），已知任务编号并入需求 §12 与门判据表并列。**被否**：保留「已完成」表但只留最近 N 条（"最近 N 条"随意的规则，改一次丢一次历史）· 把历史挪进 `ai_docs/`（它是**决策日志**不是活动流水账）· 另建 `CHANGELOG.md`（有 git 就是重复造轮子）。
- **规范先立、仓库后建**——整套质量体系以版本控制为载体（静态检查进 CI、冻结基线刷新要"提交说明写明理由"这件事可写、"内核文件差异为空"本质就是对比某个版本），所以提交规范当天先定，`git init` 留到用户明说。同一天晚些时候仓库建好并切了五笔。**被否**：顺手把 `git init` 和头几笔做掉——仓库什么时候建、建成什么样是项目负责人的决定，不是顺手能带过去的。
- **`pyproject.toml` 落 uv_build + 四条 import-linter 契约**，运行时依赖只有 `rich`（内核 / 总线 / 规则三层是纯标准库），dev 依赖六个版本全钉死（ADR-052：格式化与静态检查的结果随版本变，不同机器上打架比不出 diff）。契约按架构 §2.3 的骨架写：分层方向、内核与总线禁第三方、变体不跨层引用、系统之间互不直调。
- **`systems/` 的五个子包名先在契约里定死**（log / metrics / replay / achievements / ai），M0 建空壳时照此建——让"系统之间互不直调"从第一天就机器可验，而不是等子包建完再补契约。
- **`README.md` 面向外部读者**：定位 → 解决什么问题 → 特点 → 安装 → 使用 → 架构 → 从源码开发 → 文档导航；环境一律写"Python 3.12 或更高版本"，并写明当前还在 M0、尚未可玩。**被否**：加一句"开发请看 `AGENTS.md`"然后保留开发细节（等于没改）· 拆 `CONTRIBUTING.md`（项目还在 M0，没有外部贡献者流，拆只是多一个文件）· 删掉"从源码开发"整节（README 会显得像纯宣传页）。

### 踩过的坑

- **"已迁出"的指针必须顺着读回迁入方。** 拆分原件 §10 的标题是「迭代规划与风险（**已迁出**）」，正文写"已迁至 `docs\路线图.md`"并附了一张迁移对照表——而该文件**根本不存在**。那 33 条门判据、145 条迭代任务、FR→任务号对照表、风险与待定项是**凭空消失**，不是"在别处"。我第一轮建了 `路线图.md` 又删掉，理由是"需求 §12 只有批次级判据，任务清单大半是待补，是空壳"——**这个判断是错的**：错在我只看了拆分后的文件（内容已经迁走），看到"需求侧没有需求"就以为不需要建。回收站扫过，找不回来。
- **反复修改留下的沉积靠通读发现不了**，只有三种形态：**坏的引用**（指向不存在的章节，如 `§7.9`）、**空洞的编号**（看着有、其实没内容，如决策记录里 7 行主题为"—"的映射）、**重复的元叙述**（同一件事说两遍，读者以为是两件事）。这三种正是让后续对话的 LLM 产生同样误解的机制。
- **逐表对照才敢说"没丢东西"**。拿原件当基准、脚本解析表格逐行比对：事件 43→44、命令 16→16、快照 10→12、FR 50→50、NFR 9→9、AC 8→8、S 4→4、N 7→7、W 4→4、术语 16→16、选型表 18→18，"明确不选" 40 条落进 39 条。查出的问题：**1 条真丢**——"数据库 / ORM / 后端框架"，补进 ADR-017；**NFR-6 类别被改成"可维护性"与 NFR-5 重名**，改回"可扩展性"；`extensions` / `extensionFingerprint` 是把原件的脚注升级成契约字段（改进，不是丢失）。
- **`check` 子命令是原件里就有的孤例**——原文只在选型表出现过一次、无任何定义，删掉是对的；但同批还查出原件 §6.1 事件表抬头写 41、表里实际 43——**"41"这个数字在原件里就是错的**，拆分又加了一个事件变成 44，谁都没回头改计数。
- **拆分确实改对了一处**：原件 §6.2 的写入裁决规则写"超限整批拒绝并发出 `kernel:error`"，拆分后改成**配额超限事件**。`kernel:error` 的语义是订阅者异常，拿它表达配额超限会让 M2-23 的错误面板混淆。
- **原件还有一批东西只能确认丢失、找不回来**：7 条历史待定的闭合结论索引（落点写的是《架构设计》§2.5 / §2.8 / §2.12 / §2.18 / §4，拆分后全是坏引用）、tkinter 定时器的原始实测表（`after(1)` 975.2 次/秒、91.15% 单核等，结论保住了，原始数据没了）、6 条开放项的完整表述。结论部分保住了（架构 §1.4 + ADR-029），数字没了。
